## 一、产品概览

### 1.1 产品定位

- 产品形态：PCIe 加速卡 / OAM 模组（遵循 OCP-OAM 标准）[$TRAE_REF](https://www.kunlunxin.com/news/4791.html)
- 制程工艺：7nm（三星）[$TRAE_REF](https://blog.csdn.net/2401_84508343/article/details/161278767)
- 发布时间：2024 年
- 商业化：出货 6.9 万片，已实现万卡集群部署，最大集群规模超 3 万卡 [$TRAE_REF](http://m.toutiao.com/group/7638064583000850979/)

## 二、硬件架构

### 2.1 XPU-P 架构核心特性

**"通算传并行"（CCT）设计**：XPU-P 架构的核心创新。传统 GPU 流程为"计算 → 传输 → 计算"串行执行，CCT 设计使通信、计算、传输三者并行重叠执行，大幅提升集群训练效率。主流开源模型 MFU（有效计算占比）达 58%。[$TRAE_REF](https://blog.csdn.net/2401_84508343/article/details/161278767)

**MoE 架构深度优化**：
- 全面支持 MLA（多头潜注意力）、多专家并行等特性
- 5000 卡集群训练多模态模型时，MFU 稳定在 55% 以上
- 对 DeepSeek 系列 MoE 模型大规模训练任务支撑良好 [$TRAE_REF](https://blog.csdn.net/2401_84508343/article/details/161278767)

### 2.2 计算单元（参考 XPU-R 架构）

> ⚠️ 以下为 XPU-R 架构（昆仑芯1代/2代）的公开资料，XPU-P 架构的具体微架构参数未完全公开。P800 可能继承并扩展了此设计。

- **SDNN（软件定义神经网络引擎）**：张量计算单元，加速卷积和矩阵乘法 [$TRAE_REF](https://m.sohu.com/a/564486588_104421/)
- **Cluster（通用计算单元）**：支持 SIMD 指令，负责通用计算 [$TRAE_REF](https://m.sohu.com/a/564486588_104421/)
- 编程模型：类 CUDA 的异构计算模型，Kernel 描述 XPU 上的计算程序，host 端设置执行参数发送给 device 端

### 2.3 内存层级（参考 XPU-R 架构）

| 层级 | 名称 | 大小（XPU-R 参考值） | 说明 |
|------|------|---------------------|------|
| L0 | Local Memory | 8 KB / core | 最接近计算单元的私有内存 |
| L1 | Shared Memory | 256 KB / Cluster | Cluster 内共享 |
| L2/L3 | L3 SRAM | 64 MB（片上共享） | 全局片上缓存，P800 可能更大 |
| L4 | Global Memory | 96 GB HBM3 (P800) | 全局显存 |

> **优化要点**：用好 L3 SRAM 是提高性能非常重要的手段。数据分块分配到不同 core，搬运到 Local Memory 再计算（类似 CUDA 的 shared memory 优化）。[$TRAE_REF](https://m.sohu.com/a/564486588_104421/)

### 3.4 算子开发方式

**XPU C/C++ 算子开发**（类 CUDA 语法）：
- host 端代码 + device 端 Kernel 代码分离开发
- 三尖括号语法 (`<<<...>>>`) 启动 Kernel，类似 CUDA
- `xpu_malloc` — 设备端内存分配
- `Cluster_id` / `core_id` — 计算单元标识
- 支持 event 和 stream 并行工作模式 [$TRAE_REF](https://m.sohu.com/a/564486588_104421/)

**自定义算子注册**（飞桨框架级）：
- `paddle.xpu.register_op()` — 注册 XPU 自定义融合 OP
- `paddle.xpu.malloc()` — XPU 专用内存分配
- 自定义白名单/黑名单：`custom_white_list=['Conv2D', 'Linear']`，`custom_black_list=['LayerNorm', 'Softmax']` [$TRAE_REF](https://blog.csdn.net/AladdinEdu/article/details/151474634)

### 3.5 类 CUDA 算子开发语言：调研结论

> 调研时间：2026-08-04。结合公开资料 + 本项目 P800 服务器实际 SDK 勘察。

#### 3.5.1 结论先行

**昆仑芯 P800 在架构层面确实设计了类 CUDA 的 XPU C/C++ 算子开发语言**，编程模型与 CUDA 高度同构（`__global__/__device__` 修饰符、三尖括号 Kernel 启动、`cluster_id/core_id` 线程索引、wmma 风格 Tensor Core 指令、共享内存/本地内存层次）。但**完整原生工具链（含 XPU 离线编译器）不随硬件公开分发**，需联系商务获取正式 SDK。

#### 3.5.2 当前服务器实测的 SDK 状态

本项目 P800 服务器（`43.180.254.145`）实际安装的是 **XPU Runtime + CUDA 兼容层**（SDK 版本 5.0.21.21，CUDA 兼容版本 11.7.60，驱动兼容 515.58）：

| 组件 | 实测路径 | 说明 |
|------|---------|------|
| 运行时库 | `/usr/local/xpu/so/libxpurt.so` `libxpucuda.so` `libcudart.so` | XPU Runtime / CUDA 兼容层 |
| CUDA 兼容头 | `/usr/local/xpu/include/cuda_runtime.h` `cuda_runtime_api.h` | 提供 `cudaLaunchKernel` 等 `<<<>>>` 启动接口 |
| 原生 XPU 头 | `/usr/local/xpu/include/xpu/runtime.h` `defs.h` | `xpu_malloc/`xpu_free`/`xpu_launch_config`/`xpu_launch_async`/`XPUFunc`/`XPUStream` |
| Tensor Core 指令 | `/usr/local/xpu/include/crt/mma.hpp` | `nvcuda::wmma` + `__hmma_m16n16k16_*` intrinsic |
| 原生扩展 | `/usr/local/xpu/include/xpu/xpuml.h` | XPUML 设备监控 API（类似 NVML） |
| **离线编译器** | **不存在** | 无 `xpucc` / 无 XPU 后端 clang / 无 nvcc 等价物 |

> **关键约束**：当前服务器**没有** XPU 原生离线编译器。这意味着即便有 `cuda_runtime.h` 和 `mma.hpp`，也无法用三尖括号语法直接编译 device kernel 到 XPU 二进制。类 CUDA 的原生算子开发需要独立 SDK 包（含基于 LLVM 的定制编译器），当前环境不可用。

#### 3.5.3 类 CUDA 编程模型的三个层级

| 层级 | 编程语言/方式 | 所需工具链 | 当前环境可用性 |
|------|--------------|-----------|---------------|
| **L1 原生 XPU C/C++** | 类 CUDA kernel（`__global__` + `<<<>>>` + `xpu_malloc`），性能最高 | 完整 XPU SDK（含离线编译器 xpucc） | ❌ 需商务获取，未安装 |
| **L2 CUDA 兼容层 C++** | 用 `cuda_runtime.h` + `mma.hpp` + `cudaLaunchKernel` 写 host/device 代码 | 需配套编译器处理 device 端 | ⚠️ 头文件/运行时已装，但无独立编译器 |
| **L3 PyTorch C++ Extension** | `torch.utils.cpp_extension.load_inline` + `torch::matmul` | gcc + ninja + torch_xmlir（当前已打通） | ✅ 本项目实际使用路径 |

> **对本项目算子开发 Agent 的意义**：在未获取完整 XPU SDK 前，**L3（PyTorch C++ Extension）是当前唯一可落地、已验证的 C++ 算子开发路径**。它通过 CUDA 兼容头文件 + gcc 编译 host 代码，底层由 `torch_xmlir` 映射到 XPU/xblas 计算，性能与纯 Python `torch.matmul` 相当（实测 0.90x xblas baseline）。若后续获取完整 SDK，可升级到 L1 原生 XPU C/C++ 以获得最高性能。

## 四、性能优化要点

### 4.1 软硬协同优化技术

| 优化技术 | 效果 | 说明 |
|----------|------|------|
| **OP 融合** | 减少 42% 计算开销、35% 内存占用，加速 1.8 倍 | Conv+BN+ReLU、Linear+Add、LayerNorm+SiLU 等融合模式 |
| **内存池化** | 分配延迟从微秒级降至纳秒级，碎片率 < 5%，峰值内存减少 30-40% | 统一内存管理、智能内存复用 |
| **混合精度训练** | 2.3-3.5 倍训练加速，40-60% 能耗降低 | 自动精度选择、梯度缩放 |

> 来源：昆仑芯 XPU 与飞桨软硬协同优化实践 [$TRAE_REF](https://blog.csdn.net/AladdinEdu/article/details/151474634)

### 4.2 算子级优化建议（基于 XPU 架构）

1. **数据分块**：基于 Cluster_id 和 core_id 计算 tid，将输入数据分块分配给不同 core
2. **Local Memory 利用**：数据搬运到 Local Memory 再计算（类似 CUDA shared memory 优化）
3. **L3 SRAM 复用**：用好片上 L3 SRAM 是提高性能的关键
4. **多 stream 并行**：利用多 stream 掩盖访存延迟
5. **异步通信**：CCT（通算传并行）设计支持计算与通信重叠 [$TRAE_REF](https://m.sohu.com/a/564486588_104421/)

## 九、对算子开发 Agent 的意义

### 9.1 已知可利用的优化方向

基于公开资料，算子开发 Agent 在 P800 上可优先考虑：

1. **数据分块 + Local Memory 复用** — 类比 CUDA shared memory tiling
2. **L3 SRAM 数据驻留** — 片上缓存大，适合大 tile
3. **OP 融合** — 减少内存访问，Conv+BN+ReLU 等常见模式已验证有 1.8x 提升
4. **多 stream 掩盖延迟** — 计算与访存 / 通信重叠
5. **混合精度** — FP16/BF16 训练加速 2.3-3.5 倍

### 9.2 需要谨慎的点

1. **Triton 不支持** — P800 不支持 Triton DSL，算子需用 XPU C/C++ 或 PyTorch（CUDA 兼容层）开发
2. **微架构不透明** — 没有公开的架构调优指南，优化策略需要通过实验验证
3. **CUDA 兼容层有性能损耗** — 通过 torch_xmlir 等兼容层运行的代码，性能可能低于原生 XPU 算子
4. **Profiler 工具受限** — 没有类似 Nsight Compute 的细粒度 profiling 工具，性能调优难度更大
