# 50 · 断点续跑的完整性：半个快照、被扔掉的轮次，与「请求了续跑」这句谎

日期 2026-09-29。主题：`execution_snapshot.json` 这条**唯一**的续跑链路，在写侧与读侧各有
一处静默降级，按 task_id 搜索快照的那条分支还有两处更静的错。全部本地可复现，不占 H20 机时。

选题理由先说清楚，免得被读成「顺手清理」：#48/#54/#57 三条都要机时与选卡，用户还没批，
所以这一轮的目标是挑一条**完全能离线验证**的链路做完外部吸纳 + 落地。选中续跑链路是因为
它同时满足三件事：每轮都在写、代价以「LLM 轮次」计、而它的失效方式恰好是本仓反复出现的那一族
（**降级不响**）。取证撞出来的东西比选题大。

## 一、本仓实况（三处，全部实测过，不读代码猜）

取证脚本在 `/tmp` 跑（一次性，不入库），走真 `MockGPU` + 真 `Conductor.execute` + 真
`ArtifactStore` 落盘 —— 不用声明式假件当被测对象（doc 48 §6.5 那条纪律）。

### 1.1 半个快照会让一次续跑多烧 3 次 LLM 调用，而产物里查不到

| 场景 | LLM 调用 | stdout | 产物里有没有痕迹 |
|---|---|---|---|
| 健康快照续跑 | **1** | 「🔄 断点续跑」 | — |
| 快照被截一半后续跑 | **4** | 「⚠️ 快照加载失败，改为从头开始」 | **没有** |

机制是两半凑成的：写侧 `conductor.py` 原来是

```python
with open(path, "w", encoding="utf-8") as f:      # ← 这个 open 当场把文件截成 0 字节
    json.dump(snap, f, ...)
```

`open(...,"w")` 的截断发生在**序列化之前**，所以「写到一半进程没了」留下的不是上一个可用版本，
而是一份截断 JSON。读侧则把**任何**异常吞成一行 print 后从头跑。两边各自都「有道理」，合起来的
后果是：**续跑请求被降级成重跑，而不留任何记录** —— stdout 不归档，事后复盘看到的只是一次
跑得比较久的运行。

### 1.2 按 task_id 找快照时，永远选中**旧**的那个

`_resolve_snapshot_path` 的第三条分支是 `os.walk("output")` 里**第一个** task_id 命中的文件。
两个候选（`aaa_run_round1` 与 `zzz_run_round3`）实测：

```
创建顺序 先1后3 → 选中 run_older_round1 (round_done=1)
创建顺序 先3后1 → 选中 run_older_round1 (round_done=1)
```

两种创建顺序都选中 round_done=1，即 walk 顺序既不是时间序也没人规定过，而它替用户决定了
「从第几轮接着跑」。后果是**把已完成的轮次扔掉重来**，与 1.1 是同一件事的另一个入口。
顺带：同一条分支里 `except Exception: pass` 会**静默跳过**读不动的候选 —— 「找不到」与
「找到了三个、其中两个是坏的」在旧实现里是同一个返回值 `None`。

### 1.3 那条分支不认 `OPERATOR_AGENT_OUTPUT_DIR`

搜索根写死成 CWD 相对的 `"output"`，而产物根目录是 `ArtifactStore` 按环境变量算的。实测：
快照在 env 指向的目录里 → 返回 `None`（静默从头跑）；再在 CWD 造一个 `output/` 的诱饵
（`round_done=7`）→ 它被选中，**读的是本次配置根本没写过的目录**。同一个缺陷的两种后果：
要么丢续跑，要么捡到别的运行的状态。`_flush_snapshot` 里第 1 轮的 staging 目录也写死
`"output"`，于是设了重定向的运行会把快照落进仓库的 `output/` —— 那个变量存在的全部理由
就是别让旁路产物混进真实语料（doc 43 第三节量的正是这件事）。

## 三、改了什么（四处，全在 `conductor.py` / `artifact_store.py` / `schemas.py`）

1. **原子写**：`snap = tmp` → `flush` → `os.replace(tmp, path)`，`finally` 清残留 tmp。
   同目录（依据 ②）。效果：读者只会看到「旧完整版」或「新完整版」。
2. **续跑结局落盘成状态**：`KernelArtifact.resume_status`，五态
   `not_requested / no_snapshot / resumed / unreadable_snapshot / task_mismatch`，带
   `root`、`candidates`、`unreadable`、`reason`（**只存异常类名**，`str(e)` 可能带路径而
   `result.json` 会被搬走）、`size_bytes`、`round_restored`。
   ⚠️ 刻意**不**塞进 `artifact.metadata`：`artifact_store.py:73` 的注释明写 `metadata` 整个
   不进 `result.json` —— 挂在那儿就是下一份「算了没人读」（doc 49 §7.9 那条教训的复用）。
   落盘之后立刻补一条「从产物里读回来」的断言（同一条纪律）。
3. **搜索根跟着配置**：`_resolve_snapshot_path` 改成实例方法，根 = `self.store.output_dir`，
   与真正写产物的那个对象同源（不在第二处重读环境变量 —— 本仓有过「同一个键两个值」）。
   同时返回 `scan` 账目，于是 `no_snapshot` 能说清是「一个都没看到」还是「看到 3 个、2 个读不动」。
4. **多候选取最新可解析的那个**：key = `(round_done, mtime)`，并数出被跳过的坏候选。
   staging 目录也改用 `self.store.output_dir`。

## 四、吸纳 / 不吸纳（以及为什么这条边界画在这儿）

**吸纳**：上面四条。共同形状是「把不可能变成不可能」而不是「把日志写得详细些」——
①③④ 消除失效状态，② 让剩下的那个失效状态**必须**被记账。

**不吸纳（四条，都是主动拒绝，不是没做到）**：

⑤ **事件溯源 + 确定性重放（Temporal 那种，依据 ⑥⑦）**。它的代价是让主循环变成可重放的
   纯函数序列，而我们循环里的两个主要动作（LLM 采样、GPU 计时）都**不可重放** —— 真要照它做，
   等于把每次 LLM 响应与每次 L3 读数都记成事件并按事件恢复。那是另一套架构，而且它解决的问题
   （进程随时重启也要继续）比本仓的（崩溃后少烧几轮）贵一个量级。**本轮不建它**。
   留一条相邻的最小版本当候选：把「某轮的 LLM 响应」按 `(task_id, round)` 做键缓存，
   续跑时命中就不重发 —— 那才是 Stripe 那条幂等键（⑧）在本仓的正确落点。没做是因为
   **它需要真机长跑才能证明省下来的确实是钱**，而不是因为它难。
⑥ **`fsync` + 目录项 fsync（依据 ⑤）**。它防的是**掉电/内核崩溃**与 NFS；我们观察到并注入的是
   **进程级写失败**（`json.dump` 抛异常）。在没量过延迟、也不确定 `output/` 会不会被放到 NFS 之前，
   加 fsync 就是加一段没人测过的阻塞。记成欠账（第六节），不做成「看起来更严谨」。
⑦ **每 super-step 的更细检查点粒度**。本仓已经是每轮一写，粒度问题不存在；缺的是完整性，已修。
⑧ **把 `result.json` / `code.py` / `sketch.json` / `verify.json` / `benchmark.json` 一起改成原子写**。
   诱惑很大（同一个函数里五行），但**只有会被下一次运行读回来的那些**才需要这个保证。
   `result.json` 是这一档（它的读者是环境漂移自检的「上一次」扫描，`test_environment_drift.py:347`
   已经测过那条路读到坏文件时的行为），其余几个目前没有跨运行的读者。
   ⇒ 只把 `result.json` 记进欠账（第六节第 2 条），代码没动。一次改动铺满五处写，
   就是把「机制完整性」换成「看起来一致」。

9 例新用例（`tests/test_resume_integrity.py`）：

| 用例 | 断言的形状 |

## 六、还不能说什么 / 留下的账

1. **不能说「续跑从此可靠」**。本轮证明的是两件事：半个快照**不可能再出现**（①③④），
   以及读不动时**一定有记录**（②）。而「续跑跑完的结果 == 不中断跑完的结果」是更强的命题，
   它要求一次带真 LLM 的长跑中途被杀，再续跑对照 —— 需要机时与端点，记成 #48 那类需要批准的
   实验（新任务）。
   **【2026-09-29 更新】** 这个对照已经做了（第七节，五臂 / 13 条判据 / 含一次真 SIGKILL）。
   它把这条命题**收窄**成可证的那半：已完成的轮次不被重烧、且被真的当作下一步的起点；
   「最终产出同一个核」那半仍然没证（B 与 C 的第 2 轮签名不同，而且应该不同）。
   更值得注意的是那份读数的**归属**：跑动窗口里有并发会话在改同一条路径的文件，
   所以它不能记给任何 commit（7.5），归因重跑记成 #62。
2. **`result.json` 仍是非原子写**（第四节第 ⑧ 项）。它的读者是下一次运行的漂移自检，所以这条
   是真欠账而不是洁癖。修法和快照那条一样，但要先想清楚：`ArtifactStore.save` 一次写五个文件，
   原子性只在「读者按名字取那一个文件」时有意义。
3. **多进程并发写同一快照目录**没测过。跨进程锁保护的是 GPU 卡（`lock_identity()`），不是产物目录；
   两个进程同 task_id 同时跑本来就不该发生，但「不该发生」不是保证。
4. **NFS / 掉电场景**（依据 ⑤ 的 fsync 那条）明确不覆盖，等有机房证据再说。
5. 幂等键那条最小候选（缓存每轮 LLM 响应，键 = `(task_id, round)`）留在第五节 ⑤ 里没做，
   它才是本仓真正需要的「重放不重烧」。

## 七、真机读数（2026-09-29 补，#60）—— 以及一份**不能记给任何 commit** 的读数

§六 第 1 条留的话是：「续跑跑完的结果 == 不中断跑完的结果」是比本片更强的命题，需要一次带真
LLM 的长跑中途被杀再续跑对照。这一节做掉了它**能做的部分**，并且撞出一个比读数本身更值得记的
东西：**这份读数的归属不成立**。

### 7.1 量具先标定（`--dry`），这一步先撞出四处自己的缺陷

`benchmarks/verify_resume_equivalence.py --dry` = MockGPU + 脚本化 LLM，只验量具自己
（键名 / 找快照 / 状态字符串 / 子进程姿势），15 秒一轮。它按顺序撞出：

1. `backend.capabilities()` —— **它是 property 不是方法**，`TypeError: 'frozenset' object is not callable`。
2. `llm=None` 那一臂：`RuntimeError: LLM 未配置，规则模板已移除` —— 本仓已经没有规则模板兜底，
   dry 臂必须换成脚本化假件（并且假件**不是**被测对象，走的是真 `Conductor.execute` + 真落盘）。
3. **最重的一条**：`result_of()` 原来按 `task_id` 在产物树下取第一个命中 —— 而**续跑臂与被续的那次
   必须共用 `task_id`**（否则就是 `task_mismatch`），于是它读到的是**上一臂**的产物。dry 第一次跑
   报 `6✅/6❌`，看着像产品有六个缺陷；实际是量具瞎了。更糟的是其中两条是**假绿**：
   `B2` 拿 A 的快照去比 A 自己的 `result.json`，逐字段当然相同；`K4` 同理。
   修法不是加时间下界（那会把判据挂在墙钟粒度上，是 §7.13 那条「依赖非确定性选择的期望值」的
   又一形态），而是取本次运行自己的权威落点 `artifact.saved_dir`（`conductor.py:895` 赋的值）。
   改完 dry 变 `12✅/1❌/1➖`，唯一那条红是 `K0`——MockGPU 太快，子进程自己跑完了，dry 本来就
   不该验「崩溃」。
4. 输入没固定 seed：各臂必须看到同一份 `X/weight/bias`，否则「第 1 轮读数相同」可能是输入相同
   的巧合，也可能是输入不同的假红。

**账**：15 秒 × 4 次 dry，换掉一次 12 分钟、约 10 万次 token 的真机空跑。
通则与 doc 48 §6.5 同族：**任何新驱动先在假后端上跑一遍，看它报的绿是不是绿在它以为的东西上。**

### 7.2 真机一跑（H20，五臂）

跑法与产物：`benchmarks/verify_resume_equivalence.py`（不带 `--dry`），产物留
`output/probe-resume-20260929-181104/`。每臂各建一个 `LLMClient`（账单挂在 client 上累加，
共用一个再求和会高估 —— doc 48 的 3.25 倍事故），语料注入临时文件（doc 49 §7.17 那条坑）。

| 臂 | 设置 | 用时 | LLM 调用 | tokens | 落点产物 |
|---|---|---|---|---|---|
| A | 只跑 1 轮，制造断点 | 82 s | 4 | 18,504 | `20260929_181227_54b3efd8` |
| B | `resume_from=A`，`max_rounds=2` | 43 s | **1** | 7,899 | `20260929_181310_7089ffec` |
| C | 不续跑，从零 2 轮（对照成本） | 117 s | 6 | 28,674 | `20260929_181507_d3fce446` |
| K | 第 2 轮进行中 **SIGKILL** | — | 子进程 `-9` | 无 `result.json`（被杀在 save 之前） | 快照 round_done=1 |
| K-resume | 从 K 的快照续 | 23 s | **0** | 0 | `20260929_181721_f942db23` |
| D | 把 A 的快照截成半个 JSON 后续跑 | 67 s | 3 | 15,066 | `20260929_181828_5cedaf7c` |

各臂 `iteration_history`（签名取前 8 位，档位全是 `uninformative`，见 7.4）：

```
A   r1 generate e852076d  1.2799
B   r1 generate e852076d  1.2799   ← 与 A 逐字段相同
    r2 optimize  ba8636b3  1.4417   ← 真的接着往下走了
C   r1 generate 435b5b84  1.2917
    r2 optimize  ae2a8ad1  1.2895
K   r1 generate d47d61c3  (没走到 L3)
Kr  r1 generate d47d61c3  ← 与被杀那次相同
    r2 fix       ef4e3b7e  1.4274   ← 0 次 LLM 调用完成的
D   r1 generate 01db001c  1.2929   ← 与 A 不同：它确实从头跑了
```

**13 条判据：12 通过 / 0 失败 / 1 没有被问。**

最强的三条：

- **B2（身份）**：续跑产物里第 1 轮的 `candidate_signature` 与 `speedup` 与 A 真机测出的**逐字段相同**
  （`e852076d…` / `1.2799`）。这条在 MockGPU 上没有鉴别力（假后端计时是确定性的，重跑一遍也一样），
  在真机上才有：两次独立测量得到同一个 4 位数比值的概率足够低。
- **K0+K1+K3（真实的崩溃）**：子进程退出码 `-9`，`result.json` 根本没写过，而磁盘上已经有一份
  `round_done=1` 的可解析快照 —— 循环内那些落盘点不是装饰。续上之后 `round_restored=1`。
- **K-resume 的 0 次调用（本片最意外的读数）**：它完成了第 2 轮而**一次 LLM 都没问**。原因是被杀
  那次已经把 Fixer 的产出写进了快照的 `pending_fix`，恢复臂直接用了它（`action=fix`）。这是比 B2
  更强的等价证据：**恢复的不只是历史数字，还有一份尚未执行的、本来要烧一次模型的动作**。
  反过来也标一条弱处：`K4` 那条两侧 `speedup` 都是 `None`（那轮没走到 L3），所以它的相同只落在
  `candidate_signature` 一个非空字段上，鉴别力比 B2 低一档。

### 7.3 两条不能说出口的话

1. **不能说「省了多少」**。A+B = 5 次调用 / 26,403 tokens，C = 6 次 / 28,674 —— 同样两轮少
   1 次调用、少 2,271 tokens（≈8%）。但逐轮调用数本来就不齐（A 一轮 4 次、C 两轮 6 次、
   K-resume 一轮 0 次），n=1 的任何百分比都是编的。能说的只有方向：**续跑臂没有重烧第 1 轮**
   （B2 + B3 的轮号 `[1,2]`）。这条纪律与 doc 48 那句「本轮没为这个差设计对照，不要引用省 61%」
   是同一条。
2. **不能说「续跑与不中断产出同一个核」**。B 的第 2 轮签名 `ba8636b3`，C 的第 2 轮 `ae2a8ad1`，
   **不同，而且应该不同**（起点不同 + LLM 非确定）。所以 §六 第 1 条那个「等价」被这一节收窄成
   一个可证的命题：**已完成的轮次不被重烧，并且被真的当作下一步的起点**。至于最终产出是不是同一
   份核，那是分布层面的命题，一次对照臂不够，需要 n 台量具（#48 那类）。

### 7.4 环境：这一批加速比一条都没有判决资格

每一轮 L3 都是 `measurement_validity=uninformative`，原因逐轮写在产物里（节选）：
`launch 地板占实测时间 70.2% (> 30%) … 最慢样本是中位样本的 14.7 倍 … 卡与 5 个其他进程共享,
瞬时 util=0%`。B 的第 2 轮是 72.5% / 33.5 倍。

所以 **1.28 / 1.44 / 1.29 / 1.43 这些数字不许被当性能结论引用**（也解释了这一轮为什么零条入库）。
本实验用它们只做一件事：**同一份读数被原样搬回来的指纹** —— 指纹不需要可信，只需要可辨。
顺带一句量具该改的地方：`layernorm (1024, 512)` 对 H20 太小，70% 的时间是派发开销；
下次跑（#62）应该换大 shape，让档位有资格变 `valid`。

另外这一臂**顺带证实了 doc 49 §7.9 那个读者在真机上真的在做事**：B 的运行里打出
`[Env] 环境漂移: 无 (与 断点续跑的快照 一致)`，并且 `environment_drift` 进了 `result.json` ——
那是它第一次在真机上拿到「上一次」并比了一次。

### 7.5 ⚠️ 这份读数的归属不成立（比读数本身更值得记）

跑动窗口是 18:11:04 → 18:19 左右。同一棵树上有并发会话正在写**这条路径自己要用的文件**：

```
operator_agent/reference.py        18:12:59   （新文件）
operator_agent/schemas.py          18:13:46   （arm B 正在跑）
remote_scripts/run_kernel.py       18:15:00   （arm C 正在跑）
operator_agent/remote_executor.py  18:16:21   （arm K/D 正在跑）
operator_agent/verifier.py         18:17:54   （arm D 正在跑）
```

⇒ 五臂不是同一份代码：A 与 B 之间 `schemas.py` 变了，C 的远端 runner 脚本在跑动中被换过。
所以这一节**不能**记成「`git_head=f50ec5f` 的真机读数」，只能记成「一份混合工作树上的读数」。
它是 doc 49 §7.7 那条陷阱（脏工作树上的测试数不是 HEAD 的数）第一次发生在**真机端到端实验**上，
而不是发生在单测计数上 —— 形状更坏，因为一次真机跑没法「重跑一遍就好」。

两条处置：
- **不在净 worktree 上立刻重跑**。远端 `~/operator_agent/run_kernel.py` 是按 hash 部署的**共享状态**，
  从一个 HEAD 的 worktree 重跑会把并发会话正在用的 runner 换掉。要重跑得等树安静（记成 #62）。
- 把这条写进判据设计纪律：**任何需要归给某个 commit 的真机实验，开跑前先记录一组文件指纹
  （mtime / hash），跑完再取一次并对比**。这一份驱动没做，所以这一节的结论只能弱到
  「续跑没有静默重烧**在这次跑里成立**」。通则：**实验开始前值得为它拍一张「我跑的是哪份代码」
  的快照，成本是一次 `stat`，收益是这份读数能不能被引用。**

### 7.7 这一节自己撞出来的第二条：隔离不变量只在一个构造点上成立

跑完 §7.2 之后按 `mtime` 查并发写入（那是为了 7.5 才做的检查，结果顺手抓出另一件事）：
`output/kernel_db.jsonl` 的修改时间落在我的跑动窗口里。顺着追下去 —— 驱动里有两个构造
`Conductor` 的地方：`build()`（A/B/C/D 四臂）注入了临时语料，而 **`child_main()`（K 那个被
SIGKILL 的子进程）没有**，它走的是仓库默认路径。

量到的漏：真机那一跑写进仓库语料 **3 条 `retrieved` 事件**；四次 dry 又写了 **16 条**
（特征极清楚：每臂一批 4 条、`ids` 恰好是 `["seed_py_001"]`、microsecond 间隔 —— MockGPU +
脚本化假件只可能来自 dry）。两份都按分钟窗口删掉了（备份
`kernel_db.jsonl.bak-resumeprobe-20260929`、`kernel_db.jsonl.bak-drypollution-20260929`），
删完 113 → 94 行。

**为什么 3 条噪音也值得动手**：`retrieved` 不是日志而是**输入** —— 它喂的是检索排序里那个
「曾被检索 N 次」的计数器（doc 49 §7.15 刚把「没测过的先验数不许在排序轴上赢测量数」钉住）。
一份探针造成的计数偏差，方向和真数据一样，下游分不出来。这比 §7.17 那次「7 条失败记录进仓库」
轻，但形状完全相同，而且**这次的成因不是 `x or Default()`**（那条已经修掉了），而是
「同一个不变量我只在其中一条代码路径上设置了」——`build()` 有、`child_main()` 没有。

⇒ 通则：**任何「探针不许污染仓库」的不变量，要按构造点计数来核对，而不是按函数计数。**
一个脚本里有 N 处 `Conductor(...)`，就得有 N 处注入 —— 与 doc 48 那条「一个函数里有 N 个同型
分支时用例数按分支算」是同一条纪律搬到了「设置」这一侧。

检验方式（这次真的执行了，不是推理）：修完 `child_main()` 再跑一遍 dry，
`output/kernel_db.jsonl` 行数 **94 → 94 不变**。修法本身能被读回来，靠的是行计数而不是「看代码
像是对的」。


### 7.8 ✅ §7.5 那笔账落了一半（2026-09-30，`a3b4056`）：驱动现在知道自己跑的是哪份代码

`benchmarks/provenance.py` 是新的一只量具，`verify_resume_equivalence.py` 是它第一个读者：
开跑前取一次指纹、汇总前再取一次，**两次不同就退 3 并且根本不印汇总那行**。

三条设计都不是先想好的，是被测试撞出来的（顺序即时间顺序）：

1. **「另一个写者」优先**：哈希由**子进程**读盘算，不是驱动自己算。依据是 doc 56 引的那句
   "The remedy is another writer, not richer logging." —— 驱动算的哈希只能证明它读到了什么，
   不能证明跑动期间盘上没变。子进程失败时返回 `None`（不兜成一张表）。
2. **名单是算出来的**（`closure()` 沿 AST 的 import 边做 BFS），不是手抄的。第一版只认绝对名，
   而 `conductor.py` 那一串是 `from .verifier import` ⇒ 闭包停在 8 个文件、`verifier.py`
   压根不在名单里 —— 这份名单的用途恰恰是抓 `verifier.py` 被改（§7.5 那五个文件之一）。
   认相对 import 之后又发现第二个洞：无条件展开 `names` 会把 `from .verifier import Verifier`
   里的**类名**当子模块，造出一条 `operator_agent/Verifier.py`；而 macOS 的盘大小写不敏感，
   `exists()` 竟然为真 ⇒ **同一个文件登记两次**，「多少个文件」这个数就不可信了。
   现在按 realpath 去重，并有一条用例断言「名单里没有盘上不存在的条目」。
3. **门不许在证明不了任何事的名单上绿**：写测试时传了一个不存在的 root，子进程「成功地」算出
   两份**全 ABSENT** 的清单，逐元素一比完全相同 ⇒ `diff` 报「没变」，归属门在一份从没看过盘的
   名单上开了（CHECKLOG I25）。现在 root 不存在直接抛，而 `diff` 见到整张 ABSENT 也判失败。

归属守卫的判据是**顺序**而不是**存在**：测试要求「按归属结果提前 return 的那道门」的 lineno
小于「打印汇总那行」的 lineno。只断言 `main()` 里存在某个 `if` 是不行的 —— 随便一个 `if na:`
都能让它绿，而门写在汇总后面同样什么都没挡住。

端到端真撞过一次（`--dry`，零 GPU 零 LLM）：跑动中途改 `benchmarks/provenance.py` 自己 ⇒
退出码 **3**、印出「被改 benchmarks/provenance.py」与「这份读数不能归给任何 commit」，
而**汇总那行没有出现**。对照组是同一支不改动跑完 ⇒ 「33 个仓内文件哈希未变 ⇒ 可归给 HEAD」。**改与不改各跑一次**，而不是只看代码像是对的（§7.7 那条纪律的第二次执行）。

  pending），而且必须等这棵树安静：远端 `~/operator_agent/run_kernel.py` 是按 hash 部署的共享状态。
