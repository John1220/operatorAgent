# 35 · 处方式错误反馈真机 A/B：一个零差异结果，和它到底证伪了什么

对应吸纳项 **C1**（[`20-吸纳决策与阶段总结.md`](20-吸纳决策与阶段总结.md) 第三节），
证据来源 SPARC（arXiv:2607.09803，✅ 读过全文）。代码落在 `operator_agent/fixer.py` 与
`operator_agent/verifier.py`，驱动脚本 `benchmarks/verify_prescriptive_feedback.py`。

结论先放前面：

- ✅ **「信息补全」那一半被真机证明了** —— 语法错误源码窗口 + 去掉错误全文重复，实测注入
  prompt 从 1350 字符降到 859 字符（**-36%**），且这部分**不依赖模型行为改变**；
- ⚠️ **「归因措辞」那一半没被证明，也没被证伪** —— A/B 两臂 8/8 与 5/8 完全打平，但这个
  设计从原理上就看不见效应（第五节解释为什么）；
- ❌ 顺带挖出两个此前没人发过火的缺陷：`message` 与 `error_log` 存同一份全文（第六节），
  以及新输出要求与 SKILL 1.1 的硬冲突（第七节）。

---

## 一、要验的是什么

SPARC 的核心结论不是「错误信息写详细点有好处」这种常识，而是一条更具体、也更反直觉的话：

> **同一个错误，归因为外部来源（编译器 / 硬件 / 检查器）时模型能修，归因为它自己的输出时修不了。**

它的理论条件是误差传播算子的谱半径 ≥ 1；它测的四个骨干是 Llama-3-8B / Qwen2.5-7B /
DeepSeek-R1-Distill-7B / QwQ-32B —— 和本项目自建 `Qwen3.8-27B` 同一档位，所以这条证据不是
从 70B 模型外推来的。该文另外报告：加一个 `Wait` 类修正标记可把盲区降 89.3%。

于是本轮改动是三件事：

| 改动 | 落点 | 性质 |
|---|---|---|
| 外部归因段 + `Wait` | `fixer.py::_ATTRIBUTION` | 措辞（要靠模型行为变化才有效） |
| 每条错误配「要求 / 该改哪里」 | `fixer.py::_PRESCRIPTIONS` + `prescribe()` | 措辞 + 知识 |
| 语法错误带上源码窗口与插入符 | `verifier.py::syntax_error_report` | **信息补全**（此前根本没给） |

前两行是 `prescriptive=True` 控制的，第三行不受该开关影响 —— 这个区分是第五节全部
判读的关键。

## 二、四个真实产出方，四个不同来源的失败

为了不让「处方式反馈」停在设想层面，样本必须是从**真机**长出来的失败，而不是我手写的错误
字符串。四个 case 各代表一个产出方，`REPS=2`、`layernorm 512×768 fp16`、H20 + 自建端点。

| case | 谁报的 | 真机原文（摘录） | 命中处方 |
|---|---|---|---|
| 臆造 `tl.*` API | 远程 Triton 编译器 | `CompilationError: at 9:11: … AttributeError("module 'triton.language' has no attribute 'cache'")` | 「这个标识符在当前 Triton 版本里不存在，照记忆补 API 一定会再错一次」 |
| 数值超容差 | L2 数值检查器 | `matched_ratio 0.214890 < 1.0 (308718/393216 个元素同时超 atol=1.0e-02 与 rtol=1.0e-02; max_abs=1.35e+00)` | 「按顺序查：累加器是否 fp32 → input_precision → mask/other → stride」 |
| 反作弊屏蔽 | `anticheat.static_audit` | `第 5 行: 检测到 torch.nn.functional.layer_norm() 调用` | 「参考实现由 harness 自己跑，候选里不要调 torch 高层算子」 |
| 输出截断 | 本地 L1 预检 | `SyntaxError: unexpected EOF while parsing` + **13 行源码窗口 + 插入符** | 「编译器在这一行停止解析；真正缺的闭合符号往往在上面几行」 |

第一个 case 顺便复现了 doc 15 一手核实的那条事实：`tl.cache` 这个 API 根本不存在（当年
hints 里就写着它）。第四个 case 的源码窗口是**新能力** —— 以前 Fixer 只拿到
`invalid syntax (第 13 行)`，从来看不到第 13 行长什么样。

## 三、先确认处理真的生效了（否则零差异毫无意义）

A/B 之前必须回答「两臂的 prompt 到底有没有区别」。用 `DUMP_PROMPT=0` 摊出同一份真机失败
渲染出的两臂原文，错误段长度 **661 → 903 字符**：

```
── [L2] [输入集 1/1] 远程执行失败: Remote verification error: CompilationError: at 9:11:
   执行侧原话:
<…编译器回显的 12 行源码 + 插入符…>
   要求: 这个标识符在当前 Triton 版本里不存在, 照记忆补 API 一定会再错一次
   该改哪里: 只允许用 SKILL SPECIFICATION 与优化配方里明确出现的 tl.* 写法; 想用的 API
   不在其中就换成等价实现, 不要猜名字
```

外加归因段（「下面每一条都是编译器、GPU 或数值检查器…与上一版是谁写的无关。**Wait** ——…」）。
处理是生效的，所以下面的零差异不是「两臂本来就一样」。

## 四、结果：两臂完全打平

| case | 裸文本臂 | 处方臂 |
|---|---|---|
| 臆造 `tl.*` API | L1 2/2 · L2 2/2 | L1 2/2 · L2 2/2 |
| 数值超容差 | L1 2/2 · L2 2/2 | L1 2/2 · L2 2/2 |
| 反作弊屏蔽 | L1 2/2 · L2 **1/2** | L1 2/2 · L2 **1/2** |
| 输出截断 | L1 2/2 · L2 **0/2** | L1 2/2 · L2 **0/2** |
| **合计** | **L1 8/8 · L2 5/8** | **L1 8/8 · L2 5/8** |

16 次调用、55 274 prompt tokens、11 676 completion tokens（自托管按估算价 $0.028）。

## 五、这个零差异**不**支持的三个结论

写到这里最容易犯的错是把表格往「吸纳有效」或「吸纳无效」任一侧硬掰。三条都不成立：

**1. 天花板效应吃掉了判别力。** 4 个 case 里 2 个两臂都满分 —— 删掉一个不存在的 `tl.*`
调用、或把 `var + eps` 改回 `1.0 / tl.sqrt(...)`，对 27B 模型本来就不需要提示。这些格子
无论消息怎么写都会通过，对抗效应严格为 0。真正有信息量的只有后两个 case，而它们是 **2 vs 2**
—— 换句话说，这个实验的有效样本量是 0，不是 8。

**2. 指标选错了。** 打分口径是「一次生成的代码能否过真机 L1+L2」。但线上 Fixer 回路是
**最多 3 次预检重试**（`MAX_FIX_ATTEMPTS`），处方最该起作用的地方是**少走几次弯路**，而不是
单次通过率。正确的指标是「到达可编译所需的生成次数」，我测的根本不是它。

**3. A/B 只测了措辞那一半。** `syntax_error_report`（信息补全）在 `prescriptive=False` 时
**照样注入** —— 开关只管归因段与处方行。所以表格只否证了「换个说法」的效应量 > 单次通过率的
分辨率，没有碰「把模型从来没收到的信息给它」那一半。

反过来，**这一半是被证明了的**：见第六节。

## 六、被证明的那一半：错误全文重复，实测 -36%

采集真机原文时顺手发现：`verifier.py` 里四处把**同一份全文**同时塞进 `message` 和
`error_log`：

```python
message=f"编译失败: {e}", error_log=str(e)                    # L1 远程编译
message=f"远程执行失败: {remote_verify.get('error','')}",      # L2 远程执行
      error_log=remote_verify.get("error","")
```

而 `_format_failures` 两个字段都会写进 prompt ⇒ **全文出现两遍**，且 `message` 那一份
**不受 `_truncate_error` 约束**（截断只压 `error_log`）。Triton 的 `CompilationError` 会回显
整个核，gcc 更狠 —— 这正好是我在 `syntax_error_report` 文档串里写的「修复回路里最贵的不是
信息不准，而是信息不全」的反面版本：信息不缺，但是**付两遍钱**。

改法：新增 `failure_pair()`，`message` 只留首行（现象），全文归 `error_log`（由截断管）。
用第二节那条真实的 12 行、544 字符远程错误实测：

```
同一条真机错误注入 prompt 的字符数: 改前 1350 -> 改后 859, 省 491 (36%)
```

这条收益不依赖任何模型行为假设，落地即生效。⚠️ 但注意它**不等于**「Fixer 修得更好了」，
只等于「同样的信息少花 36% 上下文，并且长错误不再能撑爆预算」。

## 七、SKILL 1.1 与新输出要求的硬冲突（真机探到，已修）

`Wait` 标记要模型「先复述直接原因再改」，但注入在它上面的 SKILL 块写着绝对禁令：

```
- NO explanation text before or after code (outside of docstring/comments)
- Output MUST start with `import`
```

两条指令直接矛盾，谁赢纯看运气。真机单发探测（n=1）：**模型输出了 `根因:` 一行**，且
`_extract_code` 正确剥出代码（首行 `import triton`）—— 但这只是一次抛硬币。于是把覆盖关系
写进 `fixer_repair.md` 第 5 条，明确它优先于 SKILL 1.1 那两条。

顺带补了两条提取回归测试（前言 + 有 fence / 无 fence 两种回复都要能剥出可编译代码），
否则「让模型多写一行」这条吸纳会在自己制造的输出格式上翻车。

## 八、守卫与变异验证

新测试文件 `tests/test_prescriptive_errors.py`（22 例）。三类守卫值得单说：

- **死规则守卫** `test_every_rule_is_reachable`：处方表 9 条，每条都必须被某个**真实产出方**
  的文本命中。前 6 条的样本文本不是手写的，而是当场调 `FixerAgent._validate_code()` 取
  issue 原文 —— 改了预检措辞而忘了改签名，这条就报死规则。这条守卫是必要的：处方表起初
  只有 6 条，其中 4 条（截断 / 空代码 / 结构缺失 / 跨硬件禁令）只由**本地预检**产出，而预检
  反馈路径当时根本不走 `prescribe()` —— 那 4 条本会是「算了没人读」的死条目。
- **模式锁** `test_attribution_blames_the_toolchain_not_the_model`：归因段的措辞**本身就是
  被吸纳的干预**，所以按措辞断言（必须点名编译器/GPU/数值检查器 + 必须有「与上一版是谁写的
  无关」）。这是整个测试套件里唯一一条「测字符串本身」的断言，理由写在它的 docstring 里。
- **前缀污染守卫** `test_reflexion_prefix_still_distinguishes_different_errors`：Reflexion 走
  `prescriptive=False`，因为 `failure_id` 的哈希取 `_format_failures` 输出的**前 200 字符** ——
  开头若换成固定归因段，不同错误会撞进同一签名。

变异验证 13 条，全部拦下：M1 `prescribe()` 恒返回 None、M2 重试 feedback 不给处方、
M3 忽略 `prescriptive=False`、M4 L1 退回 `str(e)`、M5 `end_lineno` 属性直取、M6 宽规则提前、
M7 去掉 `Wait`、M8 处方匹配吃截断后的日志、M9/M10 归因段改口 / 不再点名 GPU、
M11/M12/M13 三处错误全文重复回潮。

⚠️ **M2 起初漏过一次**，值得记下来：断言写的是「整个 prompt 里含 `该改哪里:`」，而第二次
调用的 prompt = `base_prompt + feedback`，`base_prompt` 里本来就带处方 ⇒ 变异被无关部分满足。
改成先 `partition("上次修复未通过预检")` 再断言**反馈段之内**有处方。这是「断言被 prompt 的
另一部分满足」的第三次踩坑（前两次见 doc 33 第五节）。

## 九、下一轮怎么测才有判别力

本轮的设计缺陷是可修的，不是 C1 的判决。要真判「外部归因有没有用」，需要：

1. **换 case 来源**：只用 `logs/` 里真实「修 3 轮仍失败」的失败，不要自己造 —— 需要的是
   模型**修不动**的格子，那里才有方差；
2. **换指标**：`rounds-to-compilable`（到首次可编译所需的生成次数），不是单次 pass/fail；
3. **n ≥ 8/格**，两臂在同一 case 上**交替**跑，抵消端点侧的时段漂移；
4. 顺带把「模型是否真的先写了 `根因:`」记成打分项（本轮只有 1 次观察）。

第 1 条最便宜（`logs/` 里现成有 28 条 L1/预检失败），第 2、3 条会把成本推到 ~100 次调用，
所以这轮不做，先记账。
