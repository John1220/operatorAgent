# 44 — 基线档位与峰值显存：把 KernelBench-Verified 的三条结论逐条对到自己身上

日期：2026-09-26。真机：8×H20 的 GPU 2。外部来源：arXiv 2607.16241（KernelBench-Verified，
Zhang et al.，2026-06）。

## 一、为什么单独做这一篇

缺口 1/4 一路做下来，判据已经全部建立在「同机同卡 vs 一个基线」的加速比上，而
`c76edc8` 刚把这个 speedup 写进**跨运行语料**。也就是说：基线选哪一档、候选多吃多少显存，
以前只影响一轮判定，现在会决定下一次检索把什么样的核当示范。这篇就是去把这两件事量清楚。

## 二、外部来源：三条，逐字核过 abstract

1. **基线要开 TF32**：
   > "enabling Tensor Core acceleration with TF32 provides a more realistic estimation of
   > execution on modern GPUs."
2. **换掉基线之后成绩塌了**：
   > "the best-performing model (GPT-5.5) achieves a 0.88x geometric mean speedup,
   > significantly lower than the 1.43x speedup"
3. **一部分核吃显存**：
   > "On the memory front, 28% of GPU kernels generated by the best model increase peak
   > GPU memory usage."

## 三、第 1 条：我们的 fp32 matmul 已经比的是 TF32 档 —— 而且这次是真的跑到了

`verifier.baseline_plan("matmul", "fp32")` 返回 `["pytorch_eager_tf32", "pytorch_eager",
"torch_compile"]`，并且 `tests/test_measurement_validity.py::TestBaselinePlan::
test_fp32_matmul_prefers_tf32` 早就把它钉住了（连「fp32 名单里不许出现 fp16 基线」一起钉）。

但**名单对不等于远端真选了它** —— 远端按「第一个能跑的」定基线。所以真机复核
（`benchmarks/measure_peak_memory.py`，fp32 Triton matmul 1024³）：

```
  基线选中: pytorch_eager_tf32   speedup=0.4799
```

同一个核、同一台卡，只换基线档位的 A/B：

| 基线档位 | 候选 median | 基线 median | speedup |
|---|---|---|---|
| `pytorch_eager_tf32`（现实口径） | 0.10579 ms | 0.05088 ms | **0.481x** |
| `pytorch_eager`（TF32 关，KernelBench 原口径） | 0.10570 ms | 0.09680 ms | **0.916x** |

**同一个候选核，换个基线就从「几乎追平 PyTorch」变成「慢一倍」，虚高 1.9 倍。** 这就是
论文那句 1.43×→0.88×（1.62 倍）在我们流水线上的本地版本，而且方向完全一致。两边候选
median 差 0.09%（同一核重复测量），说明差异全在基线侧，不是噪声。

⚠️ 表里的 0.481 与上方那次单跑的 0.4799 相差 0.2%，是**同一比较的两次独立运行**，不是抄错：
驱动先按常规口径跑一遍（打印 `baseline_selected` 与 speedup），再跑 A/B 块。

顺带一个容易看错的前提：候选核走的**也是** TF32（`tl.dot` 对 fp32 输入在 Ampere+ 默认按
tf32 截断，本项目的配方里也没有写 `input_precision="ieee"`），所以两臂都在 tensor core 上，
这是一次公平的对比。反过来说，如果哪天候选显式写了 `ieee`，那它面对一个 tf32 基线就只有挨打的
份 —— 那种情况下该换的是名单（fp32 精度任务比 fp32 基线），而不是怪核写得慢。

## 四、第 3 条：额外峰值显存，一个此前完全不可见的失效模式

改之前全仓 `max_memory` / `memory_allocated` **0 命中** —— 不是「量了没用」，是根本没量。
所以第 3 条不能像第 1 条那样「验证我们已有的做法」，只能新做。

### 口径（`remote_scripts/run_kernel.py:_additional_peak_bytes`）

* 在**全部交错计时之后**单独跑，一次一臂，不混进 event 窗口，不扰动 median；
* `reset_peak_memory_stats()` → `memory_allocated()` 取基线 → 调一次 `fn()` → 同步 →
  `max_memory_allocated() - 基线`，即「这一臂每次调用额外占用的瞬时峰值」；
* 两臂都已热身，cuBLAS/Triton 的 autotune workspace 早就落成 cached-reserved，不会被算进来
  （我们要的是「这个核每次调用要多多少显存」，不是一次性常量）；
* 候选臂照旧包在 `shield_torch()` 里 —— 本文件的约定是「候选的每一次执行都在屏蔽区内」，
  多出来的这次也不例外，少包一次就是给反作弊开一个洞。

搬进 `metrics` 的三个键 + L3 message 一句（报绝对值不只报倍数）：

```
  [Verifier] L3 PASSED: 加速比 1.06x vs cuBLAS(FP16) (同机同卡 median, ...);
             每次调用额外峰值显存 候选 32.0 MiB / 基线 32.0 MiB (×1.0)
```

### 先确认量具看得见已知的那份分配

显存与时间不同，它是确定性的，所以可以**绝对标定**。真机四条（同一份驱动，
`python3 benchmarks/measure_peak_memory.py`，全部 ✅）：

| case | 候选额外峰值 | 基线额外峰值 | ratio | 说明 |
|---|---|---|---|---|
| 标定臂：故意多写一块 fp32 输出的 fp16 matmul 1024² | **6.00 MiB** | 2.00 MiB | 3.0 | 设计值 = C(2 MiB) + W(4 MiB)；差值**正好 4.00 MiB** ✓ |
| 合法 fp16 matmul 4096³ | 32.00 MiB | 32.00 MiB | 1.0 | 4096²×2 B = 32 MiB，就是输出张量本身 ✓ |
| fp32 matmul 1024³ | 4.00 MiB | 4.00 MiB | 1.0 | 1024²×4 B ✓ |
| layernorm 16384×6144 | 192.00 MiB | 192.12 MiB | 0.999 | 16384×6144×2 B = 192 MiB；eager 基线多出的 0.12 MiB 是它自己的中间量 |

**量具看得见一份已知的 4 MiB 分配，也能算出与理论值符合到小数点后两位的输出张量体积**，
所以后面引用这些 ratio 是有依据的。注意标定臂的 `×3.0`：只报倍数会把它说成「吃了三倍显存」，
而绝对值只有 6 MiB —— 这就是 message 里坚持报 MiB 绝对值的原因。

### 判定：本轮不加，但把加的条件写下来

与 D2（SM 时钟）同一处置 —— 手上只有 4 个点，硬设阈值就是造一条没有分布支撑的死判据。
改判条件（驱动结尾也会打印一份）：

1. 标定臂量不出已知的 4.0 MiB → 先修量具，别谈判据；
2. 合法核的 ratio 普遍在 1.0 附近（±10%）→ 观测可用，开始攒分布；攒到几十个真机样本之后再谈
   「超过多少算退化」；
3. 若候选普遍 **低于** 基线（ratio<1）→ 口径有问题（比如基线多算了输出拷贝），先查口径；
4. 一旦语料里出现 ratio 明显 >1 的核，就把它接进 `measurement.persist_decision` ——
   那时它才有资格当判决输入。

离线侧三个变异都验过：删掉搬运（2 条用例红）、把 `None` 折成 `0`（1 条红——
「没量到」不能读成「不吃显存」）、去掉 message 分支（红）。

## 五、第 2 条（隐藏/多分布测试集）：明确**不采纳**，以及为什么

论文的四分布隐藏测试集是它成绩塌掉的另一半原因，但本轮不吸纳，理由不是成本：

* 我们的 L2 已经是「多组输入 + 反作弊运行时屏蔽」，且 `interface_contract` 在 L1 前就拦
  参数漂移；再加一组分布**不与**它冲突，只是叠加。真正的障碍是我们还不知道**哪些分布**
  对本项目的算子有意义（KernelBench 的四个分布是为它的任务分布设计的）。
* 现在没有可比的量：要先有「同一个核在多分布下数值门失败率」的数据，才知道加它是收益还是
  纯误拦。所以顺序应该是：语料（doc 43）先攒下 L2 失败原因分布 → 再决定加哪一组。
* 这一条与 C1 的重测（doc 35 第九节）是同一个前提：都需要真实运行现场，而那正是
  `e2b455e` + `c76edc8` 才开始保住的东西。
