# 31 - 测量有效性三态：实现与真机验证

> 缺口 1 的落地记录。设计来自 [`01`](01-launch开销与shape充分性实测.md) 第五节，
> 问题诊断来自 [`00`](00-架构基线与缺口核实.md) 缺口 1。
> 本文只记「实现出来以后实测是什么样」，以及与设计的三处偏离。
>
> 状态：✅ 已实现并在 H20 上验证（2026-09-25）

---

## 一、改了什么

原来 `VerificationResult` 只有 `passed: bool`。L3 报出的数字有两种「不可信」，
但两者都被记成「性能不达标」，再被 Conductor 拿去禁用配方、累计停滞轮次。

现在分三处落地：

| 位置 | 改动 |
|---|---|
| `operator_agent/measurement.py`（新增） | 纯判定逻辑：`assess()` 吃「候选 median 时间 + launch 地板 + 测量前 util」，吐 `Validity` 三档与三个 `can_*` 布尔。不含硬件数据、不做 I/O、不依赖 torch —— 与 `tolerance.py` 同一个定位 |
| `hardware_caps.HardwareCaps.launch_floor_us` | 地板值落在这里而不是新起一张表。H20 = 20.24 µs（[`01`](01-launch开销与shape充分性实测.md) 实测 median）；默认 `None` = 未实测 |
| `verifier._assess_measurement()` | 三条 L3 返回路径（远程同机同卡 / 本地 reference / legacy 绝对目标）统一调用，把三态摊进 `metrics` 并追加到 `message` |
| `conductor._measurement_drives_loop()` | 真正的行为改动：测量不可信时跳过整段停滞判定 |

**暴露「用途」而不是「档位」。** `MeasurementAssessment` 给 Conductor 的是
`can_gate` / `can_disable_recipe` / `can_count_stagnation` 三个布尔，不是
`Validity` 枚举。理由是缺口 1 原来的失效方式恰恰是「档位算出来了，下游各自重新
解释一遍然后没人用」—— `benchmark_contaminated` 早就写进 metrics，
`conductor.py` / `fixer.py` / `agents.py` 三个文件 grep 零命中。

**结论同时写进 `message`。** metrics 是给代码读的，message 是 Fixer 与 SearchAgent
的 prompt 素材，是唯一保证被模型看到的通道。只写 metrics 会重演同一个失效模式。

## 二、真机验证

✅ `benchmarks/verify_measurement_validity.py`，H20（GPU 2，测量前 util=0%，
卡上另有 7 个进程但未争用），探测到 `launch_floor_us=20.24`：

| 用例 | 访存 | roofline 下界 | 候选 median | 基线 median | launch_dominance | validity |
|---|---|---|---|---|---|---|
| layernorm 1024×768 | 3.1 MB | 0.86 µs | 0.0325 ms | 0.0197 ms (Eager) | **0.6228** | `uninformative` |
| layernorm 16384×6144 | 402.7 MB | 109.4 µs | 0.182 ms | 0.2348 ms (Eager) | **0.1112** | `degraded` |
| matmul 4096³ fp16 | 100 MB | 27 µs | 1.0078 ms | 1.0436 ms (cuBLAS FP16) | **0.0201** | `valid` |

三档全部在真机上复现，且与 [`01`](01-launch开销与shape充分性实测.md) 的预测同向。

第一行就是项目已经踩过的那个坑：改动前它报「0.65x vs PyTorch Eager / 带宽利用率
5.4% / memory-bound 需优化」，本次同一档实测报 0.61x —— 数字量级一致，而现在
`can_gate=False`，Conductor 不会再拿它做任何闭环决策。matmul 那一档 98.7% fp16
峰值、1.04x vs cuBLAS(FP16)，`can_disable_recipe=True`，照常参与搜索。

## 三、与设计的三处偏离

### 3.1 [`01`](01-launch开销与shape充分性实测.md) 推荐的 shape 落在 `degraded` 而不是 `valid`

该文第四节建议「layernorm driver 改用 16384×6144（地板占比 14.6%）」，并把
<10% 当作 `valid` 的门槛。**这两个数出自同一篇文章却互相矛盾**：14.6% 已经越过
0.10，按第五节的分档表本该是 `degraded`。

实测把它拉回到边界上：dominance = 0.1112，仍然是 `degraded`，差一点点才够 `valid`。

| | [`01`](01-launch开销与shape充分性实测.md) 的模型值 | 本次实测 |
|---|---|---|
| 地板占比算法 | `floor / (floor + roofline下界)` | `floor / 候选实测 median`（第五节 §5.2 的定义） |
| 16384×6144 | 14.6% | **11.1%** |

两个算法口径不同，实测更低是因为真实核比 roofline 下界慢（该档带宽利用率 60.1%），
分母更大。**实现采用第五节的口径**（只用实测量，不需要 roofline 下界），第四节的
百分比因此不能直接当阈值用。

处置：不改阈值。0.10 / 0.30 本来就是经验值，而 `degraded` 的语义（判定可用、
不参与配方禁用）对这一档恰好是合适的 —— 该核 1.29x 优于 Eager、带宽利用率 60.1%，
是真信号，值得用于通过/不通过；但 11% 的地板占比还不足以支撑「这个配方没用」这种
**永久**结论。若要让推荐 shape 落进 `valid`，该用的是 65536×3072（模型值 7.9%），
代价是单张 805 MB。

### 3.2 `net_of_floor_speedup` 必须在两侧都脱离地板时才报

设计第 3 条要求「额外报告 launch-subtracted speedup 作为第二指标」。实现时才发现
它在地板支配区会产出纯噪声：

layernorm 1024×768 的 Eager 基线 median = 20.6 µs，地板 20.24 µs，扣完剩 0.36 µs
—— 而该 shape 的 roofline 下界是 0.86 µs。**净值低于物理下界，说明差值全是噪声。**
拿它去除候选的净值会得到 0.0317 这种数字，看起来像「扣掉地板后候选慢 32 倍」，
实际什么也没说。

所以加了守卫：任一侧 dominance > 0.30 就返回 `None`，metrics 里干脆不出现
`speedup_net_of_floor`。真机三档的表现符合预期：

| 用例 | speedup_vs_baseline | speedup_net_of_floor |
|---|---|---|
| layernorm 1024×768 | 0.6062 | **不报**（基线被地板吞掉） |
| layernorm 16384×6144 | 1.2901 | 1.3264 |
| matmul 4096³ | 1.0355 | 1.0363 |

后两行也印证了这个指标的定位：地板占比越小，净值比越贴近实测比（matmul 差
0.0008）。它只在 `degraded` 那一档提供额外信息，而那一档恰好是它唯一被报出来的
区间之一。**报一个由噪声相除得来的数字，比不报更糟。**

### 3.3 「地板未知」显式记录，不默认放行

`hardware_caps` 里目前只有 H20 有实测地板，其余设备是 `None`。此时
`assess()` 返回 `VALID` 但 `reasons` 里写明「launch 地板未知, 未做地板支配检查」，
且 `launch_dominance` 不出现在 metrics 里。

不选「未知即无效」是因为那会让所有非 H20 设备上的 L3 全部失去闭环能力；不选
「未知即静默通过」是因为那正是缺口 1 的原发病灶 —— 「没检查」被下游读成
「检查过了」。

## 四、Conductor 侧的行为差异

```
measurement_ok = self._measurement_drives_loop(l3_result, round_num)
if l3_result and l3_result.passed is False and measurement_ok:
    <停滞判定 / 配方禁用 / 提前终止>
```

L3 **通过**时同样要查。那一路会把本轮配方记进 `applied_recipes`，依据不可信的
测量给配方记功是「依据不可信的测量拉黑配方」的镜像错误，同样会固化到后续轮次。

`metrics` 里没有有效性键时 `_measurement_drives_loop` 返回 `True`：旧的
`execution_snapshot` 与不产 L3 的路径都不带这几个键，对它们沿用改动前行为，
不做追溯性重判。

**一个已知副作用**：若每一轮都 `uninformative`，`rounds_without_improvement`
永不递增，搜索会跑满 `max_optimize_rounds` 而不是提前终止。这是有意的 ——
`max_optimize_rounds` 才是真正的预算，而把预算花在多试几个配方上，好过花在一次
基于噪声的提前终止上。为了让这种空转可见，运行结束会打印累计轮数：

```
[Conductor] ⚠️ 本次 3 轮的 L3 测量被判为不可信 (污染 / launch 地板支配),
            这些轮次未参与配方禁用与停滞计数
```

## 五、测试

`tests/test_measurement_validity.py`，33 个用例，纯本地：

- 分档数学与阈值边界；两个信号的组合规则（污染 + 地板支配取更差一档）
- 用 [`01`](01-launch开销与shape充分性实测.md) 的两个实测数字做回归（layernorm
  0.0316 ms → `uninformative`；matmul 1.040 ms → `valid`），并断言用 median(20.24)
  还是 min(18.69) 当地板都不翻转结论
- Verifier 三条 L3 路径都要把三态写进 metrics，含「未知设备显式记录未检查」
- Conductor 端到端：地板支配时跑满预算且不禁用配方；**反向保护**：同一 harness
  换成脱离地板的计时，停滞判定照常生效并提前终止

Conductor 那两条用例把 gflops 钉成常量。原因值得记一笔：MockGPU 的 `execute()`
是真计时，同一个核逐轮会抖（实测 16.03 / 16.07），而 `current > best` 对这种抖动
毫无抵抗 —— 第 3 轮会被读成「改善」并重置停滞计数，反向保护用例直接失效。
**抖动正是本模块要隔离的东西，不能拿它当测试激励。**

变异检查：把 `and measurement_ok` 从 Conductor 的条件里删掉，2 个用例立刻失败。

## 六、仍未做

1. **layernorm driver 的 shape 没改。** [`01`](01-launch开销与shape充分性实测.md)
   第四节建议 `test_nvidia_layernorm.py` 从 1024×768 改到 16384×6144，本文第二节
   也实测确认了当前 shape 必然 `uninformative`。**没有改的原因是改不动而不是不该改**：
   该 driver 在本地用 CPU torch 算 `expected_output`（`:160`），1024×768 是 3 MB，
   16384×6144 是 400 MB，而远端路径根本不用这个值（`verify_function` 只收
   shape+dtype+seed，参考在远端算）。所以正确改法是先去掉这次无用的本地计算，
   而不是直接换 shape。输入传输本身不构成障碍 —— ✅ 核实
   `remote_executor.py:672` 的 `_serialize_inputs` 发的是 shape+dtype+seed，
   远端本地生成数据，400 MB 的张量不过网。
2. **测量无效则重测。** [`00`](00-架构基线与缺口核实.md) 缺口 1 的「待研究」项。
   现在是「不据此决策」，不是「重新测一次」。重测需要退避策略（这台机器上恒有
   7 个其他进程，立刻重测大概率还是污染），本次没做。
3. **离散度信号。** runner 已经返回 min/median/max，`max/min` 的散布是最标准的
   噪声指标，但没有实测依据支撑阈值，加进去就等于凭空造一个数。等积累几轮真机
   数据再定。
4. **交错测量（interleaved A/B）。** [`14`](14-搜索策略与硬件感知目标函数.md)
   记的外部对策。`benchmark_with_baselines` 目前是「候选跑完再跑各基线」，
   时间上不交错，慢漂移会系统性地偏袒后测的一侧。改动量不小（要动 runner 的
   计时循环），单列。
5. **地板的运行时校准。** [`01`](01-launch开销与shape充分性实测.md) 第五节第 1 条
   建议「会话启动时跑一次空核校准」，并指出这个值应当和缺口 3 的
   `HardwareCalibrator` 放一起。本次先用 `hardware_caps` 里的静态实测值，等缺口 3
   落地时改成启动校准 —— 届时 `launch_floor_us` 字段就是校准结果的落点。
