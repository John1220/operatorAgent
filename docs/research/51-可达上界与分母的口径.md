# 51 · 可达上界：roofline 的分母从「厂商标称」换成「这台卡实测」

> 目的：把缺口 3 剩下的那半（**分母**）从「一张手写的表」变成「一条按 shape / 算术强度索引的、
> 带可信位的曲线」，并且明确它要**先于**检索排序（doc 49 §八 第 14 条已经钉过顺序）。
> 本篇 = 本仓现状（自己核过 `file:line`）+ 外部一手（每条自己取原始字节 grep 过）+ 切片计划。

## 一、为什么现在动它 —— 三个已经量到的事实，不是审美判断

1. **「离标称峰值还有多远」混进了两件事**。doc 42 的真机读数：厂商参考核达到标称峰值的
   **94.7%**，而本仓生成的 matmul 达成率 **86.8%**（doc 48 §6.3 读数 ②）。那 8 个点是「模型写得
   好不好」，但分母本身还带着 5.3% 的「这台卡根本到不了标称」。拿它当 100% 就是在要求一个
   连厂商手写核都做不到的东西，而且**判停出口**（收敛判据）会因此永远不开。
2. **可达上界不是一个数，是一条按 shape 的曲线**。doc 42 量的就是这件事；今天这批再补一个样本：
   同一台 H20、layernorm 1024×512 FP32，**每轮 L3 都是 `uninformative`**，原因是
   「launch 地板占实测时间 70.2%~72.5%」（doc 50 §7.4）。一个 shape 上 70% 的时间是派发开销，
   那么这张卡的「可达带宽」在这个点上根本不是 4000 GB/s 那一档。
3. **分母的原料昨天还没有落盘，现在有了**（#63，`git_head=b0505b1`）—— 但**存量产物里一个点都没有**，
   这条是本篇写完之后被实测**推翻**的，留着是因为推翻它的那件事本身才是结论：
   每轮血缘现在带 `roofline`（算术强度、脊点、两侧达成率、`peak_source`、`peak_trusted`、
   `peak_table_key`）+ `input_shapes` + `input_dtypes`，聚合器（A 片）也建好了，跑一遍整个
   `output/` 树的读数是 **2942 份产物 / 8017 轮 / 带轴的轮次 0 条**（§五 A 行的第一份读数）。
   ⇒ 所以「用已有产物离线聚合出曲线」**不成立**；成立的是「从 #63 之后的每一次运行都在产点」。
   这一条把 §五 的顺序**改了**：等语料长到能覆盖 shape 需要的时间，比直接跑一轮标定（C 片）
   更长且不可控 —— 于是 C 片从「排在 D 前面」升为「与 A 并行可做」，而 A 片的价值变成
   **「先把仪器架好，好让 C 片与前后的运行有地方落」**（先观测后判定，doc 45/49 的既有节奏）。

## 四、吸纳 / 不吸纳（以及边界画在哪）

**吸纳 ①（分母换成可达上界，按 精度 × shape/AI 索引）**
外部依据：ERT 那条「more accurate machine characterization」+ tritonBLAS 那条「normalized to
maximum achievable performance」。形态取 TileSight 的「one-time per-architecture microbenchmark,
~minutes」——**专门跑一轮标定**，不是攒历史。为什么：攒历史要等真实语料覆盖到那些点，而
doc 49 §7.15 量的存量是 `kernel_db.jsonl` 里只有 **8 条真机记录**；靠它聚合出来的曲线在
大多数 shape 上根本没有样本，而那些点上我们会**悄悄退回标称峰值** —— 那正是「把像样的值塞进
失败里」的又一形态。标定是**可控的一次**，历史是**不可控的一堆**。

**吸纳 ②（层级那一维，但只到 L2 就停）**
2009.05257 的主张是 hierarchical（HBM / L2 / L1 / 寄存器各一条线）。本仓只取
「同一 kernel 在 HBM-bound 与 L2-resident 两种 footprint 下分母不同」这一条，做成两档而不是
四层：我们的 runner 已经量了 `candidate_peak_memory_bytes`（doc 44 §四），拿它跟 `l2_cache_size_kb`
比就能定档。**不取四层的理由**：四层需要每层各自的标定与每层各自的读者，而今天
`arithmetic_intensity` 只有一个轴；先加一档「工作集是否溢出 L2」能覆盖 doc 42 里绝大部分偏差。

**吸纳 ③（可信位必须贯穿到轴）**
`peak_trusted=False` 时 `bound_type` 不许参与配方筛选与收敛出口（#64），并把
`optimization_planner.py:507` 那句「默认视为 compute-bound」改成**显式的第三态**。外部依据是
方法学而非文献：**没有可信分母就没有「离顶还多远」这个量**，而「离顶还多远」正是那条默认值
要用的东西。

**吸纳 ⑥（把 launch 地板做成一条额外的上界，而不是只当降级理由）** ← 本轮取证时才发现的缺口。
外部依据逐字来自 2009.04598：「through an additional ceiling (**another term in Roofline's min
function**)」。本仓现状是：`verifier.py:776` 已经拿到 `launch_floor_us`，但它的唯一用法是**把档位
降成 `uninformative`**（doc 50 §7.4 那批：地板占 70.2%~72.5% ⇒ 整轮读数作废）。作废是对的判决，
但它同时**扔掉了那条信息**：地板是一个可测的、可以进 `min()` 的上界。两种用法的差别在后果上：
降档 ⇒ 这一轮不产点 ⇒ 分母永远凑不齐（A 片刚量到 8017 轮 0 个点）；加上界 ⇒ 同一个 shape 上
「可达」变成一个有限值，而且它告诉 SearchAgent「这个 shape 再怎么优化也到不了 4.0 TB/s，
因为 70% 的时间是派发」—— 那正是 doc 51 §四 吸纳 ① 想要的「按 shape 的曲线」里**最小的那一档**。
⚠️ 边界：地板项只进**报表与分母**，不进 L3 的通过/失败判决（判决那条链已经有三态门了，
把两个用途混在一个数上是 doc 49 §八 第 17 条那种「一个块里两个口径」的错）。

**不吸纳 ④（不做完整的 analytical model）**
tritonBLAS/TileSight 都是「用模型替代 autotuning / 预测绝对延迟」。本仓不做这件事：我们要的只是
**分母**，不是预测器。把它们那套搬过来等于重写计时与 roofline，而缺口 5 的教训是——
两个 runner 契约一漂，代价是整条链静默给错值。取它们的**标定思路**（微基准 + 按精度分档），
不取它们的**预测结构**。

**不吸纳 ⑤（不引入 Nsight Compute 作为测量面）**
2009.05257 的另一半是 application characterization using Nsight Compute。本仓的 L3 是
「远端 runner 里 `do_bench` 墙钟」，换成 profiler 计数会同时改掉**基线**的口径，而
doc 42/48 的整个加速比体系建立在「候选与基线同机同卡同窗口同一把尺」上。这条要在
**能同时重标基线**的时候才做，不是现在。

它同时给出三件事：分母**今天不存在**；仪器**已经在**（下一个带轴的运行就开始产点）；
以及 #48 那轮机时值多少 —— **8017 轮里没有一轮能喂这条链**，因为它们全部早于 #63。

15 例 + **9 条变异全红无逃逸**，其中一条**先逃逸后被补**：把报表里的带宽写死成 `0.0`

必须被单独钉一次（与 doc 48「三条单独看每条都像合理的数，只有排在一起看单调性才暴露」同族，
只是这次的形态是「报表对不对」而不是「账单单调不单调」）。
