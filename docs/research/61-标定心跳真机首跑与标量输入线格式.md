# 61 — 标定心跳第一次上真机：CPU 分支分离度 8.09× 成立，而它自判 RULER_BROKEN 牵出输入线的静默错值

日期：2026-10-01。真机：8×H20 的 `algorithm-h20`（`SSHExecutor` 自动选中 GPU 2，util=0%，free 38.4 GB）。
控制机：macOS，无本地 GPU。跑法：`python3 benchmarks/measure_heartbeat_real.py`（新增，见下）。

---

## 一、这次要回答什么

设计 §10.5-1 把「每 N 次真值测量前，用一对已知好/故意慢的参照物验一次尺子」写成硬纪律，
`operator_agent/calibration.py` 里也已经落成代码（`backend_bench_fn` + `heartbeat`），
但**从来没有在真机上跑过**：此前的全部证据来自 `MockGPU` 与控制机的 `perf_counter`。
四个问题按顺序问：

1. 参照对**到底量在哪** —— 哪个语言分支、哪把秒表、哪个设备？
2. 远端量出来的分离度是多少（设计期望慢核 ≈8×）？
3. 一次心跳花多少机时/时间，值不值得插在每 N 次测量前？
4. 换成 triton 参照对（走 CUDA event 分支）会怎样 —— 「按任务 DSL 选参照对」能不能先试？

## 二、实测

### ① 参照对量在远端 CPU 的 Python 秒表上（这是**设计已知**的边界，不是意外）

| 臂 | median | `language` | `device` | SSH 往返 |
|---|---|---|---|---|
| `known_good`（24×24 朴素矩阵乘） | 2.1096 ms | `numpy` | `cpu` | 8.79 s（含首次 deploy） |
| `known_slow`（同一核重复 8 遍） | 16.7163 ms | `numpy` | `cpu` | 4.96 s |

比值 **7.93×**。判据是载荷**自己报的** `device`/`language`，不是毫秒数：
`device='cpu'` + `language='numpy'` 说明这段被量在远端 CPU 上，与 H20 无关 ——
参照核没有 `import triton/torch`，`run_kernel.py:_detect_language` 判成 `numpy`，
走 `_benchmark_torch_numpy` 的 else 分支（`perf_counter`，`device_is_cuda=False`）。
这一条 doc 之前就在 `calibration.py` 的注释里写着，这次是**实测对上**。

### ② 顺带量出：`smoke_spine_h20.py` 的 §14-1/§14-2 臂量的也是远端 CPU

同一台机、同一条 `backend.benchmark`，把那份冒烟脚本的 `GOOD` 原样量一遍：

```
numpy@256: median=0.07513 ms  language='numpy'  device='cpu'
```

那份脚本的 `GOOD`/`SLOW`/`BURNER` 三个核**都是 numpy**（`np.asarray(A) @ np.asarray(B)`），
所以它的「已知好 vs 已知慢」比值是真的，但**与 H20 无关**；`BURNER` 那一路虽然写着
`CUDA_VISIBLE_DEVICES={gpu}`，numpy 不认这个变量，它占的是 CPU 核而不是卡。**结论**：
那份脚本名叫「真机 §14 冒烟」，实际覆盖的是「部署/传输/执行/计时」这条通路，
§14 里关于 GPU 的那两问它今天答不了（见 §六 的待办）。

### ③ 心跳本身：第一轮**判了自己 RULER_BROKEN**（修复前）

```
第 1 次: ok=False  好=1.0  慢/好=1.00235  reasons=['RULER_BROKEN: 已知慢核比值 1.002 偏出期望带 [2.0, inf] (slow=2.123 good=2.118, 慢核应显著更慢)']
第 2 次: ok=False  好=1.0  慢/好=0.99563  ...
第 3 次: ok=False  好=1.0  慢/好=0.98913  ...
```

慢核单独量是 16.72 ms，进这条路径只剩 2.12 ms（≈1 遍）。**健康的机器上尺子把自己判坏了。**

### ④ 心跳（修复后，同一台机连跑三次）

```
第 1 次: ok=True  好=1.0  慢/好=8.0854  耗时 8.61s
第 2 次: ok=True  好=1.0  慢/好=8.0657  耗时 8.74s
第 3 次: ok=True  好=1.0  慢/好=7.8719  耗时 8.65s
reasons=['无绝对锚点, 仅核验分离度', 'slow_ratio=8.085 在带宽 [2.0, inf] 内']
```

### ⑤ 「按任务 DSL 选参照对」的预演（triton 那对，CUDA event 分支）

`matmul @1024³`，好核 = `rule_templates.py` 的模板，慢核 = 同一个 launcher 连跑 8 遍：

| 臂 | median | `language` | `device` |
|---|---|---|---|
| triton 好核（1×） | 0.105696 ms | `triton` | `cuda` |
| triton 慢核（8×） | 0.819296 ms | `triton` | `cuda` |

比值 **7.75×**；把那对塞进 `heartbeat`（它自带 24×24 输入）也是 `ok=True`、慢/好 **5.21×**。
**所以「参照对按 DSL 选」在真机上可行** —— 覆盖边界里那条「CUDA event 分支没人验」有现成材料了。

## 三、那个 RULER_BROKEN 是谁造成的：标量输入在 SSH 线上被重新生成

慢核的遍数当时是**形参**（`def kernel(A, B, repeats=8)`），由 `backend_bench_fn` 放进
`inputs` 传过去。探针（同一台机，一次问清四个值）：

```
传入 causal=False  →  远端 np.True_                   (布尔被翻转)
传入 eps=1e-5      →  远端 np.float64(-0.0222884…)   (成了随机数)
传入 repeats=8     →  远端 np.int64(0)                (成了 0)
传入 scale=2.5     →  远端 np.float64(0.0770594…)    (成了随机数)
```

链路：`SSHExecutor._serialize_inputs` 把**每个**输入都变成
`{"shape": …, "dtype": …, "seed": crc32("键|shape|dtype")}`，远端按 seed 用
`rng.standard_normal(shape).astype(dtype)` 重新生成。数组这样传是**刻意的取舍**
（避免 4096² 矩阵的 67 MB JSON，且候选/基线共用同一套描述所以比较仍公平）；
但标量也走了同一条路，于是它的**值被一个 N(0,1) 抽样顶掉再按 dtype 截断**：
`int64` 截断成 0、`bool` 截断成 `True`（只有恰好抽到 0.0 才是 False）。
seed 只由 `键|shape|dtype` 派生、与值无关 ⇒ `repeats=8` 与 `repeats=3` 得到同一个数。

这与 `_deserialize_inputs` 自己 docstring 里那句承诺**正面冲突**（「标量/布尔直通
(如 causal=False): 不具有 shape/data 键者原样透传」）—— 那句话在 legacy 模式成立，
在轻量模式下从来没成立过。挂号 **CHECKLOG I44**。

后果不止「心跳误报」：任何带标量/布尔参数的候选核（attention 的 `causal`、layernorm 的
`eps`）在真机上**验的是另一个算子**，而 L2 会照常给出通过/不通过 —— 错值发生在门**之前**，
门看不出。这是本项目最想防的那一类失效（「量具读的不是你要量的东西」），
而它此前**没有任何测试覆盖**（`_serialize_inputs`/`_deserialize_inputs` 这一对接缝全仓零用例）。

## 四、修复与复验

两处都改在「值的来源」上，而不是在读数端加判据：

1. **`calibration.py`**：慢核的遍数**烘进源码**（`SLOW_REPEATS = 8`，`range(8)`），
   参照对只依赖数组输入；删掉 `backend_bench_fn` 里那段
   `if "repeats" in inspect.signature(...)` —— 它本身就是在依赖一个到不了远端的值。
2. **`remote_executor.py` + `run_kernel.py`**：标量走新的 `scalars` 字段按值直传
   （`np.generic` 落成 Python 标量以过 JSON），数组仍按描述生成。

复验（真机）：标量探针现在回 `causal=False eps=1e-05 repeats=8 scale=2.5`；
心跳连跑三次 **8.09× / 8.07× / 7.87×，`ok=True`**（§二③④）。
新守卫 `tests/test_input_wire_format.py`（5 条）**对旧代码 4 条变红**；
`tests/test_calibration.py` 新增一条钉住「参照核常数必须烘进源码、`inputs` 里只许有数组」。

## 五、成本账：心跳花的是**往返**，不是机时

一次心跳 = 2 次 `backend.benchmark` 往返 ≈ **8.6 s 墙钟**（每次往返 4.2~5.0 s，
首次含 deploy 8.8 s），而两条臂的测量时间加起来只有 **18.8 ms** —— 99.8% 是 SSH/uv 往返。
参照对走 CPU 分支，所以**不占卡**。按设计 §10.2 的节奏（每 N 次真值测量一次，
`heartbeat_interval` 默认 5）算：每 5 次测量多 2 次往返，**+40% 往返**、
GPU 机时 +0。

## 六、这次没做/还不能说的

- **绝对锚点仍然没有**：`expected_good` 为空，心跳只判「分离度」不判「好核该多快」
  （reasons 里那句「无绝对锚点, 仅核验分离度」）。要闭环得先有 `probe_peak` 一类的实测锚。
- **只覆盖 Python/`perf_counter` 分支**：默认参照对不走 CUDA event。§二⑤ 证了 triton
  参照对可行，但**还没接进 `calibration`**（要按 `target.dsl` 选对，且 triton 参照核必须
  自己 `A.float()`：真机实测 fp64 输入会让 `tl.dot` 编不过）。
- **§10.6 的 `abort("ruler broken")` 仍未实现**：今天坏心跳只作废它那一窗，不停整轮。
- **`smoke_spine_h20.py` 的 §14-1/§14-2 臂仍在量 CPU**（§二②）：要么按 §二⑤ 换成 triton
  那对，要么把脚本正名为「部署/传输通路冒烟」。改它属于另一件事，本轮只在脚本里留了指路注释。
