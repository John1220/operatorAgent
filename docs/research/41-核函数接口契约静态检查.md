## 一、契约是什么，以前写在哪

唯一的约定是这一行（`remote_scripts/run_kernel.py:_execute_triton`）：

```python
torch_inputs = {k: torch.from_numpy(v).to(device).contiguous() for k, v in real_inputs.items()}
...
output = kernel_func(**torch_inputs)      # ← 全关键字, 不过滤、不重排、不猜
```

也就是说：**顶层 `def kernel` 的参数名必须逐一等于任务侧给的输入名**。这句话以前
在代码里不存在，只在 `triton_skill.md:30` 用「NO missing `def kernel(A, B)` wrapper」
的形式半句带过 —— 而它约束的是**参数名集合**，不是「有没有 wrapper」。

违反它的代价也不是编译失败，而是运行时的
`TypeError: kernel() got an unexpected keyword argument 'causal'`。这行字要等到
一次 SSH 往返 + 远程 `import torch` + Triton JIT 全部走完才出现，于是被记成一次
「L2 失败」，交给 Fixer 重画一整轮。`docs/research/00` 缺口 6 记的真实历史是
**attention 连烧 3 轮**；本仓库自己的驱动 `test_nvidia_attention.py:190` 就写着
`test_inputs["causal"] = False`，也就是说这个坑是我们主动去踩的。

### 外部的量级参照（一手核过）

TritonBench（[arXiv 2502.14752](https://arxiv.org/abs/2502.14752)，ACL Findings 2025）
把**执行失败**按四类统计（Table 5/6，zero-shot 与 one-shot 两档 × G/T 两个子集）：

| 类别 | 占执行失败的比例 |
|---|---|
| Syntax | 0.00% ~ 25.25% |
| **Attr&Type** | **24.31% ~ 42.62%** |
| Name&Ref | 7.52% ~ 43.06% |
| Run&Logc | 11.81% ~ 53.61% |

⚠️ 三条必须限定清楚，不然就是拿别人的数字给自己贴金：
① 分母是**执行失败**，不是全部任务；
② `Attr&Type` 比我们判的「参数名不匹配」**宽得多**（含张量属性误用等），所以不能说
   这道门能消掉 24~43%；
③ 它的价值是说明**接口/规格类错误在真实生成里是常态而不是偶发** —— 我们原先只有
   「attention 烧了 3 轮」这一个 n=1 的现场。

顺带一条**反面参照**，比正面支持更有用：KernelFalcon（PyTorch 官方博客 2025-11-05）
明确写着 "**no manual AST parsing**；validation is by execution"。他们那样做是合理的
—— 4 个本地 worker 并行、一次执行就在手边。我们的不对称正好相反：一次执行 = 一次
SSH + 远程 import + JIT。所以「静态门」这道设计不是比他们先进，而是**我们的传输成本
结构决定的**。这个理由要留在这儿，否则将来有人加了本地执行池会以为这条可以删。

## 二、为什么用 AST，而不是 `inspect.signature`

这是本轮最有价值的一条外部教训的本地版本：**先确认量具能看见你要看的东西**
（`docs/research/34/35/36/39/40` 已经栽过五次）。这里差点栽第六次。

直觉做法是 L1 时把模块 import 进来，`inspect.signature(module.kernel)` 一比了事。
真机（triton 3.8.0 / torch 2.14.0）探下来两条都堵死：

1. **控制端不能 import 生成代码**。`@triton.jit` 在构造时要 `inspect.getsourcelines`，
   在 `python -c` 下直接 `ValueError: @jit functions should be defined in a Python file`；
   而控制端也没有 torch。项目本来就把「引用实现只在远端构建」写成了规则
   （`verifier._reference_torch` 的 docstring）。
2. **就算在远端，`inspect.signature` 也拿不到真签名**。实测：

```
--- triton.jit callable= True type= JITFunction
   signature(): (*args: 'P.args', **kwargs: 'P.kwargs') -> 'R'
   params: [('args', 'VAR_POSITIONAL'), ('kwargs', 'VAR_KEYWORD')]
   .fn signature: (x_ptr, y_ptr, n, BLOCK: triton.language.core.constexpr)
```

`JITFunction` 把自己伪装成 `(*args, **kwargs)`，真参数表在 `.fn` / `.params` 上。于是
「有 `**kwargs` 就放行」这条规则**对 Triton 核永远放行** —— 一份看起来正确、跑起来全绿、
实际永不触发的死守卫，而那恰好是唯一一类在生产里真出过事的核。

AST 路线没有这两个问题：装饰器不影响 `def` 的参数列表，而且根本不需要 import、
不需要 GPU、不需要 SSH 往返。

## 三、保守原则：只在「必然炸」时拦

误放的代价是一轮 L2（本来就会付）；误拦的代价是把一份**能跑的核**打回去重画。
所以看不准一律放行：

| 形态 | 处理 | 理由 |
|---|---|---|
| 顶层 `def kernel` 参数与输入名不符（多传 / 少必填） | ❌ 拦 | 必然 `TypeError` |
| positional-only（`def kernel(A, /)`）且该参数必填 | ❌ 拦 | 关键字传不进去 |
| 有 `**kwargs` | ✅ 放 | 什么都接得住 |
| 有**默认值**的参数调用方没传 | ✅ 放 | 完全合法 |
| `kernel = something`（别名换掉真身） | ✅ 放 | 静态看不出参数表 |
| 条件 / `try` 分支里的 `def kernel` | ✅ 放 | 形态不止一种 |
| 顶层根本没有 `def kernel` | ✅ 放 | 交给后面的层级 |
| 语法本身不合法 | ✅ 放 | 那是 L1 语法预检的话，不抢话 |

多组输入套件（L2 的 `num_input_sets`）**逐组判**：第 2 组多带一个键，那一组就会炸，
只看第 1 组就是漏。真实历史里「取并集判一次」和「只看第一组」都够蒙混过关。

## 四、开发过程中被自己的测试抓到的两个 bug

都不是设计问题，是实现里最普通的两处手滑 —— 值得记的是**它们都由测试当场抓住**，
而不是等生产：

1. **`ast.arg` 对象混进了名字集合**。`no_default = set(positional[...])` 放的是
   `ast.arg` 节点，于是后面 `名字 in no_default` **恒为 False** —— 「必填没传」与
   「positional-only 挡道」两条判断同时变成永不触发。两个用例一起红。
2. **defaults 的切片方向反了**。`defaults` 覆盖**尾部** k 个参数，必填的是**前** `n-k` 个；
   我写成 `positional[n_no_default:]`，于是 `def kernel(A, B, eps)` 的必填集合算出来是空的。
   第一版还留着一行 `missing = ...`（算的是「有默认值但调用方没传」的参数），
   那是**假阳性**：会把能跑的核打回去重画。删掉，并补一条用例钉住这个区分。

随后按本项目惯例做变异测试：10 条变异（整体 no-op、ast 对象、切片反向、去掉
positional-only 分支、去掉 `**kwargs` 放行、不识别名、Verifier 只看第一组、检查改成空循环、
必填分支短路、顶层重复 `def` 取第一个）——**第一版有两条逃逸**：

- 「不识别名」那条没被抓住，因为别名用例的代码里**压根没有 `def kernel`**，
  检查是因为找不到定义才返回 None 的，别名规则本身没被 exercized。
- 「只看第一组」没被抓住，因为当时的用例直接在检查函数层面逐组调用，没经过 Verifier 的循环。

两条都补了真会走到的路径（别名用例里同时放一个「看起来会不匹配」的 `def kernel`；
多组用例改走 `_verify_compile`）。补完 10/10 全被抓，0 逃逸。

## 五、真机四臂

`python3 benchmarks/verify_interface_contract.py`（控制端跑，触发 deploy，H20 GPU 2）：

| 臂 | 内容 | 期望 | 实测 |
|---|---|---|---|
| A | `def kernel(Q,K,V)` + 输入带 `causal`（历史现场） | L1 失败、无 L2/L3 | ✅ `interface_mismatch`，1 级，**0.04 s** |
| B | 真能跑的 Triton matmul（防误伤） | L1 通过、三级跑完、L2 数值通过 | ✅ 3 级全跑，L2 `matched_ratio=1.0`，L3 1.09x，**15.47 s** |
| C | 同一份合法核，输入套件**第 2 组**多带 `scale` | L1 失败 | ✅ `interface_mismatch`，**0.00 s** |
| D | 把 A 的核补上 `causal=False` | 放行 | ✅ L1 通过（**2.61 s** 到远程编译），随后 L2 按反作弊正确拒绝 |

D 这一臂顺带证明了两层防线没互相顶掉：签名合法但**内容**作弊（`Q @ K.transpose(...) @ V`
就是 torch.matmul 回退）仍然由 L2 拦下 —— 新检查没有变成「签名对=放行到底」。

错误消息沿用 `docs/research/20` C#1 的处方式格式（根因 / 现状 / 改法 / 位置），实测输出：

```
根因: 调用方固定以 `kernel(**输入)` 的**全关键字**方式调用核函数, 而这份代码的 kernel() 签名与之对不上 …
  本次会传入的输入名: K, Q, V, causal
  kernel() 声明的参数: (Q, K, V)
  不匹配: 调用方会传、但 kernel() 没收的参数: causal
改法: 让 `def kernel(...)` 的参数名**逐一等于**上面「会传入的输入名」; …注意不要改输入名 —— 那是任务侧给的。
位置: 第 8 行的 `def kernel`。
```

最后一行「不要改输入名」是刻意写的：模型最常见的两种「修法」里，改调用方是**错**的
（输入名由任务侧决定），只说「签名不匹配」不给方向的错误消息很可能把它推向那一侧。

## 六、顺带修掉的一处生产者—消费者漂移

`optimization_recipes.md` 的 PDL 配方里，`triton_template` 把**设备函数**直接命名为
`kernel`：

```python
@triton.jit(launch_pdl=True)
def kernel(x_ptr, y_ptr, n, BLOCK: tl.constexpr):   # ← 抄了就被 L1 判掉
```

这份模板在新检查之前也不合调用契约（`kernel(X=...)` 同样会抛 `TypeError`），只是那个
代价要等一轮 GPU 才现形。现在它会立刻现形 —— 于是把模板改成 `_pdl_copy` + 一个
`def kernel(X)` wrapper，并在原地写明「设备函数不要叫 `kernel`」。
配方文本与 harness 契约不一致是本项目反复出现的同一类缺陷（`docs/research/35` 里
SKILL 1.1「必须以 import 开头」与处方格式也撞过一次）。

## 七、第 2 片：契约由 harness 在**生成之前**广播（#76③）

第 1 片把契约变成「错了能在动 GPU 前拦住」，但拦截本身仍要付一轮：一次 `fix` 动作、
一次 LLM 调用、一次重画。真机第二份读数把这条门的命中率量出来了 ——
**16 轮里拦下 4 轮，全部 L1 失败都归它**（doc 48 §六B）。也就是说这条门在生产里
不是罕见的边角，而是 L1 唯一的失败来源；那么比「拦得快」更便宜的一侧是**让它一开始就猜对**。

外部一手（CUDA-Harness `arXiv:2609.00058v1`，本地抽取件逐行核对）：

> 行 193–195：*"the scaffold prohibits the use of dummy inputs and provides helper functions for
> reading the well-prepared test inputs. The test input paths are passed as command-line arguments,
> and **the calling convention is emitted at compile time**. Thus, the agent remains **unaware of the
> details of the test inputs** when implementing the kernel and cannot tailor an overfitted
> implementation to them."*
>
> 行 265：*"the agent first invokes the compilation tool and **is informed of the calling convention
> emitted by the scaffold** via a compile-time `#pragma message` as described in Sec. 4.1.2"*

两处的事实是同一个方向的：**契约由 harness 说，不由 agent 推测**。但我方不该照抄它的方式，
因为两件事不一样：

| | CUDA-Harness | 我方这一片 |
|---|---|---|
| 说给模型的时机 | **编译之后**（`#pragma message` 出现在编译输出里 ⇒ 第一次写的代码仍带着错的假设） | **生成之前**（进 prompt 的一个小节） |
| 为什么要藏 | 它把输入的**值/路径**也一起藏 —— 防的是 reward hacking / 针对测试数据过拟合 | 只广播**参数名**这一件结构事实，值与形状不给，过拟合面没有变大 |
| 动机 | 保护**判决**的可信度 | 省掉**一轮**（4/16 轮的比例就是它的价格） |

我方此前恰好是反的，而且反在两个地方：`planner.py:54` 的
`result.setdefault("kernel_signature", "def kernel(A, B)")` 与 `planner.py:84` 那句
`f"def kernel(A, B)" if "matmul" in kt else "def kernel(X)"` —— 按 kernel_type **猜**一个签名，
再由 `coder_pipeline.py` 的 `json.dumps(plan)` 整体注入 prompt。于是 layernorm 这类任务的
prompt 里同时存在一条错的契约，而正确的那份只有调用方知道。

落码（一片之内只做「广播 + 裁决」，不动 Planner 的输出结构）：

- `interface_contract.py:broadcast_calling_convention(test_inputs)` —— 复用 L1 已在用的
  `input_key_sets()`，所以广播与拦截**同一份口径**；四种形态各有输出：单组、多组同名（仍报
  组数）、多组不同名（逐组列，要求入口接得住每一组）、**没有输入信息**。
- 「没有输入信息」是一段**非空**文字而不是空串。这是本项目那条老纪律的又一次应用：
  缺证据不能渲染成「什么都没有」，否则模型看到的是一段消失的约束，而不是「harness 不知道」。
  `{}` 也归到这一支 —— 摊出来是一组空名字，照字面渲染会印出「会传入的输入名: （什么都没有）」，
  把一个未知说成一个**假的空集**。
- 接线：`conductor.py:545` 传 `test_inputs` → `CoderAgent.run` →（pipeline 分支）
  `CoderPipeline.run` → `_parallel_sample` → `_sample_one`；（legacy 分支）`_llm_generate_code`。
  广播文本在 `run` 里算一次，三个采样线程共用 —— 契约不该随 temperature 变。
- 四个生成模板（`coder_from_plan` / `coder_generate` / `coder_generate_triton` /
  `coder_generate_cuda_c`）各加一个 `{{calling_convention}}`。**四个都要加**：#67 那条装配
  守卫按调用点取**并集**（那是它自己的 docstring 里明写的语义），只在 triton 模板放占位符
  在它眼里是绿的，而 cuda_c 那条路上这个值就被静默丢掉了 —— 所以新用例逐个模板钉。
- 广播末句写明「计划 JSON 里的 `kernel_signature` 只是 Planner 的建议，**以本节为准**」。
  Planner 的输出结构这一片不动（它还有 `algorithm`/`steps` 这些真在用的字段），先把两条
  契约之间的**优先级**说清楚，避免出现「prompt 里有两份契约并列」。

测试：`tests/test_calling_convention_broadcast.py` 14 例，三面（内容 / 与判据同源 / 真的进了
prompt）+ 装配契约两面。**8 条变异标定 8/8 拦住、0 逃逸**，但 M5 是补出来的：

- 第一次跑标定，M5（`CoderAgent.run` 不往 pipeline 传 `test_inputs`）**全绿**。原因是用例从
  `_llm_generate_code` 和 `CoderPipeline.run` 进去 —— 测的是**被调方**，漏的正是中间那层
  **转发方**。补一条从入口 `CoderAgent.run` 进、两条分支各走一遍的用例后 M5 才红。
- 同一次标定还先报出「8 条全逃逸」这份**假读数**：变异脚本把两个测试路径当成一个字符串参数
  传给 pytest，命令根本没跑起来，而脚本只翻 stdout 找汇总行 —— 没有汇总行时它把「没跑」印成了
  「绿」。改成 `*TESTS.split()` 并在缺汇总行时直接 `SystemExit` 带 stderr。**量具报「绿」之前
  先要证明它跑过**（CHECKLOG I5 的同族）。

与判据同源那条用例值得单独说一句：它不是比字符串，而是**照广播列出的名字写一个 `def kernel(...)`
再去过 `check_kernel_interface`**，断言放行；反向再少写一个名字，断言拦下。这样「广播的文案」与
「L1 的判据」被钉在同一份事实上 —— 文案改了、判据没跟着改，这条就会红。

这张标定表撞出来的东西不止它自己那一片，两条都记在这儿因为它们都是从「M9a 本该红却全绿」
顺着挖出来的：

1. **`FailureDatabase.search_by_error` 的零相似兜底**（另开 #79 修掉）—— 三处
   `return candidates[:limit]` 在「没有可比词元」或「Jaccard 全零」时把**整套同类历史**原样
   带回，而 `fixer.py:423` 按「在不在这份返回列表里」给它们打上 `[错误相似度命中]`。
   本仓报错文案是中文而 `_tokenize` 只认 `[a-z0-9_]+` ⇒ 每条中文报错都走那条兜底。
   用例在 `tests/test_failure_memory.py`（含一条反空转的正相似用例、一条活路径的标签用例）。
   附带学到一条夹具纪律：这类用例必须 `FailureDatabase(jsonl_path="off")` —— 默认构造会重放
   仓库自己的 `output/failure_db.jsonl`，第一次写的时候**真语料把断言喂饱了**。
2. **`_L2_RETREAT` 末句的先决事实被纠正了两次**，第二次纠正的是第一次纠正：
