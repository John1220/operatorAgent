# 41 — 核函数接口契约：一条从未写下来的约定，和它烧掉的每一轮

对应 [`00`](00-架构基线与缺口核实.md) **缺口 6**（核函数接口契约是隐式的）。
落地代码：`operator_agent/interface_contract.py`、`operator_agent/verifier.py:_verify_compile`。
真机复核：`benchmarks/verify_interface_contract.py`。单测：`tests/test_interface_contract.py`（17 个用例）。

结论：契约现在**写下来了**，并且**在动 GPU 之前就被检查**。真机四臂全绿，被拦下一次
用 **0.04 s**，而走完一次真实验证要 **15.5 s**、连单纯远程编译都要 2.6 s。

## 一、契约是什么，以前写在哪

唯一的约定是这一行（`remote_scripts/run_kernel.py:_execute_triton`）：

```python
torch_inputs = {k: torch.from_numpy(v).to(device).contiguous() for k, v in real_inputs.items()}
...
output = kernel_func(**torch_inputs)      # ← 全关键字, 不过滤、不重排、不猜
```

也就是说：**顶层 `def kernel` 的参数名必须逐一等于任务侧给的输入名**。这句话以前
在代码里不存在，只在 `triton_skill.md:30` 用「NO missing `def kernel(A, B)` wrapper」
的形式半句带过 —— 而它约束的是**参数名集合**，不是「有没有 wrapper」。

违反它的代价也不是编译失败，而是运行时的
`TypeError: kernel() got an unexpected keyword argument 'causal'`。这行字要等到
一次 SSH 往返 + 远程 `import torch` + Triton JIT 全部走完才出现，于是被记成一次
「L2 失败」，交给 Fixer 重画一整轮。`docs/research/00` 缺口 6 记的真实历史是
**attention 连烧 3 轮**；本仓库自己的驱动 `test_nvidia_attention.py:190` 就写着
`test_inputs["causal"] = False`，也就是说这个坑是我们主动去踩的。

## 二、为什么用 AST，而不是 `inspect.signature`

这是本轮最有价值的一条外部教训的本地版本：**先确认量具能看见你要看的东西**
（`docs/research/34/35/36/39/40` 已经栽过五次）。这里差点栽第六次。

直觉做法是 L1 时把模块 import 进来，`inspect.signature(module.kernel)` 一比了事。
真机（triton 3.8.0 / torch 2.14.0）探下来两条都堵死：

1. **控制端不能 import 生成代码**。`@triton.jit` 在构造时要 `inspect.getsourcelines`，
   在 `python -c` 下直接 `ValueError: @jit functions should be defined in a Python file`；
   而控制端也没有 torch。项目本来就把「引用实现只在远端构建」写成了规则
   （`verifier._reference_torch` 的 docstring）。
2. **就算在远端，`inspect.signature` 也拿不到真签名**。实测：

```
--- triton.jit callable= True type= JITFunction
   signature(): (*args: 'P.args', **kwargs: 'P.kwargs') -> 'R'
   params: [('args', 'VAR_POSITIONAL'), ('kwargs', 'VAR_KEYWORD')]
   .fn signature: (x_ptr, y_ptr, n, BLOCK: triton.language.core.constexpr)
```

`JITFunction` 把自己伪装成 `(*args, **kwargs)`，真参数表在 `.fn` / `.params` 上。于是
「有 `**kwargs` 就放行」这条规则**对 Triton 核永远放行** —— 一份看起来正确、跑起来全绿、
实际永不触发的死守卫，而那恰好是唯一一类在生产里真出过事的核。

AST 路线没有这两个问题：装饰器不影响 `def` 的参数列表，而且根本不需要 import、
不需要 GPU、不需要 SSH 往返。

## 三、保守原则：只在「必然炸」时拦

误放的代价是一轮 L2（本来就会付）；误拦的代价是把一份**能跑的核**打回去重画。
所以看不准一律放行：

| 形态 | 处理 | 理由 |
|---|---|---|
| 顶层 `def kernel` 参数与输入名不符（多传 / 少必填） | ❌ 拦 | 必然 `TypeError` |
| positional-only（`def kernel(A, /)`）且该参数必填 | ❌ 拦 | 关键字传不进去 |
| 有 `**kwargs` | ✅ 放 | 什么都接得住 |
| 有**默认值**的参数调用方没传 | ✅ 放 | 完全合法 |
| `kernel = something`（别名换掉真身） | ✅ 放 | 静态看不出参数表 |
| 条件 / `try` 分支里的 `def kernel` | ✅ 放 | 形态不止一种 |
| 顶层根本没有 `def kernel` | ✅ 放 | 交给后面的层级 |
| 语法本身不合法 | ✅ 放 | 那是 L1 语法预检的话，不抢话 |

多组输入套件（L2 的 `num_input_sets`）**逐组判**：第 2 组多带一个键，那一组就会炸，
只看第 1 组就是漏。真实历史里「取并集判一次」和「只看第一组」都够蒙混过关。

## 四、开发过程中被自己的测试抓到的两个 bug

都不是设计问题，是实现里最普通的两处手滑 —— 值得记的是**它们都由测试当场抓住**，
而不是等生产：

1. **`ast.arg` 对象混进了名字集合**。`no_default = set(positional[...])` 放的是
   `ast.arg` 节点，于是后面 `名字 in no_default` **恒为 False** —— 「必填没传」与
   「positional-only 挡道」两条判断同时变成永不触发。两个用例一起红。
2. **defaults 的切片方向反了**。`defaults` 覆盖**尾部** k 个参数，必填的是**前** `n-k` 个；
   我写成 `positional[n_no_default:]`，于是 `def kernel(A, B, eps)` 的必填集合算出来是空的。
   第一版还留着一行 `missing = ...`（算的是「有默认值但调用方没传」的参数），
   那是**假阳性**：会把能跑的核打回去重画。删掉，并补一条用例钉住这个区分。

随后按本项目惯例做变异测试：10 条变异（整体 no-op、ast 对象、切片反向、去掉
positional-only 分支、去掉 `**kwargs` 放行、不识别名、Verifier 只看第一组、检查改成空循环、
必填分支短路、顶层重复 `def` 取第一个）——**第一版有两条逃逸**：

- 「不识别名」那条没被抓住，因为别名用例的代码里**压根没有 `def kernel`**，
  检查是因为找不到定义才返回 None 的，别名规则本身没被 exercized。
- 「只看第一组」没被抓住，因为当时的用例直接在检查函数层面逐组调用，没经过 Verifier 的循环。

两条都补了真会走到的路径（别名用例里同时放一个「看起来会不匹配」的 `def kernel`；
多组用例改走 `_verify_compile`）。补完 10/10 全被抓，0 逃逸。

## 五、真机四臂

`python3 benchmarks/verify_interface_contract.py`（控制端跑，触发 deploy，H20 GPU 2）：

| 臂 | 内容 | 期望 | 实测 |
|---|---|---|---|
| A | `def kernel(Q,K,V)` + 输入带 `causal`（历史现场） | L1 失败、无 L2/L3 | ✅ `interface_mismatch`，1 级，**0.04 s** |
| B | 真能跑的 Triton matmul（防误伤） | L1 通过、三级跑完、L2 数值通过 | ✅ 3 级全跑，L2 `matched_ratio=1.0`，L3 1.09x，**15.47 s** |
| C | 同一份合法核，输入套件**第 2 组**多带 `scale` | L1 失败 | ✅ `interface_mismatch`，**0.00 s** |
| D | 把 A 的核补上 `causal=False` | 放行 | ✅ L1 通过（**2.61 s** 到远程编译），随后 L2 按反作弊正确拒绝 |

D 这一臂顺带证明了两层防线没互相顶掉：签名合法但**内容**作弊（`Q @ K.transpose(...) @ V`
就是 torch.matmul 回退）仍然由 L2 拦下 —— 新检查没有变成「签名对=放行到底」。

错误消息沿用 `docs/research/20` C#1 的处方式格式（根因 / 现状 / 改法 / 位置），实测输出：

```
根因: 调用方固定以 `kernel(**输入)` 的**全关键字**方式调用核函数, 而这份代码的 kernel() 签名与之对不上 …
  本次会传入的输入名: K, Q, V, causal
  kernel() 声明的参数: (Q, K, V)
  不匹配: 调用方会传、但 kernel() 没收的参数: causal
改法: 让 `def kernel(...)` 的参数名**逐一等于**上面「会传入的输入名」; …注意不要改输入名 —— 那是任务侧给的。
位置: 第 8 行的 `def kernel`。
```

最后一行「不要改输入名」是刻意写的：模型最常见的两种「修法」里，改调用方是**错**的
（输入名由任务侧决定），只说「签名不匹配」不给方向的错误消息很可能把它推向那一侧。

## 六、顺带修掉的一处生产者—消费者漂移

`optimization_recipes.md` 的 PDL 配方里，`triton_template` 把**设备函数**直接命名为
`kernel`：

```python
@triton.jit(launch_pdl=True)
def kernel(x_ptr, y_ptr, n, BLOCK: tl.constexpr):   # ← 抄了就被 L1 判掉
```

这份模板在新检查之前也不合调用契约（`kernel(X=...)` 同样会抛 `TypeError`），只是那个
代价要等一轮 GPU 才现形。现在它会立刻现形 —— 于是把模板改成 `_pdl_copy` + 一个
`def kernel(X)` wrapper，并在原地写明「设备函数不要叫 `kernel`」。
配方文本与 harness 契约不一致是本项目反复出现的同一类缺陷（`docs/research/35` 里
SKILL 1.1「必须以 import 开头」与处方格式也撞过一次）。

## 七、还不知道 / 没做的

1. **只判参数名，不判返回**。`kernel` 返回什么、shape 对不对，仍要等 L2 —— 那需要真执行，
   不是静态可判的（也是为什么本项没顺手做 shape 推断）。
2. **真实命中率未测**。四臂是**构造出来**的正反例，不是生产统计。要知道这条在生产里
   多久响一次，得先有缺口 2（kernel_db 零持久化）把每轮的 L1 失败原因留下来 ——
   这已是第二次撞到同一个前置（`docs/research/20` 的 C3/C8 也卡在那儿）。
3. **`*args` 与位置传参**没管。当前调用点只用关键字，所以不设这条判定；若哪天有后端
   改成位置传参，`positional-only` 那条规则要反过来，届时该改判据而不是加特例。
4. 检查放在 `_compile_cache` **之前**：缓存键只含代码哈希，而同一份代码配不同输入集
   契约结论可以不同。若将来给 `_compile_cache` 加上输入签名，这条顺序可以调换。
