## 一、这一段的转折点

任务最初是「按缺口顺序把内部代码修好」。中途指示改为：

> 重点进行外部技术吸纳吧，包括不限于 agent 设计，算法开发领域技术，代码问题差不多就行，后续有时间再细致优化

这个转向被证明是对的，而且理由比「省时间」更强：**这一段真正改变结论的东西全部来自外部口径，而不是内部重构。** 三个例子：

1. 吸纳 Triton `do_bench` 的 L2 冲刷口径之后，layernorm 1024×768 的加速比**从 0.895x 翻转成 1.346x** —— 同一个核、同一台机器、同一天（`ac42310`，doc 32）。
2. 真机标定发现「launch 地板 20.24 µs」这个被写进常量的数，量的其实是**空闲 GPU 上事件窗口吃进的空等延迟**；同一个空核在 GPU 被填满时只剩 4.64 µs。这直接推翻了缺口 1 原来的判据分母。
3. 一手核对 Triton 3.8 源码，发现配方库教的 `allow_tf32` 已废弃、`tl.dot` 的**默认精度就是 tf32** —— 这才是 doc 30 那个「L2 按 fp32 判精度、L3 按 TF32 给算力」不一致的根因。

反过来，内部代码这一段的改动大多是**为了让外部口径能落地**（runner 报分位数 → 才有离散度门；能力表补字段 → 新配方才选得出来），而不是为了重构而重构。

### 2.6 峰值显存与基线档位复核（KernelBench-Verified）

| 提交 | 内容 |
|---|---|
| `e1a1ed9` | L3 每次调用**额外峰值显存**按臂各测一次并搬进 metrics + message（绝对值 MiB 与比值，**只观测不判定**）；真机复核 fp32 基线是否偷吃 TF32；带绝对校准对照的驱动 `benchmarks/measure_peak_memory.py` |

外部动机是 KernelBench-Verified（arXiv 2607.16241）点名的两类测量漏洞：**弱基线**（拿一个
没开 TF32 的 PyTorch 当对手，加速比虚高）和**只看延迟不看显存**。第一条我方**结构上已经免疫**
—— `verifier.baseline_plan("matmul", "fp32")` 把 `pytorch_eager_tf32` 排在第一位，真机
`baseline_selected` 也确实选中了它；但「免疫」从前只是读代码读出来的，这次用同一个核换两档
基线量了出来：**0.481x vs 0.916x，虚高 1.9 倍**。第二条是真空缺 —— 一个省时间但多吃 3 倍
显存的核，在 L3 里和「又省又瘦」同分。

量具可信度是先于结论建立的：校准档刻意写成「已知比基线多分配 4.0 MiB」（fp32 第二份输出），
实测正是 6.00 − 2.00 = **+4.00 MiB**，所以另外三档（fp16 matmul 4096³ 32/32、layernorm
16384×6144 192.00/192.12）不是在量测具。老 runner 不返回这些键时保持 `None` 而不是塌成 0
（0 会被读成「一点显存都不多花」，那是个假的好消息）。全过程见
[doc 44](44-基线档位与峰值显存.md)。

⚠️ **这一项目前只走完「算出来」，没走完「有人读」**：`peak_memory_ratio` 进了 metrics 和
message，但 `persist_decision` 不读它，所以「省时间但吃显存」的核照样入库。这不是漏写，是没有
样本就定阈值等于猜 —— 攒够几十条样本再补，四条改判条件写在
[doc 44](44-基线档位与峰值显存.md) 第四节（第 4 条就是「接进 `persist_decision`」）。这个 bug 类在 doc 33 开头被
命名（「算了没人读」），本条是它的一次**自愿复现**：先让信号可见可查，再在有证据的地方关门。

### 2.9 候选结构去重键（C5，只观测）

| 提交 | 内容 |
|---|---|
| 本次提交 | `operator_agent/novelty.py`：α-等价 AST 结构键 + 粗粒度描述符；Conductor 每轮把结构键与「重复于第几轮」记进 `iteration_history`，循环结束打一行 `[Novelty]` 汇总。**不参与任何跳过或判决** |

要点写在 [doc 47](47-候选结构去重键与跳过验证的代价.md)。这一项的产出主要是**否掉了一个自己原来
打算做的东西**，而且理由不依赖还没量到的基率：

1. **外部没有一家只凭静态相似就跳过性能测量。** AlphaEvolve 根本**没有去重键**（全文 `similarity`
   与 `surrogate` 各 0 命中），它的成本控制是评估级联；OpenEvolve 的 novelty 门发生在 `add()` 里
   ⇒ **只决定进不进库存，评估早已付掉**；FunSearch / AlphaCode 用的是**行为键**（每测试分数元组、
   输出向量），必须付了评估才拿得到。唯一真在程序执行**之前**跳过的是 ShinkaEvolve，而它用的
   是 embedding + 第二道 LLM 语义门，且跳过的是整套确定性适应度评测，不是我们全仓库最不确定的那个量。
2. **省下的有界**：重复轮判 `SAME` ⇒ 不禁配方但**计入停滞**（出厂 2 轮），最坏每任务多烧约 31 s；
   而在 `can_count_stagnation=False` 的不可信档位上想省的更多 —— 那恰恰是唯一**不敢复用读数**的档位。
   一个数字如果重要到值得复用就重要到必须重测，如果不重要到值得复用那笔钱就不该拿判决去换。
3. **键的位置**：按代码克隆的标准分类，我们是 **Type-1 规范化 + α-重命名、刻意不做字面量抽象**
   ⇒ 标准 Type-2 关系的**保守子集**，不覆盖 Type-3/4。而按标准定义 `BLOCK=64→128` **正是** Type-2
   克隆 —— 做了字面量抽象就丢掉 L3 唯一在量的那个变化。对照工具链：Triton 的缓存身份含
   `sha256(源文本)` + 起始行号 + constexpr 取值，所以这把键**在名字上比编译器粗、在常量上与它一致**；
   TTIR 才是真 α-等价，但 Triton 打印时开了 `printNameLocAsPrefix(true)`，**Python 变量名被烙进 IR**。

⚠️ **基率没量出来**：6 次真机运行只有 1 次转起来（ssh 链路在抽 + 一次 LLM timeout），可用样本是
3 轮全异构、分母 2 低于驱动自设的 4 轮下限。第一版驱动把 0/1 打印成「0.0%」，长得像测量值 ——
现在分母不足时它**拒绝出百分数**并以非零退出。这是「先确认量具能看见你要看的东西」的又一次应用，
只是这次看不见的原因是**循环根本没转起来**（Conductor 一通过 L3 就 break，而默认门槛第一轮就过）。

`duplicate_of`/`recipes_applied` 被丢在落盘前，**这一批的重复基率永久没了、只能重跑**）。
第三条与第四条各代表一族：第三条是「每一条单独看都像合理的数，只有排在一起看单调性才暴露」
——与 doc 40「零结果与量具瞎了输出同一行字」、doc 46「判据方向写反」同族，
**量具的失效模式通常长得像数据**；第四条是 doc 33 的 `runs`/`max_time_ms`、doc 37 的
`llm_cost` 那个形状的第四次出现，所以修法不是「把三个键补进白名单」而是**取消白名单**，
并让守卫去读真代码的 AST 键集合（夹具少一个键就红；它第一次跑就抓到夹具自己少了两键）。
细节与 7 条变异见 [doc 48](48-端到端成功率量具.md)。

## 三、两份新调研的吸纳决策

两份报告（通用 agent harness 设计、GPU kernel 性能测量方法论）由后台调研 agent 产出，下表是逐项决策。**证据分级沿用报告作者的 ✅/⚠️ 自报，其中 ⚠️ 项我未独立复核**，所以凡决策依赖 ⚠️ 证据的一律标注。

### 3.1 测量方法论

| # | 机制 | 决策 | 理由 |

## 四、真机标定：离散度阈值与一个意外发现

`benchmarks/calibrate_dispersion_thresholds.py`（新增），`algorithm-h20` GPU 2，torch 2.14.0+cu130 / triton 3.8.0，2026-09-25。30 轮 × 每轮 30 样本 × 4 个核，计时口径与 runner 完全一致（256 MB L2 冲刷排在 `start.record()` 之前）。

### 4.1 结果

| 核 | median | iqr/median p50 / p95 / max | max/median p50 / p95 / max |
|---|---|---|---|
| 空核（launch 地板对照） | 4.5 µs | 0.035 / 0.042 / 0.042 | 3.84 / 13.58 / 18.26 |
| layernorm 1024×768 | 8.4 µs | 0.030 / 0.046 / 0.050 | 4.31 / 7.10 / 8.00 |
| layernorm 16384×6144 | 256 µs | 0.005 / 0.007 / 0.007 | 1.04 / 1.25 / 1.38 |
| matmul 4096³ fp16 | 1030 µs | 0.001 / 0.002 / 0.002 | 1.00 / 1.04 / 1.04 |
| **合并** | — | 0.014 / 0.042 / **0.050** | 1.12 / 7.53 / **18.26** |

### 4.2 三个判读

1. **`DISPERSION_DEGRADED = 0.10` 站得住。** 本机最坏观测 0.050，0.10 有 2 倍余量 —— 不会误报。而参照系 NVBench 的 0.02 落在本机 p50–p90 之间，**会有一半的测量被判 DEGRADED**，正好印证报告里「那是锁频专用机的值」的告诫。
2. **`max/median` 强烈依赖核的绝对时长**（空核 18.3 vs matmul 1.04）。一次固定量级的宿主抖动对 4.5 µs 的核是 18 倍，对 1 ms 的核是 1.04 倍 —— **单一绝对阈值必然两头不讨好**。当时的处置是「只在比值有意义的区间用」+ 阈值 2.0。**该处置已被 [doc 33](33-离散度门真机验证.md) 第四节推翻并回退**：还有第二层偏差（runner 自动加采样 → max 是顺序统计量，随 n 抬高），且两层同向 —— 能通过「核足够长」前提的区间恰好是样本最多的区间。util=0% 的干净测量就已打到 1.62~1.86。该信号现为**仅诊断，不改档位**。
3. ⚠️ **意外发现：util 快照会被自己的前一轮污染。** 标定脚本每轮测量前采一次 util，读到 10–34%、21–26/30 轮非零；而同一张卡在真空闲时连续 100 次采样**全是 0%**。原因是 `nvidia-smi` 的 `utilization.gpu` 是过去约 1 秒窗口的占比 —— 我的脚本紧挨着自己上一轮 benchmark 之后采样，读到的是**自己**的残留。

   这条对现有代码是实质指控：runner 的 `gpu_util_pct > 5%` 判据是缺口 1 里「污染」的唯一证据源，而 L1/L2/L3 是**三次独立的 ssh 调用**，间隔常不到 1 秒。doc 00 记录的那次「matmul 那轮测量前 util=14% → 判污染 → 把实际有效的配方拉黑」，**有可能根本不是邻居，是我们自己上一轮的尾巴**。

   修法（`cf2d50b`）：`_sample_gpu_idle()` 改成**隔 1.2 s 采两次取 min**。自己的残留会在这 1.2 s 里排空，邻居的持续负载不会，所以较小者才接近「别人占了多少」。代价是每次 L3 多 1.2 s。

### 4.3 顺带排除的一个误判

调研输入里怀疑「runner 用 `torch.cuda.current_device()` 去问 nvidia-smi 会读错卡」。核实结果：**runner 没有这个 bug** —— 它用的是自己选卡时记下的物理 id `_SELECTED_GPU_ID`。有这个 bug 的是我的标定脚本（还错把 int 传进 `subprocess.run` 的参数列表，被 `except` 静默吞成 `-1`，所以第一版整场都报 `util=-1%`）。两处都已在脚本里改对。
