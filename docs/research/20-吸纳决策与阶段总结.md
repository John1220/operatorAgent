## 一、这一段的转折点

任务最初是「按缺口顺序把内部代码修好」。中途指示改为：

> 重点进行外部技术吸纳吧，包括不限于 agent 设计，算法开发领域技术，代码问题差不多就行，后续有时间再细致优化

这个转向被证明是对的，而且理由比「省时间」更强：**这一段真正改变结论的东西全部来自外部口径，而不是内部重构。** 三个例子：

1. 吸纳 Triton `do_bench` 的 L2 冲刷口径之后，layernorm 1024×768 的加速比**从 0.895x 翻转成 1.346x** —— 同一个核、同一台机器、同一天（`ac42310`，doc 32）。
2. 真机标定发现「launch 地板 20.24 µs」这个被写进常量的数，量的其实是**空闲 GPU 上事件窗口吃进的空等延迟**；同一个空核在 GPU 被填满时只剩 4.64 µs。这直接推翻了缺口 1 原来的判据分母。
3. 一手核对 Triton 3.8 源码，发现配方库教的 `allow_tf32` 已废弃、`tl.dot` 的**默认精度就是 tf32** —— 这才是 doc 30 那个「L2 按 fp32 判精度、L3 按 TF32 给算力」不一致的根因。

反过来，内部代码这一段的改动大多是**为了让外部口径能落地**（runner 报分位数 → 才有离散度门；能力表补字段 → 新配方才选得出来），而不是为了重构而重构。

## 三、两份新调研的吸纳决策

两份报告（通用 agent harness 设计、GPU kernel 性能测量方法论）由后台调研 agent 产出，下表是逐项决策。**证据分级沿用报告作者的 ✅/⚠️ 自报，其中 ⚠️ 项我未独立复核**，所以凡决策依赖 ⚠️ 证据的一律标注。

### 3.1 测量方法论

| # | 机制 | 决策 | 理由 |
|---|---|---|---|
| D1 | 离散度门（iqr/median） | ✅ **已采纳** | 零额外 GPU 时间（runner 本就跑 30 样本）。阈值锚在 PyTorch `_IQR_WARN_THRESHOLD=0.1`（✅），并已真机标定 |
| D1b | 窗口内抢占信号（max/median） | ⚠️ **采纳后又被真机数据降格** | 报告未提出，是标定过程中发现的：iqr 对单点离群**完全不敏感**，而 util 只在测量前采一次 —— 两条都看不见中途抢占。但真机证明该比值随样本数抬高（runner 自动加采样，而 max 是顺序统计量），干净测量就到 1.62~1.86。**现仅诊断、不改档位**，详见 doc 33 第四节 |
| D2 | 每样本 SM 频率 + 丢弃退避 | ⏸ **暂缓** | 技术上有价值（✅ NVBench `measure_cold.cu`），但需写一个包住计时区的微核算 `%clock64/Δns`，改动面比 D1 大得多。先看 D1 + util 去污染后还剩多少问题 |
| D3 | 交错 A/B，只测真正会被选中的那一个基线 | ✅ **已采纳并真机验证** | 两个成分分开成立：**只测一个基线**是无条件净收益（每次 L3 少测一个，墙钟 −33%~−48%）；**交错**是条件收益（注入持续抢占时小核跨次散布 0.0493→0.0106，安静机器上四种日程一致到小数点后三位）。前提「顺序偏置真实存在」由反向测量证出：长核 7.7%、launch 主导小核 **10⁴ 倍**。详见 [doc 36](36-交错AB真机验证.md) |
| D4 | 四态判决 FAST/SAME/SLOW/AMBG | ✅ **已采纳并真机验证** | 当初暂缓的理由（本机没有分档带宽的数）由 doc 34 第四节补齐，带宽按档位存表 0.10%/0.40%/2.00%（实测跨次散布 ×3），**只有 `SLOW` 才禁用配方**。⚠️ 落地时纠正了缺口 4 自己的表述：「按 bound 分支选指标」在同一 shape 的循环里**空转**（两条轴来自同一次测量），有后果的是**看离上界还有多远** —— 真机 matmul 4096³ 达成率 101.5% → 第一轮即判收敛，旧循环会连烧三轮配方。仍**不可**用 `paired_speedup_dispersion` 当带宽（单样本口径，系统性偏大 3~8 倍）。详见 [doc 38](38-四态判决与roofline收敛出口.md) |
| D5 | 噪声导向停止替换固定 repeat | ⏸ **暂缓（地基已就位）** | 与 D3 同属「改采样循环」。D3 落地后每次 L3 已经带回报对的散布（`paired_speedup_dispersion`），「什么时候可以停」第一次有了可判的输入 |
| D6 | 参考核做同期对照（internal standard） | ❌ **不采纳** | 报告自述在 6 个框架里都没找到对应物（⚠️ 负面证据）。我们的 cuBLAS 基线本就是 internal standard，D3 的交错才是让它可用的前提 |
| D7 | CUDA Graph 计时 | ❌ **明确不采纳作门限** | ✅ Triton 源码三条：`do_bench_cudagraph` **不清 L2**；它把 N 次调用展开进一张图背靠背 replay，测的是**吞吐不是延迟**；`cuda_graph_without_gc` 的存在是因为 CompiledKernel 析构会 unload CUDA module。更根本的是口径问题 —— 候选核若有 20 µs Python 派发开销，生产里它就是慢 20 µs，图计时恰好把这个缺陷藏起来 |
| D8 | 进程 CPU 亲和性 `sched_setaffinity` | ❌ **不采纳（本机已实测，两次跑）** | 三条理由都可复查。作用路径存在：往计时窗口注入已知 host 工作量，事件窗口线性抬高 22→134→349 µs（⚠️ 这只证明「窗口对 host 耗时敏感」，不区分「线程在烧 CPU」与「GPU 空等命令到达」）。但**收益测不出来**：192 核、平均 busy 2.5% 的机器上不钉也拿到 1.00 个有效核，三个钉核臂相对不钉的 Δp50 两次跑分别是 +0.05~+0.13 与 +0.08~+0.19 µs（0.3%~1.0%），符号检验 5/9~7/9，生产口径（LN+冲刷）两次方向还相反。唯一实测到的效应是**风险**：与邻居共占一核时 `有效核数` 0.50 而 median 只动 0.4%，**max 从 34.7 µs 变成 16027 µs ≈ 一个 CFS 时间片被换下**，且档位判定不报警（iqr 不动，只有 `max/median` 诊断字段留痕）。**若接入核数少或 host 侧饱和的平台需重估**，判据见 [doc 39](39-CPU亲和性判别实验.md) |
| — | 锁频 / MIG / MPS / CUPTI 主计时 | ❌ **全部不采纳** | 需 root 且是**全局**改动，会直接影响同机另外 7 个租户；MPS 不隔离 L2 与 DRAM 带宽（⚠️ 报告自述为推断），而带宽恰是 memory-bound 算子的命门 |

### 3.3 两条跨报告的共同教训

1. **一切外部加速比都要按「弱模型 + 共享机器」折价。** ✅ 报告自述：业界的头条数字全部在 Opus 4.5/4.8 上取得，不外推到自建 Qwen 27B；✅ 我方 doc 11 早已独立得出同一结论（外部宣称加速比普遍虚高）。两份报告在这点上互相印证。
2. **「文档写了 ≠ 实施了」是可量化的。** ✅ 481 个公开 CLAUDE.md 中只有 4–16% 的自然语言规则有对应内建强制控制，最严格匹配下 4.4%。我方那次「verifier 算出 contaminated 却没人读」不是个例，是行业常态 —— 所以防线必须是**机械断言**而不是文档。这一段所有修复都配了结构性守卫，正是这条纪律的执行。

   写本文档时又踩到一次：正文里顺手写了那个泄露过 key 的服务名，靠提交前手工跑的 grep 拦下。于是把那份人肉清单本身也落成测试（`tests/test_repo_hygiene.py`）。顺带发现清单里「vendored minified JS 会巧合命中端口模式」这条豁免**已经不再成立** —— 端口模式收紧成「带前导冒号的精确端口」形式之后，那两个 js 文件对全部 16 个模式一条都不命中。既然豁免挡不住任何真命中、却会挡住未来的真泄漏，就整个删掉了：扫描覆盖全部已跟踪文件，唯一跳过的是扫描器自身。

   （第二次于是同一条规则把自己也拦住了 —— 这段说明里举的例子本身就是一个被禁模式。守卫确实有效。）

## 四、真机标定：离散度阈值与一个意外发现

`benchmarks/calibrate_dispersion_thresholds.py`（新增），`algorithm-h20` GPU 2，torch 2.14.0+cu130 / triton 3.8.0，2026-09-25。30 轮 × 每轮 30 样本 × 4 个核，计时口径与 runner 完全一致（256 MB L2 冲刷排在 `start.record()` 之前）。

### 4.1 结果

| 核 | median | iqr/median p50 / p95 / max | max/median p50 / p95 / max |
|---|---|---|---|
| 空核（launch 地板对照） | 4.5 µs | 0.035 / 0.042 / 0.042 | 3.84 / 13.58 / 18.26 |
| layernorm 1024×768 | 8.4 µs | 0.030 / 0.046 / 0.050 | 4.31 / 7.10 / 8.00 |
| layernorm 16384×6144 | 256 µs | 0.005 / 0.007 / 0.007 | 1.04 / 1.25 / 1.38 |
| matmul 4096³ fp16 | 1030 µs | 0.001 / 0.002 / 0.002 | 1.00 / 1.04 / 1.04 |
| **合并** | — | 0.014 / 0.042 / **0.050** | 1.12 / 7.53 / **18.26** |

### 4.2 三个判读

1. **`DISPERSION_DEGRADED = 0.10` 站得住。** 本机最坏观测 0.050，0.10 有 2 倍余量 —— 不会误报。而参照系 NVBench 的 0.02 落在本机 p50–p90 之间，**会有一半的测量被判 DEGRADED**，正好印证报告里「那是锁频专用机的值」的告诫。
2. **`max/median` 强烈依赖核的绝对时长**（空核 18.3 vs matmul 1.04）。一次固定量级的宿主抖动对 4.5 µs 的核是 18 倍，对 1 ms 的核是 1.04 倍 —— **单一绝对阈值必然两头不讨好**。当时的处置是「只在比值有意义的区间用」+ 阈值 2.0。**该处置已被 [doc 33](33-离散度门真机验证.md) 第四节推翻并回退**：还有第二层偏差（runner 自动加采样 → max 是顺序统计量，随 n 抬高），且两层同向 —— 能通过「核足够长」前提的区间恰好是样本最多的区间。util=0% 的干净测量就已打到 1.62~1.86。该信号现为**仅诊断，不改档位**。
3. ⚠️ **意外发现：util 快照会被自己的前一轮污染。** 标定脚本每轮测量前采一次 util，读到 10–34%、21–26/30 轮非零；而同一张卡在真空闲时连续 100 次采样**全是 0%**。原因是 `nvidia-smi` 的 `utilization.gpu` 是过去约 1 秒窗口的占比 —— 我的脚本紧挨着自己上一轮 benchmark 之后采样，读到的是**自己**的残留。

   这条对现有代码是实质指控：runner 的 `gpu_util_pct > 5%` 判据是缺口 1 里「污染」的唯一证据源，而 L1/L2/L3 是**三次独立的 ssh 调用**，间隔常不到 1 秒。doc 00 记录的那次「matmul 那轮测量前 util=14% → 判污染 → 把实际有效的配方拉黑」，**有可能根本不是邻居，是我们自己上一轮的尾巴**。

   修法（`cf2d50b`）：`_sample_gpu_idle()` 改成**隔 1.2 s 采两次取 min**。自己的残留会在这 1.2 s 里排空，邻居的持续负载不会，所以较小者才接近「别人占了多少」。代价是每次 L3 多 1.2 s。

### 4.3 顺带排除的一个误判

调研输入里怀疑「runner 用 `torch.cuda.current_device()` 去问 nvidia-smi 会读错卡」。核实结果：**runner 没有这个 bug** —— 它用的是自己选卡时记下的物理 id `_SELECTED_GPU_ID`。有这个 bug 的是我的标定脚本（还错把 int 传进 `subprocess.run` 的参数列表，被 `except` 静默吞成 `-1`，所以第一版整场都报 `util=-1%`）。两处都已在脚本里改对。
