# 远端执行的信任边界实测

> 版本: v1.0 | 日期: 2026-09-24 | 设备: algorithm-h20（8×H20，多租户共享）
> 服务于: [`../问题识别与技术方案.md`](../问题识别与技术方案.md) 的 **P2-1（远程任意代码执行，最高危面）** 与 **P2-2（密钥与日志泄露）**，两项均标注为未实施
> 触发来源: [`10-DeepSeekHarness与插件化agent运行时.md`](10-DeepSeekHarness与插件化agent运行时.md) 第六节的 env 洗白规则
> 说明: 本文只记录**可读性判定与权限位**，未读取、未记录任何凭据内容。路径一律用 `~` 形式，不出现真实用户名。

## 一、执行链路

```
控制端 (本机)
  └─ SSHExecutor._ssh_exec_json()
       └─ ssh <别名> "cd <work_dir> && uv run python run_kernel.py"   # JSON 走 stdin
            └─ remote_scripts/run_kernel.py
                 └─ exec_module() / exec(code, ns)   ← LLM 生成的核代码在此执行
```

LLM 生成的代码在远端以**该 SSH 登录用户自身的完整权限**运行，无沙箱、无降权、无文件系统隔离、无网络隔离。

## 二、实测结果

### 2.1 本地凭据不会外泄到远端 ✅

- `~/.ssh/config` 中**没有** `SendEnv` / `SetEnv`，ssh 默认不转发客户端环境变量。
- 控制端的 `LLM_API_KEY` / `HY_API_KEY` 因此到不了远端进程。
- 控制端唯一显式下发的变量是 `OPERATOR_AGENT_GPU`（`remote_executor.py:243`）与 `CUDA_VISIBLE_DEVICES`。

这条路径是闭的。

### 2.2 远端 env 当前干净，但这是巧合而非设计 ⚠️

非交互式 ssh 不加载用户 profile，实测远端 env 只有 **17 个变量**，对 `key|secret|token|passw|cred|auth|api` 的匹配数为 **0**。

所以 DSH 那条「spawned commands 用洗过的 env」规则**在这台机器上当前是空转的**。但它是廉价保险：一旦有人往远端 env 加凭据，或 runner 改由 login shell 调用（会 source `.bashrc`/`.profile`），暴露面立刻出现。

### 2.3 真正的暴露面：生成的代码能读到 SSH 私钥 ❌

`run_kernel.py` 有 **6 处**执行生成代码（`exec_module` 于 198/200、233/235、455/457、703/705；`exec(code, ns)` 于 501、521），**没有任何一处在执行前限制文件系统访问或洗 env**。实测该进程身份下：

| 路径 | 权限位 | 可读性 |
|---|---|---|
| `~/.ssh/`（目录） | `drwx------` | 可进入 |
| `~/.ssh/<私钥>` | `-rw-------` | **可读** |
| `~/.ssh/authorized_keys` | `-rw-------` | 可读 |
| `~/.ssh/config` | `-rw-------` | 可读 |

其他常见凭据位置（`~/.aws`、`~/.aliyun`、`~/.config/gcloud`、`~/.docker/config.json`、`~/.netrc`）实测**均不存在**，所以当前唯一可读的高价值凭据就是那把 SSH 私钥。

**后果**：一把能登录这台多租户共享机的私钥，对 LLM 生成的任意代码可读。

### 2.4 触发路径不止"LLM 变坏"

不需要假设模型被攻破，有三条现实路径：

1. **Prompt 注入**（既有文档 P2-3，未实施）：用户粘贴的参考算子代码或需求描述里夹带指令，诱导生成读文件/发网络的代码。
2. **反作弊绕过**：`anticheat.py` 的 `static_audit` 按 DSL 分流拦截禁用 API，但它拦的是「走捷径算结果」这类作弊，不是「读凭据外传」。一段既算对了结果、又顺手读文件的核，静态审计不一定会拦。
3. **单纯的低级错误**：生成代码里出现 `os.environ` 打日志、把 home 目录内容写进产物目录等，都会经由 `output/` 与 `logs/` 回流到控制端。

## 三、这对吸纳优先级的影响

**修正 10 号文档的采纳清单**：env 洗白（该文档第六节第 3 条）从「采纳，代价小」降级为「采纳，但明确标注它不解决主要风险」。

原因是本文的实测：主要风险不在 env，在**文件系统权限**。洗 env 对 2.3 完全无效——私钥是文件，不是环境变量。

正确的处置顺序：

| 优先级 | 措施 | 对应 | 代价 |
|---|---|---|---|
| **P0** | runner 执行生成代码前，用独立低权用户或容器隔离；至少做到 `~/.ssh` 不可读 | P2-1 | 大（需要改远端部署方式） |
| **P0（廉价替代）** | 若短期无法上沙箱：把那把私钥从该用户 home 移走，或改用仅对特定命令授权的 `command=` 受限 key | P2-1 | 小 |
| P1 | env 洗白（丢弃 `*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*`） | P2-2 | 小 |
| P1 | 临时文件用 0700 私有目录 + 随机名 + 独占创建（`'wx'`, `0o600`）。当前 `run_kernel.py` 用 `tempfile.NamedTemporaryFile`，默认已是 0600，**但目录是否 0700 未核查** | P2-2 | 极小 |
| P1 | 产物与日志落盘前做敏感模式扫描 | P2-2 | 小 |
| P2 | 用户输入包裹数据边界标记，防 prompt 注入 | P2-3 | 中 |

## 四、未核查项（列为待办）

- `tempfile` 实际使用的临时目录权限位。
- SSH 起的 `uv run` 在控制端超时放弃后，远端进程是否真的终止（对应 DSH 的 "Dispose must reach quiescence"）。若否，会有孤儿进程长期占卡——这台机器上已经有 7 个其他租户进程，再加孤儿会加剧缺口 1 的基准污染。
- `output/` 与 `logs/` 是否会记录远端命令原文或错误栈中的敏感片段（P2-2 原始描述提到的风险）。
- `anticheat.static_audit` 的拦截清单是否覆盖 `os.environ` / `open()` / `subprocess` / 网络调用。

## 五、结论

本项目的验证链路把**性能与正确性**做了相当细的分层（L1/L2/L3 + 反作弊 + roofline），但**信任边界基本没有设防**。这在只跑自己写的核时无所谓；一旦要长期、自动、无人值守地执行 LLM 生成的代码，2.3 就是必须先关掉的口子。

建议把「廉价替代」那一行（移走私钥或换受限 key）尽快做掉——它是唯一一条代价小、且能立刻消除已实测确认的暴露面的措施。
