# 43 — 经验库到底该长什么样：调研 skill library / program database，并先量自己的存量

对应缺口 2（docs/research/00 第二节：`kernel_db` 零持久化）。日期：2026-09-26。
这一篇是「先调研、再量自己、最后才写代码」的顺序，因为量完发现**问题陈述本身要改写**。

## 一、为什么要动缺口 2：它现在挡住三件具体的事

1. **C3 配方晋升**（把「某配方在某 bound/某硬件上有效」从一次观察升级成规则）需要跨运行的
   `applied_recipes` × 结果统计。
2. **缺口 6 的生产命中率**未测 —— doc 41 的四臂是构造的正反例，「真实任务里有多少轮 L1
   是被契约拦下的」要留存每轮失败原因才量得出。
3. **doc 42 留下的收尾**：memory 轴的 roofline 出口在本机永不开（最好的 D2D 拷贝只到规格的
   84%），要修的是「按 shape 查这台卡的可达上界」，那就是一张每-shape 的持久化记录表。

这三条都不是「洁癖」：第 3 条是这次吸纳故意付出的代价，第 1、2 条是把已经做过的吸纳**判个真假**
的唯一途径。

## 二、外部机制（逐条标核到的层级）

| 系统 | 机制 | 核到哪一层 |
|---|---|---|
| **Voyager** (arXiv 2305.16440) | 一条 skill = `{program_name: {code, description}}`；**被 embedding 的是 LLM 写的 description，不是代码**：`vectordb.add_texts(texts=[skill_description], ids=[program_name], metadatas=[{"name": program_name}])`；检索用 `similarity_search_with_score(query, k=retrieval_top_k=5)`，只回 `code`。入库门是 critic 的二值 `if info["success"]` | ✅ 一手读了 `voyager/agents/skill.py`（WebFetch 到源码，`add_texts` 三参数与默认 top-k 均已核对） |
| **AlphaEvolve** (arXiv 2506.13131) | 「程序数据库」全部机制是 §2.5 一段话：受 **MAP-Elites + island 模型**启发；§2.4 的 evaluation cascade（前面几档不够有希望就不进下一档）+ LLM grader 可丢弃不合格解 | ⚠️ **只有论文，无 released code，无 schema**。它的「相似度特征 / 晋升规则 / 失败程序策略」都查不到 —— 网上流传的实现细节全是第三方复刻 |
| **OpenEvolve** (`openevolve/database.py`) | 记录字段 `id, code, changes_description, parent_id, generation, metrics, complexity, diversity, embedding, artifacts_*`；持久化 = `programs/<id>.json` + `metadata.json`（islands / archive / feature maps）。MAP-Elites 格子键 `"-".join(coords)`，默认两维是 `[complexity, diversity]`（complexity 就是 `len(code)`）；仅在 `_is_better` 时替换格子主人 | ✅ 一手读到源文件 |
| **ShinkaEvolve** (Sakana, arXiv 2509.19349, `shinka/database/dbase.py`) | **SQLite** 存记录，列里有 `correct: bool`、`code_diff`、`in_archive`、`embedding_cluster_id`；`archive_size=40`；`archive_selection_strategy` 可选 `fitness` 或 **`crowding`（更相似者被更优者替换）**，用 numpy 点积/模长实现，无外部依赖；`stagnation_threshold=100` 时新开一个 island | ✅ 一手读到源文件 |
| **Reflexion / AWM** (arXiv 2409.07429) | Reflexion 的 reflection 是 `List[str]`，**只在进程内**，没有键也没有检索。AWM 把「workflow」按输出里的空行切段存进 workflow memory，只从**成功**轨迹归纳，并把例子里的具体值抽象成 `{product-name}` | ✅ 读到 `hotpotqa_runs/agents.py` 的字段与 AWM 的切段描述。⚠️ **AWM 并没有一个数值化的晋升阈值**（它被广泛引用为「有阈值」，实际没有） |
| **记忆的存与删** (arXiv 2505.16067，代码 `yuplin2333/agent_memory_manage`) | 两条可量化的删除规则：**周期性** `1[fr_t − fr_t′ ≤ α]`（一个窗口内被检索次数太少就丢，用来给内存封顶）；**历史型**（被检索 `> n` 次而平均效用 `< β` 就丢）。它同时点名三种退化：经验跟随性、错误传播、**「看起来对但其实没用的经验」回放** | ⚠️ 机制与公式来自本轮调研的转述，**代码文件我没有逐行核**；引它的理由是「它是唯一一个给出去留规则的」，数值 α/β 我没有可信出处，**所以本次不引入具体阈值** |
| **KernelEvolve**（Meta，kernel-agent 线） | 唯一真正把**跨运行核函数库**做成一等公民的：每个搜索节点一行关系型元数据 `(id, pid, score, is_buggy, path_ref)` + 对象存储放 `kernel_n.py` / profiling / `overview.md`；复用是「按 **算子类型 + 输入 shape + 硬件平台** 查历史相似算子」；`is_buggy` 是**列**，不是丢弃 | ⚠️ 编号较新、我只读到摘要级转述，未逐字核。**它的复用路径没有用 embedding** —— 这条与我的结论一致，但请以后重核 |
| **KernelBench-Verified** (arXiv 2607.16241, 2026-06) | 把基线换成 **TF32 打开的 PyTorch** + 四分布隐藏测试集之后，最强模型的几何均值加速比从 **1.43× 掉到 0.88×**；结论句是「没有模型能在现实基线下稳定超过 PyTorch」；另有 28% 的核增加了峰值显存 | ✅ 一手读了 abstract 页，数字与 TF32/隐藏集两条都核对过 |

**明确不吸纳的**：
- **向量检索 / embedding 存储**。三个用 embedding 的系统（Voyager、OpenEvolve、Shinka）都有
  一个我们没有的前提：查询是**自由文本**、语料是**上千条异构技能**。我们的查询是结构化的
  （`kernel_type` / `hardware` / `dsl` / `tags`），而 `KernelDatabase.search()` 已经是
  「硬过滤 + 词元重叠评分」的形态。Voyager 的实现还依赖 `langchain.vectorstores.Chroma` +
  `OpenAIEmbeddings`，即**每加一条技能、每次检索都要打一次外部 embedding API** —— 与本项目
  「依赖只有 numpy/torch/triton」的约束直接冲突。
  ⚠️ 顺带纠正一处流传的说法：Voyager 仓库里**没有** `vector_store_base.py`，也没有本地 embedding。
- **OpenEvolve 的近重复判定链路**：`embedding_model` 默认 `None` → `_is_novel()` 直接返回
  `True`，也就是它宣传的 embedding 去重**出厂是关着的**，开着还要为每个近重复多花一次 LLM 调用。
- **AlphaEvolve 的 island/MAP-Elites 形状**：无代码、无 schema，抄它等于抄一句广告。

## 三、量自己：存量把问题陈述改写了

缺口 2 原来的说法是「`kernel_db.py` 文件 I/O 命中数 = 0……运行内学到的
`applied_recipes`/`disabled_recipes` 随进程死亡」。前半句成立，后半句**不准确** ——
东西其实一直在写盘，只是**只有 resume 路径读它**。全量点一遍（2026-09-26，仓库 `output/`）：

| 存量 | 数量 | 有性能数字吗 | 谁读它 |
|---|---|---|---|
| `result.json` | **2872** | ❌ **0 个**含 `performance`/`benchmark` 字段（顶层只有 `kernel_id/task_id/language/all_passed/created_at/task/iteration_history`） | 无人（`ArtifactStore.load()` 无调用点） |
| `execution_snapshot.json` | **5326** | ✅ 有 `best_gflops`，还有 `applied_recipes`/`disabled_recipes`/`optimization_history`/`rounds_without_improvement`/`verification_results` | **只有 `resume_from`**（conductor.py:816-830） |

按硬件切一刀，存量立刻不可信：

- `result.json`：`nvidia_gpu` **42**（其中 `all_passed` 只有 **7**）、`mock_gpu` **2822**、
  `kunlunxin_xpu` 8。
- `execution_snapshot.json`：`nvidia_gpu` **10**、`mock_gpu` **5316**。

也就是说仓库里 99.7% 的「经验」是**单元测试跑出来的 mock 现场**。这和 doc 20 第六节里那个
`logs/` 被测试轮掉是**同一个缺陷的两面**：`ArtifactStore.__init__` 没有 env 覆盖，测试每跑一次
就往 `output/` 灌几个目录。所以顺序必须是：

1. **先把测试现场与生产现场分开**（否则任何语料统计都是在数测试用例）；
2. 再谈「写一个持久化库」—— 而且第一版要写的不是写入器（快照已经在写），
   是**读者 + 聚合**：把快照里已有的 `(hardware, kernel_type, dsl, recipe) × 结果` 汇起来；
3. 晋升/退役门一律**只在测量可信时记账**（`measurement_can_gate`，缺口 1 的产物），
   这正是 doc 20 「先让测量可信，再谈持久化 —— 否则只是把被污染的 gflops 驱动的错判断固化成语料」
   那条判断的落地形式。

## 四、决定（本轮吸纳的形态）

| 项 | 决定 | 出处 / 理由 |
|---|---|---|
| 存储 | **JSONL 追加**（一条记录一行）+ 启动时全量读进现有内存 dict | ShinkaEvolve 用 SQLite，OpenEvolve 用 `programs/<id>.json`；两者都行，选 JSONL 是因为 `ArtifactStore` 已经在写 JSON，且零依赖、可 grep |
| 记录字段 | 复用 `KernelRecord`，补 `score`(=可信的同机加速比) / `measurement_validity` / `retrieved_count` / `created_at` | 2505.16067 的检索计数 + 缺口 1/4 的两个口径 |
| ⚠️ 刻意**不加**的字段 | `is_buggy`（这条入库路径只收 `all_passed` 的核，没有写者）、`shape_key`（读者是「按 shape 聚合可达上界」，那个读者还不存在） | 加一个没人读的字段，就是再造一份「算了没人读」 |
| 检索键 | `(algorithm, hardware, dsl)` 结构化键 + 现有词元评分 | KernelEvolve 的「算子类型 + shape + 硬件」；我们已有三键，**不加 embedding** |
| 入库门 | L2 通过 **且** `measurement_can_gate` **且** speedup > 1.0 **且** 非作弊 | Voyager 只有 `if success`；我们多两条，因为本机实测证明「success」可以是被 launch 地板污染的假信号（doc 31/32） |
| 退役 | 只**封顶**与**降权**，不物理删除；具体阈值本轮不引入 | 2505.16067 的 α/β 我没有可信数值；先攒计数器，等缺口 2 真的有量之后再定 |
| 不做 | 向量库 / LLM 近重复裁判 / island 种群 | 见第二节「明确不吸纳的」 |

## 五、落地与下一步

已落地（本轮）：

1. ✅ **产物目录可重定向**：`OPERATOR_AGENT_OUTPUT_DIR`（与 `e2b455e` 的 `logs/` 同型修复），
   `tests/conftest.py` 在测试会话里把它指到 tmp，并把 `OPERATOR_AGENT_KERNEL_DB` 设为 `off`。
   在此之前单元测试每次跑都往 `output/` 灌现场。
2. ✅ **`KernelDatabase` 有了文件 I/O**：追加式 JSONL 事件日志（`kernel` / `retrieved`），
   `promote()` 落盘、启动时重放；重放对**被截断的最后一行**只跳过并计数，不整库放弃。
   `score` = 可信同机加速比，它的读者是 `search()` 的排序权重（`_perf_weight`：有 score 用
   score，没有才回退 gflops —— 6 条手写 seed 本来就没有同机基线）。
3. ✅ **入库门**：`measurement.persist_decision()`（不可信测量 / 被抢占 / 加速比 ≤1 一律拒），
   由 `Conductor._save_to_db` 执行；被拒的核只留在本次进程内存里，**不落盘**。
4. ✅ **取用次数可见**：`search()` 记 `retrieved_count` 并累加 `retrievals_this_run`，
   每次运行结尾打一句 `[KernelDB] …… seed 6 + 历史 N …… 曾被检索 X 条 …… 本次取用 Y 次命中`。
   退役阈值**仍然没有**（理由见第四节），先攒数。

下一步（按依赖顺序）：

1. ⬜ 一个更强的真读者：Designer 的 RAG 示范优先取「同 `(hardware, algorithm)` 的历史最优核」，
   并把 seed 的 6 条手写核显式降级为先验（doc 00 缺口 3 的「静态表应降级为先验」第二次出现）。
   现在 seed 与历史记录混在同一个排序里，只靠 `_perf_weight` 区分。
2. ⬜ `FailureDatabase` 同样零持久化（`_record_failure` 只进内存）—— 负样本是 C1 重测的输入，
   也是缺口 6 命中率的分子。
3. ⬜ 有了 1、2 之后才能做：C3 晋升规则、缺口 6 的生产命中率、doc 42 的每-shape 可达上界
   （那时才给 `KernelRecord` 加 `shape_key` —— 现在加就是死字段）。

## 六、门吃过真数（2026-09-26，H20 GPU 2，`benchmarks/verify_measurement_validity.py` 同批读数）

门不是拿合成 metrics 验完就算数的，所以把今天真机三条 L3 结果原样喂给 `persist_decision`：

| 真机 case | can_gate | speedup | 门的裁决 |
|---|---|---|---|
| layernorm 1024×768 | False | 1.29x | ❌ 拒收 —— 正是缺口 1 那档「数字描述的是 launch 开销」的测量 |
| layernorm 16384×6144 | True | 1.40x | ✅ 入库（validity=degraded，档位随记录一起存） |
| matmul 4096³ | True | 1.06x | ✅ 入库（validity=valid） |

三条里拒了一条，说明门在真数上**不是恒真也不是恒假**。值得注意的是 matmul 那条：1.06x
离「大获成功」很远，但它才是本机 fp16 GEMM 的真实水平（doc 42：候选核 140.2 TFLOPS，
cuBLAS 同 shape 132.4）。语料里因此会存进一批「勉强快过基线」的核 —— 这是对的做法，
它们正是「上一次做到过什么」的答案，而不是理想化的示范。

⚠️ 端到端（真跑一次 Conductor 生成 JSONL）尚未验：入库发生在 `Conductor._save_to_db`，
需要 LLM 端点跑一整条流水线。本轮覆盖的是 14 个离线用例 + 6 条变异，其中两条
（`_save_to_db` 忽略门的结果 / `promote` 不落盘）专门钉住这段接线。

## 七、这一轮自己贡献的一个反面样本：被遮蔽的 `promote()`

`promote()` 在本轮被两次编辑各插进 `KernelDatabase` 一次，**Python 不报错、测试全绿**。
发现方式不是读代码，是变异：把落盘那一行删掉后，14 个用例**一个都没红** —— 被删的是
被后一份定义遮蔽的那份，也就是死代码。这正好是项目一直在记的那类「看起来活着」的缺陷，
只是这一次制造者是编辑过程本身。

两个改动：

- 删掉重复定义（两份逻辑完全相同，只差 docstring）。
- 加机械守卫 `tests/test_repo_hygiene.py::TestNoShadowedDefinitions`：AST 扫
  `operator_agent/` `benchmarks/` `remote_scripts/`，同一个 class 体内同名函数定义两次即红；
  另配一条「守卫不空转」用例（插一份重复定义 → 变红 → 还原 → 复绿，本轮已真跑过）。
  全仓现存重复定义数：**0**。

顺带的教训写进纪律里：**新加方法前后都该跑一次变异**，而不是只在新用例上跑 ——
这次 M1（删除落盘）的逃逸不是因为用例弱，恰恰是因为用例足够强但被指向了一份永不执行的代码。
删掉遮蔽后重跑 M1，5 个用例立刻变红。
