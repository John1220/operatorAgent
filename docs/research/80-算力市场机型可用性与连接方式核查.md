# 80 · 算力市场（gpushare 卡时）机型可用性核查

当事人 2026-11-01 换了卡的来源：从「租一张 4070 实例」改成公开算力市场的价目表，并连续问了三张
低价卡（TITAN X / P4 / Colab T4）。本文把那张价目表**逐行判过一遍**，判据全部从仓里实读，
不是我按印象排的——目的是让「哪张能用、用了要付什么代价」这件事从此有一个可复查的落点。

| 出处 | 取到什么 | 本机可达性 |
|---|---|---|

| 同上 + `product/price/` | **没有**写「一个实例 = 一张独占整卡」，也没写空闲回收与最长会话 | ⚠️ 文档缺口，只能上机举证 |
| 二手资料（2026-10 博文聚合）：CUDA 13.0 不再为 CC<7.5 离线编译；vLLM 0.20+ 要求 ≥7.5；「TensorRT-LLM、TGI、Triton 已把 sm_70 移出当前容器版本」 | 决定 V100 / TITAN V（都是 7.0）能不能编 | ⚠️ **二手，未经 Triton 官方一手核对** ⇒ 只当风险提示，上机第一件事就是证它（§5） |

SSH 这条是**决定性的**：`operator-agent run --backend ssh` 是插件臂的唯一生产路径（CLI 的 backend

Colab 那种只有 Jupyter、没有 sshd 的运行时，测的就不是插件工作流本身；而 `--backend local` 是 CPU
回退，**从今天起 Designer 对它直接抛**（[agents.py 的 `smem_budget()`](../../operator_agent/generate/agents.py#L51)），
所以它连「跑起来」都做不到。

## 2. 判据（仓内实读的门槛，不是外部评测口径）

| # | 门槛 | 出处 | 不过会怎样 |
|---|---|---|---|
| 1 | Triton 能编译该 CC | 历史错误串「Triton only supports devices of CUDA Capability >= 7.0」；仓里 `_PEAK_BY_CC` **没有任何 6.x 行** | 每个候选都编译失败，而 `_INFRA_MARKERS` 只认 oom 那一族 ⇒ **架构不支持被记成候选失败**，产出一张假的能力表（这是本期最贵的一种错） |
| 2 | `has_software_pipelining = major >= 8` | [hardware_caps.py](../../operator_agent/core/hardware_caps.py) 推断路径 | 7.x 上没有 cp.async ⇒ Triton 的 `num_stages` 流水化落空，matmul 那条轴直接退化 |
| 3 | 有没有 bf16 / tf32 | Turing 与 Volta 的 Tensor Core **只有 fp16**；Ampere 起才有 bf16/tf32 | 冻结契约若按 `--precision bf16` 就没人拦：`_KNOWN_HARDWARE["v100"]` 自己写着 `bf16_tflops=125`（Volta 做不到的事有一条分母），这是**表里的一个缺陷**，不是这张卡的能力 |
| 4 | roofline 分母命中哪一行 | 名字命中 `_PEAK_BY_NAME` 优先，否则 [verifier.py:190 起](../../operator_agent/decide/verifier.py#L190) 按 cc 回退；`peak_trusted` 只认「出处串不以 ⚠️ 开头」（[verifier.py:2524](../../operator_agent/decide/verifier.py#L2524)） | 见 §3 每行标注。⚠️ 行 ⇒ `peak_trusted=False`；非 ⚠️ 的 cc 行 ⇒ **True 但数值可能偏大 2–4 倍** |
| 5 | 判停出口真正认的是「实测过」 | [verifier.py:1875](../../operator_agent/decide/verifier.py#L1875) 那句 `未实测⇒天花板出口关闭`；§13.5 把「口径核过」与「探测过」刻意分开 | 任何新卡不跑 `calibrate_achievable_peak.py` 就没有出口——**与机型无关**。顺带更正 runbook §7 先前那句「`peak_trusted` 不为 True ⇒ 出口不开」的归因 |
| 6 | 每块/每 SM 共享内存与 L2 由卡自己报 | 本轮的 `gpu_info` → `hardware_report`；读不到省键 | 老 runner + cc 不在 `{9.0, 8.0}` ⇒ 抛。这条对下面所有档都成立 ⇒ **换卡必须连 runner 一起部署** |
| 7 | 独占可举证 | 采集器要显式 `--sharing`，不许留空（[collect_unknown_card_probe.py](../../benchmarks/probes/collect_unknown_card_probe.py)） | 填「exclusive」而实际有对手进程 ⇒ G4 的污染阈值方向反过来错 |

## 3. 逐档判定（价 = 每卡时人民币区间，取自 §1 的价目表）

### 出局：编不出来

| 机型(显存) | 价 | CC | 为什么 |
|---|---|---|---|
| TITAN X (12 GB) | 0.68–0.76 | 5.2 Maxwell | 低于 7.0；表里无行，peak=0 |
| Tesla P4 (8 GB) | 0.51–0.57 | 6.1 Pascal | 同上，且**无 Tensor Core**、GP10x 的 fp16 是 1/32 速率 |
| P40 (24 GB) | 0.68–0.76 | 6.1 Pascal | 同上。便宜 0.5 ¥/h 不是理由——它让失败路由说谎 |
| P100 (16 GB) | 1.02–1.14 | 6.0 Pascal | 同上（Pascal 无 Tensor Core） |

### 边缘：有 Tensor Core，但工具链在收口

| 机型(显存) | 价 | CC | 判定 |
|---|---|---|---|
| TITAN V (12 GB) | 0.68–0.76 | 7.0 Volta | **不建议**。二手资料说 sm_70 已被移出当前容器；fp16-only、无 cp.async；`_PEAK_BY_CC["7.0"]` 抄的是 V100 行（带宽 900 vs 实际 640） |
| V100 (16 / 32 GB) | 1.27–1.42 / 2.12–2.37 | 7.0 Volta | **不建议**，理由同上；而且名字命中 `_PEAK_BY_NAME["v100"]`（无 ⚠️ ⇒ `peak_trusted=True`）却带着那条**Volta 不存在的 bf16 分母**，是一张「表看起来可信、其实错位」的卡 |
| 2080 Ti (11 GB) | 0.76–0.85 | 7.5 Turing | **可用但异代**：Triton 支持 7.5、有 fp16 Tensor Core、**616 GB/s**（内存带宽型算子很吃这条，比 3060 的 360 与 4070 的 ~504 都高）；但无 bf16/tf32、无 cp.async ⇒ matmul 轴退化。`_PEAK_BY_CC["7.5"]` 抄 3090 且标 ⚠️未核 ⇒ `peak_trusted=False`，**必须实测**才能谈任何达成率 |
| T4 (16 GB) | 1.7–1.9 | 7.5 Turing | 同上但只有 320 GB/s，且**比 3090 还贵** ⇒ 没有选它的理由；它的用处只在零成本自测门（见下） |

### 可选：CC ≥ 8.0，bf16 / cp.async 齐

| 机型(显存) | 价 | CC | 代价（都是仓内可指认的） |
|---|---|---|---|
| **RTX 3070 (8 GB)** | **0.59–0.66** | 8.6 | 最便宜且能力齐（GA104 58 SM、608 GB/s）。两处要认：① 8 GB ⇒ 标定脚本的 4096 MB 那行要 src+dst 共 8 GiB + 256 MiB 冲刷缓冲，**必然 OOM**（而 OOM 记成基础设施失败），[calibrate_achievable_peak.py:89](../../benchmarks/calibration/calibrate_achievable_peak.py#L89) 得裁；② 独占默认预检 `min_free_mib=4096`（[s5_workflow_preflight.py:22](../../benchmarks/experiments/s5/s5_workflow_preflight.py#L22)）在 8 GB 上等于要半张卡空 |
| RTX 3070 Ti (8 GB) | 0.68–0.76 | 8.6 | 同上；61 SM、同为 608 GB/s，与 3070 同价档 ⇒ 只算等价选项 |
| RTX 3060 (12 GB) | 0.76–0.85 | 8.6 | 12 GB 免去上面的裁剪；但 **360 GB/s** ⇒ 同样形状里 launch 地板占比更高 ⇒ `uninformative` 更多，两臂对比更容易被预算截断（判据是「+1 最小可检出单位」，预算耗尽 ≠ 无增益）。cc 8.6 行是 A100-40GB 数（312/1555）⇒ 偏大 2–4.4× |
| RTX A4000 (16 GB) | 1.02–1.14 | 8.6 | 16 GB 但 **448 GB/s**，带宽反不如 3070；要显存时才考虑 |
| RTX 3080 / 3080 Ti (10 GB) | 1.02–1.18 | 8.6 | 760 / 912 GB/s，无名字条目 ⇒ 走 cc 8.6 行（偏大） |
| **RTX 3090 (24 GB)** | 1.53–1.71 | 8.6 | **唯一在仓里有名字行情的 Ampere**：`_KNOWN_HARDWARE["3090"]`（16.3/130.6/326/936、82 SM、smem 100 KB）+ `_PEAK_BY_NAME["3090"]`，但后者出处带 ⚠️「疑含 2:4 sparse」⇒ `peak_trusted=False`，实测仍是必须。综合最像「小 H20」：Ampere 代、936 GB/s、24 GB |
| RTX A6000 (48 GB) | 3.4–3.8 | 8.6 | 48 GB / 768 GB/s，唯一能装下 H20 那批形状的档；价格是 3070 的 5.8 倍 |
| A100 (40 GB) | 2.72–3.04 | 8.0 | 与 H20 同代数据中心卡（tf32/bf16/cp.async 全）。**但名字命中 `a100` 行 = 80 GB 口径**：带宽 2039 vs 实际 1555 ⇒ 分母偏大 31%，而该行无 ⚠️ ⇒ `peak_trusted=True` 是**带着错分母的可信**——这正是 §13.5 要实测的理由 |
| 3090 Ti (**8 GB**) | 2.04–2.28 | 8.6 | **先当作不可选**：真 3090 Ti 是 24 GB，标 8 GB 只可能是**切分/vGPU**。切分卡上 `nvidia-smi` 的 uuid 与可见显存都对不上整卡，G4 的对手进程观测失效、污染阈值无从判定，而我们的采集器只接受显式申报 ⇒ 独占举证不了 |

## 4. 我的排序（按「一次实验能不能被解释」排，不按单价排）

1. **RTX 3070 8 GB**（0.59–0.66）——只要肯接受「裁掉标定脚本的 4096 MB 行 + 预检阈值按 8 GB 重述」，它是能力齐全里最便宜的；608 GB/s 足够让 layernorm/softmax 这类带宽型任务的读数离开 launch 地板。
2. **RTX 3090 24 GB**（1.53–1.71）——与 H20 同代、显存带宽都在，唯一有名字条目，代价是那条 ⚠️ 口径未核 ⇒ 仍然要实测。要「读数能和 H20 讲在同一个故事里」就选它。
3. A100 40 GB（2.72–3.04）——只在需要 tf32/与 H20 同代数据中心特性时；记下分母偏大 31%。
4. 3060 12 GB / A4000 16 GB——显存省事、带宽拖后腿。
5. **零成本自测床**：Colab T4 或市场里任意 7.5 卡，只用来跑 `gpu_info → smem_budget → PROBE_JSON → 采集器 → 门` 这条链（验证「未知卡不许落进兜底」），**不进 4×2 表**；它的读数按 uuid 核对，不许与上面任何一张同表。

## 5. 上机第一天必须做的三件事（顺序不能换）

1. **必成功最小核**：`import triton` + 一个恒等 kernel 编译并跑通。这一步同时证「这台机的 Triton/torch/驱动组合能编」「`uv`/pip 环境完整（H20 教训：pip 后必 `pip check`）」，并直接证伪或证实 §1 那条关于 sm_70 的二手说法。**没这一步就别开跑**——否则失败路由会把环境问题记成候选能力问题。
2. **采集器 + 五道门**：`measure_launch_floor.py` → `calibrate_achievable_peak.py` → `collect_unknown_card_probe.py --sharing <独占|接显示器|有对手> --from-probe … --out card-probe.json` → `unknown_card_gates --from-json`。G1/G2/G3 到这里才第一次有读数；**G4 的散布带与 G5 的形状清单至今没有量具**，所以门大概率停在 unknown——那是预期结果。共享形态按容器里能观测到的如实填，观测不到就报 unknown 并停在第 0 步，不许默认 exclusive。
3. 才轮到阶段 B 的 4×2 格（每格 ≤30 次调用 / ≤2400 s 墙钟的冻结预算，见 runbook）。

## 6. 与既有文档的关系

- 判据 4/5/6/7 与本文同源的是[可迁移性 G1–G5](../design/dsh-operator-portability-4090.md)；本文是它的一次**按市场机型的应用**，不改判据。
- runbook §7 原先按 4070 写：其中第 2 条（`agents.py` 缺 8.9 分支）已闭合；第 1 条的归因**错了**（写成 `peak_trusted` 不为 True ⇒ 出口不开；实际出口只认「实测过」），要随本文一并更正。
- 换卡不改变那条优先级：**一次非 CUDA 真迁移 > 再加一张 N 卡**。上面全是 N 卡。
