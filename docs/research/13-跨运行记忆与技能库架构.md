> 版本: v1.0 | 日期: 2026-09-24
> 服务于缺口: **2**（跨运行零积累）为主，强依赖 **1**（测量有效性）与 **4**（bound 感知判据）
> 核实声明: ✅ = 本人独立核对（本机实测或直接读代码/一手文件）；⚠️ = 来自研究员报告，未独立核实

## 一、结论先行

**检索算法不是瓶颈，语料才是。**

✅ 直接读 `operator_agent/kernel_db.py:299-347` 核实：`search()` 已经做了 hardware 硬过滤、dsl 加权（精确 3.0 / python 回退 0.5 / 其余剔除）、词元重叠相关度（`2.0 × |query ∩ record|`）、子串与 tag 加分、零相关剔除、性能轻微加分。**这套设计基本正确**，不需要换成向量检索。

真正缺的是：

1. ✅ `kernel_db.py` 文件 I/O 命中数为 **0**（`open(`/`json.`/`pickle`/`sqlite` 全无），`_init_seed_data()` 填 6 条字面量，`add()` 只写进程内 dict。
2. ✅ `ArtifactStore.load()` / `list_all()` **全仓无调用点**——写入端（`conductor.py:923` `kernel_db.add`）和读取端都写好了，中间从未接通。
3. ✅ 运行内学到的 `applied_recipes` / `disabled_recipes` 随进程死亡。

所以缺口 2 的工作量比预想小：**不需要重新设计检索，需要给它接上持久化和一个会增长的语料**。

### 顺带核出两个检索缺陷（研究员未提，✅ 本人读代码发现）

**(a) 性能加分项对像样的核完全无区分度。** `kernel_db.py:344`：

```
score += relevance + min(r.performance, 100.0) / 100.0
```

而 `r.performance` 来自 `conductor.py:918` `artifact.benchmark_data.get("gflops", 0)`。实测值：layernorm 273.8、matmul 120825.5 —— **两者都被 `min(...,100)` 截到 100，加分同为 1.0**。也就是说这个「同分时优先历史高性能案例」的机制，对任何超过 100 GFLOPS 的核都退化成常数。且 gflops 对 memory-bound 算子本身就不是正确指标（缺口 4）。

**(b) `mock_gpu` 记录被当通用记录放行。** `kernel_db.py:320`：

```
candidates = [r for r in candidates if r.hardware == hardware or r.hardware == "mock_gpu"]
```

6 条种子里的 mock_gpu 记录会命中**任何** hardware 查询。这正是 Designer 每次都打印「RAG 命中 1 个相似案例」的原因——它命中的往往是一条与目标硬件无关的种子。

## 三、必须知道的两个反面案例

这一节比方案表更重要——它决定了应该以什么预期去做缺口 2。

### Sakana AI CUDA Engineer 的加速比被证伪 ⚠️

宣称 10–100×、个别 17000×。研究员报告：Lucas Beyer 用 o3-mini-high 花 11 秒发现某个「快 150 倍」的核**实际慢 3 倍**，手段是缓存复用 / 返回常量 / 跳过 conv。Sakana 自家后续论文 [2509.14279](https://arxiv.org/abs/2509.14279) 承认 "existing kernel benchmarks suffer from exploitable loopholes" 并推出 [robust-kbench](https://github.com/SakanaAI/robust-kbench)；[2604.22032](https://arxiv.org/abs/2604.22032) 将其列为 documented reward-hacking incident。

**对我方的意义**：其 archive 不可直接当语料。更重要的是，这与 [`00-架构基线与缺口核实.md`](00-架构基线与缺口核实.md) 里实测的「L2 门敞开（乘 0.97 的核也 PASS）」是**同一类失效**——不是假设风险，是这个领域已经栽过的坑。

### AWM / ReasoningBank 的增益在等 token 预算下消失 ⚠️

[2606.15017](https://arxiv.org/abs/2606.15017) 在**等 token 预算**下复现：vanilla baseline 追平或超过 AWM / ASI / ReasoningBank。AWM 宣称的 Mind2Web +24.6% / WebArena +51.1% 是作者自评。

**对我方的意义**：任何「加记忆就变强」的宣称都要用等预算对照验证。本项目做缺口 2 时必须设对照组：**同样的 LLM token 预算下，有记忆 vs 无记忆**。否则可能只是把预算花在了检索注入上。

### 另一条：self-improving memory 方差极大 ⚠️

[2608.18066](https://arxiv.org/abs/2608.18066) 多 run 复现显示提升**高度依赖任务顺序**（默认顺序构成隐式 curriculum），根因是 task/environment underspecification。

**对我方的意义**：验证「变强」必须多 seed + 打乱任务顺序 + 报告方差。跑一次成功不算数。

## 四、AutoTuneBench 的测量纪律（直接对治缺口 1）⚠️

研究员报告的关键数据，与我方 [`01-launch开销与shape充分性实测.md`](01-launch开销与shape充分性实测.md) 的独立实测高度吻合：

- best kernel 对 naive baseline **10.6×**，但对 honest baseline 仅 **2.03×** → strawman baseline 制造假加速。
  - 我方对应：`min_speedup` 的 baseline 选取已有优先级逻辑（fp16 matmul 优先 cuBLAS），方向正确，但 driver 各自传 0.8/0.5 使阈值不可比。
- 同一 config 在两台机器上测得 **1.174× vs 1.0049×** → **绝对时间跨机不可迁移**。
  - 我方对应：这正是「检索排序绝不能用绝对 GFLOPS」的依据，也就解释了第一节 (a) 那个 `min(perf,100)` 为什么错得更彻底。
- KernelBench L1 仅 **51%** 通过、中位加速 **1.0001×**。
- 四种测量失效：strawman baseline、绝对时间跨机迁移、饱和任务、基础设施缺陷伪装成科学结论。
  - **「饱和任务」正是我方 layernorm 1024×768 的情形**——已被 `01` 号文档实测证实（launch 占比 95.6%）。
- 对策：协议冻结为代码、DB 层 validator 拒绝 out-of-protocol 结果、anti-cheat 跑在 agent 不可修改面之外、预注册 readout、paired-seed、**5% cross-run CV 上限**。

**其中「anti-cheat 跑在 agent 不可修改面之外」值得特别注意**：我方 `anticheat.py` 与被验证代码在同一进程内执行（`run_kernel.py` 里 `shield_torch` 替换 torch 算子）。⚠️ 需核查生成代码能否在 shield 生效前拿到原始 `torch.matmul` 引用。列为待办。

## 五、落地建议

### 5.1 存储选型（✅ 本机实测）

```
Python 3.9.6 | sqlite 3.51.0
  FTS5                     OK
  JSON1                    OK
  window functions         OK
  enable_load_extension    属性不存在（编译期即关闭）
```

`enable_load_extension` **属性根本不存在**（比研究员报告的「= False」更强），因此 **sqlite-vec 彻底排除**。Chroma（Voyager 已暴露双存储失同步问题）、LanceDB（Rust 重轮子）、DuckDB（分析型，非事务写）同样不合适。

→ **stdlib `sqlite3` + FTS5(bm25) + JSON1，单文件**；外加 **append-only JSONL 作为 git 可审阅的 source of truth**，DB 只是可重建的索引（提供 `rebuild_index.py`）。

这样同时满足三个约束：零新依赖、可 git 版本管理（JSONL 可 diff）、可人工审阅。真需要向量时把 embedding 存 BLOB/JSON 列 + numpy 暴力 cosine（<10k 条足够），仍零新依赖。

### 5.2 Schema（三表，复用已有 `KernelArtifact` 字段）

✅ `KernelArtifact` 已含 `iteration_history`（血缘）、`compile_info`、`benchmark_data`、`saved_dir`，可平滑扩展。

- **`kernel_run`**：run_id、task_hash、kernel_type、**hardware_fp**（SM/cc/smem/driver/triton_ver 的 sha1）、dsl、precision、bound_type、shapes、sketch_json、code、code_sha256、**parent_run_id**、all_passed
- **`measurement`**：run_id、metric、value、baseline_ref、speedup、**n_seeds、cv_pct、protocol_version**、env_snapshot（load avg / 是否独占 GPU / 时钟 / **launch_dominance**）、**trust_label(gold|silver|suspect|rejected)**、trust_reasons
- **`recipe_event`**：run_id、recipe_id、applied、before/after、delta_pct、**verdict(helpful|harmful|inconclusive)**、n_observations

`recipe_event` 就是 ACE 的 helpful/harmful 计数器，把 Conductor 进程内的 `applied_recipes`/`disabled_recipes` 提升为跨运行统计。**这是缺口 2 里性价比最高的一张表**——数据已经在产生，只是被丢掉。

FTS5 虚表覆盖 kernel_type / algorithm / tags / sketch 文本 / error_summary。

### 5.3 检索键（三段式，结构化优先）

1. **SQL 硬过滤**：hardware_fp（或同 cc 家族）× dsl × precision × kernel_type × bound_type。这些维度用语义嵌入毫无优势。
2. **FTS5 bm25 稀疏排序**（对齐 daVinci-kernel 的 BM25+rerank，而非稠密向量）。
3. **质量加权**：仅取 gold/silver，按 **paired 相对加速 + n_seeds** 排序。**绝不用绝对 GFLOPS**（AutoTuneBench 证明跨机不可迁移；这也修掉第一节 (a)）。
4. 另取 **top-3 负例**作为「别这么做」（ReasoningBank）。

⚠️ top_k 要小：[2608.15008](https://arxiv.org/abs/2608.15008) 实测**过度检索会损害序贯决策**（注意力被拉离 action-critical context）。建议 k≤5，与现有 `limit=5` 一致。

### 5.4 写入门控（admission gate）

一律先写 `status=candidate` 并附 verifier 元数据；满足以下**全部**条件才 promote 为 gold：

```
all_passed
∧ n_seeds ≥ 3
∧ cv_pct ≤ 5%
∧ 与 baseline 同进程交替 (interleaved A/B/A/B) 测量
∧ launch_dominance < 0.10        ← 来自 01 号文档的实测阈值
∧ 独占性检查通过 (无污染标志)
∧ 二次复现落在首次区间内
```

**失败也要写**：`rejected + failure_class`（编译/精度/超时/加速不显著）+ 错误首行进 FTS5，构成错误模式库（按 failure_class + 错误首行聚类即可，无需嵌入聚类）。

去重用 `code_sha256`；同键且更差的旧记录 **DEPRECATE 而非 DELETE**（保审计，对齐 ACE 与 [`10`](10-DeepSeekHarness与插件化agent运行时.md) 第三节的 postmortem 0002 教训）。

### 5.5 防 memory drift

⚠️ MemGuard 指出两类失效：unreliable admission 与 memory drift。对策：
- 定期 revalidate top-K gold，过期降级 silver。
- 每条 measurement 记 `env_snapshot`；**机器/驱动变更后旧 gold 自动失效**（`hardware_fp` 不匹配即不召回）。

对我方尤其重要：本项目 2026-09-16 才从 A100 迁到 H20，迁移前任何「金标」记录在新硬件上都无意义。

## 六、与其他缺口的依赖关系

```
缺口 1 (测量有效性三态)  ──┐
                          ├──> 缺口 2 (持久化 + 语料增长)
缺口 4 (bound 感知判据)  ──┘
```

**缺口 2 必须排在 1 和 4 之后。** 理由与 [`10`](10-DeepSeekHarness与插件化agent运行时.md) 第三节相同：在没有 `measurement_validity` 的情况下持久化，只是把被 launch 开销压扁、被同机进程污染的测量固化成语料，越积累越糟。这正是 MemGuard 说的 unreliable admission，也是 Sakana 已经栽过的坑。
