# 候选联合类型与便宜代理剪枝 —— §12 的枚举半片

> 设计 §12：「接入 TVM / CUTLASS 的最大风险是接口把"候选"硬编码成源码字符串——那一刻起，
> 模板型后端就无法接入，整条链路要重写。因此 `Candidate` 必须是**联合类型**。」
> 改前全仓没有 `Candidate` / `SourceCandidate` / `TemplateCandidate` / `ParamSpace`
> 任何一个名字，也没有任何后端有 `param_space`：模板型后端接不进来这件事**无法被观测**。

这一片做的四件事，以及**没做的**（模板实例化）。

---

## 1. 联合类型：去重口径必须分开写

```
SourceCandidate(backend, source, build_flags, struct_sig)      # Triton / CUDA: 交出去的是代码
TemplateCandidate(backend, template_id, params, instantiator_ver)   # CUTLASS / TVM: 交出去的是点+参数
```

设计给了两类候选一个共同要求（去重），而**去重口径在两类上不是同一个东西**：

| 类型 | 去重键 | 为什么 |
|---|---|---|
| 源码型 | `("source", backend, struct_sig)` | 签名来自 `novelty.signature_of` —— 与 `iteration_history` 里那个 α-等价签名**同一个实现**；变量改名不算新候选 |
| 模板型 | `("template", backend, template_id, instantiator_ver, 排序后的参数)` | 模板候选**没有源码可签名**；参数谁在前不该改变身份；`instantiator_ver` 进键是因为「同一个点位由不同版本的实例化器产出」是**不同的构建** |

两个决定值得记：

* `__eq__` **跟去重口径走**，不是跟字段走。第一版只写了 `__hash__ = hash(dedup_key)`，
  于是 `{a, b}` 里两份 α-等价的候选**都在**（字段比较里源码原文不同 ⇒ 不相等）——
  「去重」当场失效。身份既已定义为去重口径，`__eq__` 与 `__hash__` 就都得从它来。
* 源码候选的键**故意不含** `build_flags`：同结构的候选是同一个候选，编译参数不同不改变
  这一点（要区分时用 `as_lineage()` 的快照）。

## 2. 那个开关：`None` 是一个有意义的答案，所以它不 raise

`backend_caps.Backend` 上可选方法的处置口径是「**一调就 raise**」，理由写在那个模块开头第 1 条：
`hasattr` 恒为真，「静默 no-op」不可表达。但 `param_space()` **不能照抄这个口径** ——
设计 §12 明写「返回 `None` 的后端 = 代码型后端」，`None` 在这里是**答案**，不是缺能力。
基类若 raise，今天每一个后端（全是代码型）都会在第一次搜索时炸。

所以：`param_space()` 立在基类上、默认 `return None`；`space_origin()` 报告
`inherited`（用基类默认）/ `overridden`（这个后端自己声明了空间）—— 第一版里那个
「协议方法都没有」的状态**按设计不可表达**，留着它等于留了一条嗅探路径。

调用侧两处：

* `param_space_of(backend, contract)` = 直接调协议方法（**不是** `getattr` 嗅探 ——
  第一版就是 `getattr(backend, "param_space", None)`，被 `tests/test_backend_caps.py`
  的 AST 守卫当场抓红，那条禁令的理由是「能力判断只许走声明好的词汇」）；
* `require_supported_space(space, backend)`：非 `None` ⇒ **fail-closed 拒绝**，
  点名那个模板并指向 §12。为什么不静默降级：§12 要挡的风险正是「把候选悄悄当成源码字符串」，
  后端声明的参数空间被无声丢掉就是同一个病。控制器把它接在**每轮搜索入口、真值测量之前**
  （拒绝要发生在花钱之前）。

## 3. 便宜代理剪枝：复用 L1 的估算器，不另立阈值

设计 §10.4 的伪码里有一步 `proxy_prune(c): continue`（不花 GPU 秒）。今天仓里**已经有**
这个量具：`resource_check` 的 smem 估算与 L1 预检，但它的读者**只有编译前那一个**。
于是明明可以「不花 GPU 秒就把明显放不下的 tile 摘掉」，却让一次真值测量去买一个必然
编译失败的 launch。

这一片把它接上，并且刻意**不发明**任何公式或阈值：

* 估算用 `resource_check.estimate_matmul_smem_bytes`（`(BM*BK + BK*BN + BM*BN) * elem`）；
* 宽松系数共用 `SMEM_SLACK = 1.2`（超限 20% 以上才拒）—— 两套阈值会长成
  「预检放行、剪枝拒绝」这种自相矛盾的行为；
* 上界由 Verifier 从 `HardwareCaps` 发布进 L3 metrics（`shared_mem_per_sm_kb`），
  与 L1 预检**同一个真源**，再经 `perf_data` 到达 SearchAgent；
* 三态：上界取不到 ⇒ `smem_limit_bytes` 返回 **`None`（缺 ≠ 0 ≠ 无上限）**，剪枝
  **不生效**并在日志里明说「未生效」。`0` 会被读成「一点都放不下」，把邻域全拒掉。

两条不是防御性代码的边界：

* **全摘光时一个都不摘**（`kept_all_to_avoid_starvation`）：剪枝是省冤枉钱，不是让这一轮
  没得跑；上界或 `elem_bytes` 猜错时，保留原集合交给远端判定比空手回上游好。理由仍留在
  `dropped` 里（说明里写「全部保留待远端判定」），所以这件事**可观测**；
* 认不出的参数轴 ⇒ 不剪（宁可漏拦，与预检同一条保守原则）。

## 5. 明写的边界

* **模板候选的实例化（`build`）未实现**：声明了参数空间的后端会被控制器 fail-closed
  拒绝。所以 §12 的目标（统一两类后端）今天只完成了「让它们接得进来且拒绝得清楚」；
  CUTLASS/TVM 的真正接入要一个实例化器。
* **参数轴只有 tiling 三维有产出者**：`stages` / `warps` / 向量宽度 / `layout` / split-K
  还没有任何地方能按参数点出核 —— 它们要等实例化器，先枚举出来只会是**没人读的键**。
* 剪枝只估**单缓冲**（不含 `num_stages` 多缓冲）⇒ 只砍明显超限的点；
* 剪枝今天接在**邻域搜索**这一处（tiling 格点）；`param_space` 的点集也接了同一个剪枝，
  但点集本身还没有模板后端来喂；
* **真机未复跑**：全在离线假 GPU 上验，能声称的是「判据与接线有产物、变异能红」，
  不是「真机上的 smem 剪枝省下了多少机时」。
