## 一、为什么单独做这一篇

`c76edc8` 给正样本库补了文件 I/O，缺口 2 的账本因此写下「🔶 半落地」，剩下两件事：
一个更强的读者，和 **`FailureDatabase` 仍然零持久化**。第二件比第一件更要紧，因为它挡着
账本里两条已经批准的决定：

* **C3「跨任务复发才升级为配方」** —— 判据是「同一类失败在几个**不同任务**上出现」。
  旧结构里这句话**算不出来**：库是进程内的 dict，进程一退就空；而库里的两个 id 方案
  都不表示「同一类失败」（第四节）。
* **C8「花 GPU 之前先排序」** —— 报告自己说主力应该是跨运行的失败统计，而那份统计
  不存在。

所以这一篇不是「补个存储」，是把 C3 的判据从概念变成可计算。

三条**负证据**，它们比正面结论更影响我怎么设计：

1. **没有任何系统做 traceback → 签名的归一化。** 全仓搜过 Ecdysis / AdaExplore /
   OpenEvolve / AWM / GEAK：没有栈哈希、没有 error-type+首帧键、没有失败 embedding 聚类。
   所以这一层没有先例可以抄，我做的是「把 Ecdysis 的 reward 分解换成 verifier 的层级 +
   异常类名」这个转译，转译的正确性只能自己验。
2. **没有系统跨任务持久化失败。** 六个系统全是「只存成功」或「进程内」。
3. **没有人评估过复发筛选本身。** Ecdysis 的消融只做「并行 vs 串行精炼」，
   AdaExplore 的消融是**整个记忆去掉**（2.65×→2.32×、100%→99%），不是那个 `>=3`。
   ⚠️ 也就是说：「复发⇒ harness 缺陷」目前是被**陈述**的原则，不是被**测过**的结论。

### 两份论文与两份仓库的不一致（这是本轮最该记住的部分）

* **Ecdysis**：论文标题句「跨任务复发优先」在代码里是**一个 prompt 里的形容词 + 一次排序**，
  没有 `>=2` 的过滤、没有阈值、没有消融。接受条件是 `candidate_score > baseline_score`
  且在同一份 train collector 上重打分 —— 没有 held-out。
* **AdaExplore**：出厂运行配置里 `memory_update: false`，而默认的记忆文件
  `results/memory/general_memory_v1_200.txt` **不在仓库树里**（`results/memory` 0 命中），
  `prompt_modules.py:29-30` 在文件缺失时返回 `""`。**干净 checkout 上，那套「失败驱动的
  经验注入」是静默 no-op**，要自己先跑离线收集器。这与 OpenEvolve 的
  `embedding_model=None → _is_novel() 恒 True` 是同一种坑，而我已经栽过第二次。

结论：这两篇都**不能**当「这样做有效」的证据，只能当「这样做是可行的、且这是别人实际
写出来的形状」。凡是要把它当**效果**引用的地方，本文一律标 ⚠️。

## 四、顺手抓出来的三个既有缺陷（读代码）

都不是「重构」，是这三行不写，上面的机制就是空的：

1. `conductor.py` 的 `failure_id=f"{task.task_id}_{len(self.failure_db)}"` —— id 是
   **插入顺序**的函数。跨运行之后同一个任务的同一类失败每次都会拿到新 id，于是
   「这是老问题还是新问题」在库里根本没有答案。现在 id 由内容决定（`cx-{task_id}:{signature}`），
   Reflexion 那条走 `rx-{task_id}:{signature}`（不同前缀，两条记录不互相覆盖）。
2. `fixer.py` 的注释写着「**固定** failure_id, 避免重复写入」，代码却在 id 末尾拼了
   `uuid4().hex[:4]` —— 每次反思都是新 id，同一份教训可以无限重复入库。
   **注释描述的是代码没做的事**，而 `sha1(kernel_type|dsl|level|错误前200字)` 那半截也正好
   把「跨算子复发」拆碎。
3. `"+".join(r.level.value for r in failed_results)` 跟着列表顺序走：同一份失败可以写成
   `L1+L2` 也可以写成 `L2+L1`，签名因此**碎成两个桶**，复发永远数不满 3（fixer 那边一直是
   `sorted` 的，两边不一致）。已改成排序去重，`test_level_order_does_not_fragment_the_signature` 钉住。

还有**第四个不是读代码读出来的**：远端编译路径把异常类名丢了。它要靠真机跑一次才看得见，
写在第五节 —— 这三条是「代码与注释/彼此不一致」，那一条是「代码与我想象的世界不一致」。

## 五、真机那一条：签名第一次跑就全落 unknown，量具因此被修好了

离线单测里那份 traceback 文本（`COMPILE_FAIL_A`）是我**读代码推测**出来的形状。所以写了
`benchmarks/probe_failure_signature.py`：只走 L1 编译与一次 L2 比对（秒级、不烧卡），
拿真机的 error_log 去喂 `failure_signature()`，并且刻意不打印原文（远程 Traceback 必然带
那台机器的目录与用户名 —— 而签名本身按设计不含路径，打印签名是安全的）。

第一次跑的输出：

```
[probe] L1 · 远端 import 就炸   首行: Remote compile error via SSH: Compile error: module
                                     'triton.language' has no attribute 'undefined_symbol'
  签名: L1|unknown|-
[probe] L1 · 真语法错           首行: Remote compile error via SSH: Compile error: '(' was
                                     never closed (tmpy09oci0q.py, line 4)
  签名: L1|unknown|-
[probe] L2 · 核体用了未定义的 tl  签名: L2|unknown|-

  采到 3 条真机失败, 3 条全部落进 unknown 桶
```

**三条全在 unknown。** 原因不在签名，而在**远端根本没有把类名送出来**：
`remote_scripts/run_kernel.py` 的编译路径写的是 `f"Compile error: {e}"`，而同文件其余每一条
错误路径都是 `f"{type(e).__name__}: {e}"`（✅ 逐条数过）。也就是说 L1 失败在 wire 上的文本里
**一个异常类名都没有** —— 这不只是签名的问题：Fixer 拿到的 L1 错误全文同样从来没有类名，
而 L1 恰恰是最需要「这是 SyntaxError 还是 AttributeError」的那一段。改成带类名之后重跑：

```
  采到 3 条真机失败, 3 个不同签名; unknown 0 条; 签名里带机器路径 0 条
    [L1] 远端 import 就炸   → L1|AttributeError|-
    [L1] 真语法错          → L1|SyntaxError|-
    [L2] 未定义的 tl        → L2|NameError|-
```

顺带两条真机事实，它们修正了我对失败形状的理解：

1. **Triton 核体是懒编译的。** 第一版探针只测「核体里引用未定义的 `tl`」，结果它**通过了
   L1** —— `SSHExecutor.compile()` 只做远端 import，那个 NameError 要等到调用才炸，落在 L2。
   不做这一步我就会把一个「L1 常见失败」的样本形状写进文档而当心。
2. **栈帧成分在真机上恒为 `-`。** 远程 error_log 里没有 `File "...", line N, in fn` 这种行
   （远端只回 `f"{type(e).__name__}: {e}"`）。所以签名第三个成分目前只在本地/MockGPU 路径上
   有机会非空 —— 它是不是该留，按第八节第 3 条判。
   **2026-09-29 复核：仍然是 `-`**，`benchmarks/verify_corpus_honesty.py` 用四条真实远端失败
   （ModuleNotFoundError / NameError / ZeroDivisionError / TypeError）+ 两条本地预检失败各记一次，
   6 条里栈帧发火 **0** 条 —— 连本篇当初那 3 条累计 **0/9**。
3. **签名还有一个相反方向的失效：过并（2026-09-29，同一支探针撞出来的）。** 第八节第 1 条
   防的是碎分（签名数≈记录数 ⇒ 门永远不开），真机上先撞出来的是**两条不同根因拿到同一个签名**：
   本地接口契约那条处方文案里写着「真跑起来必然抛 `TypeError: kernel() got an unexpected
   keyword argument …`」，那是**对未来的预言**，而 `_ERROR_CLASS_RE` 把它当成了本次失败的
   诊断，于是它与一条真的模块级 `TypeError` 同为 `L1|TypeError|-`。过并比碎分更贵，因为它**丢数据**：
   id 是 `cx-{task_id}:{签名}` 内容派生的，同一任务下第二条把第一条覆盖掉，语料里少了一条，
   而复发门把两者数成同一类。修法按第 2 条定的规矩（按真实语料补 marker，不批量臆造清单），
   细节与真机读数在 doc 49 §7.17。

至于「三条不同任务才开门」那道门：**真机上仍然一次都没开过** —— 语料是今天才开始有的，
`[FailureDB]` 那句现在读到的都是「≥3 的 0 个」。这不是失败，是本轮唯一诚实的状态：
机制在，判决还没有数据。

## 六、明确不吸纳的

* **LLM 判重 + LLM 写规则**（AdaExplore 的 `llm_judge_duplicate_batch`）：每条失败要对全部
  现有规则打一次 LLM，成本 O(|规则库|)，且规则文本是自然语言 → 判重本身不稳定。我们的
  `search_by_error` 已经用词元 Jaccard 做同类事，零外部调用。
* **FDCR 三角色 × 两轮面板**（Ecdysis 的 Analyst/Critic/Engineer + Moderator 改 harness）：
  ⚠️ 论文自报 $2.14–$8.48/域，而且它的「接受」是在同一份训练集上重打分，没有 held-out。
  我们现在连「改哪一处 harness」都还没有可判的信号。
* **失败 embedding 聚类**：与 `c76edc8` 那条同一个理由 —— 依赖外部 embedding 服务，
  而我们的键本来就是结构化的。
* **把失败核代码入库当负样本语料**：OpenEvolve 保留失败子代是为了岛屿算法的亲本多样性，
  我们没有任何对应的机制会读它。

## 七、现在还不能说什么

* 不能说「复发筛选提高了通过率」—— 没有消融，我方样本数为 0。
* 不能说「3 是对的阈值」—— 它是一篇论文的默认常数，而 AdaExplore 那篇的出厂配置里
  这个功能**根本没开**。
* 不能说「签名分得好」—— 判据（签名数/记录数）今天才开始积累；`unknown` 桶的占比是唯一
  提前可见的警号，关键词表只有 4 条。
  **2026-09-29 更新**：表有 5 条了，而真实语料第一次有了 6 条带分布的读数
  （`verify_corpus_honesty.py`：6 记录 / 6 签名、unknown 0/6、可复用 6/6、复发计数 2）。
  这仍然不是「分得好」的证据 —— 它是「第一次同时看得见碎分与过并」的证据，而且**过并那一条
  是真机撞出来的、不是审查出来的**（第五节第 3 条）。
* Reflexion 那条路径（LLM 产出 `lessons`）本轮只加了签名与 id，**没有验过它生成的教训是否
  值得复用** —— 那属于 C1 的重测（doc 35 第九节），输入仍然是缺的。

> 🔴 **2026-09-29 追加：这一篇漏掉的三处「没验证就写答案」，全部已修（doc 49 §7.14）。**
> 起因是那条长期红的用例 (`test_budget_exhausted_recorded_as_unfixed`，本篇 §九 之前把它
> 记成「与修复循环同根因」) —— 顺着它取证，挖出来的是**语料本身**的三个缺陷：
> ① **`conductor.py` 把「这条失败已经在循环内沉淀过了」写死成 `True`**，而唯一的循环内
> 沉淀是 `produce_reflexion()`，它只在 Fixer 产出可提取代码时才返回记录 ⇒ 任务结束时那段
> 兜底入库把**每一次修复尝试**都当成「已记过」跳过。后果是：**「修了半天没修好」这一类
> 失败一条都不进库**，而它恰恰是负样本记忆里最该记的那一类。修复是把第三个位置换成
> **那条 Reflexion 记录本身或 `None`**，兜底只处理没有记录的那些。
> ② **`fixer.produce_reflexion()` 无条件 `fixed=True`**，可它被调用的那一刻下一轮验证还没跑；
> 而 `FailureRecord.fixed` 的字段注释写着「该失败**最终**是否被修复」。这不是措辞问题：
> 检索侧两处排序都按「已修复优先」，于是**每条没验过的反思都以「已解决」的身份参与注入
> prompt 的排序**。本地存量语料 19 条里 5 条是 `rx-` 前缀，**这 5 条全是 `fixed=True`** ——
> 那一刻没有任何证据支持这个断言，而事后也无法补证（这一条按 §八 的规矩只能算「不可复盘的账」）。
> 现在的写法：创建时留 dataclass 默认 `False`（=还没人知道），任务结束时若产物通过，再以
> **同一条内容派生的 id** 追加一次 `fixed=True` —— 追加式日志的「后写覆盖先写」是本篇
> §三 本来就设计好的机制（`add()` 总是追加、去重交给重放），这里只是第一次真的用它做一次演进。
> 于是崩溃时教训也已经落盘，而落盘的那一份不自称修好了。
> ③ **`search_by_error` 的 tie-break 与 `search_by_context` 方向相反**：前者
> `(jaccard, not fixed, -created_at)` 配 `reverse=True` ⇒ 相似度相同时**未修复的排前面、
> 最旧的排前面**；后者按文档写的「已修复案例优先」。同一个字段在同一文件两处排序里含义
> 相反，而 prompt 只取前几条。现在两处同向，并由一条**差分守卫**（同一对候选，两条检索
> 路径必须给同一个序）盯着；控制用例证明相似度仍是主排序，不是把 tie-break 换成了永远赢。

> ⚠️ 本篇 §五 那句「签名第一次跑就全落 unknown」之外的存量账要加一条：`fixed` 这一列
> 在 2026-09-29 之前的记录上**不可当证据用**（`rx-` 的 True 是没验过的自称）。不回填、

## 八、改判条件

1. `[FailureDB]` 连续若干次运行显示 **签名数 ≈ 记录数** → 签名碎成 1:1，先摘掉栈帧成分
   （最可能因生成代码的函数名而分裂的就是它）。
   **2026-09-29：这条还没触发（6 记录 / 6 签名），但同一支探针先撞出了相反的方向 ——
   两条不同根因过并成同一个签名，见第五节第 3 条。判据因此从「只看碎分」改成两个方向都要看：
   `verify_corpus_honesty.py` 现在同时有一条读数（碎分比）和一条硬门 J1b（不许过并）。**
2. `unknown` 桶占比 >1/3 → 关键词表按真实语料补，而不是一次性补一张「常见错误」清单
   （那正是本项目记过的死判据形态）。真机三条现在都是 0，但三条不是分布。
   **2026-09-29：真实分布第一次有了 6 条 —— unknown 仍是 0/6，而按这条规矩补的第一条 marker
   （`签名与之对不上` → `interface_mismatch`）就是从这 6 条里的过并撞出来的，不是臆造的。**
3. **栈帧成分**：真机 error_log 里没有 traceback 行，所以它恒为 `-`（第五节）。若攒下的
   真机签名里非 `-` 的仍是 0 条 → 把它从签名里删掉，别留一个从不发火的成分；一旦远端
   改成回传 traceback，再验一次会不会因行号而分裂。
   **2026-09-29：新增 6 条真机签名，非 `-` 仍是 0 条（累计 0/9）—— 这条改判条件差最后一次
   就到「删掉这个成分」了。不现在删是因为远端载荷随时可能改成回传 traceback（那正是
   `runner` 与 `verifier` 不同步时会出现的形状），删了要再加回来得重做一遍分组。**
4. 门第一次开（≥3 个任务同一签名）→ 那时才允许讨论「把它升级成配方」，并且要留
   `promoted` 事件，否则 C3 的效果永远没有可复盘的账。
5. 若出现「同一条教训被反复注入却对通过率无影响」→ 与 C1 的 A/B 并做，别单开实验。
6. **下一次该主动做的，不是等读数**（2026-09-29）：清点所有处方文案里「会抛 `XxxError: …`」式的
   举例字符串，逐条判它会不会进入 `failure_signature` 的输入 —— 条件是它出现在
   `error_log or message` 里，而 `_ERROR_CLASS_RE` 分不清**预言**与**诊断**。已知的这一条
   （接口契约）是被真机撞出来的，不是审查出来的；再撞一次的成本是一条被覆盖的语料记录。
   同一笔账在 doc 49 §八 第 15 条。
