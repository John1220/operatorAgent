# 69 — §10.3 的三条件升级门：位置本身就是判据

**状态**：已落地（`operator_agent/escalation.py` + `conductor.py` 接线 + `agents.py` 发布通道）
**对应设计**：`docs/design/autonomous-operator-agent-design.md` §10.3
**CHECKLOG**：I53（零实现）→ I57（本片）
**变异**：13/13 红（含 M10「缺省裁决改成放行」——第一轮漏网，补了读者用例）

## 1. 设计那句原话，以及它要挡住的东西

> **何时才升级到 LLM 做结构性改动**（三条件同时满足，否则不许调用）：
> 1. 参数搜索已经平台化（K 轮 valid 且 SAME/AMBIGUOUS）；
> 2. 平台化有**可归因的硬限制**证据（spill-bound、smem-bound、占用率上限、bank conflict
>    报表）—— 不是"感觉调不动了"；
> 3. 还存在一个可探索的结构方向（融合 / split-K / 算法替换）。

改前（I53）：每一轮优化都无条件问 LLM 要结构改动。「LLM 在自动跑里最大的价值是结构性
跳跃，最大的风险是被当成万能调参器反复重写同一份代码」—— 当时的行为正好是后半句。

三条件写在一处（`escalation.decide`），接线只做两件事：**判据的输入装配**（conductor）与
**结果的发布**（`perf_data["structural_escalation_denied"]` → SearchAgent 走规则路径）。
门关着时循环**不停止**：它退化成参数/格点搜索，这是设计里那条「否则不许调用」的正解。

## 2. 三个真问题（都是接线时撞出来的，不是想出来的）

### 2.1 位置是判据的一部分：门放在优化分支里 ⇒ 永远开不了

第一版把裁决算在**优化分支**（要发布 `perf_data` 的地方）。实测（K=2）门能看到的判决尾巴
最多 1 条，日志里 4 轮全是被拒，理由永远是条件 1。逐事件打点后原因很清楚：

```
轮次 1: 基线(无判决)            → 优化分支 → 裁决(tail=[])
轮次 2: 判决 SAME(停滞 1/2)     → 优化分支 → 裁决(tail=['SAME'])
轮次 3: 判决 SAME(停滞 2/2) → **停滞出口 break**   ← 优化分支与裁决都没跑到
```

「记满 K 轮平坦」的那一轮，恰好是停滞出口 break 掉的那一轮 ⇒ 门**结构性不可达**。
修法：裁决移到**判决点之后、停滞出口之前**（`_escalation_decision` 的注释里写明这一点），
优化分支只**发布**已经算好的裁决。

配套的语义补完：升级**买到的是 K 轮**（`rounds_without_improvement = 0`）。理由不是「让它多
跑」而是：平台化是对**旧结构**的陈述，换了结构之后那段平坦区不再是关于它的证据。有界性由
`max_optimize_rounds`（总轮次）与「清零后要重新攒够 K 轮 valid」两条一起保证。

### 2.2 K 与停滞上限必须是**同一个数**

设计的 K 没给值，第一版取 K=3，而停滞上限是 2 ⇒ 「循环先停了，门永远开不了」。
反过来 K < 上限则会在同一段平台上反复放行。两个数独立就是两种谁也没设计过的行为，
所以：`MAX_STAGNANT_ROUNDS = 2` 一处定义，`EscalationInputs.k_valid_rounds` **必填**
（不给默认值 —— 有默认值就等于有第二个 K）。语义取「相等」：**循环准备放弃的那一轮，
正是唯一一次问 LLM 要不要结构性跳跃的机会**。

### 2.3 条件 2 的估法必须与 L1 预检**共用一个估算器**

条件 2 今天只有 `smem-bound` 一条有量具（spill / bank conflict / 占用率上限都还没有，
`hardware_caps.py` 里只有一句注释）。第一版按 **sketch 的 tiling** 估，而 L1 预检按
**代码里的 `BLOCK_*`** 估 —— sketch 与 LLM 真正出的码今天允许不一致，于是「证据」与
「预检」会变成两套算法。改成走 `check_resource_feasibility(current_code, caps)`：同一个
估算器、同一份产物（被测量的那份代码），caps 只读一个字段，用一个 shim 就够。

**可达区间是真的窄，且要写明**：L1 在 `est > limit × 1.2` 时**拒跑**，条件 2 要求
`est ≥ limit` ⇒ 只有落在「上界 ~ 上界×1.2」这 20% 带里的 tile 才既跑得起来、又构成
可归因的硬限制（H20：228~273 KiB）。带外两侧各有一条正确行为：太小的没有硬限制证据
（门该关），太大的根本不会进测量（那是预检的职责，不是门的）。

## 3. 两条 fail-closed 边界

1. **缺证据 = 条件不成立**：三条判据读取缺项/空串/0 一律返回「不成立」，不用代理量代替。
   证据文本里带出处（谁算的、拿什么算的），日志与 `artifact.metadata["escalation"]` 里
   能对回设计那一句。
2. **缺省裁决 = 拒绝**：`_denied_escalation()` 不是 `None`。「没走到重算」（测量不可信、
   进了别的分支）与「判过、没通过」对下游必须是同一个答案 —— 拿 `None` 交给读者解释，
   必然有人解释成放行。每一轮的答案都落进 `metadata["escalation"]`（同一轮**替换**，
   不追加：读者要的是每轮一个答案，而不是「轮数 × 分支数」）。

## 4. 测试写的时候撞到的两件事（都不是本模块的 bug，但会咬人）

- **环境指纹是跨运行比对的**：`OPERATOR_AGENT_OUTPUT_DIR` 是整套用例共享的，前面用例
  （别的后端/硬件名）写下的指纹会让本轮读数被判 `degraded`；而门只对**可信读数**判决
  ⇒ 裁决日志为空。现象是「单独跑绿、整套跑红」，而且同一类里**后一条**用例反而绿
  （指纹已经被本类第一次运行对上了）。修法：用例自己把指纹落点隔离到临时目录。
  这不是测试洁癖：它说明「第一轮读数会被上一次运行的环境污染 ⇒ 门不判」是真实行为。
- **`KernelDatabase(jsonl_path=None)` 不是「无库」**，而是「用默认库」（`OPERATOR_AGENT_KERNEL_DB`
  或 `<repo>/output/kernel_db.jsonl`）。用例要无库必须显式传 `"off"`。

`test_an_untrustworthy_round_still_denies_the_escalation`，同时顺手让缺省裁决也落盘 ——
于是「门算过没算过」在产物里分得开。

## 6. 还没做的（明写）

  是预期状态；要让它常开，得先有量具，而不是放宽判据。
- **条件 3 的方向来自配方目录**（`OptimizationPlanner` 选中 ∩ 未 applied/未 disabled）。
  这不是新知识来源，只是差集；真正的「融合 / split-K / 算法替换」候选库还没有。
- **§10.3 的另一半**：`score(c) = P(beats_best) × 预期增益 / 预期 GPU 秒` 与 ε-greedy
  选择还没做（今天只有计数，没有 GPU 秒核算）。分相预算（explore/refine）也等这一半。
