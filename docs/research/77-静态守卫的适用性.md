# 静态守卫的适用性：「查不了」不是「没问题」（CHECKLOG I65）

设计 §19.3 的第三条要求反作弊静态守卫**必须保留**。而今天两道守卫都是 **Python 形状**的：
`anticheat.static_audit` 走 `ast.parse` + 别名/常量折叠（解析不出就退回正则），
`interface_contract.check_kernel_interface` 找 `def kernel` 再逐一比对参数名。对一份
C++/CUDA 模板源，两者**都判不了** —— 而它们的返回值形状只有一个「有/没有问题」的通道：

| 守卫 | 返回值 | 旧读法 |
|---|---|---|
| `static_audit` | 违规列表 | **空列表**既表示「查过了没有违规」也表示「根本没查成」 |
| `check_kernel_interface` | `Optional[str]` | **`None`** 既是「签名对得上」也是「看不出来」 |

于是「查不了」被读成「没问题」。这是 **fail-open**，而且正好落在本仓的基线纪律上
（**信任全部来自验证侧**）：模板源这条路一旦真的开始执行，验证侧对反作弊/契约的信任
是**凭空产生**的 —— 没有任何一格记录说过「这次没查」。

修法不是把守卫写得更聪明（那需要真的 C++/CUDA 分析器，本机没有），而是让它们**说实话**。

## 1. 判据只有一处

`operator_agent/source_lang.py` 回答一个问题：**这两道守卫对这份源码适用吗？**

| `applicable` | 什么时候 | 下游怎么读 |
|---|---|---|
| `True` | 声明在 `AST_FAMILY`（`python`/`triton`/`cuda_python`），或声明在 `REGEX_FAMILY`（`cuda_c`），或没声明但源码解析得过 | 「没有违规」才是没有违规 |
| `False` | 声明了一个**没有任何规则**的语言（`hip_c` 之类） | 不许当通过；资格上降级 |
| `None` | 没声明且源码不是 Python（**无法确立**） | 同上，但理由不同 |

`coverage` 那一格是**第二条**信息：`ast` / `regex_only` / `none`。

**为什么 `cuda_c` 是「适用但更弱」而不是「不适用」**：这个仓的 `cuda_c` 是
PyTorch C++ Extension —— Python 文件里嵌 C++ 源码字符串，AST 只会看到一个 Constant
节点，所以**从一开始就只有文本模式可用**，而 `_GPU_DSL_RULES` 正是为此存在并且有用例钉着
（`A @ B`、`torch.matmul` 这些在 `cuda_c` 下必须被拦）。把「弱」与「没有」混在一起，
要么把能查的说成不能查（会让每一轮 `cuda_c` 都降级），要么把不能查的说成能查（原来的病）。

**声明是权威，推断只有一条**：语言声明了就按声明（不看源码）；没声明才做**一次**
`ast.parse` 推断，而且理由里写明「这是推断出来的」——「声明过」与「猜出来的」在后处理里
必须能分开。判据只在这一处：两个守卫都只消费结论，谁也不许再自己嗅一次 `def kernel`。

## 2. 三态一路走到资格层

| 层 | 干了什么 |
|---|---|
| L1（`_verify_compile`） | 判一次适用性，写进 `metrics["static_guards"]` / `["static_guards_lang"]`（成功、缓存命中、失败三条路都写）；不适用的那一档还会在 stdout 说一句 |
| L2（`_verify_function`） | 反作弊审计消费同一个判据；不适用时**不静默**（打印理由），违规列表照旧只表示真命中 |
| L3（`_verify_performance`） | 把适用性**发布**进自己的 metrics（`_assess_measurement` 是另一个方法，拿不到局部量 —— 与 `arm_device_labels`/`arm_windows` 同一写法）；`None` 不写键 |
| 收口点（`oracle.evaluate`） | `rule_inputs["static_guards"]` 三态进 provenance，并给一条 reason |
| 判据（`eligibility.derive_eligibility`） | **新规则 8**：明确的 `False` ⇒ `DEGRADED`（可判/可调/可报，**不持久化、不计进度**）；`None` ⇒ 不改判 |

规则 8 的位置很讲究：它排在规则 3/4/5（拒评）**之后**。「查不了」不比「测的是别的库」
更严重 —— 数字本身是真的，不足以支撑的只是**永久**结论（§4.3 的第二条设计意图：
低资格 ≠ 没测准）。

三态不是洁癖：`None` 表示**没观测**（老路径、直接调 `assess` 的单测），把它当 `False`
会让所有历史读数降级；把它当 `True` 就是原来的 fail-open。同族边界仓里已经有过三条
（`real_device=None`、`backend_caps=None`、`exclusive=None`），这条照抄它们的处置。

## 3. 适用性属于**那一份源码**，不是 Verifier 的状态

Verifier 一个实例会连着验多个候选（决赛候选只跑到 L2，胜者才补 L3）。所以适用性
**不许**存成实例字段 —— 那正是「记录说 A、判定按 B」那个坑。它由调用方按**这一份源码**
传下去：

```
verify()            内部把 L1 的 static_guards 传给 L3
verify_l3_only()    显式参数 static_guards=<胜者 L1 的 metrics 里那个值>
Conductor           从 selected_l1_l2 的 metrics 里读 (`source_lang.flag_from_metrics`)
重测（confirm）      从 artifact.verification_results 的各级 metrics 里读
```

`flag_from_metrics` 取最保守的一档：任一处 `False` ⇒ `False`；一条都没记 ⇒ `None`
（未观测，不是 `False`）。

## 4. 一个必须先修的坑：远端脚本

`remote_scripts/run_kernel.py` 把 `anticheat.py` **当顶层模块** `import anticheat`
（不是 `operator_agent.anticheat`），所以 `anticheat.py` 里不能直接写相对导入。
处置是仓里对这类文件的老写法：`try: from .source_lang import ... except ImportError:
from source_lang import ...`，并且 `_remote_files()` 里 `source_lang.py` 必须排在
`anticheat.py` **之前**（依赖排在读者前面 —— 半途失败只会得到「新依赖 + 旧 anticheat」，
能跑；反过来是「新 anticheat + 缺依赖」，每次远端调用都 ImportError）。

`AuditVerdict` 做成 `list` 的**子类**也是同一个考虑：这个返回值要跨进程（塞进 JSON）
也要被旧读法消费（`len`/切片/`== []`/`bool`），子类让这些读法一个字都不用改 ——
「查不了」是**新增**的一位，新读者读 `.applicable`。⚠️ 边界：`bool(verdict)` 只表示
「有违规」，**不**表示「查过」。

## 5. 变异矩阵（18 处，全红）

| # | 变异 | 结果 |
|---|---|---|
| M1 | 未声明的非 Python 读成明确不适用 | ✅ |
| M2 | 有声明但没规则的语言读成「无法确立」 | ✅ |
| M3 | `regex_only` 读成「没有覆盖」 | ✅ |
| M4 | 声明不再权威（一律看源码） | ✅ |
| M5 | 取最保守改成取任一 | ✅ |
| M6 | 没记也返回 `False` | ✅ |
| M7 | 删掉资格层那条规则 | ✅ |
| M8 | 未观测也降级 | ✅ |
| M9 | 三态收成 `bool`（字符串化 `false` 照收） | ✅ |
| M10 | 收口点不记 `rule_inputs` 里的适用性 | ✅ |
| M11 | L1 不再发布判定 | ✅ |
| M12 | L3 不把判定发布进 metrics | ✅ |
| M13 | L3 只读参数（不读发布值） | ✅ |
| M14 | `verify_l3_only` 不透传 | ✅ |
| M15 | 契约守卫对 `cuda_c` 声称适用 | ✅ |
| M16 | 找不到 `def kernel` 时声称适用 | ✅ |
| M17 | 不适用的语言仍用别家规则硬扫 | ✅ |
| M18 | 远端依赖排在读者之后 | ✅ |

M17 的第一版是**逃逸**：CUDA 样本里本来就没有禁用符号，「不适用就早退」与「拿别家规则
硬扫」在用例上不可区分。补了一条观察面（`// 这里不能用 torch.matmul(` 这样的 C++ 注释
在 `hip_c` 下不得被当违规）之后才红 —— 变异能活下来时先怀疑用例的覆盖面。

## 6. 边界（➖/⏳）

- ➖ **没有任何后端能执行非 Python 源**：`MockGPU`/`LocalExecutor` 都按 Python 执行，
  `L1` 的本地语法预检也只对 `cuda_c` 放行。所以「非 Python 模板源端到端跑起来」今天
  **无法观察** —— 这一片的三态只在静态层与资格层可见，端到端等价物要等真模板后端。
- ⏳ **`cuda_c` 的文本覆盖仍然看不穿宏与头文件**：`#include` 进来的东西、宏展开出来的
  调用，正则都看不见。这已经是那一族的上限（不是「暂时没接」），记在 `coverage` 里。
- ➖ **接口契约那道守卫对非 AST 语言恒不适用**：它要 `def kernel`。真正需要的是
  「C++ 入口签名」的定义（谁包一层、调用方怎么命名参数），今天没有。
- ➖ **降级的后果是「不进长期记忆、不计进度」**，不是拒绝。要不要让某些任务把它升成
  拒评，需要任务侧先说「我必须被静态守卫覆盖过」—— 那是 `required_caps` 那一族的一个
  新旋钮，今天没加（加了就要有人写它）。
- ➖ 真机未复跑（本机无 GPU）：这一片没有新的设备侧行为，但 `verify_l3_only` 的签名改了，
  真机路径的复跑列在 §15 的待办里。
