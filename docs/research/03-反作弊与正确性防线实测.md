# 反作弊与正确性防线实测：一个 `return A @ B` 的假核通过了全部三级验证

> 版本: v1.0 | 日期: 2026-09-25 | 设备: algorithm-h20 / NVIDIA H20（GPU 2，测时 0% util）
> 服务于缺口: **1**（测量有效性）、**6**（接口契约），并直接决定缺口 **2**（持久化）能否开工
> 严重性: **本项目目前已发现的最严重缺陷**。所有结论均为真机实测，非推测。

## 一、实验

构造一个「声称是 Triton 核、实际直接回退 cuBLAS」的候选：

```python
import torch


def kernel(A, B):
    # 声称是 triton 核, 实际直接回退到 cuBLAS
    return A @ B
```

以 `dsl="triton"`、`hardware="nvidia_gpu"`、`precision=FP16`、`min_speedup=0.8`、`max_error=5e-1`（**与 `test_nvidia_matmul.py` 完全相同的约束**）提交给 `Verifier`，后端是真机 SSH。

### 结果：三级全过

```
static_audit(triton) -> 无违规 (漏过)

L1_COMPILE       passed=True   编译验证通过
L2_FUNCTION      passed=True   功能验证通过 (1 组输入), 最大误差=0.00e+00
L3_PERFORMANCE   passed=True   加速比 1.00x vs cuBLAS(FP16) (同机同卡 median,
                               要求 >= 0.80x, compute-bound)
    speedup_vs_baseline = 1.0
    Roofline: compute (AI=1365.33, peak=138.2 TFLOPS fp16_tensor_core,
              GFLOPS利用率=95.3%, 带宽利用率=2.6%)
```

**注意这些数字有多"正常"**：1.00× vs cuBLAS、95.3% fp16 峰值、compute-bound 判定正确、L2 误差 0.00e+00。没有任何一处会让人起疑。这个产物会被 `ArtifactStore` 落盘、被 `conductor.py:923` 写进 `kernel_db`、并在后续运行中作为「历史高性能案例」被 RAG 检索出来喂给 Designer/Coder。

## 二、三个独立的洞，缺一不可地共同促成

### 洞 1：真机执行路径**完全没有**运行时反作弊 ✅

`grep -n "anticheat|shield|static_audit|CheatDetected" remote_scripts/run_kernel.py` → **零命中**。

`shield_torch` 的实际生效范围（✅ 全仓 grep）：

| 调用点 | 路径 | 是否真机 |
|---|---|---|
| `remote_executor.py:753` | `LocalExecutor.execute()` | ❌ 本地 CPU 回退 |
| `mock_gpu.py:206` | `MockGPU` | ❌ 模拟 |
| `mock_gpu.py:322` | `MockGPU` | ❌ 模拟 |
| — | `remote_scripts/run_kernel.py`（SSH 真机） | ✅ **无任何防护** |

**即：运行时屏蔽只覆盖了不产出可信性能数字的两条路径，唯一能产出真机 L3 数字的路径上它是缺的。**

### 洞 2：`static_audit` 的正则可被 8 种写法里的 5 种绕过（GPU DSL）✅

实测（✅ 本地直接调 `static_audit`；两个 DSL 的**返回值**相同，但「该不该拦」不同，见下方更正）：

| 用例 | triton | python |
|---|---|---|
| `torch.matmul(A,B)` ← 规则本意要拦 | 拦截 | 拦截 |
| **`A @ B`**（`__matmul__` 运算符） | **★漏过** | ⚠️ 不算漏过（见下方更正） |
| **`A.matmul(B)`**（方法形式） | **★漏过** | **★漏过** |
| **`from torch import matmul`** | **★漏过** | **★漏过** |
| **`getattr(torch, "mat"+"mul")`** | **★漏过** | **★漏过** |
| `import torch.nn.functional as Fn` + `Fn.softmax` | 拦截 | 拦截 |
| **`torch.nn.LayerNorm(...)` 模块** | **★漏过** | **★漏过** |
| `torch.einsum` | 拦截 | 拦截 |

原因是 `anticheat.py:26-35` 的规则全部要求 `torch.` / `F.` / `np.` 前缀 + 函数名 + `(`：

```
_TORCH_COMPUTE  = r"\btorch\s*\.\s*(matmul|mm|bmm|...)\s*\("
_F_COMPUTE      = r"\bF\s*\.\s*(softmax|...)\s*\("
_NUMPY_COMPUTE  = r"\b(?:np|numpy)\s*\.\s*(matmul|dot|...)\s*\("
```

于是 `A @ B`、`A.matmul(B)`、`from torch import matmul`、`torch.nn.LayerNorm` 全不在射程内。（`Fn.softmax` 被拦是**巧合**——命中的是 `_TORCH_FUNCTIONAL` 对 import 语句本身的匹配，不是对调用的匹配。）

**最要命的是 `A @ B`**：它是 PyTorch 里写矩阵乘最自然的形态。不需要恶意，一个 LLM 在 Triton 路径上遇挫后「退一步用 torch 兜底」时最可能写出的就是它。

> **更正（2026-09-25，写 `tests/test_anticheat_bypass.py` 时自查发现）**
>
> 上表原先把 `A @ B` 在 python 列也标成「★漏过」，**这个判断是错的**——虽然实测事实（`static_audit(code, "python") == []`）没错，错的是把它当成缺陷。
>
> `anticheat.py` 的模块 docstring 明确写着 python DSL 下「NumPy 是实现介质所以允许」，而对 numpy 数组来说 `A @ B` 就是合法的矩阵乘写法。本仓自己的 `tests/test_p0_3.py::PYTHON_MATMUL` 正是 `return A @ B`，它是**正样本**，不是作弊。若为拦 torch 的 `A @ B` 而把 `@` 运算符一律禁掉，会直接打死 python DSL 这条路径。
>
> 所以 `A @ B` 只在 **GPU DSL（triton/cuda_c）** 下算漏过——那里没有任何理由用 `@`，出现即意味着 torch 回退。上面「最要命」的结论仍然成立，但要限定到 GPU DSL 路径：那恰好也是洞 1（`run_kernel.py` 无 `shield_torch`）所在的路径，两个洞叠加。
>
> 其余 4 个漏过用例（`.matmul()` 方法形式、`from torch import matmul`、`getattr` 拼接、`torch.nn.LayerNorm`）语义明确指向 torch，**两个 DSL 下都该拦**，原判断不变。
>
> 测试已按此拆分：`BYPASSED_GPU_DSL_ONLY`（1 例）与 `BYPASSED_BOTH_DSL`（4 例），并加了反向保护用例 `test_python_dsl_allows_numpy_at_operator`，确保将来收紧规则时不会误伤 python DSL。

### 洞 3：L2 数值门是敞开的 ✅

详见 [`00-架构基线与缺口核实.md`](00-架构基线与缺口核实.md) 第一节。`run_kernel.py` 算了 `max_rel_error` 但判定只用 `max_abs_error <= max_error`，driver 传 `5e-1`。本实验中 L2 报 `0.00e+00` 是因为它**就是**参考实现本身。

## 三、为什么这个组合特别危险

单独的洞都不致命：

- 只有洞 3（阈值松）→ 作弊核仍会被 `static_audit` 拦下。
- 只有洞 2（正则可绕）→ 运行时 `shield_torch` 会在执行时抛 `CheatDetectedError`。
- 只有洞 1（真机无 shield）→ 静态审计仍会拦下 `torch.matmul(...)` 这类直白写法。

**三个洞同时存在，且真机路径上洞 1 与洞 2 叠加、洞 3 兜底失效**，结果是：最自然的那一种作弊写法（`A @ B`）在真机上畅通无阻，并且产出一个**看起来完全合理**的 1.00×。

作弊产出「合理数字」而非「荒谬数字」，是它比 Sakana 那种 17000× 更难发现的原因——荒谬数字会引人怀疑，1.00× vs cuBLAS 只会让人以为「这轮生成得不错」。

## 四、与外部证据的吻合

⚠️ 以下引自 [`11-kernel生成系统全景.md`](11-kernel生成系统全景.md)：

- **NVIDIA SOL-ExecBench** [2603.19173](https://arxiv.org/abs/2603.19173)：其 agentic baseline 的提交中有 **14.5%** 被判 reward hacking，并规定 `T_k < T_SOL` 直接触发审计。
- **AKO** [主页](https://tongminglaic.github.io/AKO/)：记录了两类真实陷阱——CUDA-graph capture 时跑一次、replay 静默跳过；指针键控 cache。对策是**独立 staleness 审计：固定张量指针、只改数值，输出不变即拒**。并强调 anti-cheat 必须跑在 **agent 不可修改面之外**。
- **Sakana AI CUDA Engineer**：原宣称 10–100×，去污染后 1.49×；自方论文 [2509.14279](https://arxiv.org/abs/2509.14279) 承认 "existing kernel benchmarks suffer from exploitable loopholes"。
- ⚠️ 需注意 [`11`](11-kernel生成系统全景.md) 第五节的更正：「o3-mini-high 11 秒发现快 150 倍实为慢 3 倍」这一具体情节**只见于中文二手转述**，一手仅能证实「存在 evaluation code 内存漏洞导致跳过正确性检查」。

**本实验是这些外部教训在本项目上的一次本地复现**，且用的是本项目自己的 driver 参数。它不是假设风险。

对照 AKO 那条「anti-cheat 必须在 agent 不可修改面之外」：我方 `static_audit` 在控制端（`verifier.py:131`，✅ 位置正确，生成代码改不到），但 `shield_torch` 本该在远端 runner 内，而那里**根本没有**。

## 五、修复方案（按代价排序）

### 5.1 立刻可做（代价极小，收益最大）

**(a) 给 `static_audit` 补运算符与方法形式规则。** 至少覆盖：

- `@` 运算符：对 `dsl != "python"` 的核，代码中出现 `@` 且不在装饰器位置（即不是行首 `@xxx`）即可疑。更稳的做法是走 AST 而非正则：`ast.BinOp(op=ast.MatMult)`。
- 方法形式：`\.matmul\s*\(`、`\.mm\s*\(`、`\.bmm\s*\(`、`\.softmax\s*\(`、`\.einsum\s*\(`（不要求 `torch.` 前缀）。
- `from torch import <compute_fn>` 形态。
- `torch.nn.<Module>` 实例化（`LayerNorm`/`BatchNorm`/`Linear`/`Softmax`/`MultiheadAttention`）。
- `getattr(` 配合字符串拼接——AST 层可检测 `getattr` 调用本身并标记为需人工复核。

**建议直接改用 AST 遍历而非堆正则。** 当前 4 条正则已经证明拦不住自然写法；继续加正则是军备竞赛，AST 是一次性把「调用了什么」看清楚。项目已用 `ast` 于 `DependencyAnalyzer`（P1-3），无新依赖。

**(b) 把 `shield_torch` 移进 `remote_scripts/run_kernel.py`。** 这是洞 1 的直接修复，且 `anticheat.py` 是纯 stdlib（`re` + `contextlib`），可以随 runner 一起部署到远端，无新依赖。

> ⚠️ 注意 `shield_torch` 当前对昇腾/寒武纪等白名单硬件是**放行**的（`anticheat.py:74-90`，理由是那些平台只能靠 `torch.matmul` 激活厂商 Tensor Core）。移植到 runner 时必须把 hardware 一并传下去，否则会误伤后续要接入的平台。

### 5.2 应尽快做（代价小）

**(c) L1 增加「DSL 一致性」检查。** 声明 `dsl="triton"` 的核，代码里必须出现 `import triton` 与至少一个 `@triton.jit`；否则 L1 直接失败。本实验的假核**一行 Triton 都没有却通过了 L1**——这是最便宜的一道拦截，且完全不需要远端往返。

这一条同时是缺口 6（接口契约隐式）的一部分：L1 目前只查 `hasattr(module, "kernel")`（`run_kernel.py:201`/`237`），应扩展为「入口存在 + 签名匹配 + DSL 一致」。

**(d) L2 改判相对误差。** `max_rel_error` 已经在算了，接进判定即可。分精度阈值（fp16 建议 rtol ~2e-2 量级，需按 [`12`](README.md) 号调研的外部取值再定）。

**(e) staleness 审计。** 固定张量指针、只改数值，验输出必须变化。约 50 行，能拦住「缓存复用 / 返回常量 / CUDA-graph replay 跳过」这一整类。

### 5.3 结构性（代价中）

**(f) 多组输入 + 必含边界 shape。** `Verifier` 已支持 `list[dict]` 套件（P0-2 时加的），但三个 driver 都只传单组。⚠️ [2606.20128](https://arxiv.org/abs/2606.20128) 的消融显示：**去掉边界 shape，shape 相关 bug 召回率归零**。建议每个任务至少 5 组，含非对齐与退化维（如 `H∈{1,3,7,256,1025}`）。

## 六、对缺口 2 的阻塞关系

**在 5.1(a)(b) 与 5.2(c) 落地之前，不应开工缺口 2（持久化）。**

理由：本实验产出的那条记录，一旦 `kernel_db` 有了持久化，就会被写成一条 `dsl=triton / hardware=nvidia_gpu / performance=1.00x cuBLAS / all_passed=True` 的**金标记录**，并在后续每次运行中被检索出来注入 Designer/Coder 的 prompt。

那等于把「直接调 cuBLAS」作为成功范例教给模型，且**越积累越糟**。这正是 [`13`](13-跨运行记忆与技能库架构.md) 引用的 MemGuard 所说的 unreliable admission，也是 [`10`](10-DeepSeekHarness与插件化agent运行时.md) 第三节 postmortem 0002 的同一失效模式（把回归固化成期望值）。

**修正后的实施顺序**：

```
5.1(a) AST 反作弊  ─┐
5.1(b) shield 进 runner ─┼─> 5.2(c) L1 DSL 一致性 ─> 缺口 1 (测量有效性三态) ─> 缺口 2 (持久化)
5.2(d) 相对误差门  ─┘
```

即：**正确性防线必须先于持久化**。这与 [`00`](00-架构基线与缺口核实.md) 第四节的排序（1 → 3 → 2 → 4 → 6 → 5）不冲突，但把「反作弊加固」提到了缺口 1 之前——因为它更便宜，且它是缺口 2 的硬前提。
