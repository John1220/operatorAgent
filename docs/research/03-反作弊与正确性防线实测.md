# 反作弊与正确性防线实测：一个 `return A @ B` 的假核通过了全部三级验证

> 版本: v1.0 | 日期: 2026-09-25 | 设备: algorithm-h20 / NVIDIA H20（GPU 2，测时 0% util）
> 服务于缺口: **1**（测量有效性）、**6**（接口契约），并直接决定缺口 **2**（持久化）能否开工
> 严重性: **本项目目前已发现的最严重缺陷**。所有结论均为真机实测，非推测。

## 一、实验

构造一个「声称是 Triton 核、实际直接回退 cuBLAS」的候选：

```python
import torch


def kernel(A, B):
    # 声称是 triton 核, 实际直接回退到 cuBLAS
    return A @ B
```

以 `dsl="triton"`、`hardware="nvidia_gpu"`、`precision=FP16`、`min_speedup=0.8`、`max_error=5e-1`（**与 `test_nvidia_matmul.py` 完全相同的约束**）提交给 `Verifier`，后端是真机 SSH。

### 洞 2：`static_audit` 的正则可被 8 种写法里的 5 种绕过（GPU DSL）✅

实测（✅ 本地直接调 `static_audit`；两个 DSL 的**返回值**相同，但「该不该拦」不同，见下方更正）：

| 用例 | triton | python |
|---|---|---|
| `torch.matmul(A,B)` ← 规则本意要拦 | 拦截 | 拦截 |
| **`A @ B`**（`__matmul__` 运算符） | **★漏过** | ⚠️ 不算漏过（见下方更正） |
| **`A.matmul(B)`**（方法形式） | **★漏过** | **★漏过** |
| **`from torch import matmul`** | **★漏过** | **★漏过** |
| **`getattr(torch, "mat"+"mul")`** | **★漏过** | **★漏过** |
| `import torch.nn.functional as Fn` + `Fn.softmax` | 拦截 | 拦截 |
| **`torch.nn.LayerNorm(...)` 模块** | **★漏过** | **★漏过** |
| `torch.einsum` | 拦截 | 拦截 |

原因是 `anticheat.py:26-35` 的规则全部要求 `torch.` / `F.` / `np.` 前缀 + 函数名 + `(`：

```
_TORCH_COMPUTE  = r"\btorch\s*\.\s*(matmul|mm|bmm|...)\s*\("
_F_COMPUTE      = r"\bF\s*\.\s*(softmax|...)\s*\("
_NUMPY_COMPUTE  = r"\b(?:np|numpy)\s*\.\s*(matmul|dot|...)\s*\("
```

于是 `A @ B`、`A.matmul(B)`、`from torch import matmul`、`torch.nn.LayerNorm` 全不在射程内。（`Fn.softmax` 被拦是**巧合**——命中的是 `_TORCH_FUNCTIONAL` 对 import 语句本身的匹配，不是对调用的匹配。）

**最要命的是 `A @ B`**：它是 PyTorch 里写矩阵乘最自然的形态。不需要恶意，一个 LLM 在 Triton 路径上遇挫后「退一步用 torch 兜底」时最可能写出的就是它。

> **更正（2026-09-25，写 `tests/test_anticheat_bypass.py` 时自查发现）**
>
> 上表原先把 `A @ B` 在 python 列也标成「★漏过」，**这个判断是错的**——虽然实测事实（`static_audit(code, "python") == []`）没错，错的是把它当成缺陷。
>
> `anticheat.py` 的模块 docstring 明确写着 python DSL 下「NumPy 是实现介质所以允许」，而对 numpy 数组来说 `A @ B` 就是合法的矩阵乘写法。本仓自己的 `tests/test_p0_3.py::PYTHON_MATMUL` 正是 `return A @ B`，它是**正样本**，不是作弊。若为拦 torch 的 `A @ B` 而把 `@` 运算符一律禁掉，会直接打死 python DSL 这条路径。
>
> 所以 `A @ B` 只在 **GPU DSL（triton/cuda_c）** 下算漏过——那里没有任何理由用 `@`，出现即意味着 torch 回退。上面「最要命」的结论仍然成立，但要限定到 GPU DSL 路径：那恰好也是洞 1（`run_kernel.py` 无 `shield_torch`）所在的路径，两个洞叠加。
>
> 其余 4 个漏过用例（`.matmul()` 方法形式、`from torch import matmul`、`getattr` 拼接、`torch.nn.LayerNorm`）语义明确指向 torch，**两个 DSL 下都该拦**，原判断不变。
>
> 测试已按此拆分：`BYPASSED_GPU_DSL_ONLY`（1 例）与 `BYPASSED_BOTH_DSL`（4 例），并加了反向保护用例 `test_python_dsl_allows_numpy_at_operator`，确保将来收紧规则时不会误伤 python DSL。

### 洞 3：L2 数值门是敞开的 ✅

详见 [`00-架构基线与缺口核实.md`](00-架构基线与缺口核实.md) 第一节。`run_kernel.py` 算了 `max_rel_error` 但判定只用 `max_abs_error <= max_error`，driver 传 `5e-1`。本实验中 L2 报 `0.00e+00` 是因为它**就是**参考实现本身。

## 三、为什么这个组合特别危险

单独的洞都不致命：

- 只有洞 3（阈值松）→ 作弊核仍会被 `static_audit` 拦下。
- 只有洞 2（正则可绕）→ 运行时 `shield_torch` 会在执行时抛 `CheatDetectedError`。
- 只有洞 1（真机无 shield）→ 静态审计仍会拦下 `torch.matmul(...)` 这类直白写法。

**三个洞同时存在，且真机路径上洞 1 与洞 2 叠加、洞 3 兜底失效**，结果是：最自然的那一种作弊写法（`A @ B`）在真机上畅通无阻，并且产出一个**看起来完全合理**的 1.00×。

作弊产出「合理数字」而非「荒谬数字」，是它比 Sakana 那种 17000× 更难发现的原因——荒谬数字会引人怀疑，1.00× vs cuBLAS 只会让人以为「这轮生成得不错」。

## 六、对缺口 2 的阻塞关系

**在 5.1(a)(b) 与 5.2(c) 落地之前，不应开工缺口 2（持久化）。**

理由：本实验产出的那条记录，一旦 `kernel_db` 有了持久化，就会被写成一条 `dsl=triton / hardware=nvidia_gpu / performance=1.00x cuBLAS / all_passed=True` 的**金标记录**，并在后续每次运行中被检索出来注入 Designer/Coder 的 prompt。

那等于把「直接调 cuBLAS」作为成功范例教给模型，且**越积累越糟**。这正是 [`13`](13-跨运行记忆与技能库架构.md) 引用的 MemGuard 所说的 unreliable admission，也是 [`10`](10-DeepSeekHarness与插件化agent运行时.md) 第三节 postmortem 0002 的同一失效模式（把回归固化成期望值）。

**修正后的实施顺序**：

```
5.1(a) AST 反作弊  ─┐
5.1(b) shield 进 runner ─┼─> 5.2(c) L1 DSL 一致性 ─> 缺口 1 (测量有效性三态) ─> 缺口 2 (持久化)
5.2(d) 相对误差门  ─┘
```

即：**正确性防线必须先于持久化**。这与 [`00`](00-架构基线与缺口核实.md) 第四节的排序（1 → 3 → 2 → 4 → 6 → 5）不冲突，但把「反作弊加固」提到了缺口 1 之前——因为它更便宜，且它是缺口 2 的硬前提。
