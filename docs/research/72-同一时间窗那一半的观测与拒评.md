# 「同一时间窗」那一半：窗口观测、拒评，以及两个被它照出来的形状（CHECKLOG I60）

设计 §11-2 的原话：

> 一个候选的基线必须租到**同一张卡、同一时间窗**。**A 卡基线 vs B 卡候选的"加速比"
> 直接作废** —— 多卡下最容易犯、也最难发现的错。

这句话在代码里是 `placement.pairing_conflict(cand_dev, base_dev, cand_win, base_win)`，
四条判据**早就都在**（spine-review P3-16 把它从测试文件搬进了库里）。设备那半此后接上了
观测喂给者（doc 63，CHECKLOG I47）；**窗口那半一直没有**，于是：

1. `pairing_conflict` 的窗口比较要求两侧都非 `None` —— 而生产上 `baseline_window` 恒为
   `None` ⇒ **这道比较从未执行过**；
2. 更隐蔽的一层：oracle 里那道配对检查整体挂在
   `if candidate_device is not None or baseline_device is not None:` 上 —— 也就是说，
   **一个观测的缺席会掐掉另一个观测的判决**。哪天 runner 报了窗口却没报逐臂身份，
   窗口那道比较仍然不会被执行，而日志里看不出任何区别；
3. `candidate_window` 这个参数当时被喂的是**心跳窗口 id**（`heartbeat.window_id`），
   与「测量窗」不是一回事。它今天是**惰性的**（因为 `baseline_window` 是 None），但
   一旦两侧都变成真观测，这两种窗混用就会让心跳那一段判成「别窗读数」。

本文记的是这三条一起修掉的过程，以及修的时候被照出来的另外两个形状。

## 1. 生产者：一扇窗，两臂各自带回自己的那一扇

`remote_scripts/run_kernel.py` 的 `_bench_pair_interleaved` 是**唯一**把两臂放在同一扇
时间窗里的地方（按块交错 + 每块一次 setattr 群，见该函数 docstring 里的真机数据）。
所以窗口 id 在那里生成，并且**由两臂各自的样本带回**：

```python
window_id = _new_window_id()          # 一扇窗 = 一次交错调用
...
paired = {"paired_runs": ..., "paired_block_samples": block,
          "arm_windows": {"candidate": window_id, "baseline": window_id}, ...}
```

几个刻意的选择：

| 选择 | 为什么 |
|---|---|
| id 用 `uuid4().hex[:12]` 而不是全局计数器 | 常驻 runner 里两次调用要在同一进程内可区分；计数器还会**跨进程撞名**，而撞名 = 把跨窗读成同窗，正是这道检查要抓的反面 |
| 落在 `paired` 而不是塞进逐臂 `stats` | `stats` 是样本统计的容器；窗口是**配对属性**。塞进去会让「哪一臂的窗」与「这一臂的时间」混成一个 dict |
| **不加**第四个返回值 | `benchmarks/probe_block_series.py` 按三元解包这个函数，改元数会静默打断那个探针（这条约定是上一轮 probe 工作时留下的） |

两臂在这里同值是**结论**（同一次交错调用），不是空转：观测是**每臂产出的**，一旦哪条臂
的样本被复用/短路（缓存），带回来的就是旧窗。用例不 mock 计时 —— 它真的在 CPU 路径上
调一次 `_bench_pair_interleaved`（`device_is_cuda=False`），并断言**两次调用拿到不同的窗**
（否则常量也能让「同窗」恒真）。

## 2. 三态、进入条件、拒评

控制端 `placement.observed_windows(cand, base)` 与 `observed_pairing` 同形：**缺观测返回
`None`**（`""` 会造成一次恒真的比较），三态 `same_window` / `cross_window_refused` /
`unobserved` 写死在**一个函数**里。

oracle 侧两处改动：

```python
# 进入条件: 两个观测各自成立 —— 不能挂在设备那一项上
if (candidate_device is not None or baseline_device is not None
        or pair_candidate_window is not None or pair_baseline_window is not None):
    pair_why = pairing_conflict(candidate_device, baseline_device,
                                pair_candidate_window, pair_baseline_window)
```

- 观测到**不同窗** ⇒ `reasons=["pairing_conflict"]`、资格全 False、`value=None`，
  provenance 里两个窗口都落盘（拒评理由必须能复核）；
- 观测到**同窗** ⇒ 这道检查放行（有条目为证）；
- **没观测** ⇒ `unobserved`，不声称同窗也**不拒评** —— 与设备那半同一边界
  （老 payload / 本地路径）。「没观测到」不等于「观测到不同」。

verifier 侧与跨卡对称：`if _win_scope == WINDOW_DIFFERENT: passed = False`（跨窗的加速比
同样**没有指称对象**，所以「通过」这个结论也不许立）。发布两个**分开的**键
（`arm_windows` / `measurement_window_scope`）：一个是「在哪张卡上」，一个是「在哪扇窗里」，
合成一个 scope 串会让「同卡但跨窗」两种解释都说得通。

## 3. 测量窗与心跳窗：两组参数，不是一回事

oracle 现在收两组窗口，并且名字上就不能互换：

| 参数 | 回答的问题 | 出处 |
|---|---|---|
| `candidate_window` | 这条读数**属于哪一扇心跳窗**（§13.5 的尺子范围） | Conductor 的 `heartbeat.window_id` |
| `pair_candidate_window` / `pair_baseline_window` | 两臂是不是在**同一次测量调用**里量的（§11-2 配对） | runner 的 `paired["arm_windows"]` |

混成一个参数的两种失效都看不出来：**恒真**（把心跳窗抄给两侧）或**恒假**（心跳窗 ≠ 测量窗
⇒ 心跳被判成别窗读数 ⇒ 该窗口的尺子状态变成未知）。用例刻意让两者取不同的值来钉这条。

## 4. 被照出来的第一个形状：写了却读不到

窗口喂给者接上后，第一版在 oracle 调用处用了 `_cand_win`（`_verify_performance` 的局部量）
—— 而那段 oracle 代码在 `_assess_measurement` 里，**另一个方法**。报错没有炸出来，因为
那里有一层 `except Exception` 把观测失败留痕吞成 `metrics["observation_error"]`：

```
observation_error = NameError: name '_cand_win' is not defined
```

这正是「生产者写了、判决读不到」那一族：守卫没坏、数字也还在，只是**收口点那一轮没跑**，
资格停在 fail-closed 的 all-False 上（所以不会放行），但**拒评理由永远不出现**。
修法与设备那半一致：从**产物里记的那一份**读（`metrics["arm_windows"]`），而不是拿
另一个方法的局部量。留痕这一层是有价值的 —— 它让这次失败变成一行可查的证据。

## 5. 被照出来的第二个形状：控制端的缓存基线是跨窗的

`_measure_baseline` 按 `(算子, 输入签名)` 缓存（`self._baseline_cache`）。非远程路径上，
**第二轮 L3 用的就是第一轮量的基线** —— 按 §11-2 的字面意思，这是「候选与基线不在同一
时间窗」。它今天**不作判决**，理由是明写的：

1. 这条臂是**控制端参照臂**（`_build_reference_fn`，torch eager / NumPy），不是设备租约臂
   —— §11-2 说的是设备上的两臂；
2. 复用是**声明的**优化（省一次 baseline 的墙钟），不是漏掉的检查；
3. 但在真卡上以 `mode="local"` 跑时，这条基线确实可能是**这轮之前的**读数。

所以处理是「诚实记录、不作判决」：产物里 `baseline_reused`（观测，不是档位），L3 消息里
明写「⏳ 基线复用本轮之前的测量 (跨窗, §11-2 的窗口前提不成立)」。**它从此不再是沉默的**。

顺带一提，`tests/test_p0_3.py::TestBaselineCache` 原先用 `assertIs(b1, b2)`（同一对象）
当「命中缓存」的代理。这条代理正是让跨窗复用一直沉默的东西（同一性是实现细节）。用例改成
断言**可观测的事实**：`b1["baseline_reused"] is False`、`b2["baseline_reused"] is True`、
且两次的时间值相同（复用同一次测量，不是重测）。这不是放宽 —— 它比同一性更直接地钉住了
「没有第二次测量」这个性质。

## 6. 变异矩阵（11 处，全红）

| # | 变异 | 期望 | 结果 |
|---|---|---|---|
| M1 | 缺观测返回 `""`（恒真比较） | 红线 | ✅ |
| M2 | 不同窗也当成同窗 | 红线 | ✅ |
| M3 | oracle 拿心跳窗比测量窗 | 红线 | ✅ |
| M4 | 进入条件挂回设备那一项 | 红线 | ✅ |
| M5 | 跨窗不改写 `passed` | 红线 | ✅ |
| M6 | runner 不给两臂盖窗口 | 红线 | ✅ |
| M7 | runner 的窗口 id 是常量 | 红线 | ✅ |
| M8 | 复用缓存时不再标记 | 红线 | ✅ |
| M9 | 消息里不写跨窗 | 红线 | ✅ |
| M10 | 产物里不发布 `baseline_reused` | 红线 | ✅ |

M7 是「观测是不是真的每扇窗不同」的钉：常量 id 会让这道比较永远为真。

## 7. 明写没做到 / 仍然是纸面的

1. **真机未复跑**：本机无 GPU。证据是离线用例（含一次真的 `_bench_pair_interleaved` CPU
   调用、一次真的 `Conductor.execute`）+ 11 处变异。
2. **远端路径上「同窗」今天由构造保证**：一次配对调用里两臂必然同窗，所以真实的
   `cross_window_refused` 今天**不可能**在真机上出现。拒绝路径是活的（fakes 用例 +
   M2/M3/M4/M5 证明），但「它会响」这件事还没有真机证据 —— 它保护的是将来某一天
   基线被缓存/短路。
3. **`pairing_conflict` 的窗口判据仍然只在两侧都非 None 时比**：这是刻意的边界
   （`unobserved` 不拒评），代价是「旧 runner 不报窗口」这件事看不出来 —— 只有
   `measurement_window_scope="unobserved"` 这一格。
4. **控制端复用的判决化**（例如把跨窗复用降为 DEGRADED）**没做**：本地路径的参照臂不是
   设备臂，一旦降级，多轮 mock 的每一轮都会带一个 DEGRADED —— 那是「把噪声当信号」。
   要做也应当先有「真机 `mode="local"` 多轮」的实测分布。
5. **多卡并行**（§11-1）与 **`interference_domain`** 依旧没有生产喂给者（doc 71 §4）。
