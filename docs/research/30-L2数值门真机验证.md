| 场景 | 改造前（纯 atol，`max_error=5e-1`） | 改造后（AND 形式 + 分档容差） |

**doc 12 预测的缺陷在真机上被复现，修复后被关闭，且没有误杀正确核。**

## 二、doc 12 留下的未决问题：参考自身准不准

doc 12 第五节标了一条 ⚠️ 未核实：如果 `allow_fp16_reduced_precision_reduction` 为 True，我们的 cuBLAS 参考自身就是降精度归约的，那么「候选与参考之差」里有一部分是参考的误差，容差表就不能照抄 KernelBench 的 1e-2。

**现已一手核实**（H20 上直接读 `torch.backends`）✅：

```
matmul.allow_tf32                        = False
cudnn.allow_tf32                         = True      ← 不对称确实存在
matmul.allow_fp16_reduced_precision_red  = True      ← 参考确实走降精度归约
matmul.allow_bf16_reduced_precision_red  = True
```

于是量了参考离真值有多远（4096³ fp16，输入 `standard_normal × 0.1`，与 runner 的 `_deserialize_inputs` 同配方）✅：

| 比较 | max_abs | max_rel | 结论 |
|---|---|---|---|
| **[A]** cuBLAS fp16 参考 vs fp32 累加真值 | `9.91e-04` | `7.47e+01` | 参考确实有误差，但只有 ~1e-3 量级 |
| **[B]** 正确的 fp32 累加候选 vs 我们的参考 | `1.95e-03` | `2.40e+01` | **门禁实际看到的量级** |
| **[C]** 0.97 缩放核 vs 参考 | `9.96e-02` | `5.82e-02` | 比 [B] 大 51 倍 |
| **[D]** 0.999 缩放核 vs 参考 | `3.91e-03` | `2.00e-03` | 与 [B] 同量级 |

`cudnn.allow_tf32=True` 与 `matmul.allow_tf32=False` 的不对称在本项目里**暂时无害**：`_reference_torch` 只用 `A @ B`（走 matmul，TF32 关）和 `F.softmax` / `F.layer_norm`（走 cudnn 的路径不涉及 TF32 矩阵乘）。但如果将来加入 conv 类参考实现，这个不对称会让参考悄悄降到 10-bit 尾数，误差来自参考而非候选 —— 记录在此备查。

**[B] 的 max_rel = 2.40e+01 再次印证 AND 形式是必需的**：正确的核在近零参考处的相对误差就有 24 倍。若按直觉把 `max_rel_error <= rtol` 加进门禁，每个正确核都会被判死。

## 三、容差表标定结论

fp16 档取 `atol = rtol = 1e-2`（照 KernelBench v1 `eval.py:93-99`）。实测余量：

- 真机 Triton fp16 matmul（fp32 累加器）对 cuBLAS 参考的误差是 **`max_abs = 0.0`** —— 逐元素完全相等。1024³ 与 4096³ 都是 0。
- 也就是说 `atol=1e-2` 对这个组合**保守了约 4 个数量级**；即使被 `ConstraintSpec.max_error` 默认值 1e-5 压到 `atol=1e-5`，正确核依然 `matched_ratio=1.000000` 通过（实测 ✅）。

**结论：容差表可以直接上线，不需要为 fp16 matmul 放宽。** 但要注意这只覆盖了 matmul 一种算子；softmax / layernorm / attention 的参考与候选走的是不同数值路径，余量需要在各自任务上重新量。`rho=1.0` 暂时够用（实测坏点数恒为 0），如果将来某个算子出现少量离群点，先量清楚是算子本身的问题还是参考的问题，再决定是否把 `rho` 降到 0.999，不要一上来就放宽。

一个反直觉的实测事实，已写进测试钉住 ✅：**MockGPU 不是标定 fp16 容差的合适代理**。同一个逐元素相等的核，MockGPU 在 FP16 档下报出 `max_abs=1.33e-2`、1.9% 坏点、`matched_ratio=0.981`（会判失败），因为它把输入降成 float16 后用 numpy 的 fp16 累加算，而真机 `tl.dot` 用 fp32 累加器。拿 MockGPU 的数字去调容差表会得到一个只对 MockGPU 成立的值。

## 四、部署链路验证 ✅

`SSHExecutor.deploy()` 改成按清单推送、逐文件比对 hash。实测输出：

```
[SSHExecutor] 脚本已部署到 algorithm-h20:~/operator_agent/tolerance.py (hash=838ab3fa9a1d)
[SSHExecutor] 脚本已更新到 algorithm-h20:~/operator_agent/run_kernel.py (hash=6e1a429e4ad8)
```

依赖先于 runner 到位（顺序由 `_remote_files()` 保证并有测试钉住），中途失败只会留下「新依赖 + 旧 runner」而不是「新 runner + 缺依赖」。第二次运行报 `远程脚本已是最新`，证明 hash 短路生效。

顺带修掉一个既有缺陷：原先远端 hash 查询用 python 的 `open()` 读 `~/operator_agent/run_kernel.py`，而 `open()` 不展开 `~`（shell 与 scp 会），所以查询**恒定失败**、每个任务都白推一次脚本。补 `os.path.expanduser` 后才真正短路。

## 五、验证过程中新发现的一个缺陷（未修）

`test_nvidia_*.py` 三个 driver 传给 Conductor 的是 `RemoteExecutor` 门面，而门面**没有** `ensure_environment`：

```
RemoteExecutor.ensure_environment 存在? False
RemoteExecutor.deploy 存在?         False
SSHExecutor.ensure_environment?     True
```

`conductor.py:233` 的守卫是 `if hasattr(self.backend, "ensure_environment"):` —— 对门面恒为 False，于是**「任务开始前的环境自检」在真机路径上从来没有跑过**。而 `docs/问题识别与技术方案.md` 的 P1-3 把这一条标为 ✅ 已实施（"任务开始前 `SSHExecutor.ensure_environment` 全链路检查 ssh→uv→python→torch→triton→cuda→gpu，失败提前返回"）。

这是**缺口 5（后端 isinstance 分派）**的一个具体后果：门面与实现的接口不一致，而 duck-typing 守卫在缺失时静默跳过而不是报错。同类问题还有 `verifier.py:73` 的 `self._is_remote = isinstance(backend, RemoteExecutor)`。

处置：单独一个提交修（给门面补 `ensure_environment` / `deploy` 委托），不混进本次数值门改造。
