## 一、为什么非要真机

设计文档第 30 行自己立了一道门：

> 真机 §14 冒烟之前，不对外说资格审计带来收益。

这道门是必要的原因是：§14 那八条问的**不是**「资格审计的代码对不对」（那是离线的活），
而是「真机上这一刻的读数有没有被正确地判成不可用」。两者之间隔着一整条链路
（远端 runner → 载荷 → verifier 的收口点 → 发布出去的 `metrics` → 入库判据），
而**这条链路上每转一次手，就有一个「算了但没接上」的机会** —— 本仓已经登记过三回
（I45 判据零调用者、P1-4 声明了没人派发、doc 61 的标量输入被重新生成）。

这一趟证明那道门是值钱的：八条里有两条 ❌ 都**不是**代码逻辑错，而是**接错了地方**。

## 二、方法：全部走生产链路

上一版的冒烟脚本有个致命形状：它自己拼 `metrics` 再喂给 `oracle.evaluate(...)`
（自己写 `validity="valid"`）。那正是 `397d87b` 消掉的那个毛病的同族 ——
「测的判据」与「用的判据」不是同一个。这一版重写的判据只有一条：

> 所有资格结论都取自 `Verifier._verify_performance(...)` **真实产出的** `metrics`，
> 脚本不许自己造 `Observation`、不许自己写 `eligibility`。

重写时顺带发现旧版还有两条更安静的问题（都实测了，见 §4.3）：三个核全是 numpy
⇒ 在远端 **CPU** 上量的（doc 61 §二② 已经记过这条），而干扰器也用 numpy
⇒ 它占的是 CPU 核，不是卡 —— 于是「造出了竞争」那一臂量的是安静窗口。

## 四、抓出来的两个真源

### 4.1 F1 · 发布的资格位不是收口点算的那份（资格审计在真机上**没生效**）

**原话**：设计 §14.8 表格第 8 行 —— 「关掉心跳 | 该窗口观测全部不可用，**不写记忆**」。

**实证**（`run1.log`，改动前）：同一次测量写出的 `metrics` 里并排出现

    ruler_broken=True   reason='RULER_BROKEN: 标定心跳到期, 但本次没有参照读数'
    eligibility={'can_verdict': True, 'can_tune': True, 'can_persist': True,
                 'can_report': True, 'can_count_progress': True}

尺子自己说这窗口坏了，资格位却说这位读数可以入库 —— 而入库判据读的正是后者。

**根因**：`_assess_measurement` 里有**两份资格推导**。先一份是它自己调的
`derive_eligibility(validity=..., real_device=..., lib_fallback=..., cv_exceeded=...,
launch_dominance_exceeded=..., partition_drift=...)` —— 这份**读不到心跳窗口**，
被写进了 `metrics["eligibility"]`；随后 oracle 收口点又算一份（输入是同一组 + 心跳），
只写进 `metrics["observation"]["eligibility"]`。两份在「坏窗口」这一格上必然分叉。

**为什么第一趟没写进语料**：只是**另一道门**偶然挡住了 —— 那次真机的 `speedup=0.4155x`，
`persist_decision` 先拒（拒因原文：`相对同机基线没有加速 (speedup=0.4155)`）。
换一条跑得赢的读数就会进去。**「被别的门挡住」不是「这道门有效」**，这正是本仓
反复吃亏的形状。

**修法**：发布值改成收口点的答案（`metrics["eligibility"] = obs.eligibility.as_dict()`），
verifier 里那份本地推导**删掉**，只留一句 fail-closed 的 `ALL_FALSE` 保底
（收口点没跑成 ⇒ 不许有任何一位自称有资格）。这与 397d87b 是同一味药：
**一个判定只能有一处实现**。附带删掉一个零读者的键（`eligibility_derive_error`）。

**守卫**：`tests/test_stage1_acceptance.py::Acceptance8_...::test_published_eligibility_is_the_closure_points_answer`
—— 走**生产 L3 入口**（`_verify_performance`）而不是只测 `evaluate`：分叉正好落在两次
调用**之间**，只测收口点测不到。**对旧代码变红**（旧代码那次甚至打印了 `L3 PASSED`，
而尺子是坏的）。

### 4.2 F2 · 远端运行时盾的证据不落地

**原话**：spine-review P1-4 —— 「反作弊命中必须把 `lib_fallback` 写进 metrics，
否则资格规则 4 恒 False」。

**实证**（`run1.log` §14-3）：把名字拼出来的假候选 `getattr(torch, "mat" + "mul")`
静态审计**看不见**（实测 `static_audit` 返回 `[]`），真机上是**远端进程里的盾**拦下的：

    L2 FAILED: [输入集 1/1] 远程执行失败: Remote verification error:
               CheatDetectedError: 反作弊: 验证执行期间禁止调用原生算子 torch.matmul()

L2 如实失败了，但那次读数里 `lib_fallback=None` —— 因为 `take_lib_fallback()` 读的是
**本地**全局变量，而盾跑在**远端进程**里。证据只活在一句错误文本里。

**后果**：资格规则 4（`lib_fallback` ⇒ 全 False）恰恰是给「静态审计漏了、盾拦住了」
这条路径准备的，而对这条路径**恒 False** —— 又一次「算了、没人读」。

**修法**：`anticheat.py` 里把盾那句话的格式收成**一个常量**
（`_RUNTIME_CHEAT_MARK`，生产者与解析器共用），加 `lib_fallback_from_error(text)`
只认自家文案（**不做模糊匹配**：否则任何含 `matmul` 的报错都会被读成库回退），
`lib_fallback_metrics(violations=..., remote_error=...)` 把它写成
`runtime:<符号>` 段（与既有的 `static:<违规>` 对称），verifier 的远端 L2 失败分支喂进去。

**守卫**：修改后真机复跑，同一臂读到 `lib_fallback=True  evidence='runtime:torch.matmul'`；
离线侧加三条（真机原样文案 → 认回符号 / 不是盾的报错 → 不认领 / 解析器形状），
**摘掉喂给那一行 ⇒ 对应用例变红**。

### 4.3 附带：冒烟脚本自己的三处（都在真机上打出来的）

1. **干扰器是 `SyntaxError`**：循环写成 `exec("while ...:\n x = a @ a")`，那个 `\n`
   经 `ssh` → bash 单引号 → `python -c` 之后变成**字面换行**，而 Python 不许单行字符串
   字面量里有真换行 ⇒ 占位一启动就死。现场只剩「util 序列 23 个 0」。
   ⇒ 改成多行 `-c` 脚本，并加一条**离线棘轮**：把 `-c` 那段抠出来交给 `ast.parse`
   （判据是语法，不必连那台机器）。对旧写法变红。
2. **`nohup ... &` 仍占住 ssh 通道**：启动命令卡 30 秒直到 `_run_remote` 超时，
   而 `TimeoutExpired` **把整个脚本掀翻**（已跑完的读数与后面的诊断一起作废）
   ⇒ 改 `setsid` + stdin 归 `/dev/null` + 子 shell + 回执 `echo launched`；
   `_run_remote` 就地捕获超时、回一个显式标记（**一次远端卡住是要记的事实，不是要命的错误**）。
3. **占位根本没占那张卡**：`CUDA_VISIBLE_DEVICES=2 cd ~/operator_agent && ... python` 里那个赋值
   是**前缀赋值**，只作用于 `cd` 这一条命令（而 `cd` 还是内建命令）⇒ 变量**没进 shell 环境**，
   python 落在 **GPU 0** 上。真机现场完全自洽地骗人：卡 2 的 util 序列 23 个 0（占位正在卡 0 上
   跑）、L3 报 `util=0 validity=valid`、拆除报 `quiescent` —— **每一条都是真的，合起来却什么都没测到**。
   ⇒ 改 `env CUDA_VISIBLE_DEVICES=N` 显式传环境，并让占位自己把 `device_count()` 打进日志
   （钉住 = 1，没钉住 = 8）当判别式。修后 `util 序列 [0, 100]`。
4. **拆除的读回自己骗自己**：`pgrep -f <落点>` 会匹配到**执行它的那个 shell**
   （wrapper 的 cmdline 里就写着那个 pattern）⇒ 干扰进程早已死掉，读回却永远报
   「远端仍有 1 个进程」，`quiescent` 这条判据根本立不起来 —— 它是 CHECKLOG H5 的
   **同一失效、第二处**。⇒ 用 H5 已经用过的方括号技巧（末字符包成字符类：
   `x.log` → `x.lo[g]`），目标进程照样匹配、pattern 文本自己匹配不到自己；
   判据写成**行为**：拿生成出来的那条命令当 cmdline，用它自己的正则搜，必须搜不到。

## 五、这一趟**没有**覆盖的（明写，别让台账读成全覆盖）

- **§14-5（kill + 重启 → 日志完整 / 可续跑 / 最好的一版还在）**：需要 `Conductor.execute`
  起一次真跑，而它要 LLM（`LLM_API_KEY` 未设，规则模板已移除）⇒ 只有离线那一半
  （`Acceptance5`）是绿的。
- **§14-6（篡改契约文件 → 拒绝）**：纯离线，`Acceptance6` 覆盖。
- **§14-7 的运行时检查**：**检测器**（离线）绿，但真机上的生产喂给者是缺的 ——
  `pairing_conflict` 的输入 `candidate_device`/`baseline_device` 全仓只有定义与消费，
  生产者一个都没有（登记 CHECKLOG **I47**）。真机上「两臂同卡」是**结构保证**：
  `benchmark_with_baselines` 在一次调用里跑完两臂、载荷只报一个 `selected_gpu`。
  这两件事不是一回事：一旦有人把两次调用的读数拼成一个加速比，没有任何东西会作废它。
- **§14-4 的语料级对照 / §14-8 的拒因归属**：真机候选打不过 TF32 cuBLAS（`0.416x`），
  而入库判据里 **速度门先于资格门**、且那道门把 `1.0x` **写死**在
  `measurement.persist_decision`（`speedup <= 1.0` ⇒ 拒，**不吃**调用方给的 `min_speedup`）
  ⇒ 这台机器上拒因永远先落在速度门那一条。所以「拒因点名尺子」这一形状**在这台机器上不可达**，
  脚本把它明写成 ➖（而不是把一条恒假的断言留在台账里假装绿）。
  **能证的那一半已经证了**：判据读的那一位（发布出去的 `eligibility`）**只换心跳就两臂相反**
  （坏 `can_persist=False` / 好 `True`），而坏窗口那条确实没进语料（尽管归因不唯一）。

## 七、成本

六次真机复跑（run1–run6，含两次因脚本自己的缺陷而作废的）；一次冒烟 = 8 次 L3 级测量（§14-1 ×3 + §14-2 + §14-3 两臂是非 L3 的 L1+L2 + §14-4 +
§14-8 两臂）。单次 L3 墙钟 4.8–6.6 s（含 runner 自己的 1.2 s util 采样），
§14-4 的占位另占卡 180 s（自带截止时间）。**全程零 LLM 调用**（§14-5 因此未覆盖）。
