## 二 · `2609.11987v1`：它测的是「harness 到底值多少」，而我方所有对照都把这个量混进了别的东西

### 2.1 设计（行 66、76）

模型固定、只换 harness：Opus 4.8 跑在 vendor-native SDK 与 neutral harness（deepagents）上，
GPT-5.5 同理，另加两个 side cell。**结论是「两边都没测出平均优势」**（行 61，逐字摘）：

> "Neither contrast resolves an average advantage for either harness. The paired difference in
> solve rate is −1.25 pp for Opus 4.8 (48.8% native against 50.0% neutral, task-bootstrap 95% CI
> [−10.0, +7.5]) and +1.25 pp for GPT-5.5 (55.6% against 54.4%, CI [−4.4, +6.9])."

对本文更有用的是**下一句**（同一行）：那个平均数把方向相反的两层合成了一件事 ——

> "The Opus average combines opposite strata: the native harness trails by 9.0 pp on the 61
> repository tasks (CI [−17.2, −0.8]) and leads by 23.7 pp on the 19 contest tasks (CI [+2.6, +44.7])."
> 配一个置换检验 p=0.003，然后自己写明「这个分层是看过数据之后选的，所以只作为需要设计性重复
> 来验的事后模式报告」。

**读到我方**：doc 48 §六B 那两个数（`0a4f0fd` 5/6 与 `4e80b13` 3/6，Fisher p=0.545 ⇒ 我方自己
写了「n=6 判不出回归」）。同一形状的坑它给了两个具体的填法：
① **成对同模型对照**才是"harness 变了"的读法 —— 我方两次跑之间除了 harness 还变了 5 个生产文件
（doc 50 §7.5），所以那本来就不是 harness 对照，而是「一份混合工作树 vs 另一份混合工作树」；
② 平均数必须连同**分层方向**一起报，并且要显式写明分层是先验还是事后（我方 `#48` 的
rounds-to-pass 散布正好能给这一栏）。⇒ 挂号 #88。

### 2.2 墙钟上界不是失败（行 349，这条最贵）

> "The August manuscript treated the wall-clock ceiling as a graded failure. The archive shows
> otherwise. The driver cancels the agent at 1,200 s and the oracle grades the patch present at
> cancellation. Of 81 graded runs that hit the ceiling, **22 passed**."

同一行还给了配套的另一个端点：neutral harness **更常撞到上界**（C2 32/160 vs C1 1/…），
所以「撞不撞线」是 latency/cost 事实而不是能力事实；并且它自己补一句
"The neutral harness also issued about twice as many tool invocations per session …
**This is a descriptive count of tool_call_started events and not a validated count of model calls.**"

**读到我方**：#53（`persist_decision` 把 `speedup=None` 报成「没有加速」）与 #64
（`peak_trusted=False` 时 `bound_type` 仍替它判了）是同一族的两次发作 —— **缺证据被当成否定证据**。
这条是同一族的第三个外部实例，而且发生在「通过率」这个我方最核心的数上：我方 `harness_pass_rate`
与 `stop_interferer`/轮次上限把「被时间切断、没被判定」计入失败分母，而 #71 要新增的
`stopped_reason="budget"` 出口正是为此。它给 #71 两条具体的口径要求：
① **被切断的运行不进通过率的分母**（或至少单列一栏，像它那样把 22/81 报出来）；
② AReaL-TIK 那边有个现成的机制（§3.3 的 κ）可以作为预算计数的形状 ⇒ 并进 #71，不另开项。

### 2.3 缓存语义（行 78 与行 1108-1111）—— 本轮唯一落码的一条

> 行 78: "input-token fields are cache-inclusive on some SDKs and cache-exclusive on others,
> and a normalizer that assumes one convention **doubles** the other."
> 行 1108-1111: Anthropic Messages 的 `input_tokens` **排除**缓存读写；OpenAI Responses 的
> `usage.input_tokens_details.cached_tokens` **包含**；LangChain `UsageMetadata.input_token_details` 包含。

它付出的代价写在行 1073：八月版的**全部成本结论与 stop-loss 用的货币**都被自家归一器污染，
而「**no graded verdict**」—— 没有一个判定受影响。这正是我方的处境：`llm_client.py` 原来只读
`usage.prompt_tokens`/`completion_tokens`，把全部输入按表价算钱，缓存命中那部分**不知道是几成**，
`#70` 刚落盘的 `llm_cost` 与 #71 要用的预算货币都建立在这份没人核对的数上。

**已落（`57a16eb`）**：`parse_usage()` 按「出现的是哪个字段」判约定，inclusive 侧**不再加第二遍**、
exclusive 侧把读/写加进总量；账本条目带 `cached_prompt_tokens` / `cache_semantics` / `cost_basis`，
`pretty()` 在有缓存命中时明写「这是按全价算的，不是账单」。价格表**不加**缓存折扣价
（本仓不抄没核过的数；行 1100-1101 那组 ~0.1×/~50% 是别家的价目，不是我们的端点）。

我自己在这条上犯的错值得单独留：**第一版按「有 `input_tokens` 这个键」判 exclusive**，
而 Responses 也用同名键且语义相反 ⇒ 它的缓存被读成 0。与外部那句是镜像关系：
假设错方向时，不是翻倍就是**漏掉**，两种都表现为「一个像样的数字」。判别信号必须是
「**哪个字段出现了**」，不是键名。（CHECKLOG I26）

## 三 · `2609.35140v1`：它把「优化过程」做成一份 IR，而我方是三份互相抄的清单

§4.2（行 133）一句话给全了设计动机：

> "The IR links attempted modifications to source implementations, motivations, and measured
> outcomes so later decisions can use the evidence behind aggregate scores."

五类记录（行 135-143，逐条对应我方今天有没有）：

| 它的记录 | 它存什么（行号） | 我方今天 |
|---|---|---|
| Optimization-opportunity | 提出方向：机制、受影响的工作负载/入口、支持证据、**不规定具体改法**（135） | `optimization_planner` 的 recipe 里混着「方向」和「怎么改」，且没有「哪些实现可能受影响」的引用 |
| Implementation | 一份完整源码实现 + 目标架构 + 入口 + 共享源码区 + **入口之间的数值要求**（137） | `KernelRecord` 有源码与结构签名，没有「入口之间的数值要求」（我们的 L2 有 tolerance 表，但那是**全局**按精度分档，不是 per-implementation 的要求） |
| Action | 精确改动 + 起于哪条 opportunity/parent + 作用范围 + 预期硬件效应 + **数值风险** + 「**哪个测量会推翻它的理由**」（139） | 我们有 `applied_recipes`（哪些配方被用了）但没有那条反证测量 ⇒ 事后无法回答「你说会快 20%，量到了吗」 |
| Audit | 编译/执行/正确性/实际 dispatch/逐工作负载延迟 + 编译器与 profiler 证据；**失败检查与不完整测量都留作证据，不隐含任何验证或晋升**（141） | `execution_snapshot.json` 存了逐轮读数；三态（#25）已把「不可信」与「失败」分开，但**没有**「不完整测量也算证据」的落点 |
| Lineage-management | agent 对 audit 的解读 + 分支状态 + 有证据支撑的后续（143） | 无。我们的 `iteration_history` 是流水账，没有分支状态 |

三条更值得抄的**规则**（不是数据结构）：

1. **评测规格不可变**（行 150）："𝒮 is the **immutable** evaluation specification … It keeps
   correctness and performance criteria fixed across attempts." 我方 `gate_params` 是从任务约束
   与容差表算出来的、逐轮重算；没有一条守卫说「跑动中不许有东西改它」。这与 #80/#81（两条 L2
   路径口径不同源）是同一条纪律的另一面：不是「算得对不对」，是**整条 run 里是不是同一把尺**。
   ⇒ 已落第 1 片（一次验证内的多组输入那一半，见 §3.2），跨轮那一半在 #87 第 2 片。
2. **晋升四条件**（行 209）：verified **且** fully measured **且** 满足**每一个**逐工作负载延迟上限
   **且** 聚合延迟严格更低；否则 incumbent 不变、`κ` 不清零。我方今天的「改善」判据是单点
   speedup 与 bound 类型解耦的（缺口 4 的病灶），而它这里 `fully measured` 与
   「每一个上限」正是我方缺的两条 —— 尤其**分母不可信时不进晋升**，与 #64 完全对上。
3. **失败的后代不许当修订起点**（行 214）："If an offspring fails, revisions must start from a
   retained **verified** parent, not that offspring." 外加四种分支动作
   （Continue / Merge / Archive / Abandon，行 214-220），Abandon 的条件是「反复重试仍未 verified
   或审计证据**否证了方向**」，并且 "failed attempts remain as negative evidence"。

   这句直接回应 doc 57 §五 留的那个洞：我方 Fixer 的默认动作就是「修最近那一版」，
   而我说「redesign 那一路缺的是『这一版的结构值不值得保留』的判据，不能凭空写」——
   **它给了一个可写的判据**：起点必须是 verified 实现。这不需要发明，需要的是把
   「这一版被验证过」这件事在线段里记下来（我方 `iteration_history` 有 passed 字段，
   但 Fixer 的父候选选择没读它）。挂号 #85，且这是 #76① 缺的那一路的第一块砖。

不吸纳的部分：它是 RL 训练栈（PPO/GRPO 的 rollout/update 两个 kernel 数值不一致）这一具体域，
我方没有 rollout 侧；`T(ℐ)` 那种聚合式与 bitwise-consistency 检查（行 208 的入口之间**逐位一致**）
对我们是另一种域（我们的入口只有一个 kernel），只登记。

### 3.1 第 3 条规则已落第 1 片（`conductor.py`，13 例 / 7 条变异 7/7）

写下来才发现我方那条**先决事实**比规则本身更需要先钉住：`conductor.py` 里 Fixer 唯一的入口是
`self.fixer.run(current_code, task, failed_results)`，而 `current_code` 就是**刚刚失败的那一版**
—— 于是「修 → 又失败 → 再修」必然在坏的后代上叠层。落下来的样子：

- 谓词 `correctness_verified(results)` = **L1 与 L2 都到场且都通过**。不含 L3：一个「正确但不够快」
  的核正是该留在手里当起点的那份（这也是我方 `all_passed` 与外部 `verified` 的口径差，
  后者不看性能）。要求「两级都在场」是因为 `Verifier.verify()` fail-fast —— L1 挂时列表里

- 每轮验证完立刻记 `verified_parent`（`current_code` 下一轮会被 `pending_fix` 覆盖，那一刻不记就没了）；

### 3.2 第 1 条规则已落第 1 片（`verifier.py`，11 例 / 8 条变异 8/8）

先决事实是在改的时候才看清的：它说的「同一把尺」在我方有一个**已经在漏**的位置 ——
L2 多组输入聚合处。原来是

```python
gate_params = {}                       # 循环外
if not gate_params:                    # ← 第一个报了值的输入组代表全部组
    gate_params = {k: m[k] for k in ("atol", "rtol", "required_matched_ratio") if k in m}
```

而它下面聚合的是跨组的量（`max_error` 取 max、`matched_ratio` 取 min、`bad_elements` 求和）。
落下来的样子：逐组收集成 `gates`，循环后交给 `_single_ruler(gates)`，判据是**「每一组都在场
且每一组同值」** —— 缺一组也算冲突（不能假设它与别人同值），冲突的那个键**直接不发布**而不是
挑一个（与 #64「分母不可信时 `bound_type` 不许替它判」同形），并把每组的实际取值摊进
`metrics.gate_params_conflict`、在 message 里念出是哪几个键。

⚠️ **一条要说清楚的实话**：今天从内置的两条比对路径走，「各组的尺不同」这一侧**构造不出来** ——
一次 `_verify_function` 只有一个 `task`，而 AND 那条的三把尺全来自
`tolerance.effective_atol(precision, max_allowed)`，组间必然同值。所以本片的行为与改之前**完全
相同**（`benchmarks/probe_l2_sampling_gate.py` 输出逐字未变，1051 → 1062 的净增全是新用例）。
它钉的是一条不变量，不是一只在场的 bug。那它凭什么不是本仓反对的那种「写了走不到的分支」？
因为**「某一组报了、某一组没报」这一侧今天真能发生**：远端那路是按 `_REMOTE_L2_METRIC_KEYS`
**逐键过滤**（`if k in remote_verify`）透传载荷的，远端跑旧版脚本或某组走了缺字段分支，就会出现
「A 组报了 `required_matched_ratio`、B 组没报」—— 而旧写法会从 A 组那一份把三个键全部发布，
仿佛 B 组也在同一把尺下判过。M2（把 `len(vals) == len(gates)` 放松成 `> 0`）就是专打这一侧的，
2 条红。

两片学费：

1. **实现自己撞出了一条本仓老毛病。** 第一版 `_single_ruler` 逐键循环没有 `if not vals: continue`，
   于是**谁都没报过**的键带着一个空证人进冲突表（`{"rtol": {}}`），message 照着念「这几组用的
   不是同一把尺 `['rtol']`」。那是**拿缺证据当反证** —— 守卫用它自己要禁止的那种东西去报警。
   是 `test_one_set_publishes_itself` 第一次跑就红才发现的（M7，3 条红）。
2. **正向对照需要一条专门的变异才派得上活。** 那条不发放、走 MockGPU 真实 AND 路径的用例，
   在 M1~M7 下**全绿**（应该的：它测「不许过度报警」，而那些变异都是「少报」）。但一条任何变异
   都杀不掉的用例等于没写，所以补了 M8（把判据写成 `if False:`，总是报警）→ 8 条红，含那一条。
   ⇒ I19/I23 那句「两侧取样」不只适用于判据，**也适用于用例**：用例也要有能杀掉它的那个变异。

**第 2 片已落**（见 §3.3）。上面这几处提到的 `_single_ruler` / `verifier.GATE_PARAM_KEYS`
现在都住在 `measurement.single_ruler` / `measurement.GATE_PARAM_KEYS` —— 第 2 片要用的正是
同一个键集合，两处各写一份就是两套口径。**#87 剩下的**记在 §3.3 末尾。

### 3.3 第 2 片：跨轮的同一把尺（`measurement` + `conductor` + 量具，29 例 / 12 条变异 12/12）

动手前先查了一件我之前**当成已知**的事：控制端到底有没有办法知道「这一轮的 L2 是用哪把尺判的」。
答案是只有一条，而且是被判对象自报 —— `remote_scripts/run_kernel.py:584` 在自己的进程里调
`tolerance.effective_atol(precision, max_error)`，把算出的三个数写进载荷（行 633-635），控制端
再按 `_REMOTE_L2_METRIC_KEYS` 逐键透传。所以：

⚠️ **这条守卫测的是「报了不同的尺」，测不出「报了一把它自己没用的尺」。** 部署在远端的脚本
若把 `atol` 写死成一个常量而实际按别的值判，控制端无从发现。这与 #89（端点自报的模型标识要与
请求值并排）是同一条纪律的第二个实例，也解释了为什么它的处置只能是**观测**：拿一份自报去否决
别人的判决，本仓没有这个资格（doc 49 §3.5 那句「载荷自报的 `mode`/`device` 只用作与声明对照的
第二手证据」说的正是同一件事）。

上收了一步：`GATE_PARAM_KEYS` 与那条「同值才配发布单值」的规则原先长在 `verifier.py`（第 1 片），
跨轮这半必须用**同一个键集合**，于是搬到 `measurement.py`（与 `CORRECTNESS_LEVELS` 做邻居，
那里的规矩就是「两个读者读同一个集合」）。`verifier` 反过来 import 它，方向无环；
`_REMOTE_L2_METRIC_KEYS` 的注释留在那里，因为「某一组报了、某一组没报」的物理现场就是那个逐键
过滤。

落下来的形状（产它一个点，读它两个点）：

```
每轮 L2 metrics → l2_ruler_reading → 血缘里那一项 l2_ruler
                                        ↓
                    cross_round_ruler(iteration_history) → ruler_note
                     ↑                              ↑
        conductor 每轮那句 [Ruler]          harness_pass_rate 的【跨轮的尺】
```

三态不是装饰：`reported` / `self_conflict`（第 1 片那道守卫在这一轮内部就报了警）/ `unreported`
（fail-fast，L1 挂了就没有 L2）。**「自己说不清」与「换了尺」的修法不同** —— 前者查多组输入的
口径，后者查部署 —— 所以两个桶必须分开数；`ruler_same` 也留了 `None`，把「不到两轮报过」折成
True 是拿缺证据当通过，折成 False 是当反证，两个方向都错过（#53 那一族）。

真跑了一次 Conductor（MockGPU、零机时、零 LLM 调用），把「第 2 轮起换了一份容差表」当作部署
漂移的等价现场，两侧各读一遍：

| 场景 | 血缘里两轮报的 atol | `ruler_same` | `[Ruler]` 印了几行 | L2 判决 |
| --- | --- | --- | --- | --- |
| 没换表 | `0.0001`, `0.0001` | `True` | 0 | `[True, True]` |
| 第 2 轮换表 | `0.0001`, `0.001` | `False`（证人 `{1: 0.0001, 2: 0.001}`） | 1 | `[True, True]` |

最后一列是本片存在的条件：报警了，而判决一位没动。「只观测不判定」在这里不是免责声明，是唯一
今天付得起的处置 —— 跨轮换尺**没有阈**（rtol 从 1e-4 变 1e-3 要紧、从 1e-4 变 1.0000001e-4 不要紧，
这种「要紧」本机还没有分布能答），与环境漂移停在 DEGRADED 是同一条。

三片学费：

1. **一处口径是被用例逼出来的，不是先想清楚的。** 我写的期望是「有一轮说不清它的 atol ⇒ 整场
   `ruler_same` 该是 None」，实现给的是 `True`（rtol 两轮都报了且一致）。停下来想了哪个对：站在
   实现那侧，因为本片跟着第 1 片立的就是**逐键**规则，「一个键打架就让别的键陪着沉默」正是那条
   M6 反对的事；而「一致」会被读成覆盖全了三把尺这件事，交给 `ruler_keys_partial` 显式说出来
   （M4 专打它：写死成永不成立 → 2 条红）。
2. **血缘里的读数只能抄那三个键，不能抄整份 metrics。** `max_error` 跟着**候选代码**变，
   把它当尺就会把「这一版算得不准」读成「这一轮换了尺」—— 与本仓那条「分支判别键要选只在一种
   约定下出现的字段」（I26）是同一件事的反面：这次是**别把会随被测对象变的字段当口径**。M5 → 4 条红。
3. **M10 又是只有正向对照杀得掉**（把打印条件反转后，漂移那一轮照样会印，因为
   `not 0` 为真）。这是 I27 那句话的第二个实例，两次都不是设计出来的：`assertNotIn("[Ruler]")`
   那条不发放的真实路径用例，是这批 12 条里唯一给它派活的。

**#87 剩下的**：① 𝒮 那句话覆盖的是 correctness **和** performance 两套判据，这片只管了 L2 的
数值门三键；L3 的 `min_speedup`、`NOISE_BAND`、`ROOFLINE_CONVERGED_PCT` 跨轮是否同一把，今天没有
读数；② 跨运行那一半（晋升语料时换尺重测）在 #93；③ 报警的**阈**需要真机分布才能定（#82/#89 同批）；
④ 高精度那把尺（`ref_oracle`/`oracle_rho`）还没进跨轮读数 —— 今天只有 AND 那三键穿过落盘边界。

### 3.4 第 3 片：把同一套判据问到**性能**那一半（`measurement` + `verifier` + `conductor` + 量具，18 例 / 12 条变异 行为 9/9 + 结构 3/3）

§3.2/§3.3 两片问的都是 `atol/rtol/ρ`，也就是 𝒮 那句里的 correctness 那一半。外部那句原文是
"It keeps correctness **and performance** criteria fixed across attempts" —— 所以「一次运行里
换没换尺」这个问句今天只问了一半：L3 的通过门跨轮是不是同一把，**一个读数都没有**。

这一片的键集合是 `measurement.PERF_GATE_PARAM_KEYS = ("min_speedup_required", "perf_criterion",
"bound_type")`。三个都值得单独说一句：

- **`perf_criterion` 才是本片的新东西**。`verifier._verify_performance` 有**三条**比对路，
  前两条比 `speedup >= min_speedup`，第三条（legacy 无基线）比的是 `gflops >=
  target_gflops * min_speedup` —— 同一个 `min_speedup=1.5` 在前者是「快 1.5 倍的地板」，
  在后者是「把绝对目标乘 1.5 的系数」。**只看数值会把一次换了量纲的漂移读成「尺没变」**，
  所以这一键记的是「判的是哪个量」而不是它的阈值。顺带：第三条路在此之前**一个尺键都不报**
  （它判过，而在跨轮读数里是「这一轮没报」），本片补上了它的 `min_speedup_required` 与判据。
- **`bound_type` 是收敛出口的轴**。`roofline_converged` 比的是「这条轴上达到上界的百分比」，
  轴从 compute 翻到 memory 时同一个 90% 意思是两件事（本机两条轴可达性实测不对称：
  compute 轴最好 94.7% 打得开口、memory 轴最好 84% 永不开，§见 `ROOFLINE_CONVERGED_PCT` 那段）。
- ⚠️ **`unknown` 不算一个读数**（本片落地前被 `tests/test_bound_axis_gate.py` 那张读者清单
  逼出来的，登记 **I35**）。那条守卫要求：新增一个 `bound_type` 的读者，必须写明拿它做什么、
  并确认它认识 `"unknown"` 这个第三态。查的过程中发现：两轮都 `unknown` 时逐键判据会给该键
  `same` ⇒ 「谁都不知道是哪条轴」被印成「已确认是同一把尺」。所以 `_ruler_reading` 多了一个
  `not_a_value` 参数，这类占位值在收读数时就剔掉，该键随后进不了可比对（与「这一轮没报」同处，
  而不是与「报了且相同」同处）。

**判据只有一份**：`cross_round_ruler` / `_ruler_reading` 都是参数化到「键集合 + 血缘键」的
同一个实现，L2 那半走默认参数、输出与本片之前**逐字节相同**（既有读者与钉它们的用例一个都不动）。
`ruler_note` 多了 `label` 与 `advice` 两个参数，默认值同样保持旧输出不变；带标签是因为日志里
从今天起有**两行「各轮的尺…」**，而那两行的修法还不同（数值尺换了去查部署；只有绑定轴换了
通常只是候选自己变了形状）。

**读者**：conductor 每轮写 `l3_ruler` 并在尺真变时多印一行；端到端报表的【跨轮的尺】从今天起
是**两栏**（`_ruler_stats` 一个实现出两半的五栏，L2 那半键名不变）。性能那半今天只有两态
（`reported` / `unreported`），第三态 `self_conflict` 结构上到不了 —— L3 只拿**第一组输入**做基准，
没有跨组可打架，所以报表里那句 0 是真话而不是没接上。

**两条被本片撞出来的量具自身的错**（都不是本片要修的东西，但都由本片逼出）：
① **P7 第一版 0 红**：`_round_perf_ruler` 的两条用例都是直接调那个 helper，**没有任何一条
用例从真实循环里查过「血缘有没有这一格」** ⇒ 「conductor 忘了写」在整张网里不可见，而它一丢
报表只会退成「测不到」——一个听起来已经尽职的词。补的用例走真主循环（复用 §3.3 那条的夹具）。
② **I35**：那张读者清单把 `BOUND_AXIS_KEY = "bound_type"` 整行当 docstring 剔掉了，
也就是它对「把键名收成常量」——本仓一直鼓励的方向——系统性失明。修法（docstring 必须是
本行第一个非空白 token）配了一条双向证人：常量赋值要留着、docstring 要剔掉。

⚠️ 本片**不改任何判决**：L3 的 `passed` 今天与昨天逐字相同。这一点由那条 AST 守卫钉住
（`_verify_performance` 里每个判定位置——`If`/`Compare`/`BoolOp`/`IfExp` 的**条件那一侧**——
都不许出现新加的名字），变异 P10 就是「顺手让判决读它」，它的 `and` 恒真所以行为不可区分，
只有那条守卫杀得掉。第 4 片的位置留着：`NOISE_BAND[validity]` 那条**改善判据**跨轮是不是同一把
——今天没做，因为它的漂移与测量质量混在一起（档位降级本来就会让带宽变宽），要跟 #82/#89 同批定阈。

1. **marker 排最前是优先级，不是随手放的**：`_record_failure` 那次兜底拿的是**所有轮次**拼起来的
   文本，一轮里可以同时有「本级判不出」与别的失败。「这一轮什么都没证明」必须盖过「这一轮判出了
   坏结果」，否则后者的处方建立在一次并不存在的观测上。
2. **`_INFRA_CLASSES` 改名成 `_NOT_KERNEL_CLASSES`**：第二条进来之后「infra」不再描述这个集合的
   共同性质（坏参考不是基础设施）。留一个只装得下一半成员的名字，下一次加进来的人会以为这里
   是按硬件分的。这一处是搬家不是新增，但它的**文案副本**在 `docs/user_guide.md` 6.1 总表与 §6.6
   各写了一份「目前仅此一条」—— 只改代码会造出两张矛盾的图（本仓那条老规矩）。
3. **计数必须打印**：门如果看不见就等于没生效（缺口 2 的失效方式），所以 `K` 那一栏与
   `suppressed_by_kind` 同行、同一条断言打在**紧邻的轮数**上。

自我纠正在这里发生了一次，而且是好事：**反向对照替我撞出了一条永真断言**。
`assertIn("参考侧判不出", log)` 对任何输入都成立 —— 结尾那行账每次都印这四个字，印的还是 0 轮；
而我给数值那一侧写的对照当时是 `assertNotIn("参考侧判不出", log)`，第一跑就红。修法是把断言
打在 `参考侧判不出 1 轮` / `… 0 轮` 上（M11 因此才有牙齿）。这是 CHECKLOG I32 那族的第 3、4 次，
同一个会话里第三次；同一次还拆出第二个成员 —— M6/M7 与 M12/M13 的红名单逐条相同，因为两条断言
挤在同一个测试方法里，而标定报的是**方法名**，拆成两个方法之后归属才分得开。

读数：`tests/test_reference_uninformative_route.py` 22 例；变异表 14 行进仓
（`benchmarks/mut_specs/reference_uninformative_route.py`），**行为分母 12/12 + 结构分母 2/2 全拦下**。
结构那两行是 M13（只改桶名的值 —— 它会被写进已入库记录 id `cx-{task}:{signature}`，证人是一条把
`L2|reference_uninformative|-` 整串钉成期望值的用例，与 fixer_stage_branch 的 M21 同族）与
M14（写库侧换成自己正则看文案 —— 今天与分类器给出同一个答案，只有 AST 守卫杀得掉）。

**这一片没做的事**（都不是遗漏）：

* 控制流照旧调 Fixer ——「本级判不出」那一轮仍然烧一次 LLM。省掉它是更省的改法，但它改的是
  循环形状，要一次前后对照才敢动（#48/#77 那一族），另片。
* 远程那一路 `remote_scripts/run_kernel.py` 还没有第 1 片那个掩码，所以它今天**产不出**这句话，
  这条分流在远程路径上是空转的（无输入，不是失效）。补它要给远程脚本加同一个形状，而部署需批准。
* 模板 `fixer_repair.md` 里那句「以下代码未通过验证」对 hold 轮仍然是错的措辞。给它加分支要新
  开一个占位符，而那条占位符的守卫与 `fixer_stage_branch` 表的 M6 那行是同一处锚点 —— 一次改两处
  会让那张表的红名单不再可归因，所以留作下一次连同 M6 一起重排。
* 坏参考**本身**的审计不在这条线上：负样本库是用来教模型的，不是用来查参考的。查「这个任务的
  参考解自己就不产可比值」是 #95（Φ-Bench 行 172-173：任务准入要过双向门，参考解自证可达）。
