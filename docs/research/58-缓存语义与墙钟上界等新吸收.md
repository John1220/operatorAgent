## 二 · `2609.11987v1`：它测的是「harness 到底值多少」，而我方所有对照都把这个量混进了别的东西

### 2.1 设计（行 66、76）

模型固定、只换 harness：Opus 4.8 跑在 vendor-native SDK 与 neutral harness（deepagents）上，
GPT-5.5 同理，另加两个 side cell。**结论是「两边都没测出平均优势」**（行 61，逐字摘）：

> "Neither contrast resolves an average advantage for either harness. The paired difference in
> solve rate is −1.25 pp for Opus 4.8 (48.8% native against 50.0% neutral, task-bootstrap 95% CI
> [−10.0, +7.5]) and +1.25 pp for GPT-5.5 (55.6% against 54.4%, CI [−4.4, +6.9])."

对本文更有用的是**下一句**（同一行）：那个平均数把方向相反的两层合成了一件事 ——

> "The Opus average combines opposite strata: the native harness trails by 9.0 pp on the 61
> repository tasks (CI [−17.2, −0.8]) and leads by 23.7 pp on the 19 contest tasks (CI [+2.6, +44.7])."
> 配一个置换检验 p=0.003，然后自己写明「这个分层是看过数据之后选的，所以只作为需要设计性重复
> 来验的事后模式报告」。

**读到我方**：doc 48 §六B 那两个数（`0a4f0fd` 5/6 与 `4e80b13` 3/6，Fisher p=0.545 ⇒ 我方自己
写了「n=6 判不出回归」）。同一形状的坑它给了两个具体的填法：
① **成对同模型对照**才是"harness 变了"的读法 —— 我方两次跑之间除了 harness 还变了 5 个生产文件
（doc 50 §7.5），所以那本来就不是 harness 对照，而是「一份混合工作树 vs 另一份混合工作树」；
② 平均数必须连同**分层方向**一起报，并且要显式写明分层是先验还是事后（我方 `#48` 的
rounds-to-pass 散布正好能给这一栏）。⇒ 挂号 #88。

### 2.2 墙钟上界不是失败（行 349，这条最贵）

> "The August manuscript treated the wall-clock ceiling as a graded failure. The archive shows
> otherwise. The driver cancels the agent at 1,200 s and the oracle grades the patch present at
> cancellation. Of 81 graded runs that hit the ceiling, **22 passed**."

同一行还给了配套的另一个端点：neutral harness **更常撞到上界**（C2 32/160 vs C1 1/…），
所以「撞不撞线」是 latency/cost 事实而不是能力事实；并且它自己补一句
"The neutral harness also issued about twice as many tool invocations per session …
**This is a descriptive count of tool_call_started events and not a validated count of model calls.**"

**读到我方**：#53（`persist_decision` 把 `speedup=None` 报成「没有加速」）与 #64
（`peak_trusted=False` 时 `bound_type` 仍替它判了）是同一族的两次发作 —— **缺证据被当成否定证据**。
这条是同一族的第三个外部实例，而且发生在「通过率」这个我方最核心的数上：我方 `harness_pass_rate`
与 `stop_interferer`/轮次上限把「被时间切断、没被判定」计入失败分母，而 #71 要新增的
`stopped_reason="budget"` 出口正是为此。它给 #71 两条具体的口径要求：
① **被切断的运行不进通过率的分母**（或至少单列一栏，像它那样把 22/81 报出来）；
② AReaL-TIK 那边有个现成的机制（§3.3 的 κ）可以作为预算计数的形状 ⇒ 并进 #71，不另开项。

### 2.3 缓存语义（行 78 与行 1108-1111）—— 本轮唯一落码的一条

> 行 78: "input-token fields are cache-inclusive on some SDKs and cache-exclusive on others,
> and a normalizer that assumes one convention **doubles** the other."
> 行 1108-1111: Anthropic Messages 的 `input_tokens` **排除**缓存读写；OpenAI Responses 的
> `usage.input_tokens_details.cached_tokens` **包含**；LangChain `UsageMetadata.input_token_details` 包含。

它付出的代价写在行 1073：八月版的**全部成本结论与 stop-loss 用的货币**都被自家归一器污染，
而「**no graded verdict**」—— 没有一个判定受影响。这正是我方的处境：`llm_client.py` 原来只读
`usage.prompt_tokens`/`completion_tokens`，把全部输入按表价算钱，缓存命中那部分**不知道是几成**，
`#70` 刚落盘的 `llm_cost` 与 #71 要用的预算货币都建立在这份没人核对的数上。

**已落（`57a16eb`）**：`parse_usage()` 按「出现的是哪个字段」判约定，inclusive 侧**不再加第二遍**、
exclusive 侧把读/写加进总量；账本条目带 `cached_prompt_tokens` / `cache_semantics` / `cost_basis`，
`pretty()` 在有缓存命中时明写「这是按全价算的，不是账单」。价格表**不加**缓存折扣价
（本仓不抄没核过的数；行 1100-1101 那组 ~0.1×/~50% 是别家的价目，不是我们的端点）。

我自己在这条上犯的错值得单独留：**第一版按「有 `input_tokens` 这个键」判 exclusive**，
而 Responses 也用同名键且语义相反 ⇒ 它的缓存被读成 0。与外部那句是镜像关系：
假设错方向时，不是翻倍就是**漏掉**，两种都表现为「一个像样的数字」。判别信号必须是
「**哪个字段出现了**」，不是键名。（CHECKLOG I26）

### 2.4 另外两条只登记不吸纳

- 行 89 的 **runtime drift gate**：每条腿开跑前核验「服务端实际模型标识（带日期快照归一）」，

  路由器的默认线路，而实验跑在另一条固定线路上 ⇒ 探测被修订成「测这次跑的确切固定后端」。
  我方 `backend_caps`（#44/#45）已在管「后端声明能力」，但**没有**任何东西核验「端点今天答的是
  哪个模型标识」；LLM 端点漂移会直接污染 prompt 对照实验。登记为 #89（先观测）。
  **观测那半边已落**（本片的第二个提交）：账本条目带 `reported_model`（响应里自报的那个），
  账单摘要与 `pretty()` 把「请求 X → 自报 Y」逐族报出来，7 例 / 6 条变异全拦。

## 三 · `2609.35140v1`：它把「优化过程」做成一份 IR，而我方是三份互相抄的清单

§4.2（行 133）一句话给全了设计动机：

> "The IR links attempted modifications to source implementations, motivations, and measured
> outcomes so later decisions can use the evidence behind aggregate scores."

五类记录（行 135-143，逐条对应我方今天有没有）：

| 它的记录 | 它存什么（行号） | 我方今天 |
|---|---|---|
| Optimization-opportunity | 提出方向：机制、受影响的工作负载/入口、支持证据、**不规定具体改法**（135） | `optimization_planner` 的 recipe 里混着「方向」和「怎么改」，且没有「哪些实现可能受影响」的引用 |
| Implementation | 一份完整源码实现 + 目标架构 + 入口 + 共享源码区 + **入口之间的数值要求**（137） | `KernelRecord` 有源码与结构签名，没有「入口之间的数值要求」（我们的 L2 有 tolerance 表，但那是**全局**按精度分档，不是 per-implementation 的要求） |
| Action | 精确改动 + 起于哪条 opportunity/parent + 作用范围 + 预期硬件效应 + **数值风险** + 「**哪个测量会推翻它的理由**」（139） | 我们有 `applied_recipes`（哪些配方被用了）但没有那条反证测量 ⇒ 事后无法回答「你说会快 20%，量到了吗」 |
| Audit | 编译/执行/正确性/实际 dispatch/逐工作负载延迟 + 编译器与 profiler 证据；**失败检查与不完整测量都留作证据，不隐含任何验证或晋升**（141） | `execution_snapshot.json` 存了逐轮读数；三态（#25）已把「不可信」与「失败」分开，但**没有**「不完整测量也算证据」的落点 |
| Lineage-management | agent 对 audit 的解读 + 分支状态 + 有证据支撑的后续（143） | 无。我们的 `iteration_history` 是流水账，没有分支状态 |

三条更值得抄的**规则**（不是数据结构）：

1. **评测规格不可变**（行 150）："𝒮 is the **immutable** evaluation specification … It keeps
   correctness and performance criteria fixed across attempts." 我方 `gate_params` 是从任务约束
   与容差表算出来的、逐轮重算；没有一条守卫说「跑动中不许有东西改它」。这与 #80/#81（两条 L2
   路径口径不同源）是同一条纪律的另一面：不是「算得对不对」，是**整条 run 里是不是同一把尺**。
2. **晋升四条件**（行 209）：verified **且** fully measured **且** 满足**每一个**逐工作负载延迟上限
   **且** 聚合延迟严格更低；否则 incumbent 不变、`κ` 不清零。我方今天的「改善」判据是单点
   speedup 与 bound 类型解耦的（缺口 4 的病灶），而它这里 `fully measured` 与
   「每一个上限」正是我方缺的两条 —— 尤其**分母不可信时不进晋升**，与 #64 完全对上。
3. **失败的后代不许当修订起点**（行 214）："If an offspring fails, revisions must start from a
   retained **verified** parent, not that offspring." 外加四种分支动作
   （Continue / Merge / Archive / Abandon，行 214-220），Abandon 的条件是「反复重试仍未 verified
   或审计证据**否证了方向**」，并且 "failed attempts remain as negative evidence"。

   这句直接回应 doc 57 §五 留的那个洞：我方 Fixer 的默认动作就是「修最近那一版」，
   而我说「redesign 那一路缺的是『这一版的结构值不值得保留』的判据，不能凭空写」——
   **它给了一个可写的判据**：起点必须是 verified 实现。这不需要发明，需要的是把
   「这一版被验证过」这件事在线段里记下来（我方 `iteration_history` 有 passed 字段，
   但 Fixer 的父候选选择没读它）。挂号 #85，且这是 #76① 缺的那一路的第一块砖。

不吸纳的部分：它是 RL 训练栈（PPO/GRPO 的 rollout/update 两个 kernel 数值不一致）这一具体域，
我方没有 rollout 侧；`T(ℐ)` 那种聚合式与 bitwise-consistency 检查（行 208 的入口之间**逐位一致**）
对我们是另一种域（我们的入口只有一个 kernel），只登记。

### 3.1 第 3 条规则已落第 1 片（`conductor.py`，13 例 / 7 条变异 7/7）

写下来才发现我方那条**先决事实**比规则本身更需要先钉住：`conductor.py` 里 Fixer 唯一的入口是
`self.fixer.run(current_code, task, failed_results)`，而 `current_code` 就是**刚刚失败的那一版**
—— 于是「修 → 又失败 → 再修」必然在坏的后代上叠层。落下来的样子：

- 谓词 `correctness_verified(results)` = **L1 与 L2 都到场且都通过**。不含 L3：一个「正确但不够快」
  的核正是该留在手里当起点的那份（这也是我方 `all_passed` 与外部 `verified` 的口径差，
  后者不看性能）。要求「两级都在场」是因为 `Verifier.verify()` fail-fast —— L1 挂时列表里
  根本没有 L2 那行，`all(...)` 数那种列表会给 True（doc 49 §八 那一族的又一次）；
- 每轮验证完立刻记 `verified_parent`（`current_code` 下一轮会被 `pending_fix` 覆盖，那一刻不记就没了）；
- 进 Fixer 前 `repair_base = verified_parent`（有才退，没有就与改之前完全一致），
  但**错误证据仍取失败那一版的** —— 起点退回 while 把 `failed_results` 一起退回是另一种「修不了」
  （M6 的证人就是这条）；
- 续跑不新开快照字段：祖先从**血缘最后一条**的 `levels_passed` 重建（快照的 `current_code` 就是那一轮那份）。
  重建不出来时如实返回 `None` ⇒ 退回改之前的形状，**不猜祖先**。⇒ 这条「续跑只能重建一步」
  是本片有意接受的限制，写在这里而不是藏在代码里。

两片学费值得单独留：

1. **抄来的夹具要重跑。** 第一版那份「能过 L1+L2 的核」是抄 `tests/test_iteration_lineage.py` 的
   `CORRECT`，第一次跑就红：那份核过 L1 但**过不了 L2**（`got 9, want 8`），而那个文件的用例
   只断言过 L1 —— 「它是我已有的正确夹具」不构成证据。
2. **M4 第一版逃逸**（`verified_parent != current_code` 那半句删掉后 13 例全绿）。原因是我当时
   写了一个**当时构造不出反例**的条件：`verified_parent == current_code` 只在「同一份文本两次验证
   给出不同答案」时才可能，而那需要非确定的验证。补一只发放预写结果的假 Verifier 造出那个现场之后，
   同一条变异变成 KILLED，观察面是那句 print（起点没变却报「退回」= 一句谎话）。
   ⇒ 与 CHECKLOG I19/I23 同族：**要么把反例造出来，要么把条件删掉**，不许留一个「观察不到的条件」。

**仍未做**（#85 保持 pending）：晋升四条件里「fully measured + 每一个逐工作负载上限」那两条要
#61/#65/#48 的分母才有数；分支四态（Continue/Merge/Archive/Abandon）我方 `iteration_history`
里根本没有分支状态这个东西；而这条规则在真机上到底省下多少轮修复，得有机时才能答。

## 四 · 只读了结果段的两篇：KernelZero 与 KernelOPT（各留一条能用的和一条不能用的）

**KernelZero `2609.33074v1`**（方法节 §2 未读 ⇒ 不对 proposer/coder 的机制下结论）。
读了 §3.2 的结果段（行 495-503）。一行可用的事实（行 499-501，逐字）：

> "KernelZero achieves 43.9 fast1@1 and 87 fast1@10 with Triton on Level 1, compared with 17.6 and
