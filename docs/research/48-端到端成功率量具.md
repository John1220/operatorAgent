# 48 — 端到端成功率量具：三个业务指标第一次有仪器，以及为它补的两处血缘搬运缺陷

日期：2026-09-28。真机：8×H20 的 GPU 2（util=0% 起跑）。
本篇不引外部来源——它的动机全部来自**本仓库自己的空白**：67 个提交之后，
「生成的核有多少比例能过 L2、中位加速比多少、平均烧几轮」这三个数一次都没被量过。

---

## 一、为什么这是下一步

前一段的每一篇调研文档都以「本轮吸纳了什么、没吸纳什么」收尾，而那些「没吸纳」的理由
几乎全是同一句：**没有分布**。

* doc 44：峰值显存只有 4 个点，硬设阈值等于猜。
* doc 46：false-stop 曲线来自人造污染 + 单 run，不是这台机器的邻居分布。
* doc 47：重复基率分母只有 2 轮，驱动拒绝出百分数。
* doc 35：C1 的 A/B **完全打平**，而那个设计从原理上看不见效应（4 格里 2 格天花板、
  指标是单次通过率而非 rounds-to-compilable）。

四条独立地指向同一个缺失：**这个项目没有一台能跑「一批任务」并给出分布的仪器。**
现有 30 个 driver 全是单点探针——一次量一个机制，这在标定阈值时是对的，
但要回答「流水线整体好不好」就需要另一种东西。

而 `tests/golden_regression.py` 结构上答不了这个问题：它的注释原文是
「保证 MockGPU 能稳定通过 L1/L2, 且给出稳定的『伪 GFLOPS』数字」——
它验的是**接线**，不是**能力**。

## 二、量具的形状

`benchmarks/harness_pass_rate.py`。固定任务集 × K 次重跑，报表出：

| 指标 | 口径 |
|---|---|
| L1 / L2 / L3 通过率 | **分母 = 走到该级的轮数**，不是总轮数 |
| 任务级成功率 | 最终 `all_passed` 的运行数 / 完成的运行数（崩溃样本单独计数，不进分母） |
| rounds-to-pass | 首次 `all_passed` 的轮号（`fix` 轮不算通过点） |
| 测量档位分布 + decision-grade 占比 | `valid` 档的轮数 / 有 L3 读数的轮数 |
| 加速比分布 | **两套口径分开报**：全部轮次 / 仅 decision-grade |
| 入库率 | 通过的运行里被 `persist_decision` 收下的比例 + 拒收理由 |
| 成本 | tokens / 估算美元 / 墙钟 |

语料（第一版，故意一档一个）：

| 用例 | 精度 | shape | 预期档位 | 依据 |
|---|---|---|---|---|
| matmul | fp16 | 4096³ | `valid` | doc 31 实测 launch 地板占比 0.020 |
| layernorm | fp32 | 16384×6144 | `degraded` | doc 31 实测 0.111 |

**门槛用生产值 `min_speedup=1.0`**，不是 doc 47 那个故意达不到的 10x。
这里量的是「达不达标」，用一个永远失败的门槛量出来的通过率没有意义。
（doc 47 用 10x 是因为它要的是**轮次**，而 Conductor 一通过就 break。）

## 三、三条设计纪律，每条都对应一个已经犯过的错

### 3.1 分级通过率的分母是「走到该级的轮数」

死在 L1 的轮次**根本没有 L2/L3 的条目**。拿总轮数当分母，L1 的失败率就会污染 L2/L3——
「L2 通过率 50%」可能实际含义是「一半的运行连 L2 都没走到」。

这与 doc 47 第一版把 `generate` 轮算进 `optimize` 分母是同一个错，只是方向相反。

### 3.2 分母不足时拒绝打印百分数

`MIN_DENOM = 4`。低于它，报表打印「分母不足」并以非零退出，**不出任何百分数**。

这条是被逼出来的：doc 47 的驱动第一版把「1 轮里 0 轮重复」打印成
「重复率 0.0%」，看起来像一个测量值。`0/1` 和 `0/12` 都写成 `0.0%` 是量具最坏的失效方式
——它长得像数据。

### 3.3 通过率与档位必须并列，加速比不许合并口径

在 `uninformative` 档上「通过」的核，它的加速比**没有资格驱动任何闭环决策**（缺口 1）。
所以报表把两者并排印，并且加速比给两套分位数：全部轮次 / 仅 decision-grade。

合并成一套的后果是具体的：一份全是 `uninformative` 的产物会给出一个漂亮的加速比中位数，
而那个数在本项目的语义里等于「没测」。

## 四、为它补的两处血缘搬运缺陷

量具要算 rounds-to-pass 与逐轮加速比，而**这两样在产物里都不存在**：

* `iteration_history` 原来只记 `all_passed`；
* `all_verification_results` 每轮被覆盖（`all_verification_results = verify_results`），
  所以出了循环只剩**最后一轮**的分级结果。

于是「第 2 轮卡在 L1」与「第 2 轮卡在 L3」在产物里无法区分。这与 doc 33 抓到的
「`runs`/`max_time_ms` 在远程路径上从来没进过 metrics」是同一类缺陷：**算出来了，
但在到达读者之前就丢了**。

补三键：`levels_passed`（每级 bool）、`measurement_validity`（本轮档位）、`speedup`（本轮加速比）。

⚠️ 一个顺手发现的陷阱：`KernelArtifact.all_passed` 是
`all(v.passed for v in self.verification_results)`，而 **`all([])` 是 `True`** ——
一份没有任何验证结果的产物会被判成「全过」。两条早退路径（入口校验失败 / 环境自检未通过）
都填了合成的 L1 失败，所以现在踩不到；但量具仍显式要求「至少有一轮」，
因为「跑出了候选」本来就该是任务成功的定义之一。

## 五、标定：七个变异 + 三条血缘断言

聚合逻辑写成可 import 的纯函数（`aggregate` / `format_report` / `first_pass_round` /
`cost_from_metadata` / `record_rounds`），配 31 条离线单测，不碰 GPU 与网络。
理由是 doc 46 那条：**判据方向写反时，量具明明看见了信号却报「看不见」**，
而一份坏掉的报表会打印出很像样的百分数。真机一轮很贵，所以算法必须能离线验。

变异逐个验证能失败（前两条是首版标定，后五条是 6.4 那四个缺陷修完补的）：

| 变异 | 结果 |
|---|---|
| 分级分母改成「总轮数」 | 2 条红（`TestLevelRateDenominator` 两条） |
| `decision_grade` 改成「全部有档位的轮」 | 2 条红（`TestDecisionGradeIsSeparateFromPassRate` 两条） |
| 白名单回到 `record_rounds` 里 | 红（`test_a_key_added_later_survives`：一个它没听说过的键必须原样穿过） |
| 重复率的分母含第一轮 | 红（`test_a_flagged_repeat_is_counted`：分母变大，100% 变成 50%） |
| 「没有签名」报成 0% | 红（`test_missing_signature_reports_unmeasurable_not_zero`） |
| 报表不打 `passed_via` | 红（`test_fix_rescues_show_up_in_the_report`） |
| 成本不打调用次数 | 红（`test_llm_calls_are_summed_too`） |

血缘三键各配一条行为断言，三个变异（逐个把键名改掉）全部被抓住——
其中 `levels_passed` 那条变异让 2 条红，因为它同时被「通过的轮」和「卡住的轮」两条用例读。

还有一条**夹具守卫**值得单说：`_round()` / `_run()` 这两个假记录的键集合，是去
`conductor.py` 与 `harness_pass_rate.py` 的 AST 里读那两个字典字面量核对的，不是手抄的。
手抄的那一刻是准的，之后就开始漂——而漂移的后果正是 6.4 第 4 条：**聚合逻辑在一套比生产
少的键上被验，少掉的那个键从来没人验过**。这条守卫第一次跑就抓到夹具自己少了
`kernel_type`/`shape`。

方向检查是这组测试的主体：`test_all_pass_and_all_fail_report_opposite_rates`
断言「全过」与「全挂」给出**相反**的成功率，而不是只断言某一个具体数字——
后者在判据整体失效时也可能碰巧成立。

## 六、真机结果：第一份基线

2026-09-28，GPU 2（起跑 util=0%，卡上另有 7~8 个别人的进程），`git_head = 0a4f0fd`，
门槛 `min_speedup=1.0`，`max_optimize_rounds=3`，2 用例 × 3 次 = 6 次运行 / 12 轮，
墙钟 856 s，真实 token 总量 **166,345**（见 6.4 那条缺陷）。

### 6.1 报表

| 指标 | 值 |
|---|---|
| L1 通过率 | **10/12 = 83.3%** |
| L2 通过率 | **10/10 = 100%**（走到 L2 的全过） |
| L3 通过率 | **5/10 = 50.0%** |
| 任务级成功 | **5/6 = 83.3%** |
| rounds-to-pass | median **2** · p25 1 · p75 2 · max 3（n=5） |
| decision-grade 占比 | **10/10 = 100% `valid`** |
| 加速比（全部轮次） | median **0.99x** · p25 0.9705 · p75 1.0705 · min 0.9697 · max 1.3196 |
| 加速比（仅 decision-grade） | 与上完全相同（因为本轮全是 `valid`） |
| 入库 | 通过的 5 次**全部**入库；另有 1 条拒收：`相对同机基线没有加速 (speedup=0.9769)` |

逐次明细（`卡住级` 来自新补的 `levels_passed`）：

| 运行 | 轮数 | 逐轮加速比 | 卡在哪级 | 结果 | 通过方式 | tokens | 墙钟 |
|---|---|---|---|---|---|---|---|
| matmul#1 | 1 | 1.0514 | — | ✅ 入库 | `generate` | 15,638 | 98.6 s |
| layernorm#1 | 1 | 1.3196 | — | ✅ 入库 | `generate` | 18,819 | 84.0 s |
| matmul#2 | 3 | 0.970 / 0.9705 / 0.9769 | L3 / L3 / L3 | ❌ | — | 44,344 | 242.3 s |
| layernorm#2 | 2 | —（L1 挂）/ 1.0711 | L1 / — | ✅ 入库 | **`fix`** | 22,355 | 104.5 s |
| matmul#3 | 3 | 0.9697 / 0.990 / 1.051 | L3 / L3 / — | ✅ 入库 | `optimize` | 42,561 | 223.8 s |
| layernorm#3 | 2 | —（L1 挂）/ 1.0705 | L1 / — | ✅ 入库 | **`fix`** | 22,628 | 103.1 s |

（tokens 一列是按 6.4 修好的口径**逐次差分**重算的；原始 JSON 里存的是累计值。）

### 6.2 四条读数

**① 瓶颈完全在 L3，而且它卡在门槛的刀刃上。** L2 是 10/10——走到功能验证的核**没有一个
算错**。所有失败都是「加速比差 2~3% 没到 1.00x」：matmul 的七个读数是
0.9697 / 0.970 / 0.9705 / 0.9769 / 0.990 / 1.051 / 1.0514，**中位数 0.98x**。
也就是说这个流水线生成的 matmul 与 cuBLAS(FP16) 基本打平，任务成不成由 ±3% 决定。

⚠️ 由此得到一条对**语料设计**的指控：把用例选在「能力中位数刚好等于门槛」的位置，
量到的成功率主要是**门槛位置**的函数，不是能力的函数。83.3% 这个数换一套 shape 就会变。
下一版应当要么把门槛与用例分开扫（同一批核在 0.9/1.0/1.1x 三档下的通过率曲线），
要么在报表里同时给「加速比分布」而**不给**单一成功率——分布才是可搬运的，成功率不是。

**② layernorm 明显更强，matmul 基本到顶。** layernorm fp32 三次是 1.3196 / 1.0711 / 1.0705x，
matmul fp16 中位 0.98x。这与 roofline 一致：本轮 matmul 4096³ 的 GFLOPS 达成率是
**86.8%**（分母 148 TFLOPS dense，出处随日志打印，即 doc 42 那套机制在工作），
而 doc 42 用参考核量到的是 94.7%（140.2 TFLOPS）——**LLM 生成的核比参考实现低约 8 个百分点**，
这 8% 就是优化循环理论上还有的空间。

**③ 优化循环的边际价值第一次被量出来，而且是有条件的。** 两个跑满 3 轮的 matmul：

* matmul#3：0.9697 → 0.990 → **1.051**，累计 **+8.4%**，越过门槛，任务从失败翻成成功；
* matmul#2：0.970 → 0.9705 → 0.9769，累计 **+0.7%**，始终没过。

代价是明确的：3 轮的墙钟 224~242 s、tokens 42.6k~44.3k；1 轮的是 84~99 s、15.6k~18.8k。
**约 2.4 倍墙钟、2.4~2.8 倍 token，换来「有时 +8.4% 并越过门槛，有时 +0.7% 白烧」。**
这是「多轮优化值不值」这个问题第一次有数可引——在此之前它只是直觉。
注意 SearchAgent 的建议本身是具体且合理的（`BLOCK_K` 64→128、`BLOCK_N` 128→64、
`GROUP_SIZE_M` 16、`num_stages` 3~4），三轮结构各不相同（`[Novelty] 3 轮候选, 3 个不同结构,
0 轮重复`），所以**不是模型在原地打转**——doc 47 那个「重复」假设在这批数据上没有得到支持。

**④ L1 失败全部出现在 layernorm，且都被 Fixer 一轮救回。** 6 次运行里 2 次（33%）第 1 轮
死在 L1、第 2 轮由 `fix` 通过。这两次**没有**被接口契约门（doc 41）拦下，说明它们不是
签名不匹配而是真的编译错误——契约门的保守放行是按设计工作的。但 33% 的首轮 L1 失败率
本身就是个可优化项，且它每次的代价是一整轮（约 20 s + 22k tokens）。
这条读数是**手算**出来的（逐次明细表的「通过方式」列）；修完 6.4 第 4 条之后它会变成报表里的
一行 `通过方式: {'generate': 2, 'fix': 2, 'optimize': 1}`——括号里这个分布是按明细表手算的，
**本批的落盘记录里没有这个字段**（`passed_via` 是修缺陷 1 时才加的字段，跑这一批的代码还没有它）。

### 6.3 收敛出口没有误动作（一个被证伪的假设）

看到 matmul 在 86.8% 达成率上连烧三轮，我第一反应是「doc 38 那个 roofline 收敛出口
本该在第 1 轮就把它停掉」。**这个假设是错的**：出口阈值是 90%，86.8% 不该触发。
出口行为正确。记下来是因为它差一点变成一条「已核实缺陷」——
达成率 94.7%（doc 42，参考核）与 86.8%（本轮，LLM 核）是两个不同的核，不能混用。

### 6.4 量具自己的四个缺陷（三个在真机运行里暴露，第四个在写这一节时暴露）

这一节的分量不低于 6.1：**一份没被标定过的报表会打印出很像样的数字**。

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| 1 | `rounds_to_pass` 排除了 `fix` 轮 | layernorm#2/#3 **任务成功**却 `rounds_to_pass=None`，被分位数静默丢掉 → 报表 `n=3` 而实际 5 个成功样本，median 报成 1 而真实是 **2** | 改成「第一次 `all_passed` 的那一轮，不管 action」，`fix`/`generate`/`optimize` 的区分移到单独字段 `passed_via`；抽成纯函数 `first_pass_round()` 并配 4 条单测 |
| 2 | 成本读错键名 | 读 `cost_usd`，而 `CostTracker.summary()` 的真键名是 **`total_cost_usd`** → 全程报 `$0.0`，540114 tokens 配 0 美元，安静得像「自建端点不要钱」 | 抽成 `cost_from_metadata()`；配一条**直接对着真的 `CostTracker().summary()` 查键**的机械守卫（键名再漂移就红） |
| 3 | 账单跨运行累加 | `main()` 只建一个 `LLMClient` 传给所有运行，而 `CostTracker` 挂在 client 上累加 → 六次的 token 数是 15638→34457→78801→101156→143717→166345 一条**单调递增**曲线；报表把累计值再求和得 540114，真实总量 166345，**高估 3.25 倍** | `run_one` 内部自建 client（顺带让每次运行成为独立样本）；守卫是「`run_one` 的签名里不许再出现 `llm` 参数」 |
| 4 | 落盘时给血缘键做了**白名单** | `run_one` 只挑 7 个键写进 `pass_rate.json`，于是 Conductor 算好的 `candidate_signature`/`duplicate_of`/`recipes_applied` 在落盘前被丢掉。**这一批 12 轮的重复基率因此永久没了**——第七节第 2 条那句「跑完就能离线算重复率」在写下的当下是假的 | 取消白名单，抽成 `record_rounds()` 原样搬（只规整 `all_passed`→bool、`levels_passed`→dict），落盘处加 `default=str` 以免一个不可序列化的值毁掉整份已付钱的报表；守卫见下 |

第 3 条最值得记：**每一条单独看都像合理的数**（15638 tokens 跑一次 matmul 完全正常），
只有把六条排在一起看单调性才暴露。这与 doc 40 那条「零结果与量具瞎了输出同一行字」、
doc 46 那条「判据方向写反」是同一族——**量具的失效模式通常长得像数据**。

第 4 条是**在写这一节的时候**被发现的：我去落盘 JSON 里算重复率，`candidate_signature`
一个都没有（`run keys` 里有 `rounds`，`round keys` 里只有那 7 个）。白名单的真正问题不是
漏了哪三个键，而是**血缘每加一个键都要记得来这里加一次，而忘记的代价是静默的**——
doc 33 的 `runs`/`max_time_ms`、doc 37 的 `llm_cost` 都是这个形状。所以修法不是「把三个键补进
白名单」，而是取消白名单，并让守卫**去读真代码的键集合**（`conductor.py` 与
`harness_pass_rate.py` 的 AST 里那两个字典字面量），假记录少一个键就红。这条守卫当场抓到
它自己的测试夹具也少了 `kernel_type`/`shape` 两键。

三个真机缺陷都不影响 6.1 里的通过率与加速比（那些字段读的是血缘与 `benchmark_data`，
与账单无关），只影响 `rounds-to-pass` 与成本两行；两行都已用落盘的原始记录**离线重算**修正
——这也是「报表落原始 `runs` 而不只落聚合」这个设计第一次挣回它的成本。
第 4 条没这个运气：**丢掉的键不在任何落盘文件里，只能重跑**。

### 6.5 一个顺带查清的口径缺陷（不在量具里，在 verifier 里）

本轮 matmul 的 `AI=682.67 FLOP/Byte`，而 doc 42 同一个 shape 是 `1365.33`——正好差 2 倍。
查下来是 `_compute_arithmetic_intensity()` 用 `a.itemsize`，即**调用方传进来的 numpy 数组的
dtype**，而不是任务声明的 `precision`；而 runner 会把候选输入按声明精度转换
（`run_kernel.py:521-525`：`precision == "fp16"` 时 `.to(torch.float16)`）。
本量具（沿用 `measure_candidate_duplicates.py` 的输入构造）传的是 float32 数组、声明 FP16，
于是 AI 是在一个**核根本见不到的 dtype** 上算的。

影响分级（这决定它有多急）：

* **达成率不受影响**——`GFLOPS/peak` 与 dtype 无关，所以 6.2 ② 里 86.8% 与 94.7% 的比较成立；
* **计时对比不受影响**——候选与基线都被 runner 转成 fp16，是公平的；
* **受影响的是 AI、带宽利用率、以及 bound 分类**。脊点 = 148/4.0 = 37 FLOP/Byte，

### 顺带查出的三个新问题（其中两个已在同一篇里修掉）

**① 报表把「门从没被问过」印成「门拒了 3 条」——入库率的分子分母不同源（本库这一族里最隐蔽的一次）**

原来那行是 `admit_rejections = {r["admit_reason"] for r in **ok_runs** if 未入库}`，而入库率的
分母是 `passed_runs`。`_save_to_db()` **只在 `artifact.all_passed` 那一支被调**
（`conductor.py:1112` 的 docstring 自己明写），所以未通过的运行在生产里**根本不会被这道门问**——
它们的判定是**假想事件**。后果不是哪个数算错，是**故事讲反**：报表先印「入库 3/3 = 100%」，
紧跟三条「拒收」，读者自然得出「门拒了 3 次好核」；而真相是**这道门本轮一次都没拒过任何东西**。

修法不是把名单删掉，是**分栏**：`admit_rejections` 只取 `passed_runs`（与分母同源），
未通过那批挪进 `counterfactual_rejections` 并明写「生产里不会问这道门」。另外补两条同族的
诚实化：空名单也要说一句「本轮没有拒收任何一次通过的运行」（不印的话「拒了 0 条」与
「没被问」在报表里长得一样）；通过的运行若**没有判定记录**要显眼报出（门没被问 ≠ 门放过了）。

还有一个自己踩出来的小坑：`admit_rejections` 是**按理由去重**的集合，所以「另 3 条」到底
是 3 次还是 3 种，原文说不清——现在两个数都给（`4 次运行, 4 种不同的理由`）。写测试时
我用了 3 条样本，结果被量具自己那条「分母不足不出百分数」的纪律（§3.2）整份短路，
于是才看清**这条纪律是全局短路而非只藏百分数**——这是既有设计，不是缺陷，测试改成 4 条。

**② `persist_decision` 把「没有读数」说成「没有加速」**（同一族的文案问题，已修）

那三条假想拒收里有一条是 `speedup=None`，却被印成「相对同机基线没有加速」。
**先查原因再改文案**：拿 `pass_rate.json` 的逐轮记录复盘，那些轮**同时** `speedup=None` 且

拦截），不是键被搬运丢了。所以这不是 §6.4 第 4 条的复发，纯属表述把缺证据当成否定证据。
修成三态：非法/缺失 ⇒「没有可用的 speedup 读数……这是缺陷信号」，测到了且 ≤1.0 ⇒ 保留
原判定句。顺手补一条 Python 层的洞：`isinstance(True, int)` 为真，所以一个被写成 `True` 的
