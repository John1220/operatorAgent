## 一、要验的是什么

`cf2d50b` 把离散度门写完了，单测全绿，但**没在真机上跑过**。项目里反复出现的一类缺陷是「算了没人读」—— verifier 早就把 `benchmark_contaminated` 写进 metrics，而 conductor/fixer/agents 三个文件 grep 零命中。新加的 `p25/p75/dispersion_*` 走的正是同一条 `bench["candidate"] → metrics` 搬运路径，所以单测绿不能证明它通了。

三个必须回答的问题：

1. runner 报的分位数，真的出现在 L3 metrics 里吗？
2. 标定出来的阈值在**真实采样路径**上是否仍然成立？
3. util 快照改成「隔 1.2 s 采两次取 min」之后，污染判据还会不会乱触发？

## 二、第一个问题就失败了

```
speedup=1.3611  runs=None(请求 None)  contaminated=False (util=0%, 其他进程=7)
样本分布: p25=0.0072 p75=0.0074 min=0.0072 max=None ms
```

`runs=None`、`max_time_ms` 缺失。

根因：verifier 里那个字段搬运循环只在 `bench` **顶层**查，而远程路径上 `bench` 顶层只有 `success/device/gflops/gpu_util_pct/...`，**所有样本统计量都在 `bench["candidate"]` 里**。我上一提交补的分位数字段用的是另一个循环（查 `candidate_metrics`），所以侥幸对了；而 `runs` / `max_time_ms` 在旧的单一循环里，从来没通过。

这不是新引入的 bug，是一直存在的：runner 特意报出 `runs`（实际轮数）与 `runs_requested`（请求轮数），注释写着「快核会被自动加采样，下游要知道这个数字有多少样本撑着」—— 然后搬运环节把它丢了，下游从来没有知道过。

修法：合并成一个循环，`bench` 优先、`candidate_metrics` 兜底。同时补 `median_time_ms` 这个键：`metrics["min_time_ms"]` 从建表那一刻起装的就是 median（`kernel_min_ms = median or min or exec_time`），是个误名；不敢改它的含义（会波及 kernel_db 历史快照），所以另加一个名字说清楚的键。

配套用例 `test_every_sample_stat_survives_the_remote_path`：**直接拿 runner 的 `_sample_stats()` 真实返回值当输入**，断言每个键都出现在 metrics 里。以后 runner 加字段而 verifier 忘了搬，这里就会红。

## 四、第二个问题掀翻了我自己刚写的判据

`max/median`（窗口内抢占旁证）这一列才是本次的真正产出。它证明**这个统计量不能当判据**。

标定阶段我用的是固定 30 样本/轮，测到长核的 `max/median` 最坏 1.38，于是定阈值 2.0，并加了一条前置条件「只在 `dominance <= 0.10` 的长核区间启用」。当时以为这样两头就都对了。

真机数据推翻它，原因有**两层同向叠加**：

1. **绝对时长**（标定时已知）：一次 ~30 µs 的宿主抖动对 4.5 µs 的核是 18 倍，对 1 ms 的核只有 1.04 倍。
2. **顺序统计量随 n 抬升**（标定时没看见）：runner 按毫秒预算自动加采样。`max` 是尾部的极端次序统计量，样本越多天然越靠外。

而致命的是这两件事**同向**：要通过 `dominance <= 0.10` 这个前提，净时间必须 ≥ 9 × 地板 ≈ 182 µs；而按 50 ms 的重复预算，182 µs 的核正好换来 ~274 个样本。**「用得上这条判据的区间」恰好就是「样本最多、max 被抬得最高的区间」。**

决定性的一行是 `layernorm 16384×6144`：util=0%、同机其他租户没插队、iqr/median 只有 0.0107（主体极稳），却报出 `max/median = 1.62 ~ 1.86`（两轮），距阈值 2.0 一步之遥。把它当判据，就会系统性地把**干净**的测量判成污染 → `can_disable_recipe=False` → 闭环静默关掉。那正是缺口 1 最初的病，我差点用一条新规则把它请回来。

处置：**降格为诊断**。仍然上报、仍然写进 `reasons`（因为缺口 1 的教训是「算了没人读」，reasons 会进 Fixer / SearchAgent 的 prompt），但措辞自我声明「仅诊断，不影响本轮判定」，并另置一个 `measurement_intruder_suspected` 布尔供程序读取。真机上确认它出现在 `uninformative` 那一档的 message 里而**没有改变档位**。

要救回这条判据，得换成对 n 稳健的形式，例如「> 2×median 的样本占比」—— 占比不随 n 漂移，且真能区分「个别尾部样本」与「整体在抖」。在重写并有新数据之前不做。

### 4.1 关于标定脚本的教训

`benchmarks/calibrate_dispersion_thresholds.py` 刻意固定 30 样本/轮，本意是让各核可比。结果它把真实采样路径的一个决定性变量（n）给控制掉了，于是给出一个「看起来干净」的阈值。

**标定一个下游要用的统计量时，必须走真实的采样路径，而不是理想化的固定参数。** 这条已写进脚本自身的待办语境，脚本保留 —— 它仍然是测 iqr/median 的好工具（那个统计量对 n 不敏感），只是不能用来定 `max/median` 的阈值。

## 五、守卫与变异验证

- `test_every_sample_stat_survives_the_remote_path` —— 用 runner 的真实 `_sample_stats()` 输出驱动，断言键全覆盖。
- `TestWindowIntruderSignal.test_never_changes_validity_even_at_absurd_ratios` —— 用 2.1 / 19.17 / 500 三个比值断言档位与 `can_disable_recipe` 均不受影响。**这条断言的是「它拦不住什么」**，是少见的反向契约。
- `test_real_machine_clean_measurement_stays_valid` —— 把本次真机那一行数据（median 0.1636 / dominance 0.11 / iqr 0.0107 / max 1.86 / util 0）钉成回归锚点，断言 DEGRADED 只来自地板越线、reasons 里不得出现「抢占」。

变异验证（每次改完都确认守卫真的会红）：

| 变异 | 结果 |
|---|---|
| 去掉 `candidate_metrics` 兜底 | 3 个用例红（含新增的覆盖用例）✅ |
| 把抢占信号重新变成 `_worse(..., DEGRADED)` | 2 个用例红 ✅ |
| 第一次尝试该变异 | **perl 静默未命中，测试仍全绿** —— 我差点把「没有红」当成「守卫有效」。改用 Python 精确替换 + `assert` 锚点命中数之后才拿到真实结果 |

顺带记一次操作失误：验证变异时用 `git checkout -- <file>` 还原，把当轮尚未提交的降格改动一起冲掉了（该文件相对 HEAD 有未提交修改）。正确做法是先 `cp` 一份再覆盖还原。丢失的四处改动已逐条重做，每处都用「锚点必须命中恰好一次」的断言校验，未留下静默偏差。
