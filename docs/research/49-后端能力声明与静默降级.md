## 一、为什么现在做它

三条理由，都不是「架构洁癖」：

1. **它是六个缺口里唯一一处代码都没动过的。** 核实：全仓 `operator_agent/` 里对后端类的
   `isinstance` 只剩一处——`verifier.py:204` 的 `self._is_remote = isinstance(backend, RemoteExecutor)`，
   它派生出三处分支（`:384` L2 走远端比对还是本地比对、`:506` 要不要同机基线、
   `:522` **连 bench 字典的形状都按后端类型分叉**：remote 有 `candidate` 子字典、mock 没有）。
2. **用户明说这个项目可能接入其他 GPU 平台。** 而今天接一个新平台要改的地方不是一处，
   是第三节盘出来的**六类共 20 余处**，其中三处的失效方式是「静默给出一个像样的错值」。
3. **迁移代价已经被别人量出来了。** KernelGenBench（arXiv [2607.27231](https://arxiv.org/abs/2607.27231)，
   2026-07-22，✅ abstract 逐字核过）：*"spanning six hardware platforms"*、
   *"AutoKernel accuracy fell from 87% on NVIDIA to 25% on Iluvatar CoreX."*、
   *"specialized agents averaged 4.99 million tokens per successful operator"*。
   同一个 agent 换一个厂商掉 62 个百分点——**这不是「模型不会写」，是平台知识没有可声明的地方**。

而且第三节里有**三个当前就在生效**的缺陷（不是假想风险）：一条生产死分支、两条伪造硬件信息。

## 二、外部一手：三套机制，一个共识

### 2.1 Triton 的后端插件（本地 vendored 逐字核过，HEAD `84cae05df0`）

⚠️ 先记一个坑：`python/triton/backends/{nvidia,amd}` 在本地是**指向不存在路径的符号链接**
（`amd -> ~/repos/github/triton/third_party/amd/backend`），真文件在
`third_party/<vendor>/backend/`，且 NVIDIA 的 `BaseBackend` 子类叫 **`CUDABackend`**、在 `compiler.py` 里，
不在什么 `backend.py`。按文档里的路径去找会以为文件不存在。

四条机制，全部逐字核过：

| 机制 | 位置 | 原文要点 |
|---|---|---|
| **可选方法在基类上存在、但一调就 raise** | ✅ `python/triton/backends/driver.py:149-153` | `def allocate_default_profile_scratch(...)` **不是** `@abstractmethod`，函数体是 `raise NotImplementedError`。于是 `hasattr()` 恒为真、`getattr(..., None)` 恒不为 `None`——**「静默 no-op」在这个设计下不可表达** |
| **注册时 0 个或 >1 个实现都报错** | ✅ `python/triton/backends/__init__.py:19-29` | `_find_concrete_subclasses`: `if len(ret) == 0: raise RuntimeError(f"Found 0 concrete subclasses…")`；`if len(ret) > 1: raise`。**没有默认值、没有「取第一个」** |
| **选择后端时三种歧义全部 raise** | ✅ `python/triton/runtime/driver.py:8-21` | 指名了但不存在 → raise；指名了但 `is_active()` 为假 → raise；自动探测出 **不等于 1 个** active → raise（`f"{len(active_drivers)} active drivers … There should only be one."`）。**零个 active 是错误，不是「回退到 CPU」** |
| **能力用类属性声明，不用类型判断** | ✅ `python/triton/backends/compiler.py:24` + `third_party/amd/backend/compiler.py:141` | 基类 `supports_native_tensor_specialization = True`，AMD 覆写成 `False`。**没有任何调用方 `isinstance(backend, HIPBackend)`** |

另外两条值得单独记：

* ✅ `compiler.py:26-28`：`BaseBackend.__init__` 里 `assert self.supports_target(target)`——
  **能力校验写在基类构造函数里**，于是「拿错后端」根本构造不出来，而不是构造出来后在某个分支里被绕过。
* ✅ `compiler.py:8-14`：`GPUTarget(backend: str, arch: int|str, warp_size: int)`——
  **目标身份是数据，不是类型**。（对照本仓：`platform: str = "nvidia"` 是数据，但它被用来在
  六处 `if self.platform != "nvidia"` 里做类型判断，见 3.3。）
* ✅ 上表第 4 行那个类属性**是有读者的**，而且读者不在 Python 里：
  `python/src/specialize.cc:69` 声明 `has_native_tensor_spec_attr`、`:140` intern 这个名字、
  `:364-366` 用 `PyObject_GetAttr(backend, has_native_tensor_spec_attr)` 决定走不走
  native 的 data_ptr 对齐特化（`:371` 注释明写取不到就 graceful 落到 `false`）。⚠️ **记这条是因为它差点被写成反例**：本轮子代理在 vendored 树里
  只 grep 了 `.py`，据此报告「声明了却没人读」，并把这条当成「Triton 自己也有 3.5 那种缺陷」——
  而它的读者在 C++ 扩展里。**跨语言实现的属性，只在 Python 侧数读者等于没数**；
  「算了没人读」这条判据本身要先证明扫描范围覆盖了所有读者。
* ⚠️ 一条反面教材也在这里：Python 的 ABC **不校验签名**——`add_stages(self, stages, options, language)`

### 2.5 SYCL 2020 `aspect` ✅ **已独立核实（2026-09-29，自己下载 spec 后 grep）**

上一轮的抓取在 §3.6 截断（4.18 MB HTML），所以本篇当时把它记为待核。这次自己下全文
（`registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html`，4,179,135 字节）
剥标签后逐条 grep，五条全部成立：

* ✅ 能力是**闭合枚举**：`namespace sycl { enum class aspect : /* unspecified */ { cpu, gpu,
  accelerator, custom, emulated, host_debuggable, fp16, fp64, atomic64, image, online_compiler,
  online_linker, queue_profiling, usm_device_allocations, usm_host_allocations, … } }`。
* ✅ `aspect::emulated` 原文："A device with this aspect is **not intended for performance**,
  and instead will generally have another purpose such as emulation or profiling."
  —— 「这个器件的数字不能当性能分母」在标准里就是一句**能力声明的注释**，不是靠用法约定。
* ✅ 字符串式的扩展查询被弃用：`platform::has_extension` / `device::has_extension` 都标
  "Deprecated by SYCL 2020. [Note: Use platform::has / device::has instead.]"
  —— 与本仓 `requires_caps` 从字符串比较走向闭合枚举同方向。
* ✅ 派生谓词**定义为**能力查询而不是第二份真源：`is_gpu()` 的 Returns 逐字写作
  "The same value as `has(aspect::gpu)`"（`is_cpu` / `is_accelerator` 同型）——
  对照本仓 `capable_or_raise` 与 `capabilities` 的关系：一个定义在另一个之上，不留两份会漂的表。
* ✅ **最关键的一条区分**：`device::has(aspect)` 的签名是 `bool has (aspect asp) const`，
  Returns "The value true if this device has the given aspect"，**不抛**；抛的是**选择器**——
  typed selector 的原文是 "The SYCL class constructor using it **must throw** an exception with
  the `errc::runtime` error code if no device matching this requirement can be found."
  也就是说标准把两件事分开：**「这台设备没有这个特性」= false**，**「一个符合条件的设备都找不到」= 异常**。
  本仓对应的正是这条线：`Cap` 查询（`require()`）在没有可兑现的后端时抛 `BackendUnavailable`，
  而 `has_tma` 这类器件特性只影响配方是否入选、不抛。
  ⚠️ 反过来说：`Cap.SIMULATED_PERF` **不是** SYCL 词汇表里的东西——全文 `simulated` 出现 **0 次**
  （最接近的是 `emulated`）。这个名字是我们自己起的，别在文档里把它记成「抄 SYCL」。

这一节虽然是**事后**才核上的，但本篇的结论本来就不依赖它：`emulated` 那个意思在早已核实的
`sandbox.md:22`（完备度是被上报的事实）里同样成立，而「缺失必须响」的五处一手表述全部来自 DSH。
核它的价值在于：现在可以给「`has()` 返回 false / 找不到设备才抛」这条**分界线**标出处，
而不是只写我们的直觉。

### 2.6 算子 agent 领域怎么做：预部署环境 + 语料，没有人 type-check

⚠️ 本节 KernelEvolve 与 CudaForge 已**本轮自己核过一手出处**（KernelEvolve 下载
`/html/2512.23236v1` 全文、CudaForge 下载 abstract 页逐字对照），
GEAK / Kevin / AMDKernelVault 仍是子代理 abstract 转述。

* **KernelEvolve**（Meta，arXiv 2512.23236）：三个平台（NVIDIA/AMD/MTIA）各一个**专用
  interpreter 环境**——`meta_kernel_gpu_interpreter` / `meta_kernel_amd_interpreter` /
  `meta_kernel_mtia_interpreter`，它们是 **Bento（Meta 的 Jupyter notebook 平台）kernel**，
  由 **Conveyor** 持续重建部署；评估则异步派发到手脚架扩展过的 **FaaS**（Tasklet 资源模型
  从 CPU/RAM 扩到 GPU）端点执行。统一评估接口 + 平台知识放在**分层文件语料**里按需检索
  ——不是 Python 接口、不是类型分支。
  ⚠️ 上一轮本节写的是「**容器化** interpreter」——**那是我转述出来的词，论文里没有**：
  全文 `container` / `docker` / `sandbox` 各出现 **0 次**（本轮自己下载 `/html/2512.23236v1`
  剥标签后数过）。措辞要跟着机制改，因为 4.2 那条「不抄它」的决定当时是**建立在这个错词上的**，
  见 4.2 的更正。
* **GEAK**（AMD）/ **Kevin**（CUDA）/ **CudaForge**（NVIDIA **四张卡**：A100、RTX 6000、
  4090、3090——abstract 逐字 "generalization across GPUs (A100, RTX 6000, 4090, 3090)"；
  上一轮写的「四代卡」是错的，A100 与 3090 同为 Ampere，跨的是**档次**不是**代**）：单厂商，不做抽象。
* **AMDKernelVault**（arXiv 2609.12471）：**显式 fork**——HIPKernelGen 与 TritonKernelGen 两条流水线。
* 结论：唯一真的跨厂商跑同一条流水线的系统，抽象层次在**执行环境**（每平台一套预部署、
  由 CI 持续重建的 interpreter 包 + 一条异步评估通道）而不在语言接口，
  且**器件知识是声明出来的语料，不是探测出来的**。这与 4.3 的归属划分一致。

## 四、决定：吸纳什么、不吸纳什么

### 4.1 吸纳（五条，每条都有上面的一手出处）

1. **可选方法「在基类上存在、一调就 raise」**（Triton `driver.py:149-153`）。
   这是**单条杠杆最大**的一处改动：它让 3.2 那一整类缺陷**不可表达**——`hasattr` 恒真，
   于是 B6 从「静默 no-op」变成「第一次 L1 失败时抛 `CapabilityMissing`」。
2. **闭合的能力枚举，由提供方声明**（Triton 的类属性 ✅ + DSH `sandbox.md:22`「完备度是被上报的事实」✅；
   SYCL 的 `aspect` ⚠️ 待核）。枚举而不是字符串：DSH `:43` 的 `mode` 是四字面量联合类型，
   而本仓 `platform: str` 是自由字符串，于是「拼错」与「不支持」不可区分。
   **未知名字要拒绝，不能回答 False。**
3. **消费方在构造时声明自己需要什么**（DSH 2026-08-19 `:23,24,30`：宁可首次访问就失败，
   也不允许静默降级）。`Verifier(backend, required={…})` ⇒ 降级过的后端**构造不出来**。
4. **适配器必须保留下层的结构化失败**（postmortem 0004 Lessons，⚠️ 行号未标）。
   `CapabilityMissing` 要带**下层的原因**，不能换成自己最近的泛型类别——
   这正是 B3/B4 把 `None` 重载成两个意思的病根。
5. **双向完备性守卫 + 「先把它弄红」的纪律**（`gen-doc-graphs.ts:297-298` ✅、`testing.md:35` ✅）。
   守卫要同时抓「新后端没登记能力」与「登记里挂着已不存在的后端」；
   每条守卫上线前必须先注入回归看它变红（本轮 doc 48 的变异标定就是这个纪律，
   而它自己也被 Python 的字节码缓存骗过一轮——见 doc 48 §6.5）。

### 4.2 不吸纳（三条，理由都是具体的）

* **不做「一角色一包」的拆分。** DSH 自己在 `:25` 写"Don't split preemptively"。
  本仓是 4 个提供方 + ~3 个消费方的**扁平模块布局**，一个 ABC + 一个枚举放一个模块就是正确尺寸。
* **不在同一个改动里合并那 7 张硬件表。** `_PEAK_SOURCE`/`peak_trusted`（`verifier.py:76-88, 807-819`）
  是缺口 3 里**唯一被机械强制**的部分（未核实的分母不开判停出口）；把它压成 dataclass 的一个字段，
  有把一道**门**降格成一句**注释**的风险。合并是另一件事，可以以后做，但不要捆绑。
* **不抄 KernelEvolve 的执行环境。** ⚠️ 本条上一轮写的是「不抄它的**容器**」——那个词不是它做的
  （2.6：全文 `container`/`docker`/`sandbox` 各 0 次），它做的是**每平台一套 Bento interpreter 包 +
  Conveyor 持续重建 + FaaS 异步评估通道**。决定本身不变，但**理由要跟着真机制重说**：
  不抄是因为那条链的前提我们不具备——Meta 有一个跨厂商的**包发布系统**（Conveyor）和一个
  带 GPU 资源模型的 **FaaS 池**，所以我们能让「环境」变成一次部署而不是每轮现场装配。
  本仓的等价物——「每平台一个 runner 脚本 + `uv` 现装 + 一条 `ensure_environment` 自检」——
  **形状是对的**，缺的正是那条持续部署链；而它错的地方在别处：两个 runner 的**契约漂了**（3.6），
  那用一条对照守卫修，约 40 行。
  ⚠️ 附带一条**该抄而没抄的**：它的 "Interpreter isolation ensures reproducible profiling
  across tree search iterations" 与 "compilation occurs once during interpreter deployment
  rather than per-kernel evaluation" 讲的其实是**测量有效性**（同一环境 = 可比），
  而这一点我们已经用另一条路径做到了（环境指纹 + 漂移降 DEGRADED，见 7.9）。

### 4.3 归属划分：两种「capability」必须分开声明

DSH `:38` 点名的同名陷阱在本仓是真实存在的：

* **器件能力**（硅的事实：`has_tma`、`shared_mem_per_sm_kb`、`supported_dsls`、`launch_floor_us`）
  → **`hardware_caps.py` 继续拥有**。它已经是一套声明系统，`optimization_planner._check_caps_requirement`
  已经在按 `requires_caps` 字符串评估它，`_caps_failure_note` 已经能区分「硬件不够」与「配方拼错」。**不要搬。**
* **传输/提供方能力**（`REMOTE_VERIFY`、`SAME_DEVICE_BASELINE`、`ENV_PROVISION`、`DEPLOY`、
  `DEP_ANALYSIS`、`GPU_PINNING`、`HW_PROBED`，外加 `REAL_DEVICE`/`EMULATED`/`SIMULATED_PERF`）
  → 新的 `Backend` ABC + `Cap` 枚举拥有，**放在提供方旁边**，不进 `hardware_caps.py`。
  证明这两轴独立的例子：指向**同一台 H20** 的 `SSHExecutor` 与 `HTTPExecutor`，器件能力完全相同、
  后端能力完全不同。
* `mock_gpu.py` 声明 `{EMULATED, SIMULATED_PERF}`——**这才是 3.5 里那个没人读的 `mode` 字段应有的读者**。

### 7.1 计划外的第十项能力：`FULL_OUTPUT_TENSOR`

`isinstance(backend, RemoteExecutor)` 在 `_verify_single_set` 里其实**同时**承担两个判别：
① 走不走远端紧凑比对协议；② `execute()` 回的是全量张量还是采样。①对应
`Cap.REMOTE_VERIFY`，②在计划里没有词——而没有词就没法把 `isinstance` 拆干净。
盘点四个提供方的返回类型：SSH/HTTP/Local 三个都回 `RemoteExecutionResult`（只有
`output_sample`），只有 `MockGPU` 回 `ExecutionResult`（有 `output`），于是补
`Cap.FULL_OUTPUT_TENSOR`，由 MockGPU 单独声明；采样那一路的 `coverage` 保留在 metrics 里
（覆盖不足是数据，不能因为「比过的那部分都对」就读成通过）。

L3 那处（`_verify_performance`）反而**不需要**新词：判别看的是拿到的载荷
（`remote_bench is not None`），比按能力分派更准，顺手修掉 B4 的形状错配。

### 7.2 第七条守卫是这一片自己踩出来的

往 `SSHExecutor.__init__` **尾部**插 `@property capabilities` 时，属性体的
`return frozenset(caps)` 后面跟了原本 `__init__` 的最后一行 `self._uv_path = "…"`。
Python 不报错、不警告，那行就此不执行，而 `ensure_environment` 会在**真机上**
AttributeError——本地测试全绿，因为没有任何用例走那条路径。于是多了第 ⑥ 条守卫。

| # | 守卫（`tests/test_backend_caps.py`，21 例） | 抓什么 |
|---|---|---|
| ① | 登记表 ↔ `concrete_backends()` **双向** diff | 新增后端忘了登记 / 登记表里的僵尸条目 |
| ② | 每个后端声明的 `capabilities` == 登记表写死的那一份 | 改声明必须是一次有意识的编辑 |
| ③ | 声明了可选能力 ⇒ 解析到的方法**不是**基类存根 | 「声明多了」挪到测试期，不等运行时炸 |
| ④ | 门面五个可选方法都**只转发**（AST，去 docstring 后判） | getattr 垫片复活 |
| ⑤ | `operator_agent/` 里禁 `isinstance(x, <后端类>)` / `hasattr|getattr(backend, …)` | 类型嗅探复活 |
| ⑥ | `return`/`raise`/`break`/`continue` 之后不许有语句 | §7.2 那个 bug |
| ⑦ | `require()` 必须有真实消费方 | 「算了没人读」 |

④ 有一个坑值得记：那五个转发方法的 docstring 里**恰恰引用了**旧写法
`getattr(self.backend, "verify_function", None)` 来解释为什么不能再那么写。判据若不去掉
docstring 就会被自己的说明文字喂出假阳性——而假阳性长得像「抓到了什么」，下一个人会去
改说明文字而不是改判据。所以配了 `test_the_shim_guard_is_not_fooled_by_the_docstrings`，
它断言**前提**（说明文字里确实还有那些字样）仍然成立，前提没了这条对照就该退休。
⑤⑥ 同样各配一条已知答案对照与一条反向对照（不许「什么都拦」）。

### 7.4 假件必须声明能力，否则 monkeypatch 静默失效

改完后 21 个用例变红，全是同一个形状：

```python
backend = RemoteExecutor(mode="local")
backend.benchmark_with_baselines = lambda *a, **kw: bench   # ← 再也不会被调用
```

门面能力派生自内层 LocalExecutor（空集），消费方那道 `Cap.SAME_DEVICE_BASELINE in caps`
恒为 False。这不是测试写错，而是新模型把一类「看起来生效其实没生效」的写法暴露了出来。
`tests/backend_fakes.py` 的 `DeclaredFakeBackend` 因此把规则做成**构造期**检查，且双向：
替换了某个可选方法 ⇒ 自动声明对应能力；声明了可选能力却没给实现 ⇒ 构造时就
AssertionError。③ 那条守卫在单个假件上的缩影。

`require()` 只给了**一个**消费方：`benchmarks/harness_pass_rate.py` 开工前
`backend.require(Cap.REAL_DEVICE, Cap.SAME_DEVICE_BASELINE)`。理由是 `mode="ssh"` **当时**
只是偏好，连不上会静默降级到 CPU，那份报表会装满 CPU 数字而表头照旧写着真机；量具不许这样。
（第 2 片之后 `mode="ssh"` 已是承诺、连不上直接抛，见 §7.8；这道 `require` 因此从**唯一**
防线降为**第二**防线，但它还管着 `SAME_DEVICE_BASELINE` 那半边，所以留着。）
只给一个消费方是刻意的——一个没人调的 `require` 比没有更糟，它让读者以为需求已经声明过了。

### 7.6 第 4 片·请求侧：两个 runner 的契约对照守卫

（写这一节时响应侧「查清了没动」，理由见下文；响应侧后来在 §7.9 落了，两者是**同一个第 4 片**
的前后两半，不是一件事做两遍。）

守卫（`tests/test_runner_contract.py`，11 例）从两个 runner 的源码里解析出
「action → 它读的 payload 键」，与控制端发出的 payload 对照，五个方向都断言：action 集合
相等／同名 action 键集相等／发的都被派发／派发的都有人发／发的键都被消费。**零手抄期望值**，
认 if/elif 链与 dispatch 字典两种写法（靠 `<表>.get(action)` 认表名，否则 handler 的返回
字典会被当成分派表、凭空多出 `success`/`error` 两个假 action；靠 `args = payload` 跟别名）。
另有 `TestExtractorIsNotVacuous`：拿两段合成源码证明解析器不是空转——没有它，一个把 region
找错、于是两边都返回空集的解析器会让全部相等断言**永真地绿着**，而那个绿正是全部安全感
的来源。

`run_kernel.py` 只把 `code`/`inputs` 的读取挪进各分支（行为不变），让「这一支读哪些键」在
源码里可见；提到分派之前的话，所有 action 都会算成读了全部键。

**范围判断（需要记账）**：为了让守卫能绿，`run_kernel_xpu.py` 改了约 90 行——补
`baseline_selected`（修那个 100% 硬失败）、加 candidate-only `run_benchmark`、按
`baseline_priority` 只测一个基线并过滤本平台建不出的（cuBLAS-FP16/TF32 是 NVIDIA 独有通路；
被过滤的名字记进 `baseline_attempts` 而不是单开字段，因为控制端按闭合名单搬运响应）、
`precision` 改为**显式拒绝**而不是收下再忽略（该文件数值门只有绝对项：喂 fp16 会误杀合法核，
不喂就是拿 fp32 的成绩充当 fp16）。这与「昆仑芯屏蔽掉就行，不用大改」有张力；选择改而不是
把 xpu 排除在守卫之外的理由是：排除等于让一个已知分叉的 runner 永久无人看守。
⚠️ **这 90 行没有在真昆仑芯上跑过**（无该硬件）。AST 守卫只保证请求侧契约对齐，不保证运行时

### 7.8 第 2 片：`mode="ssh"` 从偏好变成承诺（S3/S4/S6 + A3）

`mode` 现在有三种语义，写在 `RemoteExecutor` 的类 docstring 里：`"ssh"`/`"http"` 是**承诺**
（探测失败抛 `BackendUnavailable`，不试别的传输、不落到 CPU）；`"auto"` 是**偏好**（仍可一路
降到本机 CPU，但降级记进 `Resolution.degraded`）；`"local"` 是显式选择本机 CPU。

- **S3** 梯子最后那级无条件 `self._backend = LocalExecutor()` 删掉了。失败时**不给
  `_backend` 赋值**，于是下一次访问会再抛一次 —— 失败状态不该被缓存成一个能用的对象
  （DSH：*it never degrades to a default value*）。
- **S4** `LocalExecutor.check_connection()`（恒 True）**删掉而不是改成返回 False**：对 CPU
  回退问「能不能连上」没有意义，它不是远端；降级到它是梯子的**终点**，不是一次探测的结果。
  两个真传输的 `check_connection() -> bool` 换成 `probe_connection() -> (ok, reason)`：
  旧写法把异常吞成 False，于是「连不上」在日志里只剩一行 print，而**为什么**连不上
  （DNS / 认证 / 超时）永远查不到。
- **S6** `_lock_key()` 改为 `self.backend.lock_identity()`，按**解析后的**后端取键。旧写法按
  请求的 `self._mode`：`mode="auto"` 降级后键是 `auto:<host>`，而 `if self._mode == "local"`
  对它永远不触发 ⇒ 两个都跑在本机 CPU 上的后端拿到**两把不同的锁**，可以并发争同一份 CPU。
  `lock_identity()` 是 `Backend` 上的新方法（默认 `return self.label`），SSH 覆写成
  `ssh:<target>` **不带 platform** —— 锁保护的是那张卡，不是那份配置，所以
  `SSHExecutor@h(nvidia)` 与 `SSHExecutor@h(xpu)` 必须共用一把锁（`label` 做不到这一点，
  这也是为什么不能直接用 `label` 当锁键）。
- **A3** 三个 `test_nvidia_*` 驱动里的 `if "LocalExecutor" in remote.name:` + 假 H20 兜底
  整段删掉，换成一行 `remote.require(Cap.REAL_DEVICE, Cap.SAME_DEVICE_BASELINE)`。
  删掉的那段值得原样记一次，因为它是这类缺陷里最坏的形状：

  ```python
  backend = MockGPU(name="MockH20", compute_units=78, warp_size=32)
  ```

  **名字与 SM 数都是真的，只有「它是模拟器」这件事是假的** —— 于是产出的性能数字看起来
  完全像 H20 的，而 `metrics["backend"]` 里写的还是 `MockH20`。三个驱动各抄了一遍。

**变异标定：10 条注入全部变红，无逃逸**（`tests/test_backend_resolution.py`，21 例）。
其中 **M5 第一次真的逃逸了**：把真 `SSHExecutor.probe_connection` 的 `except` 改回
「吞掉异常只返 False」，21 条用例全绿。原因是那些 reason 断言喂的是**假传输** ——
守卫测的是我的假件，不是产品代码。补了三条驱动**真实现**的用例（只把最外层那次 I/O 换成
必抛/必返 503），M5 与新增的 M9/M10 才都变红。**假件可以让守卫绿，但假件不能被守卫当成
被测对象** —— 与 doc 48 §6.5 那两条逃逸的变异同一个教训，只是换了一层。

### 7.9 第 4 片（响应侧）：三个「算了没人读」第一次有了读者

§3.5 数出的三处「算了没人读」——**环境指纹**、`mode` 的 `"simulated"`、`device=="cpu"`——
这一片把它们从「算出来丢掉的字符串」变成判据的输入。三条各自独立，但共用同一条纪律：
**判据走声明（`Cap`），载荷自报的字符串只用来与声明对照**，不从 `device`/`name` 的子串去
推断能力（§3.1 记的三处名字匹配毛病就是这一类）。

**① 出处门（`measurement.provenance_conflicts` + `Verifier._refuse_l3_pass`）**
任务在 `TargetSpec.required_caps` 里声明它要什么，执行侧在 `capabilities` 里声明它有什么，
两侧相减就是 `capability_shortfall`。另外收一份**自相矛盾**：声明了 `REAL_DEVICE` 却报
`mode="simulated"` / `device="cpu"`，或载荷自报 `simulated` 而后端没声明 `SIMULATED_PERF`
（那是一次未声明的降级）。两者后果不同，所以分成两份而不是一份：

- shortfall ⇒ 这一轮 L3 **不许 `passed=True`**；
- 只有矛盾 ⇒ 降 `UNINFORMATIVE`，但**不**拒绝通过。

第二条是刻意的：本地 mock 运行本来就没有真卡，如果「矛盾」单独就够格拒绝，一份老实写着
`device="cpu"` 的本地运行会被判死——那是**把观测当判据**。这条边界有专门的用例
（`test_contradiction_alone_does_not_refuse_the_pass`）与专门的变异（M8）。

`l3_pass_is_refused` 与既有 `can_gate` **分成两条**，理由写进了 docstring：`can_gate=False`
说的是「这个数字撑不住结论」，历史上它不把 `passed` 拉成 False，而 launch 地板支配那一档的
核可能确实是对的；出处不对是另一回事——那份加速比不是测得不准，是**压根没测**，
「通过」这个结论没有对象。三条 L3 返回路径（远程 / 本机 reference / 绝对 GFLOPS 兜底）
全部过这道门，并由一条 AST 守卫 `TestEveryL3ReturnPathIsGated` 盯着「以后新增的 L3
return 有没有被门住」——这条守卫自己配了两条自核（看得见一个没门住的 return、
不被 docstring 骗），正是 §7.2 与 §7.4 各踩过一次的坑。

顺带把语料门也接上：`persist_decision` 新增 `backend_real_device` 一条。用 `is False`
而不是 `not`——老产物没这个键，不做追溯性重判。于是「纯模拟基准与真机实测在产物里
权威性等价」这条（§3.5 第 2 处）第一次有了后果。

**② 环境漂移（`environment.fingerprint_of` / `compare_fingerprints`）**
注释写着「用于环境漂移自检」而全仓 3 次命中都在那 6 行里的那个机制，现在真的存在了：
构造、比较、**三个读者**（`result.json`、`execution_snapshot.json`、L3 有效性输入）。
四个设计决定都值得记：

- **执行侧身份单独立一个键**（`backend`）。门面 `RemoteExecutor(mode="ssh")` 连不上时
  解析到 `LocalExecutor`，器件名与三个版本号**一项都不会变**，只有这个键会变——
  而这正是 §3.1 A1 的失效形态。只比硬件字面的指纹对这类漂移是瞎的。
- **`hw_info` 里缺的键就缺席，不填默认值**。「上一次报了 `triton_version`、这一次没报」
  本身就是一种漂移，填平会把它抹掉（与 §3.3「把不知道翻译成一个像样的值」同一族）。
- **「没有上一次」与「比过了、一样」是两件事**：`EnvironmentDrift.comparable` 三态。
  混成一个空列表就会把前者读成后者，而那正是 `assess()` 里「launch 地板未知」
  已经付过学费的坑（缺证据 ≠ 检查过了）。
- **只降到 `DEGRADED`，且不设阈值**。「torch 从 2.14 变成 2.15 该不该让一次运行作废」
  本机没有分布能回答，现在定阈值就是编一个门。所以漂移只做到「变了哪些键」可见，
  不许禁用配方、不许累计停滞、**不许据此判核失败**——按项目「观测先于判定」处置。

「上一次」的来源有两个，优先级是查过的：**续跑快照优先**，因为那条路径上
`best_gflops`、`iteration_history`、已禁用配方全是从上一次继承来的，环境一变那些数就不再
可比——这是漂移唯一会**直接污染判决**的场合；没有续跑才回落到产物库里最近一次同
`(算子, 硬件)` 的运行。分桶而不是全库找最近一份，是为了不把「换了一个任务」误报成
「换了环境」。`PREVIOUS_SCAN_LIMIT = 200` 的上限也不是臆造的：仓库 `output/` 里存着
**2872 份没有指纹的**历史产物（写这一片时实测的数），不设上限每次运行都要把它们全读一遍
才承认「没有上一次」。

⚠️ 刻意**没有**改成每轮重探一次 `get_hardware_info()`：那会给每一轮加一次远端往返，
而「这一轮跑在哪张卡上」已经随 L3 载荷回来了（`selected_gpu`/`device`/`sm_clock_*`）。
轮内漂移用那些键复盘，跨运行漂移用指纹。

**③ 一处列举会过期的地方**：Conductor 汇总里那句「(污染 / launch 地板支配)」是硬编码的
两项，而判据已经有五项（还有样本离散度、数字的出处、环境漂移）。改成只报数、
逐轮原因指回上面已经打过的那一遍——这是「算了没人读」的镜像毛病：**算了也没人更新**。

**变异标定：20 条注入全部变红，无逃逸**（`tests/test_environment_drift.py` 32 例 +
`tests/test_l3_provenance.py` 51 例 = 83 例，全量 549 → **632 passed**，长期红的 4 条不变。
前 15 条是这一片本体，后 5 条是真机探针逼出来的那几个 metrics 键，见本节末）。
覆盖的每一条都是一个机制而不是一句注释：shortfall 恒空（M1，15 红）、L3 通过门整个拆掉
（M2，7 红）、调用方不再传能力（M7，11 红）、矛盾单独够格拒绝（M8，1 红）、能力事实算了
不落盘（M9，4 红）、`device` 改回子串匹配（M10，1 红）、conductor 不把漂移交给 Verifier
（M11，2 红）、指纹/漂移不落 `result.json`（M12/M13，9 红 / 2 红）、快照不带指纹
（M14，2 红）、找不到上一次返回 `{}` 而不是 None（M15，1 红）、漂移不再降档（M4，4 红）、
缺的键填默认值（M5，2 红）、「没有上一次」被读成「没漂移」（M6，15 红）、语料门不再读那个键
（M3，1 红）。

⚠️ **M2 第一次找错了文件**：脚本按 `measurement.py` 去替换 `_refuse_l3_pass` 的那行，
`count=0` 如实报了「模式没找到」并跳过，而不是随便挑一处替换——§7.4 那条「变异模式必须唯一」
的规矩这次是以「必须能找到」的形式又生效了一遍。**变异标定本身也要先标定**，这条又记一次。

**真机标定（2026-09-28，`benchmarks/verify_provenance_gate.py`，`algorithm-h20` GPU 2，EXIT=0）**：
上面那条 ⚠️ 已经还了。五臂只差一个变量（`required_caps` 或注入一次漂移），用
`min_speedup=0.0` 让基线臂的 `passed` 恒真——**不是放水，是让任何 False 都只能来自那道门**
（与 `verify_measurement_validity.py` 同一口径，同样直调 `_verify_performance` 绕开 L1/L2）：

| 臂 | 注入 | 实得 |
|---|---|---|
| A | 要求真机已有的 `{REAL_DEVICE, SAME_DEVICE_BASELINE}` | `passed=True`，拒绝位 False，档位 `degraded` |
| B | A + `FULL_OUTPUT_TENSOR`（真机**没**声明） | **`passed=False`**，`shortfall=['full_output_tensor']`，拒绝位 True，档位 `uninformative` |
| C | 不声明（老行为） | `passed=True` |
| D | 只要求 `{DEPLOY}`（真机有） | `passed=True` ⇒ 门看的是**差集**，不是「required_caps 非空」 |
| E | 能力齐全 + 伪造一项 `torch_version` 漂移 | **`passed=True`**、档位 `degraded`、拒绝位 False ⇒ 漂移只降档不判死，「观测先于判定」在真机上成立 |

同一轮顺带读出三个真机事实：layernorm 16384×6144 fp16 在同机 `PyTorch Eager` 面前是
**1.41x**、带宽利用率 61.9%、`AI=1.75` ⇒ memory-bound，launch 地板占比 11.1%（> 10% ⇒
`degraded`，与 doc 31 那档一致）；卡与 4 个其他进程共享而瞬时 util=0%；分母那一行报的是
148 TFLOPS 且自带出处串。

**这一轮还挖出一个本片自己留下的「算了没人读」**——而且不是读代码读出来的，是**写读数
代码时撞出来的**：探针去 `metrics` 里取 `measurement_capability_shortfall`，取到 `None`。
`capability_shortfall` / `provenance_conflict` / `environment_drift` 和那个拒绝位当时只活在
内存里的 `MeasurementAssessment` 上，从没进 `metrics`，也就进不了 `result.json`；下游想区分
「核太慢所以没过」与「压根没测所以没资格过」只能去 string-match message 里那个 ⛔。
修法是四个键一起进 `as_metrics()`，并且**沿用同一条三态纪律**：没做过出处检查时**不写**
（缺键 ≠ 空列表，否则下游把「没检查」读成「检查过、干净的」）；再给拒绝位配一个生产读者
（`Conductor` 汇总里单独数 `refused_rounds`，与 `invalid_measurement_rounds` 并列——两者含义
相反：一个是「测了但撑不住结论」，一个是「压根没测过可判定的东西」）。
新增 5 例 + 5 条变异（拒绝位不写 / shortfall 不写 / 没检查也写空列表 / 漂移不进 metrics /
conductor 不再读拒绝位）**全部变红、无逃逸**。

教训值得单独记一句，因为它比这条缺陷本身更通用：**判据算出来的东西要立刻写一个「从产物
里读回来」的探针**，而不是只写「它被消费了」的单测——单测读的是内存对象，看不见落盘边界。

### 7.12 #52：报表里「跑在哪张卡」改从执行侧取（2026-09-29）

**形状**：`benchmarks/harness_pass_rate.py` 的 payload 写
`"gpu": os.environ.get("OPERATOR_AGENT_GPU", "(未固定)")`，而 `SSHExecutor` **从不读**那个变量
——它在本进程按 (低利用率, 高显存余量) 自动选一张卡存进 `_gpu_pin`，再把**自己选中的号**前缀给远端。
于是 #49 那次我给进程设了 `OPERATOR_AGENT_GPU=2`，日志打的是「固定使用 GPU 7」，报表会写 2。
这是「算了没人读」那一族的**反面变体**：字段有人读，但**读错了对象** —— 记录的是「用户想要什么」，
被当成了「发生了什么」。

**修法（三件，缺一件还会漂）**
1. `Backend.selected_gpu`（基类 property，默认 `None`）+ `SSHExecutor` 覆写 + 门面纯转发。
   基类**必须有**这个 property：否则「这个后端能不能告诉我用哪张卡」又只能靠 `hasattr` 猜
   （§4.1 第 1 条那条病）。它**不触发**一次 ssh 往返 —— 问「它在用哪张卡」不该变成「再花一次往返」。
2. `_gpu_pin` 的三态（`None` 未解析 / `-1` 解析过但不固定 / `>=0` 卡号）在对外视图里折叠成两态，
   **不往值里塞哨兵数**：「没有卡」与「第 -1 号卡」不能共用一个数。剩下那一态由
   `Cap.GPU_PINNING` 与值**合起来**表达，所以报表有三种字符串：不具备固定 / 具备但这轮没解析出号 /
   就是这张卡。把它们都塌成 `(未固定)` 就是把「压根没有这件事」记成「有但没做成」。
3. 报表的顶层 `gpu` 字符串换成 `device` 对象（`gpu/state/can_pin/requested_env/conflicts/source`），
   并在「用户设了而不一致」时打一行警告。⚠️ 今天**没有**受支持的钉卡开关 —— 要真的钉住某张卡得改
   `_pinned_gpu()` 的选卡策略，那是行为改动、需要另一次对照（这条也写进 `docs/user_guide.md`
   那一行，因为它原本被文档当成一个可用的运行期开关）。

**守卫**：16 例（10 条报表侧 + 6 条执行侧），含一条**源码级**守卫：那个环境变量的读取只许活在
`device_record` 里当对照，别处再出现就红。

**变异标定：10 条注入全部变红、无逃逸**，其中一条给「守卫空转」补了**第三种形态**（值得单记）：
源码守卫第一版只认字面量 `os.environ.get("OPERATOR_AGENT_GPU")`，而真代码写的是
`env.get(...)`（`env` 是那个 `env=None → os.environ` 的默认参数）——于是扫描器对**真代码返回空集**，
那条「只许在 device_record 里」的断言就会因为「哪儿都没找到」而恒真地绿。
以前的两种空转是「解析区域找错」和「模式被 docstring 喂出假阳性」，这次是
**解析的写法比被测代码窄**：判据扫不到的东西，等于判据没写过。
控制用例现在同时喂两种写法（直接读 `os.environ` 与经由局部别名），并断言两个函数名都被认出。

**真机标定**：并入 `benchmarks/verify_hardware_probe.py`（判据数随切片增长，以脚本自己头部那张表为准；
#52 落地时 13 项，H20 上全 ✅ —— 其中 7c 那条后来被查明是**靠运气绿的**，见 §7.13 末）。
这一条的「已知会被看见」信号是**跨源核对**：`ex.selected_gpu`（控制端记的号）必须等于
远端 runner 在同一份载荷里自报的 `selected_gpu`。单看控制端自洽是不够的——
报表与代码来自同一次错误就一起错。⚠️ 那个号是**自动选的、每轮可以不同**（§7.13 重跑时两次
都落在 GPU 2，而 #52 那轮是 7），所以任何把它写成字面量的判据或文档都是错的。
另外两条：读 `selected_gpu` 不增加 `_ssh_exec` 次数；
向 `device_record` 注入一个**必然不等于实卡**的号时 `conflicts` 必须为真而 `gpu` 仍是实卡
（⚠️ 原文这里写的是「注入 `{"OPERATOR_AGENT_GPU": "2"}`」—— 那个字面量与自动选卡撞车过一次，已改）。

⚠️ **已付的钱不能重取**：#49 前两份基线报表里的 `gpu` 字段仍是本地环境变量值，永久不可信

交错计时的，所以加速比与通过率仍然有效；受影响的是元数据。

### 7.13 §八 第 3 条：推断路径从「裸默认」改成「默认不承诺」（2026-09-29）

**改了什么**：`detect_hardware_caps` 的推断路径原来第一行是 `HardwareCaps(vendor=…, device_name=…,
compute_capability=…, sm_count=…)` —— 只填四个字段，**其余全部继承 dataclass 默认**。默认里
`has_block_reduce / has_warp_shuffle / has_warp_primitives / has_shared_memory / has_atomic_fadd /
has_fast_math` 是 `True`，`supported_dsls` 是 `{"cuda_c","python"}`。于是一张 vendor/device/cc
三者皆空的卡拿到的是「这是一台支持 CUDA C、有共享内存与 warp shuffle 的类 NVIDIA 设备」，
而同一个模块的 `unknown_caps()` 对同一件事给 False + 空集：**两个「不知道」的口径相反**，
且推断路径是乐观的那一个。现在推断路径 `caps = unknown_caps(...)` 起步，只往上加该分支能推出来的东西：
`nvidia` 分支把那六项**显式**写 True（依据是「已知这是 CUDA 设备」= PTX ISA 在整个受支持架构区间
都保证的事，不是默认值替它答应），`cpu` 分支保持全 False（旧写法在那里**只**否认了 warp shuffle，
其余五项是默认值答应的 —— 同一个分支一边说「这不是 GPU」一边宣称 `has_shared_memory=True`）。

**没有动的东西，以及为什么**：dataclass 那六个 `True` 默认**保留**。表里 8 个条目有 5 个从没显式写过
`has_warp_primitives / has_shared_memory / has_fast_math`（`has_block_reduce / has_atomic_fadd`
只在 a100、h20、mock 三处写过），翻默认等于**同时改掉每一张已知卡的承诺**，包括 H20 —— 那会把
「哪些配方还选得上」这件事变成一次无人对照的行为改动，与本条要修的东西不成比例。
代价是留下一处不对称：已知卡的这六项仍然来自默认值而不是来自条目自己，已记成 §八 第 10 条。

**口径变化实测**（把 HEAD 那份模块装成 `hc_old` 与工作树那份并排跑，逐个取样例对照全字段）：

### 7.15 缺口 4 的另一半：检索排序里「没测过的先验数」赢了测过的数（2026-09-29，#51①）

### 7.16 #50：把「墙钟加速比 ≥ 阈值」这类判据与机器忙不忙解耦（2026-09-29）

§7.7 记下过这件事：`test_p0_3` 有一条断言控制机 CPU 上**真测**的加速比 ≥0.50x，
两个后台 agent 并发时全量跑约 **3/24** 次多出一条红，机器安静时 HEAD 与工作树各 12 次全绿。
本轮把它清掉，并顺手把同一文件里另一条同形状的断言一起改了。

**取证先做，改法由数据定。** 在 6–8 个 CPU 占用进程下重复跑这个文件 8 次：
softmax 那条改完后 **0 次红**，而红出来的是**另一条** ——
`test_equal_impl_passes_with_speedup_metrics`（「同一实现应当判通过」，同样是拿真实比值当阈值）。
⇒ 「那条负载敏感的用例」本身也是一个**按名字归因**的假设（与 §7.14 同一个教训的第二次落地）。

**两条的改法不同，因为它们想守的东西不同：**
1. `test_softmax_uses_memory_bound_metrics` 想守的是**管线**（访存型算子必须落到 memory 轴、
   判定必须读加速比、阈值必须传到判定处）。改成断言 `bound_type=="memory"`、
   `speedup_vs_baseline > 0`、`min_speedup_required == 0.5`，**不再断言 `r.passed`**。
2. 「判定到底读的是哪个数」这件事本来就该用**确定性的量**来测 ⇒ 新增
   `TestSpeedupGateIsAFunctionOfTheRatio`：候选固定 2.0 ms、基线固定 3.0 ms
   （`_FixedTiming(MockGPU)` 换掉计时、`mock.patch.object(verifier, "_measure_baseline")`
   给出已知基线），于是加速比是**算出来的 1.50x**。阈值放 1.4 必须过、放 1.6 必须拒
   （拒的时候还得点名「加速比」并印出 1.50x）。第三条是量具自检：报出来的比值必须等于
   我注入的幅度 —— 这条不是装饰，M3（把上报的比值乘 2）只有它能抓到。
3. 同实现那条改成**单向一致性**断言：`if r.passed:` 就要求它自己报出的比值 ≥ 阈值
   （通过了不许自相矛盾）。不做双向相等，因为 `passed` 还可以被测量有效性门合理拒 —— 双向
   断言会把「机器太忙所以这次不可信」这个正确结论测成一条假红。

**负载实验**：8 个 CPU 占用进程下 12 次单文件全绿；同一负载下全量 2 次
**707 passed / 0 failed**。改动前同条件是 8 次里 1 次红（§7.7 当年量到的是 3/24）。

**守卫与变异**：+3 例（**4 条变异全部变红**：阈值写死 0.5 → 2 红；`passed=True` 恒过 → 2 红；
上报比值乘 2 → 1 红；不再回报 `min_speedup_required` → 1 红）。
测试 704 → **707 passed / 0 failed / 3 skipped**。
⚠️ 这不是「判据不再需要阈值」，而是把**用真机噪声去验证一个规则**换成了
**用已知量去验证规则、用真机去验证管线** —— 与 §7.13 那条通则同一形状：
判据里任何依赖非确定性测量的期望值，要么由那次测量派生，要么把测量换成可注入的已知量。

### 7.17 语料记账的真机核对：探针自己 15 项全绿，而它把记录写进了仓库（2026-09-29，还 §八 第 13 条的一半）

**为什么再跑一次真机**：§八 第 13 条记的是「§7.14/§7.15 只有离线用例」。离线用例喂的是我自己
写的错误文本，而签名 `level|cls|frame` 的三个成分里，`cls` 到底走关键词表还是走「最后一个异常名」、
`frame` 在远端回传的文本里是不是恒为 `-`、真实错误文本能不能在 JSONL 里逐字往返 —— 都取决于
远端那份载荷长什么样。doc 45 §八 的三条改判条件要的是**真实文本的分布**，而当时只有 3 条。
新驱动 `benchmarks/verify_corpus_honesty.py`：六个各有独立根因的失败（四条设计成必须到了远端才红、
两条设计成被本地预检拦住），全部经**生产函数** `Conductor._record_failure` / `_save_to_db` 入库，
语料注到 `tempfile` 目录，不烧一个 LLM token。

**第一个发现的不是语料，是探针自己。** 读数印出「19 条记录 / 6 个不同签名」，而临时目录里那个
`failure_db.jsonl` **一行都没有**。原因在 `Conductor.__init__`：

```python
self.failure_db = failure_db or FailureDatabase()     # ← 修前
```

`FailureDatabase` 定义了 `__len__`（返回记录数），于是**一个刚建好、还没有记录的实例是 falsy 的**
—— `or` 把调用方给的实例换成一个新的默认实例，它绑到仓库的 `output/failure_db.jsonl`。后果链有
两层，第二层才是重点：探针读的、判的、断言的，全是那个**被换上去的**实例，所以它的每一条记账
判据都绿，而那 7 条探针记录正在污染**下一次运行要重放进 Fixer prompt 的语料**。仓库语料从 19 行
被写到 26 行；已摘回 19 行（原文件留了 `output/failure_db.jsonl.bak-probe-20260929`，只删这次加的
那 7 行）。

这就是缺口 5 那一族的最后一处，只是它不在后端层而在**依赖注入层**：`mode="ssh"` 那把永远成功的
梯子拆掉之后（§7.8），`x or Default()` 是形状相同的那一把 —— 显式给的协作者被无声换成一个默认
实例。**通则：注入的协作者不许用真值性判断来「兜底」，要用 `is None`；而任何「我把东西交出去了」
这类前提，观察面必须同时含身份（`is`）与落点（它要写的路径）** —— 只查身份会漏掉「对象对了但路径
不对」，只查落点会漏掉这次这种「写进了另一个实例」。修后：

```python
self.backend = backend if backend is not None else MockGPU()
self.kernel_db = kernel_db if kernel_db is not None else KernelDatabase()
self.failure_db = failure_db if failure_db is not None else FailureDatabase()
```

守卫 `tests/test_kernel_db_persistence.py::TestInjectedCorpusIsTheOneWritten` 两条：一条断言身份 +

照样可用（防「修 = 强制注入」）。探针侧加 J14（两个注入实例就是被写的实例）与 J10（仓库语料一行
没多），并把落点确认提到**烧 GPU 时间之前** —— 一旦发现写到仓库就立刻退出，不再往下污染。

**第二个发现是签名本身，方向和 doc 45 §八 第 1 条相反。** 那一条担心的是碎分（签名数≈记录数，

27. **检索没匹配到时返回整套候选，并把它们标成「相似度命中」**（同一次、由变异标定撞出）
    —— `FailureDatabase.search_by_error` 的 docstring 声明按词元 Jaccard 排序，而
    `kernel_db.py` 里有三处兜底把「没找到」写成「找到了」：`if not error_text` /
    `if not error_tokens` 两处 `return candidates[:limit]`，末尾 `... or candidates[:limit]`。
    本仓错误文案是中文，而 `_tokenize` 只认 `[a-z0-9_]+` ⇒ **中文报错一个词元都取不出来**，
    于是每条中文报错的运行都走第二条兜底，把整套同类历史原样带回；`fixer.py:423` 的标签
    是按「在不在这份返回列表里」算的，这些记录全被印成 `[错误相似度命中]`。
    发现方式不是读代码：M9a（滤掉上下文检索里的 L3）本该让用例红，却全绿 —— 那条记录
    从假命中那条路回来了。**修法**是三处都返回空：冷启动覆盖本来就由调用方并进来的
    `search_by_context` 提供，兜底没买到任何东西，只买到一个假标签。
    附带一条夹具纪律：这类用例必须 `FailureDatabase(jsonl_path="off")` —— 默认构造会重放
    仓库自己的 `output/failure_db.jsonl`，第一次写的时候真语料把断言喂饱了。
    **通则**：**兜底返回值必须与它声称的判据同源**。一条声明「按 X 匹配」的检索在「X 不成立」
    时返回非空，等于用返回值的存在性冒充 X 成立；而下游几乎总会用存在性打标签。

28. **新分支的判据与产它的返回值不同形 ⇒ 那条分支永远为假**（2026-09-29，#76① 第 2 片）
    —— Fabrica 那三路分流落到代码上只有第三路是新的，而它第一版是**死文字**：
    `if signature == "interface_mismatch"` 里的 `signature` 来自
    `kernel_db.failure_signature()`，那个函数返回三段 `层级|类名|最内层帧`
    （拿门自己的输出实测：`"L1|interface_mismatch|-"`），与裸类名永远不相等。
    它不会红：`stage_directive` 照样返回非空取向、模板里 `{{stage_directive}}` 照样有读者、
    「取向永不为空」那条用例照样绿 —— 这就是「算了没人读」换了个形态：**值算了、有人读，
    但读它的那条分支从不成立**。修法是把取类名这件事放进 `kernel_db`（`failure_class_of`，

    **通则**：新增分支时除了问「它会不会生效」，还要问「它比的那个值的**形状**是不是产它的那个

    （CHECKLOG I18；doc 55 §3.3）
