# 62 — 常驻远端会话：传输固定开销 4.5 s → 0.038 s，而每次测量只快了 2.4×

日期：2026-10-01。真机：8×H20 的 `algorithm-h20`（会话钉住 GPU 2）。控制机：macOS，无本地 GPU。
跑法：`python3 benchmarks/measure_session_vs_oneshot.py`；协议守卫 `pytest tests/test_persistent_session.py`。

---

## 一、为什么要试它

doc 61 §五 把账算到了这一层：一次心跳 8.6 s 墙钟，而两条臂的测量合计只有 18.8 ms ——
99.8% 是固定开销。拆开看（doc 62 的实测，见 §四）：ssh 握手 0.57 s、`import torch` 1.09 s、
CUDA 上下文 0.20 s、首个张量 0.24 s、runner 本体 import、每调用一次的 JSON 往返。
于是问题变成：**固定开销里有多少是「每次新起一个进程」造成的**。

答案是几乎全部 —— 但那不等于测量就快 30 倍，见 §三。

## 二、做法：一条连接、一个进程、多请求

`remote_scripts/runner_server.py`（新）+ `SSHExecutor(persistent=True)`（默认**关**）：

    ssh <host> 'cd ~/operator_agent && uv run python -u runner_server.py'
    请求  {"id": <标量>, "action": "...", ...}
    响应  {"id": <原样回显>, "result": {...}}

四条设计约束，每条都对应一个具体失效：

1. **共用同一份分派**：`run_kernel.py` 里那段 `if action == ...` 链被整段搬进
   `run_action(payload)`，`__main__`（一次性）与常驻服务端都只调它 —— 抄第二套 if 链
   的代价是两边慢慢漂开。契约测试已扩成「两个分派现场」：kernel runner（每平台一个）
   与常驻服务端，服务端专属 action（`ping`/`shutdown`）**不许**出现在 kernel runner 里。
2. **id 回显是归因设施**：没回显（进程死了 / 还在算）、回显且 `success=false`（跑了且
   失败，可归因）、回显 id 不是自己发的（流错位）—— 三态分开。一次性路径把这三态折成
   一个 `success=False`，那正是 doc 60 §二 记的读数缺陷。修在 `SessionError.session_state`。
3. **stdout 只许走协议行**：处理请求期间把 `sys.stdout` 换成 stderr（uv/triton 会往
   stdout 打东西）；杂音行不算回答、也不判死 —— 真错位会以「id 对不上」的形式出现。
4. **stderr 必须有人读**：远端 stderr 也是管道，写满 64 KB 没人读，远端就**阻塞在 print 上**，
   表现成「测量突然全部超时」。读线程 + 排水线程 + 会话内锁（一条会话是共享通道，
   两个并发调用会互相读走对方的回显；锁在里面，不指望调用方守纪律）。

## 三、三个数

### ① 每次测量的墙钟（24×24 朴素 matmul，Python 分支，n=5）

| | 墙钟 median | 读数 median | 读数 mad/med |
|---|---|---|---|
| 一次性 | **4.570 s** | 2.094 ms | 0.0027 |
| 常驻 | **1.870 s** | 2.096 ms | 0.0005 |

**2.4×**。首次调用 8.65 s（含 deploy + 服务端 import + 握手），会话钉住 GPU 2。

### ② 一次心跳（`heartbeat(backend_bench_fn(backend))`）

| | 墙钟 | 慢/好 |
|---|---|---|
| 一次性 | 8.75 s | 7.93 |
| 常驻 | **3.75 s** | 7.95 |

2.3×，分离度与 doc 61 的三次（8.09 / 8.07 / 7.87）在同一个带上 —— 这条是两条路
**互相对上**的证据，不是各自自述。

### ③ 重复性：常驻进程会不会改变读数？（triton matmul @1024³，CUDA event 分支，n=5）

| | 读数 median | mad/med |
|---|---|---|
| 一次性 | 0.106 ms | 0.0030 |
| 常驻 | 0.106 ms | **0.0003** |

两条路差 **0.36%**，常驻的跨次离散度反而更低。**没测到冷启动偏置** —— 但这条只覆盖
一个形状、且 runner 自带 `warmup=1`。要掀翻默认路径还得重标 doc 31（launch 地板
18.69 µs）、doc 40（DVFS）、doc 37（热冷两层）那三套阈值。

## 四、账要对平：省下的是传输，剩下的是量具自己

会话内分段实测（同一条会话，各测 3~5 次取 median）：

| 会话内往返 | 耗时 |
|---|---|
| `ping`（纯框架，无 GPU 无 nvidia-smi） | **0.038 s** |
| `gpu_info`（起一次 nvidia-smi） | 0.367 s |
| `benchmark`（24×24） | 1.836 s |

所以：**传输/框架 4.5 s → 0.038 s**（这正是「每次新起一个进程」的全部代价），而每次
测量的墙钟只从 4.57 s 降到 1.87 s，因为剩下的 1.83 s 里：

- ~1.47 s 是 `benchmark` 支路自带的 `_sample_gpu_idle()`（**隔 1.2 s 采两次**卡上占用）
  与第二次 `read_gpu_state`，
- 0.33 s 是那次 nvidia-smi，
- 实测只有 ~2 ms。

**即：会话把传输开销清掉之后，每次测量的大头变成了量具自己的采样政策。** 那是一个
独立决定（要防邻居抢卡就得付这个钱；也可以与测量并行采、或只在上一窗有污染时才加密
采样），不属于本轮。

## 五、收尾到静止（以及我的检测器先撒了一次谎）

只杀本地 `ssh` **不保证**远端进程停（`benchmarks/_scratch.py` 的纪律），所以 `close()`
的顺序是：发 `shutdown` → 关 stdin（EOF 才是远端真正退出的信号）→ 等 → 才 terminate/kill。

第一版核查写的是 `pgrep -u $(whoami) -f runner_server.py`，它**匹配到自己那条命令行**
（执行该 pgrep 的 shell argv 里就带着这个字符串），于是报出一个不存在的残留 pid。
改成两个不自匹配的判据后实测：

```
服务端自报 pid=322402 → GONE
ps 全表里剩下的 runner_server 行: (无)
```

挂号 **CHECKLOG H5**：过程存活判据不能用会匹配到自己的模式。这类「量具先撒谎」的坑
本仓已经踩过同族（I4 的文本子串判据）。

## 六、结论：常驻可用，默认路径**不换**

- **换的理由不充分**：真正的瓶颈已经从「传输」挪到「量具的采样政策」，换默认路径
  换不来那 1.8 s；而常驻带来三个**新的失效面** —— 会话死在测量中间（世界未知那一格
  谁记账）、进程内状态跨请求（今天的「每次新进程」是天然隔离）、以及已标定阈值需要重测。
- **但它是可用的，且该按需打开**：`RemoteExecutor(..., persistent=True)` 已透传；默认
  `False`，一次性路径一行没动（全套 1592 → **1612 passed**）。适合的场景是「一次会话里要
  连续做很多次测量」——心跳密集的无人值守运行、探索期的重复计时、以及任何想避开
  4.5 s 固定开销的小测量。
- **下一步该动的不是传输**：把每次测量的 1.2 s 利用率采样从「无条件付」改成「有理由才付」
  （与测量并行、或按上一窗的污染证据决定），并把 doc 60 那个「超时后世界未知」在
  harness 层真的记成一格。两者都与传输无关。

## 七、守卫

- `tests/test_persistent_session.py`（19 条，全部离线：本地起真 `runner_server.py` 当远端，
  或起一段内联脚本当故障注入源）覆盖：id 回显、超时/EOF/错位三态、stdout 杂音不算错位、
  并发不互抢、关闭幂等且进程真的退出、坏请求不带走会话、非 JSON 行有应答、握手记下卡号、
  握手不应答则 fail-closed、`ping`/`shutdown` 不进 kernel runner、分派现场只在一个函数里。
- **非空转**：三处变异各自精准打红 —— 去掉 id 校验 → `test_desync_is_detected` 红；
  超时改成 `return {}` → `test_timeout_is_its_own_state_not_a_failure` 红；去掉会话内锁 →
  并发用例红。
- **重构没弄坏一次性路径**（真机证据）：`run_kernel.py` 那段 1527 行的分派链被整段搬进
  `run_action()`，而 §三① 的「一次性」臂与 §三② 的「一次性」心跳就是搬完之后在 H20 上跑的 ——
  读数 2.094 ms、心跳 `ok=True` 慢/好 7.93，与 doc 61 修复后的口径一致。契约测试是 AST 的
  （读源码，从不 import runner），所以它只能证明两边**声明**一致，真机这一趟才是「跑得通」。
- `tests/test_runner_contract.py` 扩成两个分派现场（新增「服务端专属 action 不许进 kernel
  runner」一条反向判据）。这一条**当场抓到了我**：加了 `shutdown` 之后它报
  「控制端在发没人派发的 action」，而它是对的 —— 于是 `ping` 被接到会话的握手上
  （确认服务端活着 + 拿到钉住的卡），不再是一条死分派。

## 八、这次没做

- **多卡/多会话**：一次会话钉住一张卡（选卡发生在远端 import 时）。跨卡并发没做。
- **超时之后的记账**：`SessionError("timeout")` 已经把三态分开了，但 harness 层
  （`transport_outcome` 那一套）还没消费新那一格。
- **xpu 平台**：明确**拒绝**（`persistent=True` + 非 nvidia 平台构造时就抛）——
  `run_kernel_xpu.py` 用 dispatch 字典、没有 `run_action`，静默退化成一次性会让
  「我开了常驻」变成一句没有读者的声明。
