## 一、先说一个比缺口 4 更紧急的 bug（✅ 本人已核实）

缺口 4 原本的描述是「改善判据固定用 gflops，对 memory-bound 算子选错目标」。核实代码后发现**还有一个独立的记账 bug，且它才是 layernorm 提前终止的直接原因**。

`conductor.py:276` 初始化：

```python
best_gflops: float = 0.0
```

`conductor.py:430` 的分支守卫：

```python
if current_gflops > 0 and best_gflops > 0:
    ...  # 正常比较
else:
    # "gflops 不可用" 分支
    rounds_without_improvement += 1        # :458
    disabled_recipes.add(r.id)             # :455-457
    print("[Conductor] 性能指标不完整 (gflops=..., speedup=...)")
```

**首轮 L3 失败时 `best_gflops` 仍是 `0.0`，守卫为假**，于是掉进「gflops 不可用」分支——哪怕 `current_gflops` 明明是个正常数字。缺少「首个观测即建立基线」这一支。

这与 layernorm 的实际日志逐字吻合：

```
[Conductor] 性能指标不完整 (gflops=232.55, speedup=0.5941), 连续 1/2 轮
[Conductor] 性能指标不完整 (gflops=273.76, speedup=0.6519), 连续 2/2 轮
[Conductor] 连续 2 轮无性能改善，提前终止优化
```

`gflops=232.55` 完全可用，却被报成「指标不完整」。**且第 2 轮的 gflops 273.76 比第 1 轮的 232.55 提升了 17.7%——优化实际在起效，却因为记账 bug 被判为停滞并终止。**

后果分三层：

1. 首轮的应用配方**必然**进 `disabled_recipes`（`:455-457`），与它是否有效无关。
2. `max_stagnant_rounds = 2`（`:278`），所以最多两轮就终止。
3. `:452` 那个 `if speedup > 0 and speedup < 1.0 and round_num >= 2: pass` 只保护了第 2 轮及以后，**第 1 轮不在保护范围内**。

**这是纯记账缺陷，与 bound 感知无关，修复代价极小（加一个「`best_gflops == 0` 时把当前值立为基线、不计停滞」的分支），应排在缺口 4 之前。**

> ✅ 好消息（本人核实）：`verifier.py:324-341` 已经把 `memory_bandwidth_gbs`、`bound_type`、`gflops_utilization_pct`、`bandwidth_utilization_pct`、`arithmetic_intensity`、`ridge_point` 全部输出进 metrics。**判据改造不需要任何新指标，只需接线。**

## 二、bound 感知的正确做法：用 roofline 的 `max()` 统一，而不是分支选指标

⚠️ 本节方案来自研究员报告，引用 [SOL-ExecBench 2603.19173](https://arxiv.org/abs/2603.19173) 与 [SOL-guidance 2603.29010](https://arxiv.org/abs/2603.29010)。

我在 [`00`](00-架构基线与缺口核实.md) 里原本的建议是「按 bound 类型选择目标（memory-bound 看带宽利用率，compute-bound 看 FLOPS 利用率）」。**这个方案应该被下面这个取代**，因为它更好：

```
t_SOL = max(FLOPs / peak_compute,  bytes_moved / peak_bw)
g     = t_measured / t_SOL          # headroom，越小越好
```

`max()` 本身已经自动完成了 bound 分派：layernorm（AI=0.875）由第二项支配，GFLOPS 从此根本不进判据。不需要 `if bound_type == ...` 分支，也就不存在「两侧不对称」的问题。

跨算子可比性用 **SOL Score**（有界、无量纲）：

```
SOL_score = (T_b − T_SOL) / ((T_k − T_SOL) + (T_b − T_SOL))
```

对齐 baseline ⇒ 恰好 **0.5**；触达硬件极限 ⇒ **→1.0**。这让 layernorm 与 matmul 的分数可以直接平均，解决「不同算子 GFLOPS 天然不同量级」的问题——也就顺带修掉了 [`13`](13-跨运行记忆与技能库架构.md) 第一节 (a) 那个 `min(perf,100)/100` 的截断缺陷。

### 四处改造

| # | 改动 | 说明 |
|---|---|---|
| 1 | **首轮判据** | ✅ 本人核实：`t_SOL` 只需 FLOPs 与 bytes 计数，而 `_compute_arithmetic_intensity(task, inputs)`（`verifier.py:518`）是**纯解析**的、不依赖实测。当前把「解析 bound」和「实测 gflops」耦合在同一个 roofline 对象里，才导致首轮 `roofline=None`。**拆开即可让首轮就有判据** |
| 2 | **改善判据** | `g_new < g_best × (1 − δ)`，δ 取当轮实测噪声带（见第四节），而非裸 `>` |
| 3 | **停止条件** | `t_best ≤ (1+ε)·t_SOL` 即停。⚠️ SOL-guidance 用同一判据**分配预算**（把轮次重分给 headroom 大的问题，省 19–43% token 保留 ≥95% 收益）。我方 layernorm 的 `31.6µs / 0.86µs ≈ 37` ⇒ headroom 巨大，**绝不该提前终止** |
| 4 | **诊断指标** | `bandwidth_utilization_pct` / `gflops_utilization_pct` **只进日志与 Planner，不进判据**。取 `max()` 即 roofline 利用率 |

### 必须同时加的反作弊闸

若 `t_measured < 0.9 × t_SOL`（比物理下界还快 10% 以上）⇒ 判定 benchmark gaming。

⚠️ robust-kbench 实测：KernelBench 排除污染任务后平均加速比从 **3.13× 掉到 1.49×**，作弊核虚报 **50–120×**。

> 与我方 [`03`](03-反作弊与正确性防线实测.md) 的关系：该文档实测的 `return A @ B` 假核报出 `1.00x vs cuBLAS`、`95.3% fp16 峰值`——**没有低于物理下界**，所以 SOL 闸拦不住它。两者是互补的：SOL 闸拦「快得不可能」，AST 反作弊拦「根本没在算」。不能只做一边。

**关键结论**：抗噪声设计基本只存在于 **bandit / successive-halving 谱系**。Hyperband 把调优形式化为 pure-exploration non-stochastic infinite-armed bandit，用自适应资源分配 + 早停。⚠️ 穷举类（Triton/CUTLASS）默认「一次测量定胜负」，**在共享机器上必然误判**——这正是我方缺口 1 的情形。

### LLM 与传统调优的分工（证据明确）

⚠️ 本节均为研究员报告：

- **[KernelBand](https://arxiv.org/abs/2511.18868)**：把 kernel 优化形式化为分层 MAB，臂 = (kernel 候选, 优化策略) 复合对，分层 UCB；reward = `1 − t_new/t_prev`，非法执行罚 −1；用在 **9 个硬件性能计数器**上训练的逻辑回归给出 compatibility probability 作为 UCB 偏置项。在 TritonBench-G、3 种 GPU、4 个 code LLM 上比 SOTA（GEAK 等）平均高 **33%+**，并观察到竞品「exhibit clear saturation」而 bandit 随预算继续提升。
- **反向证据（LLM 不该调数值参数）**：[tritonBLAS](https://arxiv.org/html/2512.04226v1) 用纯解析「competing rooflines」选 tile（代价函数 = 指令延迟 + 多级 cache 命中概率 + 带宽 + pipeline 启停），**0 次实测**，配置选择从数十秒降到微秒，在 15 万个测试矩阵上拿到穷举搜索 **94.7%** 的性能。
- **[Record-Remix-Replay](https://arxiv.org/abs/2604.11109)** 给出最佳分工模板：外层 LLM-guided MAP-Elites 改源码，内层 **BO 30 步**调 compiler pass 序列 + launch 参数。比 OpenEvolve 快 ~10×，QUDA 上端到端延迟 −28.4%。
- **AlphaEvolve 消融**证实两侧都必要（`No evolution`、`Small base LLM only`、`No full-file evolution`、`No meta prompt evolution` 每项都显著变差）。LLM 的价值在「用世界知识自动构造变异算子，无需预定义算子集」，**不在调数字**。

**对我方的建议**：`SearchAgent` 保留 LLM 做**源码级/结构级**提案；把 tiling、`num_warps`、`num_stages`、hints 交给一个小 BO/UCB（30–60 次实测预算）；配方选择交给 bandit。

> ✅ 我方已有基础：`CoderPipeline` 已实现 T=0.1/0.4/0.7 三路并行采样 + compile-select + ≤2 轮 stateful repair（见 `CLAUDE.md`）。缺的是把「选哪一路继续」从固定规则换成 bandit。

## 四、测量卫生：两个实测问题的可落地对策

### 4a. shape 太小 / launch 开销支配

⚠️ robust-kbench 原文确认这是行业公认问题：*"run-time profiling of these tasks is often compromised by CPU overhead, which can dominate measurement for small kernels and lead to misleading optimization targets."*

✅ 这与 [`01-launch开销与shape充分性实测.md`](01-launch开销与shape充分性实测.md) 的独立实测完全一致（该文实测 launch 地板 18.69µs、layernorm 工作集 3.15MB 完全常驻 60MiB L2、报告 0.65x 而净值差 6.8x）。

| 对策 | 说明 | 与我方 01 号文档的关系 |
|---|---|---|
| **测量有效性门控** | 先测 launch-only baseline `t_launch`，要求 `t_kernel ≥ 10 × t_launch`，否则标 `measurement_invalid=True`，**该轮不参与改善判据、不计入停滞轮数、不禁用配方** | ✅ 与 01 号文档第五节的三档设计（valid/degraded/uninformative）等价，且 `10×` 对应我实测的 `launch_dominance < 0.10`。**两个独立来源给出同一阈值** |
| **CUDA Graph** | Triton 已有 [`do_bench_cudagraph`](https://github.com/triton-lang/triton/blob/main/python/triton/testing.py)：把 N 次调用录进 graph 后 `g.replay()` 批量执行，明确「bypasses standard CPU scheduling latency and interpreter scheduling costs」 | 这是小 shape 下**唯一能让信号浮出来**的手段，且能直接解释我方 `torch_compile` 反而慢 2.5× 的现象。⚠️ 注意新版 autotuner 的 `warmup/rep/use_cuda_graph` 参数已 deprecated |
| **强制最小工作量** | 调优期把 shape 放大到 `t_SOL ≥ ~100µs`（或 `t_kernel ≥ 1ms`）再搜索，选出的 config 回原 shape 验证 | ✅ 对应 01 号文档建议 layernorm 改用 16384×6144（地板占比 14.6%） |
| **同时报告 small/large 两档，只有 large 进判据** | ⚠️ CANN Bench 的做法相反但可借鉴：刻意保留紧凑 tensor 维度以**暴露** invocation latency | 值得采纳：小 shape 的诊断价值在于暴露 launch 问题，不该被丢弃，只是不能进判据 |
| **warmup 必须够长** | ⚠️ Triton `do_bench` 默认 `warmup=25, rep=100`（**毫秒预算制**，非次数制）；[issue #2306](https://github.com/triton-lang/triton/issues/2306) 实测 warmup 过短会**低估 30%**，维护者建议 warmup >150ms（典型 500ms） | ⚠️ 需核查我方 `run_benchmark_with_baselines` 的 `warmup=10, repeat=30` 是次数还是毫秒 |
| **输入去别名** | ⚠️ SOL-ExecBench「inputs are duplicated to prevent pointer caching」 | 直接对应 AKO 记录的「指针键控 cache」作弊 |

### 4b. 共享机器噪声（同卡恒有其他租户）

| 对策 | 出处 | 我方现状 |
|---|---|---|
| **锁频** `nvidia-smi -lgc 1500` | ⚠️ SOL-ExecBench（"SM clocks locked at 1,500 MHz"）与 KForge（同样 pin 1500MHz，并**关闭 autotuner 以避免非确定性 kernel 路由**，报告 sub-0.1% 变异） | ❌ 未做。⚠️ 需核查该机上是否有权限；无权限则把实测 SM clock 作为协变量记录 |
| **L2 flush**：每次计时前 zero 一个 ≥256MB buffer | ⚠️ SOL-ExecBench 用 256MB；Triton `do_bench` 同机制；CANN Bench「evicts the L2 cache between timed runs」 | ❌ ✅ 本人核实 `run_kernel.py:553-574` `_timed_runs` 无任何 flush。**但见 [`11`](11-kernel生成系统全景.md) §3.2 的警告：不要简单加 flush 就完事**，warm-L2 对推理类重复调用是现实工况，真问题是基准未声明且不一致 |
| **交错测量（interleaved A/B/A/B）** | ⚠️ 对时变漂移**唯一有效**的手段。SOL-ExecBench 承认会因 "power capping or thermal throttling" 漂移；robust-kbench Figure 9 专门展示评估环境对已发现 kernel 性能的影响 | ❌ 未做。配对差分能抵消共同漂移，先后测量不能。**这是让 `0.91x vs cuBLAS` 站得住的关键一步** |
| **稳健统计量**：≥3 trial ×（10 warmup + 50 timed），取 **median 而非 mean** | ⚠️ KernelBand 用 1000 次/shape；robust-kbench 用 2000 次 + 25 warmup | ✅ 我方 `verifier.py:313` 已用 `median_time_ms`，**正确，保持** |
| **污染检测升级为前后双采 + 丢弃重测** | — | 🔶 我方已有测前采样（`util_before > 5%`），但只标记不重测。⚠️ 建议：测前**和**测后都采，任一 >5% 或前后差 >10 百分点 ⇒ 丢弃重测；连续 3 次污染 ⇒ **挂起搜索**（等待/重试），而不是记为「无改善」 |
| **改善需超过噪声带**：用同轮 baseline 的重复测量估 σ（或 MAD），要求 `|Δ| > 2σ` 才算改善，否则记 **tie**（既不加改善也不加停滞） | — | ❌ 未做。**这直接修掉第一节那个记账 bug 的噪声放大效应** |
| **子进程隔离 + 超时上限** | ⚠️ SOL-ExecBench 用 sandboxed subprocess + 300s abort cap | 🔶 我方走 SSH 天然进程隔离，但超时后远端进程是否真终止未核查（见 [`02`](02-远端执行的信任边界实测.md) 第四节待办） |
| **任务级过滤**：剔除输出落在 −0.01..0.01、跨 seed 输出 std <0.01、跨随机输入输出变化 <0.01 的任务 | ⚠️ robust-kbench 借 METR 标准；METR 指出 KernelBench 250 题中约 **40 题**有问题 | ❌ 未做。若将来建自己的 benchmark 套件需采纳 |

## 五、进化式方法要点（供后续参考，暂不采纳）

⚠️ 全部来自研究员报告：

- **AlphaEvolve 循环**（白皮书 Fig.2 原文）：`parent, inspirations = database.sample()` → `prompt = prompt_sampler.build(parent, inspirations)` → `diff = llm.generate(prompt)` → `child = apply_diff(parent, diff)` → `results = evaluator.execute(child)` → `database.add(child, results)`。
- **防种群塌缩**：database「inspired by a combination of the MAP elites algorithm and island-based population models」。RRR 给出可抄的具体形式：MAP-Elites 网格按 **code complexity × sequence divergence** 索引，每格只留一个 elite，仅当更优才覆盖；再加 island 迁移——定期用 peer island 的 top half 替换本 island 的 bottom half。
- **变异算子**：AlphaEvolve 用 LLM 生成 diff 取代手写算子。⚠️ robust-kbench 的消融给了直接可用的结论：context 提供「top-5 最优、按 **least-to-most 升序**排列」比「单个最优」和「10 个随机」都更稳定。**我方 `SearchAgent` 的 prompt 应按此重排历史。**
- **多目标的意外收益**：AlphaEvolve 原文——「even if one metric is of particular interest, optimizing for multiple metrics often improves results for the single target metric」，因为不同指标下的优胜程序结构不同。⇒ 我方 archive 应同时记 `gflops_util` / `bw_util` / `SOL_score` **三个**分数，而非单一 GFLOPS（这也再次印证第一节的记账 bug 危害）。
- **预算**：AlphaEvolve 每解可花 ~100 compute-hours，必须并行化评估；RRR 上限 200 iteration / wall-clock / stagnation，4 GPU per kernel。

**暂不采纳的理由**：本项目单次任务预算远小于 AlphaEvolve 量级，且缺口 1（测量可信）未解决前，进化搜索会放大噪声。
