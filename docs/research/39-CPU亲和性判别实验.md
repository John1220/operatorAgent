# 39 · D8 判别实验：CPU 亲和性对 launch 地板有用吗

对应吸纳项 [doc 20 第三节 D8](20-吸纳决策与阶段总结.md)（`sched_setaffinity`，
来源是 Google Benchmark 明列为**无需 root** 的降噪手段之一 ✅ 一手文档）。
决策从 ⏸ 暂缓 → ❌ **不采纳（本机口径下）**。

工具：[`benchmarks/probe_cpu_affinity.py`](../../benchmarks/probe_cpu_affinity.py)
（自包含，在 GPU 机上跑，不需要 LLM）。

数据来自**同一脚本的两次连续运行**，本文给每个数字标来源：
**A run**（03:43，主实验表，机器状态完整：`loadavg 8.2/4.1/3.3`，192 逻辑核，平均 busy 2.5%）、
**B run**（03:48，复现 + 当前文案的两道控制）。GPU 2，同一台 H20。

---

## 一、这个问题为什么值得单独花一次真机时间

`docs/research/01` 测出的「launch 地板 20.24 µs」 dominating 了小 shape 的全部测量，
而 [doc 32](32-吸纳Triton-do_bench计时口径.md) 证明它其实是**宿主侧派发**：同一个空核，
GPU 空闲时事件窗口 20.03 µs，被 256 MB 冲刷填满后只剩 4.64 µs。

「host 侧」这个定性一旦成立，就自然引出 D8：那 20 µs 不是 GPU 在算什么，而是我们这条
线程在提交命令 —— 要么在烧 CPU，要么在等驱动。把它钉在一个干净的核上、避开迁移和邻居，
是不是就能压低地板、从而让 layernorm 1024×768 那一档从 `uninformative` 里救出来？

这条链条上有三个**各自可证伪**的前提，全都没人验过：

1. 事件窗口真的对 host 侧耗时敏感（否则地板压不动，D8 无从下手）；
2. CPU 争用在这台机器上**测得出来**（否则任何零结果都不作数）；
3. 钉核真的会改变被测数字（这才是收益）。

## 二、两道控制，以及第一版为什么整个作废

`docs/research/34/35/36` 在同类错误上摔过三次（拿看不见被测量级的量具报零结果），
所以这次实验设计的第一原则是**先造出一个必须失败的对照**。第一版两道控制全都没通过，
原因各不相同，都值得记下来：

### 2.1 控制 1 的第一版：`hog` 臂和 `idle` 臂钉在同一个核上

第一版里 `hog_cpu = idle_cpu`（都想当然地选「最闲的那个核」）。而第二次运行时
`idle_cpu` 恰好是 0 号核 —— 于是 `idle`、`core0`、`hog` 三臂全部挤在同一个核上，
四臂塌成两臂。报告出来的「hog 臂没变慢」因此**不是物理结论，是设计缺陷**。

修法是显式给 hog 留一个与 `idle` 臂不同的核，并且**直接量争用本身**而不是靠猜：
每个臂测一次「0.6 s 墙钟里本线程真正烧掉多少 CPU 秒」。

### 2.2 控制 1 的第二版：2 ms 的采样短于一个 CFS 时间片

即使分开钉核，用 2.2 ms 的纯计算采样仍然量不出争用（同核放着 100% 邻居，中位数纹丝
不动）。原因在 `/proc/<pid>/stat` 的读数里现形：**采样窗口短于调度片，线程压根没被
换下过一次**。把窗口拉到 1 s，效果立刻出现（下表）。

> 这一条对主实验有直接含义：一次 launch 的事件窗口是 20 µs，1500 个样本才 30 ms，
> **仍然短于一个时间片**。所以「钉核会不会伤 median」这个问题，在这套口径下几乎注定
> 答案是「不会」—— 调度噪声只能落在样本的**尾部**，落不进中位数。

### 2.3 两道控制最终都通过了

```
=== 控制 2: 事件窗口含不含 host 时间 ===         (B run)
  窗口内注入      0 次 Python 迭代 → median=  21.84 µs
  窗口内注入   4000 次 Python 迭代 → median= 133.98 µs
  窗口内注入  12000 次 Python 迭代 → median= 349.41 µs
  ✅ 抬得动 → 事件窗口对 host 侧耗时敏感。注意这只证明「敏感」, 并不区分
     「我们的线程在烧 CPU」与「GPU 空等命令到达」

=== 控制 1: 争用可见性 (秒级窗口才测得出) ===     (B run)
  钉到 hog 核     有效核数=0.50
  钉到空闲核      有效核数=1.00
  不钉           有效核数=1.00
  hog 所在核 2 实测 busy=100% (state=R)
```

A run 的这两道控制是同一个形状：注入 0/4000/12000 → 22.30 / 134.70 / 342.66 µs；
有效核数 0.49 / 1.00 / 1.00。

控制 2 是**注入已知的 host 工作量**（在 `s.record()` 与 launch 之间跑一段 Python 空转），
事件窗口按注入量近乎线性地抬高：4000 次迭代 ≈ +112 µs，12000 次 ≈ +320 µs。

⚠️ 这条控制证明的是**「事件窗口对 host 侧的墙钟耗时敏感」**，比标题那句弱一档，
而且必须分清：它区分不了「我们的线程在烧 CPU」与「GPU 空等我们提交命令」——
按 [doc 32](32-吸纳Triton-do_bench计时口径.md) 第一节的读法，20 µs 地板属于后者
（`start.record()` 之后 GPU 无事可做，等命令到达的这段时间被计进窗口）。
但这个弱一档的性质对 D8 已经够用：**倘若窗口对 host 耗时完全不敏感，钉核就没有任何
路径能改善它**；正对照抬得动，才说明「让 host 侧这段更快/更稳」这件事值得测下去。

顺带回答了一个口径问题：**候选核若有沉重的 Python 侧 launch 开销，我们的 L3 会把它
如实计进窗口**，不会藏起来 —— 与 doc 20 拒绝 CUDA Graph 计时（D7）的理由互相印证。

## 三、主实验：钉核在 median 上没有任何作用，在尾部有 460 倍的副作用

四臂按轮交错（起始臂轮换，取消顺序偏置），每臂每轮 1500 个 launch 样本，
对 `default`（不钉）做同轮配对差分。下表是 **A run**：

| 臂 | 钉到 | p50 µs | Δp50 | 符号 | p90 | Δp90 | **max µs** | 生产口径(LN+冲刷) | 有效核数 |
|---|---|---|---|---|---|---|---|---|---|
| default | 不钉（192 核） | 19.49 | — | — | 20.32 | — | 34.7 | 25.47 | 1.00 |
| idle | 最闲核 2 | 19.49 | +0.13 | +5/9 | 20.35 | +0.03 | 34.3 | 25.41 | 1.00 |
| core0 | 0 号核 | 19.58 | +0.05 | +5/9 | 20.35 | +0.06 | 32.9 | 25.38 | 1.00 |
| hog | 被自家进程独占的核 4 | 19.46 | +0.08 | +5/9 | 20.38 | +0.19 | **16027.2** | 25.66 | **0.51** |

三个读数：

1. **收益为零**。`idle` 与 `core0` 相对 `default` 的 Δp50 是 +0.13 / +0.05 µs
   （0.7% / 0.3%），符号检验 +5/9 —— 就是抛硬币。生产口径（layernorm 1024×768 +
   L2 冲刷）Δ ≤ 0.10 µs。这台机器 loadavg 8.2 摊到 192 核，**本来就没有争用可缓解**，
   不钉的线程也已经拿到 1.00 个有效核。
2. **风险是实测的，不是推测的**。`hog` 臂的 `有效核数 = 0.51` 证明它确实与人分享了
   一个核，此时 **median 只涨了 0.4%，但 max 从 34.7 µs 变成 16027 µs（460 倍）**，
   而且 9 轮里 8 轮都出现、数值几乎一模一样（16024.9 ~ 16028.8 µs）。那个 ~16 ms
   正是**一个 CFS 时间片**：一次被抢占就把一个样本整体推迟了一整个时间片。
   （没出现的那一轮 `有效核数` 仍是 0.51 —— 抢占落在采样窗口之外，这恰好说明
   median 与尾部量测的是两件事。）
   反过来这也给出一个独立的定量结论：**一次 launch 的 host 段（≈20 µs）远小于一个
   时间片（≈16 ms）**，所以哪怕只拿到半核， typical launch 也照样在同一个时间片内
   跑完 —— 这就是 CPU 份额砍半而 median 不动的原因，不是「钉核效应不存在」。
   这坐实了 doc 20 D8 那行写的顾虑（「钉到的核若被别人占满会更糟」），
   也给出了它的真实形态：伤的是尾部，不是中心。
   另一个旁证：第 5 轮 `core0` 臂的 `有效核数` 自己掉到了 0.77 —— 0 号核也会被邻居
   落到上面，「挑个核钉住」并不是一个能长期成立的选择。
3. **尾部不是没人看，但它不该改判定**。`max/median` 在我们的诊断字段里
   = 16027/19.46 ≈ 824，远超 `INTRUDER_MAX_OVER_MEDIAN = 2.0`，会被标成
   `measurement_intruder_suspected`；而 `iqr/median` 完全不动（这正是 doc 33 第四节
   把这条信号降格为「仅诊断」的原因）。也就是说：钉核如果钉错了，我们的**档位判定
   不会报警**，只有诊断字段里有痕迹 —— 收益 0、下行风险只能事后从 max 里查，
   这笔账不划算。

### 3.1 B run 复现：median 的结论稳住了，max 那一列没有

同一脚本 5 分钟后重跑（未记录 loadavg，但**default 臂自己的尾部明显更重**：
max 中位 34.7 → 161.2 µs，单轮最高 312.8 µs）：

| 臂 | Δp50 | 符号 | Δp90 | hog/钉核臂 max | 生产口径 Δ | 有效核数 |
|---|---|---|---|---|---|---|
| idle | +0.16 µs | +6/9 | +0.03 | 38.4 | +0.29 µs | 1.00 |
| core0 | +0.19 µs | +7/9 | −0.06 | 73.9 | +0.67 µs | 1.00 |
| hog | +0.08 µs | +6/9 | −0.06 | **16026.9** | +0.26 µs | **0.50** |

三条读法：

- **median 结论复现**：Δp50 全在 +0.08 ~ +0.19 µs（0.4% ~ 1.0%），符号检验 6/9 与
  A run 的 5/9 一样是抛硬币级别。方向上两次都**略微变慢**，也就是说钉核连那 1% 都
  没赚到。
- **16 ms 的独占离群复现**（hog 臂 max 16026.9 µs，9 轮里 7 轮出现），而
  `default` 臂这一列在两次跑之间从 34.7 µs 漂到 161.2 µs —— **尾部统计量随机器负载
  漂移，不能拿来下判断**，能拿来下判断的只有「hog 臂稳定地长出一枚一个时间片长的
  离群样本」这一条定性事实。
- **生产口径（LN + L2 冲刷）两次的方向不一致**：A run 里 idle/core0 略快（−0.10/−0.06
  µs），B run 里三个钉核臂都略慢（+0.26 ~ +0.67 µs）。两次都不显著 → 结论是
  **钉核在这条口径上的效应低于本实验的分辨力**，而不是「有一点收益」或「有一点损失」。

## 四、决策与适用边界

**D8 → ❌ 不采纳。** 三条理由，都可复查：

1. 作用路径存在（控制 2：窗口对 host 耗时敏感）但**本机无可观测收益** —— 两次跑
   三个钉核臂相对不钉的 Δp50 都在 +0.05 ~ +0.19 µs（0.3% ~ 1.0%）之间，
   符号检验 5/9 ~ 7/9；生产口径（LN + L2 冲刷）两次方向还相反（§3.1）。
2. 唯一的实际效应是**把偶发的一整个时间片抢占集中到我们钉的那个核上**，
   表现为一枚 460 倍离群样本，而 L3 的决策统计量是中位数 —— 收益进不了决策，
   代价只在尾部；
3. 前提压力不存在：这台机器 192 核、平均 busy 2.5%，不钉也能拿到 1.00 个有效核。
   D8 真正适合的是「核少且 CPU 饱和」的机器。**若将来接入的平台核数少、或 L3 与
   其他宿主进程抢 CPU，这条决策要重估**，判据就是本探针的两道控制 + Δp50 / max 两列
   （max 那一列只作定性：它在两次跑之间随负载漂移了 4.6 倍）。

## 五、可复用的三条方法学

1. **对照臂要检查它们没有互相踩**。第一版四臂塌两臂，是读代码读不出来的，
   只有把「争用本身」量出来（有效核数）才暴露。凡是多臂 A/B，先加一条
   「这一臂是不是和被污染的那一臂共用资源」。
2. **采样窗口短于调度片，就永远测不出调度类噪声**。要么把窗口拉到秒级，
   要么明确「我看的统计量本来就不该对此敏感」—— 本次结论属于后者，而且是被
   `max` 那一列证实的。
3. **~16 ms 这个数是这台机器 CFS 时间片的独立估计**，值得进测量手册：
   任何「一个样本比另一个慢 ~16 ms」的现象都不是 GPU 抖动，是宿主被换下了。
