## 0. 四条结论

1. **阶段 A 的出口判据不能只靠存量证据达成。** 「谁在哪个环节花时间」需要人工活跃时间，而本仓**从未记录过人时**（§2）。**处置（2026-10-31 定案）**：路线 §5 的条件已按「甲」拆成两半——机器侧的「哪些环节会失败、单次代价多少」留在门槛内（本档 §4 已答），历史人时移出门槛，未来人时由 [T3.7 量具](../design/operator-development-phase1-execution-20261031.md)当场记录（`core/human_ledger.py`：六环节、unknown 缺省、分母恒全、人档与机器秒不折叠）。存量证据只能回答「哪些环节会失败、失败一次花多少机器时间」。
2. **机器侧基线已经能建起来，且失败高度集中在两处**：L3 性能判定（两批独立复现：L2 通过率 100%，而 L3 分别 5/10 与 3/12=25%，加速比中位 0.99x）与 L1/契约形状一致性（matmul 三臂 0/3，全是 `expected 3, got 2` 这类维度不一致）。第 2 处还有**外部同向**证据（§3.1）。
3. **外部一线流程最耗时的前两段，本仓仪器数量为零。** KernelAgent 把循环定为 Profile→Diagnose→Prescribe→Orchestrate→Explore→Measure，并明说人工这套循环「要数天到数周」；而我们的 `TOOL_PROFILER` 与 `TOOL_SHAPE_SWEEP` 都是 `None`（[generate/agent_runtime.py:153](../../operator_agent/generate/agent_runtime.py#L153-L154)，本次实读）。
4. **拿别人的数替这个格子也不行——因为没有人有这个数。** 本轮专门去找「按环节的人工时间百分比」，公开材料里**一条都没有**（§3.1）：只有定性表述、「12 天 / 283 小时」这类**总耗时（含排队，不是人时）**、以及端到端可改份额。所以缺口不在「谁忘了记」，而在**这个口径从没被定义过**；可执行的动作是定义口径并当场测，而不是等回忆。

## 3. 外部一线流程（T2.3；这是公开资料核查，不是本项目用户访谈）

来源：**PyTorch 官方博客 KernelAgent**（2026-03-06，本次 2026-10-31 直接抓取全文核对；页面可能变更，复用时重核）。

| 他们的环节 | 做什么 | 关键读数 |
|---|---|---|
| Profile | ProfilerAgent 用 Nsight Compute 采硬件指标（DRAM 吞吐、L2 命中、warp stall、SOL） | 指标以结构化字典交给下一段 |
| Diagnose | SOL 做 roofline + LLM 找根因，产出 `BottleneckReport` | 示例：memory-bound，70.3% DRAM，long-scoreboard 37.69%，occupancy 30.08% |
| Prescribe | 结合 GPU 规格与配方库给具体修法 | 例：加 `num_stages` / 降 BLOCK_K / 控寄存器 |
| Orchestrate | 汇总历史轮次 + reflexion 定搜索策略 | reflexion 明确记「诊断对但修复无效，性能退化 37.4%」 |
| Explore | 多 worker 并行探不同修复（beam，2 核 × 2 瓶颈 = 4 worker） | Round1 4/4 成功、Round2 3/4 |
| Measure | 先对拍正确性再测性能（warmup 25 / repeat 100 / 基准锁） | 逐轮 7.80 → 4.0457 → 3.1118 ms |

他们的头条：100 道 L1 KernelBench 上，对同 correctness-only 基线 **2.02x**、对默认 `torch.compile` **1.56x**（赢 65/100），H100 roofline 效率 **89%**；单个 matvec 案例经 4 次**架构性**改动 9.52 → 6.80 → 6.20 → 4.03 → **1.95 ms**，每次由寄存器压力/占用/合并访存指标定瓶颈；文中明说工程师手工做这套循环「**通常要数天到数周**」，且大部分收益在首轮拿到、之后靠 hill-climb；停止判据是「连续轮次在 roofline 效率与运行时间上都无有意义改善」。

**与本仓的对照（这才是阶段 A 的产出）**：他们最前两段（Profile / Diagnose）在本仓是 `None` —— 我们既采不到指标也没有瓶颈分类，所以「读性能数据—提假设—排实验—判结果」这个外部认定的人工耗时主环节，我们**连基线都无从测量**（[roadmap §5.1](../design/operator-development-product-roadmap.md#L173) 也要求把已有与新增分开写）。路线里另外两条实践（Meta GDPA、NVIDIA 工具链）**本次未重新核查**，沿用路线 §2.3 的记录与核查日期。

### 3.1 追问：有没有人给出「按环节的人工时间百分比」——没有（2026-10-31 核查）

因为本仓缺的就是这个数，本轮专门去找外部能否代替。**结论：公开材料里找不到任何按环节拆分的人工时间百分比**，能找到的只有定性表述、总耗时、或端到端可改份额。逐条如下（访问日期均 2026-10-31）：

| 来源 | 它说了什么 | 是不是人时 |
|---|---|---|
| [KEET, arXiv 2605.04467](https://arxiv.org/abs/2605.04467) | 开发者「spend significant time analyzing and comparing profiles」——**唯一明确把「解读性能指标」点名为成本环节**的来源 | 定性 |
| [Harness Engineering, arXiv 2607.17979](https://arxiv.org/abs/2607.17979)（Baidu，MLSys-26 FlashInfer，B200） | 附录 Table 5「**Human and Agent Contribution Matrix**」把人与 agent 的贡献按 目标与指标 / harness 与工具 / 参考与检索 / 搜索策略 拆开；明说「humans design the harness, curate references, decide evaluation budget, and make final promotion decisions」 | **最接近「谁在干什么」的公开读数，但是定性的、不是分钟** |
| [FuriosaAI RNGD 案例, arXiv 2610.38329](https://arxiv.org/abs/2610.38329) | 「Our run lasted **12 days (283 h)**」，人只提交任务文件 | **总耗时≠人时**：这是机器与排队时间，恰是我方路线 §6.3 禁止混用的那种 |
| [NVIDIA 博客：Spark UDF 改写, 2026-10-13](https://developer.nvidia.com/blog/rewrite-apache-spark-udfs-gpu-acceleration-ai-agents/) | 「on the order of **hours rather than days or weeks**」 | 量级表述，供应商自述 |
| [KernelBench, arXiv 2502.10517](https://arxiv.org/abs/2502.10517) | 「writing them is a time-consuming challenge」；「it took **5 years** from the release of the Transformer architecture to obtain performant kernels」 | 定性 + 历史数字 |
| [Astra 2509.07506](https://arxiv.org/abs/2509.07506) / [TritonBench 2502.14752](https://arxiv.org/abs/2502.14752) / [综述 2601.15727](https://arxiv.org/abs/2601.15727) | 「time-consuming engineering cycles」「labor-intensive…trial and error」「notoriously time-consuming and non-scalable」 | 全部定性 |
| [arXiv 2609.21058](https://arxiv.org/abs/2609.21058) | 端到端可改份额被量化：transformers 上 **80–86% 运行时间花在 cuBLAS GEMM 与 FlashAttention，把真实的端到端改善限制在约 1%**；「Benchmark results supply σ and are silent on s」 | **量化，但量的是可改份额不是人时** |

四条直接可用的推论：

1. **本仓缺这个数不是本地孤立缺陷，而是全行业没有这个口径。** 那么「等有人回忆出来」就不是可执行的路线，能执行的是**定义口径并从现在起测**。
2. **接口/契约问题被外部独立复现。** [AgentKernelArena, arXiv 2605.16819](https://arxiv.org/abs/2605.16819)：「The dominant failure mode is a missing or malformed `PYBIND11_MODULE` entry point」——失败在**接线与入口契约**而非数值。这与本仓 matmul 三臂 0/3 全是 `expected 3, got 2` 同向，使 §4 的第 2 位从「我方单批」升级为「外部同向」。
3. **接入阶段全行业都没有小时数。** [Sakana 2509.14279](https://arxiv.org/abs/2509.14279) 明确「many LLM-optimized kernels fail to translate their benchmark performance to real-world applications due to…diverse input shapes, precision requirements, and integration with existing frameworks」；Astra 虽有把核接回 SGLang 的 post-processing 步骤，也**没报耗时**。所以本仓「没有接入阶段」是与外部一致的缺口，不是独有的偷懒；但 2609.21058 的「端到端约 1%」提醒：**kernel 达标不等于业务收益**，两档必须分开报。
4. 一条不得混用的提醒：2609.21058 的「约 1%」与我方 A/C 实测的 C−A 1.34%/0.24% **是两个不同的量**（前者是端到端可改份额，后者是同预算下两个候选的相对差），数值巧合不构成证据。

可达性备注：`export.arxiv.org`（仅 https）、`arxiv.org/html`、`developer.nvidia.com`、`sakana.ai` 本机直连可；`pytorch.org` 本轮一度返回 200 但博客索引里检索不到该篇（同一条 URL 在本会话早些时候可正常取全文）——**按主机名记，别把一次失败当不可达**。

## 5. 场景选择（T2.4）

选 **1 条完整工作流**：在目标硬件上对**已有正确实现**做性能确认与优化（LayerNorm 大形状 + matmul 尾段类），不是从零生成算子。

一句可反驳的理由：**在所有有记录的运行里，正确性几乎不是瓶颈（L2 10/10、layernorm/softmax 接近满），失败集中在「L3 判定」与「契约形状一致性」两处；因此先缩短「值不值得继续优化」的判定过程，比再生成一个候选更能省达标时间。**

推翻条件：一旦 §6 的真实人时读数显示工程师实际卡在写核与编译（而非判定与形状契约），本选择作废，改从第 2 位（L1/契约）起。

## 6. 复盘提纲（T2.2 字段表，必须由人来填；本轮一律记「未知」）

任务与验收标准 / 当时用的工具与助手（含是否用 AI）/ 逐环节**人工活跃时间**与实际等待 / 反复失败的原因 / 最终是否接入 / 哪些环节愿意委托 / 额外配置与纠错成本。

选任务的标准（T2.1）：3–5 例，每例须有可描述的输入范围、精度要求、目标硬件、参考实现与预算；优先「最近完成或卡住」的真实任务；允许用当事人自己的既有代码与实验记录还原。

**本文不替人填这些格子。** 上一节排序里第 1、2 位已经能用存量证据成立，第 3–5 位需要人时读数才能定。

**从下一次运行起改用形式**：这四格不再依赖回忆，而由 [T3.7 量具](../../operator_agent/core/human_ledger.py)当场记录（`involved / action / reason / minutes_band`，缺省 `unknown`、未答进分母、人档与机器秒分列）。本节提纲保留为**历史任务的唯一补救途径**——若将来真的找回了某次的人时，按同一字段补记，并注明是事后追认而非当场读数。
