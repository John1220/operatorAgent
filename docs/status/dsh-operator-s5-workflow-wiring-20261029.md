## 1. 历史结论更正与任务语义

[历史结果报告](dsh-operator-s5-formal-results-20261028.md)补充了复核更正：

- matmul 清单中的三元组是 `(M,N,K)`；旧提示错误地写成了 A、B 各自的三维 shape，验证器却使用二维 `A[M,K]、B[K,N]`。例如 tail 应为 `A[31,19]、B[19,47]`。旧记录里的断言/解包错误不能归因为模型写不出可编译 matmul。
- C/matmul-tail 在 12 次调用后发生流式传输错误，账本上限为 24、仍余 12 且未 abort，不再记成预算耗尽。校准阶段的中断与 v6 的 30 次分母分开；本轮 29 次取得最终候选、1 次中断。
- 仓库路径提及数不是成功读取次数。A 可读取仓库的环境限制仍然成立。

`benchmarks/s5_formal_run.py` 修正提示，冻结前从验证服务的真实 `contract.json` 对照主输入的名称、shape、dtype；不一致直接拒绝。新计划同时保存输入语义、开发期额度和实现哈希。

**评测制度边界**：复用的是 10 项历史任务的标识/算子/尺寸/精度；服务使用生产内建 correctness suite，不是历史质量集原有 pattern/layout/seed 与 holdout 的等价重放。任务仍须支持非连续输入，生产套件的具体输入由冻结契约确定，不把任务名里的 strided/extreme 等词当成输入保真证明。

## 2. 共用服务与三个真实入口

监督器为每个任务/组启动独立的 `DevelopmentService`，固定声明、契约、后端与 GPU 身份。三组拿到相同结构的 L1/L2 `status + feedback` 投影：

| 组 | 开发期入口 | 实际调用路径 |
|---|---|---|
| A | `s5-verify --code-file candidate.py` | 独立标准库客户端副本 → 共用服务；不添加 core import/PYTHONPATH |
| B | `operator-agent verify --run-dir TASK --code-file candidate.py --stop-after L2 --backend BACKEND` | 实际 CLI → 原有前台 worker → 显式启用的服务转发 |
| C | 同 B，额外发现 `mcp__operator__operator_verify` | 实际 DSH MCP client → 本仓 MCP server/worker → 同一转发 |

B/C 的 CLI 使用说明逐字相同；C 额外获得实际 MCP schema/说明及本仓插件加载配置。本地测试强制脚本化调用来验证接线，**真实模型是否选择 MCP 由事件记录决定，不能因为安装了插件就声称用过它**。`/op` 斜杠命令不是这次的验收对象。

实验配置通过 `OPERATOR_AGENT_S5_DEV_CONFIG` 指向临时私有文件。文件只含回环服务的一次运行能力和固定任务信息，不含服务商或 SSH 凭据；它与临时 patch 在 DSH 退出后删除。DSH 会清理 shell 子进程中 TOKEN 类环境变量，因此不把能力令牌直接放进 bash 环境。CLI/MCP 的默认路径没有启用该配置，原有生产验证照常执行。

这是显式的实验后端转发，不能描述为“未经修改的生产后端”。`hitl_tools.verify` 在已 prepare、契约重算一致后才转发；配置缺项、契约错误、L3、另选后端或提供远端连接参数均拒绝，不回退本机执行。在该配置下，repair/run/bench 拒绝，MCP 仅发现 prepare/verify/capabilities；模型自行修改候选源码。此阶段比较范围是**外层开发 + 监督 L2 的使用流程**，不代表内层生成/自动修复全功能对照，也不恢复 Q1。

## 3. 配额、最终判定与证据

后续模型配置按 2026-10-29 用户指定冻结为：

| 项目 | 配置 |
|---|---|
| 思考强度 | `medium`，同时设置 DSH 宿主和 Responses 网关 |
| 单次最大输出 | `32768`（32K，包含服务商按输出额度计的内部推理） |
| 每组模型调用上限 | 24 次，失败不退款 |
| 总输出预留 | `24 × 32768 = 786432`，是上限而非实际消耗 |
| 模型上下文元数据 | `1000000`，与当前 DSH provider profile 中该模型一致，避免原来 16K 宿主上下文压缩输出额度 |
| 单请求监督截止 | 900 秒；模型/开发期会话仍受 2400 秒上限约束，最终验证另有 600 秒上限 |
| 原始响应传输上限 | 64 MiB（含 SSE 开销），保留有界传输，避免原来的 1 MiB 限制先截断长推理 |

这些是下一次新冻结的协议参数，不修改用户 DSH profile，不改变 v6 的历史 `none / 8192` 事实，也没有触发新付费请求。32K 是最大输出额度，不能保证每次请求都产出 32K；真实服务的中等思考、多轮上下文与大输出仍待下一轮受控预检确认。

实际 DSH 在启用推理时还发送 `reasoning.summary=auto` 与 `include=[reasoning.encrypted_content]`。网关现在严格接收这些已核对的字段，保留推理摘要设置与加密推理回传选项，只把 effort 固定为 medium；未知摘要值/额外字段仍在预留前拒绝。完整回归另发现旧网关的共享 `/tmp` 调试写入触发守卫，已移除，不再把原始响应或上游异常写入固定共享路径。

新协议每组最多 **2 次开发期验证 + 1 次独立最终验证**。模型请求仍使用已有共享预算网关，开发期验证不附赠模型额度。失败、unknown、评测异常都消耗已预留的验证额度；并发请求串行计数，重新创建同一证据目录拒绝，不能重启后重置计数。

最终入口只由监督器 Python API 在 DSH 结束后调用。HTTP 没有 final 路由，开发期额度不可使用最终预留；最终结果不回传模型，不能据此继续修复。最终源码即使与最后一次开发候选相同，也独立验证一次。会话中断而无最终源码时不补造最终候选，保留 unknown、已用预算和耗时。

每次验证先落盘 `request.json` 与候选，然后执行，保存 `response.json`、`record.json` 以及底层 CLI 完整证据。每条记录绑定顺序、阶段、候选 SHA256、契约、服务计划、起止时间和反馈哈希。`development.json` 留存账本，`development-audit.json` 对照 DSH 的真实 tool_call/tool_result，检查反馈投影、调用 ID 与顺序，并单独标记是否观测到 operator MCP 验证。CLI/MCP 外层附加的 invocation_id 等回执与共用反馈投影分别留痕。

这些材料可以追踪“候选—反馈—后续候选—最终提交”。哈希和转录审计只证明合作环境中的对应关系，不证明反馈导致了模型改进，也不建立同 UID 防篡改或防旁路边界。开发期无验证记录时不伪造一次工具调用。

## 4. 本地验证

专项 `tests/test_s5_workflow.py` 在用户修订配置后 **30 项通过**，包括：

- 10 项提示与生产主输入的 shape/dtype 绑定，以及维度、精度漂移反例；旧执行协议仅可分析，不可再派发。

- 每组 3 次脚本化假模型请求、2 次开发期 mock 验证；模型结束前最终额度为 0，随后独立最终验证为 1，最终结果未触发新模型请求。
- 配额超限、并发竞争、过期、未知候选、配置缺项、契约/后端漂移、HTTP 越权/额外字段/重复字段，以及反馈篡改均有负例。
- 实际 DSH 经受监督的 Responses 转发进程访问本地假上游，观察到 `reasoning={effort:medium, summary:auto}` 和 `max_output_tokens=32768`，账本事前预留 32768；不是只核对配置字面量。上下文不足、未知推理选项、传输大小/时间超限均有拒绝反例。

测试只执行两份事先审核的固定 Python 候选，mock 模式对其他源码消耗额度并报 unknown，不执行它们。它不是 GPU 正确性或模型收益测量。真实 DSH 工具循环在本次专项使用本地 Chat Completions 假协议；真实 Responses 转发继续由既有网关测试覆盖，完整 Responses 多轮 GPU预检尚未运行。
