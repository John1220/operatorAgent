## C 组为何没有使用插件验证（2026-10-30 复核）

完成首轮的六个 C case 均实际调用一次 `operator_capabilities`，MCP 初始化和工具列表请求也正常应答；其开发验证共七次，全部通过公共 `check.py`，零次 `operator_verify`。没有“先调用 verify 失败再回退”的记录。具体事件下标和转录文件哈希保存在 `execution/plugin-choice-audit-20261030.json`。

存在三项可核验的使用引导问题：

1. 共用任务提示直接给出 Python 解释器、`check.py` 绝对路径及 `--code-file candidate.py` 的完整命令，对插件只说“可用时使用正常插件工具”，没有给出同样清晰的当前连接条件。
2. MCP 的 `operator_verify` schema 沿用普通直连后端描述：backend 默认 mock，host 描述为 SSH 必需；六次 capabilities 都返回 `ssh.env_present=false` 和 host 需求。但任务要求 backend 固定 ssh、不得提供 host，MCP relay 的参数白名单又实际拒绝 host。实际监督模式由外部服务持有连接信息，工具无需 host；对模型展示的说明没有完整反映这种模式。
3. 监督模式 initialize instructions 已被简化为 prepare→verify，但任务目录其实已 prepare。能力返回仍混合本地控制机信息与监督验证能力，未明确“本机 SSH 环境缺失不代表监督 GPU 验证不可用”。工具通用 schema 的 L3/local/连接参数与本次只允许 L2/固定后端也不完全一致。

这些事实支持“公共路径更明确、插件说明存在冲突”的解释，不能据此建立某一个因素导致所有六次选择的因果结论，也不能解释成模型根本没发现插件或插件 verify 已尝试但不可用。先前单独强制入口验收证明过该路径可用；本次对照没有测到它的自然使用效果。

建议修复监督模式的真实产品接口：让 tools/list、initialize instructions 和 capabilities 一致反映固定后端、已准备任务、无须且不能提供 host、仅 L2 和共同额度；区分本机能力与监督服务能力，不伪报 SSH 连通性。保留普通直连模式原有 host 要求。先用无模型 schema/说明一致性和正常工具调用测试验收，再另冻版本；不改写本批提示/结果，不用只对 C 临时强制调用来制造使用率。当前模型调用数差异不能作为插件验证工具增益证据。
