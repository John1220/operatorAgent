# IEEE FP32 基线与分块宽度复测

2026-11-08 · H20 GPU 3 · FP32 Triton Matmul 4096³

CUDA 真机的内建 FP32 Matmul 现在明确请求 `pytorch_eager_fp32_ieee`。远端在配对窗口使用 IEEE FP32，窗口结束后恢复原来的精度设置。控制端要求回执确认选中该基线。候选的 FP32 计算路径从唯一的 Triton 编译产物 PTX 读取。缺少证据或出现混合指令路径时，保留未知计算路径，不报计算余量或据此触发判停。

原 R2 起点 `e52f637c8acf…` 在新口径下通过完整 L2，L3 有效。候选中位时延 **5.490912 ms**，同窗 IEEE FP32 基线 **4.520304 ms**，加速比 **0.8232×**。PTX 回执为 `fp32_cuda_core`，规格分母 39.5 TFLOPS，达成率 63.4%。候选时延与原 R2 起点接近，加速比变化来自基线口径。见 [原 R2 首对](r2-fp32-pair-1-20261108.md)。

## 单变量复测

冻结 `operator-v08-ieee-fp32-tile-control-v1`，保留 C 臂终稿的所有源码，只替换 `BLOCK_N`。起点回归后按 64 → 128 → 128 → 64 在同卡串行测量。预检带宽 `0.100836%`，四次均通过完整 L2，L3 均有效。

| `BLOCK_N` | 两次中位时延 | 两次中位时延均值 |
|---|---|---:|
| 64 | 5.268976 / 5.268208 ms | 5.268592 ms |
| 128 | 5.071728 / 5.071360 ms | 5.071544 ms |

在 C 终稿代码上，仅改分块宽度就使时延下降 **3.74%**。该变化的量级接近原 R2 两份终稿的 0.203 ms 差距。它说明这一配置对 C 源码的影响，诊断能否让模型更常选到这样的配置由单独的诊断开关对照回答。

仓外证据 `output/v08-r2-20261107/ieee-fp32-tile-control-20261108/` 包含冻结计划、开跑门、三份源码、五份 L1–L3 回执及 `summary.json`。

## 消费侧：`None` 不许被印成数字（2026-11-08 补）

修好"计算路径不明就报 unknown"之后，`gflops_utilization_pct` 会真的变成 `None`。
那是对的，但它一路走到 `generate/agents._num()` 的 `fmt.format(None)` 上抛 `TypeError`，
被上层吞成 `[Search] LLM 优化失败 (…) ⇒ 回退规则优化` ——**结构搜索静默消失**，而日志只像是
一句回退。同一次里，`hw_peak_gflops=0.0`（verifier 的"0 = 不知道"约定）会被印成"峰值 0.0"。

修法：`_num` 显式区分三种"没有读数"（`refused` / `None` / 数值），峰值用 `or None` 走同一条；
`_performance_projection` 已有 `compute_unknown` 分支，缺席而非补 0，并有测试钉住
（`tests/unit/v08/test_unknown_compute_path.py`）。

边界：这条修复不改变任何判据——它只保证"没测到"在 prompt 里长得像"没测到"，
而不是像 0。读数本身是否成立仍由 `measurement_validity` 与 8 条 case 决定。
