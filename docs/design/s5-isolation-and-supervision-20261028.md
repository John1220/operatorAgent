## 需要建立的执行边界

1. 以每个任务、每组一次性独立环境启动相同版本的 DSH。三组均只读挂载共同任务材料和相同运行时，工作目录相互隔离；B、C 额外挂载相同哈希的 core 和固定说明，C 再加载冻结的插件；A 不可读取本仓、插件、其他组工作目录或历史候选。不能挂载宿主 home、SSH 凭据、Docker socket、共享缓存或监督器账本的可写副本。
2. 容器/命名空间禁止直接外网和访问其他组；模型凭据只存在于容器外受监督的网关。外层 DSH 和 B/C 内层模型请求均必须经此网关，网关在真实网络交接前执行共享预留并记结果。只靠 DSH middleware、Python SDK hook 或同用户 SQLite 无法证明模型无法通过 shell 或其他库绕过，不能视为正式预算门。网关必须验证任务身份、禁止 fallback/隐式重试并限流，缺 usage 记 unknown；请求预留和输出上限不是账单金额硬上限。
3. 三组开发期间通过同一受监督的验证服务获取可比反馈；服务在调用前记录候选源码、契约、输入和验证预算，在运行后记录分级事件及远端会话状态。首次完整 L2 的时间和调用水位只能来自可信的开发期事件；没有该事件时记 unknown。统一最终评测另计成本，不允许基于终评反馈继续开发。
4. 当前 core 的真机路径使用 `RemoteExecutor` 经 SSH 调用远端 runner；简单移除 SSH 会让 B/C 的真实路径不可用。必须设计并测试受监管的 GPU 执行适配，保持现有 CLI/MCP、输入保真、运行状态、预算和远端 owned 会话清理契约；A 也使用同一验证服务。不要用 mock backend 替代真机证据。
5. 监督器位于受试环境外，持有任务与账本身份，负责串行启动、停止和收集完整分母。账本故障或身份变化时，若持久 abort 无法确认，监督器必须中止所有归属进程并标记全局停止未知；SQLite 标记只能阻止之后通过该账本的预留/交接，不能撤回已经交接的请求。

建议先做仅连接 fake provider 的网关，限定模型、请求体大小、输出上限和时间，验证真实 DSH 的流式/tool-call 及 Python 客户端共同受限，再引入任务专属 Unix socket 和独立网络命名空间进行绕行测试。网关应是唯一跨层预留权威：若同时对同一请求启用当前外层拦截器或内层共享桥，会重复扣额；各客户端自身的本地预算仍可独立保留。不能仅凭客户端自报的标头判定外层/内层成本归属，缺可信来源时记 unknown。受监督验证服务执行候选代码时也必须限制其文件和网络访问。

2026-10-28 对 H20 主机只读检查：`bwrap`、Python 3 和 Docker daemon 可见；默认 PATH 中未找到 `node` 或 `dsh`。这不排除其他路径上的安装，但尚未证明目标 Linux 环境有可运行的同版本 DSH。容器或 `bwrap` 存在、daemon 可访问，也都不构成上述隔离通过。

同日进行的临时基础探测中，`bwrap` 可同时建立 user、PID、network 命名空间；遮蔽 `/home`、`/tmp`、`/run` 并使用独立 `/dev` 后，探针未见宿主 home、Docker socket 或 NVIDIA 设备，网络接口只有 loopback。宿主缓存了 Node 20 Alpine 与 Python 3.11 slim 镜像；没有拉取镜像或运行容器。常见系统、用户 Node 和全局 npm 路径未找到 Node/DSH，但未扫描所有路径。该探针以根目录只读绑定，仍暴露其他未遮蔽路径；没有验证任意网络绕行、凭据、完整 DSH 运行或 GPU 验证服务，不能视为隔离验收。

本机全局 DSH CLI 为 `0.1.1-rc.2`，Desktop 内嵌 DSH/pi-ai 为 `0.2.1-rc.2`；两者不能混作同一宿主。当前插件声明 Node ≥22，Desktop 声明 `^22.19` 或 ≥24，远端缓存的 Node 20 镜像不满足这些版本要求。正式对照前须选择并冻结三组实际一致的 Linux 宿主及其兼容运行时，不能把现有缓存镜像视为已满足条件。

Desktop `0.2.1` 的启动路径还依赖 `node-addon-require-builtin` 原生模块；本机包内只有 Darwin 构建，尽管另一个 `node-pty` 依赖含 Linux 预构建文件，也不意味着整套目录可复制到 Linux 后运行。尚未证明本机缓存包含该模块的 Linux 安装包；须取得并冻结兼容的 Linux x64 依赖与 Node 运行时，再在全新 HOME/DSH_HOME 内验证假模型启动，不复制用户 profile 或凭据。Desktop 包树中的 `dsh-headless@0.2.1-rc.2` 可作为候选共同入口研究，但还未证实其 Linux 依赖闭包、是否受此原生模块影响或 Alpine 的 musl 兼容；其基础配置中的 retry 和 session-title 调用须显式禁用或统一计入预算。

## 放行前的离线检查

- 在拟定真实宿主上分别测试 A/B/C 文件可见性，验证 A 对 core、插件、私有提示、其他工作区和宿主凭据的读取均失败，B/C 的 core 摘要一致，C 的实际插件入口确实被调用。
- 分别测试 shell、子进程、子 agent、辅助调用、重试以及 Python 直连均无法绕开模型网关；测试断网、账本损坏、文件替换、监督器退出、预算耗尽、取消和进程逃逸。对正在交接的请求保留状态未知，不假设它未到达服务商。
- 用 fake provider 和 mock 验证服务测试三组从启动到收尾的实际路径、事件与可重算汇总；再独立验证受监管真实 GPU 适配的 runner 版本、输入、同卡执行、停止和清理。以上任何一项未知均不能升级成正式实验资格。
- 冻结模型、端点、源码、依赖、任务、提示、次序、调用与输出预留、墙钟、GPU 时段及总费用控制；GPU 空闲快照不是租约。固定分母包含失败、未执行与未知，不能因结果选择性重跑。

## 现有原型与限制

`operator_agent/s5_shared_budget.py` 提供 SQLite 事务化预留、交接意图、完成与不可撤销停止；`operator_agent/s5_inner_budget.py` 是显式环境变量启用的内层桥；`integrations/s5-budget-observer/` 是外层 DSH waterfall 原型。两侧已用假 provider 和真实 SQLite 做离线测试，但它们只覆盖配合使用的调用；账本同 UID 可被替换、身份核对和数据库操作间有竞争窗口，不提供进程隔离。交接事件只是**准备将请求交给传输层**，不能证明网络请求已发出或已被服务商接收。

`benchmarks/s5_l2_evaluator.py` 仅执行可信本地 Python fixture，原始 10 项可在 mock 上检验主输入和 holdout；4 项大任务受内存边界限制而为 unknown。它不运行 Triton 生成代码，不是隔离沙箱，不能产生正式 GPU L2 或性能结论。

`benchmarks/s5_three_group_run.py` 用冻结计划把 A/B/C 三组的安装面、共享账本、DSH headless 启动和 supervisor 侧统一 mock 提交串起来，并用 `benchmarks/s5_arm_env.py` 记录每组环境可达性（**A 组实测仍可读本仓**）。它只证明接线与记录可复算，不构成隔离、真实模型或 GPU 验证；正式执行仍须完成上文第 2、3 项。
