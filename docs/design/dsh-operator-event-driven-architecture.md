# DSH 算子开发插件：事件驱动与持久任务架构设计

日期：2026-10-31  
状态：设计提案，尚未实现  
参考：DeepSeek《Super-agent 设计探索：迈向更自主的 Agent 系统》

本文讨论如何把当前 DSH 算子开发插件从“MCP 工具集合”渐进升级为“可持续运行、事件驱动、异常可恢复的算子任务系统”。参考文章是架构探索，不是 DSH 现有产品功能说明；本文不假设 DSH 已提供文章中的 Super-agent、Thread 或事件推送 API。

## 0. 结论先行

当前插件已经具备独立后台 `operator_run`、持久化 `run_dir`、任务预算、取消、`lost` 状态、契约冻结和 L1/L2/L3 证据链，不需要推倒重写。

优先改造的是控制面，而不是生成或判定内核：

1. 为 `run/verify/repair/bench` 建立统一的异步任务与事件协议。
2. 增加确定性 Watchdog，处理失联、无进展、远端清理未知和执行环境漂移。
3. 用 Compact Status 与按需证据召回降低上下文占用。
4. 多任务出现时再引入 Router/Worker 与订阅直通。
5. 投机执行必须受 GPU、模型调用和审计预算约束，最后实施。

这套设计改善的是任务编排、交互连续性、可恢复性和可观测性。它不能单独证明算子正确率、生成质量或 GPU 吞吐提升。

## 1. 背景与现状

### 1.1 参考文章的可迁移思想

参考文章的核心不是增加更多 Agent 角色，而是将 Agent 从单次同步会话改造成持续运行的任务系统：

- 用 Router/Worker 双层结构分离全局交互与具体执行。
- 用 Trigger、Thread 和订阅直通替代所有事件都经主会话转发。
- 用异步 `start/stop` 和完成事件消除长工具调用对对话的阻塞。
- 用 Inline & Spill 与链式召回控制上下文预算。
- 分离计算、持久状态和执行环境。
- 用外部 Watchdog 发现基础设施故障和任务无进展。
- 在受控预算下进行投机执行。

这些思想可映射到算子开发，但必须结合本项目的 GPU 资源、证据和安全约束重新落地。

### 1.2 当前已有底座

| 能力 | 当前实现 | 与目标架构的关系 |
|---|---|---|
| 后台整段开发 | `operator_run` 启动独立进程，立即返回 `invocation_id` | 已有 Worker 雏形 |
| 持久状态 | `run_dir` 保存 declaration、contract、状态、日志和证据 | 已有状态分离雏形 |
| 状态查询 | `operator_status` 返回 `running/done/failed/cancelled/lost` | 可扩展为统一状态投影 |
| 取消 | 后台 run 与前台长调用均有实例身份和取消协议 | 保留并复用，不另造一套 |
| 长任务监督 | 前台 verify/repair/bench 由独立 worker 执行 | 可渐进改为可选异步返回 |
| 判定与证据 | 契约哈希、候选源码哈希、L1/L2/L3、资格与逐轮证据 | 属于稳定内核，本设计不改判据 |
| 执行后端 | mock/local/ssh，SSH 当前单主机、单卡、串行 | Worker 并发不等于 GPU 可并行 |

主要现状代码：

- `operator_agent/app/autonomous.py`：后台 run 的独立进程与状态落盘。
- `operator_agent/app/tool_calls.py`：前台长调用的监督、实例身份与取消。
- `operator_agent/app/mcp_server.py`：MCP 工具契约、分发与使用说明。
- `operator_agent/app/hitl_tools.py`：prepare/verify/repair/bench/run/status/cancel 业务封装。
- `operator_agent/app/conductor.py`：生成、验证、修复与搜索主循环。

### 1.3 需要解决的问题

1. **长同步调用阻塞交互。** 真机完整 verify 已达到分钟级，repair 可达几十分钟；当前只有 run 是完整后台模式。
2. **完成状态依赖主动轮询。** 缺少统一的完成事件、游标续读和宿主通知适配层。
3. **异常可发现但缺少外部恢复环。** 已有 `lost` 和清理未知，但没有独立控制环持续对账本地、远端和状态文件。
4. **多轮任务上下文容易膨胀。** 状态、源码、日志和证据需要按相关性内联，而不是全部塞入模型上下文。
5. **多任务与单 GPU 资源语义尚未分离。** 生成可以并行，测量与验证必须受资源队列约束。
6. **主动化扩大安全边界。** 当前候选代码并非在完整沙箱内执行，MCP 工具也不经过 DSH 审批层；不能直接把任意外部消息变成执行触发器。

S5 已记录 idle timeout、网关链路 unknown、执行文件哈希变化和设施中断等情况。这些问题说明 Watchdog 与状态对账是现实需求，不是纯粹的概念性扩展；但现有对照仍未建立插件整体优于原生 DSH 的结论。

## 2. 目标与非目标

### 2.1 目标

- 后台执行期间，DSH 仍能接受新指令、修改方向或请求取消。
- 所有长任务使用一致的实例身份、状态投影、事件序列和取消语义。
- MCP 或宿主重启后能够重新发现任务，不重复启动 Worker。
- 迟到事件、旧候选结果和基础设施异常不会污染新契约或新候选。
- 模型默认只接收高信号摘要，能够沿 ID 引用按需读取完整证据。
- Watchdog 能区分候选失败、设施失败、取消和未知，不补造判定事实。
- 保留现有同步调用和人工一步步驱动工作流的兼容性。

### 2.2 非目标

- 不修改容差、反作弊、资格、入库门、测量有效性或 `route/eligibility/conflict` 语义。
- 不重写 Designer/Coder/Fixer/Search，不默认启用 CoderPipeline。
- 不把每个生成或验证步骤拆成独立 LLM Session。
- 不要求把 Agent Loop 迁移到云端，不要求引入数据库或云控制面。
- 不承诺多 Worker 能提高单卡 GPU 吞吐量。
- 不用编排指标替代算子正确率、性能或生成质量评价。
- 不让 Watchdog 自动修改提示词、判据或候选源码。

## 3. 设计原则

1. **判定事实只能由既有验证链产生。** 事件、Watchdog 和 Router 只传递、投影和恢复事实，不授予通过资格。
2. **状态可重建，事件可追溯。** 状态文件是当前投影，事件与既有证据用于审计；二者冲突时保持未知并报告，不静默覆盖。
3. **实例与内容身份同时绑定。** 每次执行有 `invocation_id`，每份判定绑定契约与源码哈希。
4. **先确定性控制，后模型自治。** Fast Path 处理订阅、过滤、路由和恢复；LLM 只处理需要语义判断的部分。
5. **兼容优先，渐进切换。** 同步工具默认行为先保持不变，异步与推送能力验证后再调整默认。
6. **未知不被“恢复”为成功或失败。** 缺少证据时保留 `unknown/lost/cleanup_unknown`。
7. **GPU 是显式预算资源。** 投机、重试和并发都必须可计量、可取消、可审计。

## 4. 总体架构

```text
人 / 外部工作信道
        │
        ▼
DSH 会话（交互与跨任务协调，逻辑 Router）
        │  start / status / events / cancel
        ▼
任务控制面（现有 MCP + CLI 扩展）
  ├─ Task Registry：实例身份、所有权、任务索引
  ├─ Event Log：追加事件、单调序号、游标续读
  ├─ Status Projection：当前状态与紧凑摘要
  └─ Event Adapter：宿主通知；未确认推送能力时使用轮询降级
        │
        ▼
Worker Supervisor（每个 invocation 一个执行所有者）
  ├─ autonomous run → Conductor
  ├─ verify         → Verifier
  ├─ repair         → RepairLoop / Fixer
  └─ bench          → L3 exploration
        │
        ▼
资源调度与既有 Backend（mock / local / ssh）
        │
        ▼
GPU / LLM / 远端执行环境

独立确定性 Watchdog：读取状态与心跳，执行有界对账和恢复；
不经过 LLM，不改变判据，不直接生成候选。
```

### 4.1 职责边界

| 组件 | 负责 | 不负责 |
|---|---|---|
| DSH / 逻辑 Router | 用户交互、新任务分派、跨任务决策、交付解释 | 不直接制造验证事实，不转发每条 Worker 内部日志 |
| 任务控制面 | 实例注册、事件、状态、取消、游标续读 | 不改变生成策略与判定语义 |
| Worker | 专注完成一次 run/verify/repair/bench | 不直接对外多头回复，不处理无关任务 |
| Watchdog | 心跳、所有权、进展、远端和环境对账 | 不修改提示词、源码、契约或通过结论 |
| GPU 资源调度 | 串行或受控并发、资源互斥、队列公平 | 不把排队时间隐藏为模型执行时间 |

P0 不需要新增一个常驻 LLM Router。现有 DSH 会话先承担逻辑 Router 职责；只有多任务吞吐证明其成为瓶颈后，才考虑独立 Router Session、批处理或分片。

## 5. 任务身份与引用图

### 5.1 标识体系

| 标识 | 含义 | 约束 |
|---|---|---|
| `run_dir` | 一次声明及其相关任务的持久容器 | 不复用历史目录伪装新任务 |
| `invocation_id` | 一次具体 run/verify/repair/bench 执行实例 | 启动前建立，不可覆盖 |
| `contract_hash` | 冻结契约身份 | 契约变化后旧结果不得自动套用 |
| `candidate_id` / `source_hash` | 候选与其内容身份 | 判定和事件必须绑定实际源码 |
| `verification_id` | 一次验证或修复内验证的证据身份 | 指向既有逐轮证据，不复制判据 |
| `event_id` / `seq` | 事件身份与实例内顺序 | 消费者可去重、续读和识别缺口 |
| `artifact_id` | 最终或中间产物身份 | 不隐含正确性或交付资格 |

### 5.2 引用关系

```text
invocation_id
  → contract_hash
  → candidate_id / source_hash
  → verification_id
  → evidence_path
  → artifact_id
```

工具回包和事件内联当前对象摘要及下一跳 ID。模型需要修复或审计时，再沿引用读取源码、失败日志或完整报告，避免把全部历史同时装入上下文。

### 5.3 一致性不变量

- 事件必须属于一个已登记的 `invocation_id`。
- 同一实例的 `seq` 单调递增；消费者按 `invocation_id + seq` 去重。
- 已完成实例的终态不可被迟到心跳或旧 Worker 覆盖。
- 取消与完成竞争继续采用现有共享单调时钟和实例所有权规则。
- 旧 `contract_hash` 或 `source_hash` 的事件可以留存，但不得更新新任务的当前结论。
- `done` 只表示流程结束，仍须读取判定、停止原因、预算和清理回执。
- 本地进程结束不自动推导远端 GPU、所有子孙进程或模型服务商已经停止。

## 6. 事件模型与持久化

### 6.1 事件类型

首期只保留少量稳定类型：

- `task.started`：实例已登记并启动。
- `task.heartbeat`：所有者存活及当前阶段，低频写入。
- `phase.changed`：如 L1→L2→L3、生成→验证→修复。
- `verification.completed`：一次既有验证结果已形成，携带摘要和证据引用。
- `task.completed`：流程到达 done/failed/cancelled 等终态。
- `task.lost`：所有者消失或状态无法恢复。
- `cleanup.updated`：本地、远端或服务商清理事实发生变化。

事件类型不是新的判定词表。`verification.completed` 可以表示通过、失败或未知，具体仍以既有 `VerificationResult` 为准。

### 6.2 事件 envelope 示例

```json
{
  "schema_version": 1,
  "event_id": "evt_...",
  "invocation_id": "0123456789abcdef0123456789abcdef",
  "seq": 42,
  "type": "verification.completed",
  "occurred_at": "2026-10-31T15:00:00Z",
  "contract_hash": "sha256:...",
  "source_hash": "sha256:...",
  "summary": {
    "level": "L2",
    "passed": false,
    "route": "debug_fix"
  },
  "refs": {
    "verification_id": "verify-2",
    "evidence_path": "/abs/run/verify-2/result.json"
  }
}
```

完整源码、长日志、大矩阵错误样本和模型原始响应不进入 envelope，只通过受控引用读取。

### 6.3 存储布局

```text
<run>/
  launch.json
  run-status.json          # 自主 run 的现有状态投影
  events.jsonl             # 自主 run 的追加事件
  watchdog.json            # 最近对账结果，不是判定事实
  tool-calls/<id>/
    launch.json
    status.json
    events.jsonl
    worker-result.json
```

约束：

- 每个实例只允许一个事件写入所有者，避免多进程交错写同一日志。
- 状态 JSON 继续原子替换；事件追加失败时保留执行事实并显式报告事件面退化。
- 事件面故障不得让未执行的验证变成通过，也不得阻塞既有同步库调用。
- 消费者发现序号缺口或事件损坏时，从状态与证据对账，结果保持未知，不自动补事件。
- 事件压缩或轮转不能删除既有验证证据；游标必须能明确报告已截断区间。

## 7. 统一异步工具协议

### 7.1 兼容式 API 演进

| 工具 | 演进方式 |
|---|---|
| `operator_run` | 保持现有立即返回实例 ID 的行为 |
| `operator_verify` | 增加可选 `wait`；默认 `true` 保持同步，`false` 时启动后返回实例 |
| `operator_repair` | 同 verify；异步不代表放宽轮次、预算或反伪修复门 |
| `operator_bench` | 同 verify；仍只返回 exploration 级测量，不获得裁决语义 |
| `operator_status` | 统一返回当前投影、预算、停止原因、清理回执和引用摘要 |
| `operator_events` | 新增游标续读入口：`after_seq + limit`，作为推送不可用时的降级 |
| `operator_cancel` | 复用现有按 `run_dir + invocation_id` 取消及竞争规则 |
| `operator_prepare/capabilities` | 保持同步、短调用 |

异步启动回包只表示任务已接受或启动，不表示候选通过：

```json
{
  "accepted": true,
  "phase": "running",
  "invocation_id": "...",
  "status_ref": "...",
  "events_ref": "..."
}
```

在宿主推送能力未确认前，`operator_events` 是必需降级路径；不能仅设计一个依赖未知 DSH API 的通知方案。未来若确认宿主支持事件注入，再由 Event Adapter 将新事件投影到对应会话或任务 Thread。

### 7.2 全双工行为

- `wait=false` 或 run 启动后，DSH 可继续处理新输入。
- 新输入可以查询进度、要求停止，或声明新的契约与候选。
- 完成事件到达后，DSH 先核对实例和内容身份，再决定是否汇报。
- 用户改变方向不自动篡改旧任务；旧任务按取消协议结束，新任务使用新实例。
- 同步 MCP 取消通知和 CLI 中断语义继续保留。

### 7.3 默认值迁移

第一阶段 `verify/repair/bench` 的 `wait` 默认仍为 `true`，避免破坏现有客户端。只有以下条件全部成立后，才评估是否改为异步优先：

1. DSH 真实客户端能在后台执行期间继续接受输入。
2. 完成事件或游标续读不会丢失终态。
3. MCP 重启后能重新发现实例且不重复启动。
4. 取消、预算、证据和远端清理回归全部通过。

## 8. Watchdog 设计

### 8.1 部署与权限

Watchdog 是主 Worker 之外的独立确定性控制环，可先做 CLI/独立进程，不需要 LLM。首期权限按两步开放：

1. **只读审计：** 读取 launch、状态、事件、心跳和既有后端回执，生成对账报告。
2. **有界恢复：** 仅执行预定义的重查、重连、请求取消和状态标记；不接受任意 PID、路径或 shell 命令。

不实现文章所述“在线增删提示词、调整触发规则”。这会绕过当前变更与评测纪律。

### 8.2 检查与动作

| 观察 | 判定与动作 | 禁止行为 |
|---|---|---|
| owner 消失且未写终态 | 核对启动身份后标记或保留 `lost`，记录清理未知 | 不按可能复用的 PID 发信号 |
| 心跳陈旧但状态仍推进 | 继续观察并记录心跳异常 | 不仅凭单一超时判任务死亡 |
| 长时间无阶段进展 | 检查预算、Worker 和远端执行；必要时请求有界取消 | 不自动改写候选后继续跑 |
| MCP/宿主重启 | 从 launch/status 重新发现实例并恢复查询 | 不重复启动同一 invocation |
| 本地 cancelled、远端 unknown | 重查本次拥有的精确会话与清理回执 | 不把本地退出写成远端全部停止 |
| runner 或执行文件哈希变化 | 将受影响测量资格保留为 unknown，要求重新确认环境 | 不复用旧读数授予通过或入库 |
| 服务商响应中断 | 保留已发生调用和未知终态 | 不假设未计费或已停止 |
| 事件缺口或状态冲突 | 标记控制面退化并保留原始文件 | 不补造事件、时间或判定 |

### 8.3 恢复边界

- 不实现任意断点续跑；能否重连必须由具体后端提供可验证身份。
- 自动重试必须有次数与预算上限，并使用新的执行尝试身份或明确的 attempt 记录。
- 已经完成的独立验证事实可以保留，未完成的步骤不补造结果或 `complete.json`。
- Watchdog 的每次动作写入审计记录，包含观察、依据、动作和结果。

## 9. Inline & Spill 与交互投影

### 9.1 默认内联内容

`operator_status` 和完成事件默认只包含：

- 当前阶段、是否终态、停止原因。
- L1/L2/L3 摘要及必要的 `route/eligibility/conflict`。
- speedup、GFLOPS、validity 等当前关键指标。
- 预算用量、清理状态和异常类别。
- `invocation_id`、契约/源码哈希、证据与产物引用。

### 9.2 窗口外内容

完整源码、长编译日志、逐步工具输出、模型原始响应、所有历史事件和大规模测量明细留在窗口外，通过现有证据路径或受控续读工具获取。

`operator_events(after_seq, limit)` 支持分批读取；批量状态变化可以合并成一条面向用户的摘要，但底层事件不可被改写。

### 9.3 面向人的输出

- `/op` 继续首行短回执，适应默认折叠卡片；不把长路径和完整事件塞入首行。
- DSH 通知只在需要决策、验收、异常介入时主动出现，避免心跳刷屏。
- 最终交付继续使用结构化报告，完整区分正确性、性能、资格、预算与清理未知。

## 10. 订阅直通、Router/Worker 与资源调度

### 10.1 Thread 的算子任务映射

一个 `invocation_id` 对应一条任务事件流。Worker 启动后订阅自己的事件流，后续验证、修复和清理事件直接进入该 Worker 的控制与状态投影，不要求外层模型逐条转发。

事件过滤采用两级策略：

- **Fast Path：** 实例白名单、事件类型、订阅关系、来源与权限检查，全部由确定性代码完成。
- **Slow Path：** 只有新任务是否需要启动、跨任务冲突和是否值得主动行动才交给模型判断。

任意外部消息不能直接成为 GPU 代码执行 Trigger。

### 10.2 Worker 粒度

Worker 按一次算子任务或工具实例划分，不按每个 ReAct 步骤划分。Conductor 内部生成、验证和修复仍由既有流程协调。

同层 Worker 不直接互相通信。共享 GPU、运行目录或候选产物的冲突由资源锁、实例所有权和 Router 协调。

### 10.3 单 GPU 约束

当前 SSH 后端为单主机、单卡、串行，因此：

- LLM 生成、报告整理可以并行。
- 需要同一张 GPU 的编译、正确性和性能测量进入资源队列。
- `bench` 多候选不天然获得并行执行权。
- 排队、执行和等待模型时间分别计量，避免把资源排队误报为模型变快或变慢。
- Router/Worker 的收益主要是交互连续性和多任务管理，不是绕过硬件限制。

## 11. 投机执行（后续可选）

可选场景：

- 完整 L2 通过后，在空闲 GPU 上预跑小范围参数探索。
- 出现明确失败信号后，后台先复现并生成诊断假设。
- 用户讨论优化方向时，提前准备候选，但不自动交付为已验证结果。

硬约束：

1. 默认关闭，按任务或全局显式开启。
2. 使用独立 GPU/模型调用预算，与正式任务预算分开记账。
3. 相同契约、源码和配置去重。
4. 用户改变方向或资源紧张时可立即取消。
5. 投机 bench 仍为 exploration；survivors 必须重新走 verify。
6. 没有有效结果时保持安静，但不能隐藏已经产生的资源消耗。
7. 不自动入库、不自动授予性能或正确性资格。

## 12. 安全与隐私门槛

事件驱动和主动执行之前必须落实以下最低门槛：

- 触发源、任务类型、后端和允许工作目录使用白名单。
- 外部文本只能作为候选需求或事件数据，不能直接拼接为远端命令。
- 保留现有参数白名单/黑名单，禁止通过事件注入 `atol/rtol`、反作弊开关或语料路径等受控参数。
- 每个任务具有 wall clock、模型调用、oracle 和 GPU 资源预算。
- 凭据继续通过既有引用或文件机制使用，不进入事件、状态、模型上下文和证据。
- Watchdog 只拥有预定义最小权限，所有恢复动作可审计。
- 候选代码执行威胁模型不因异步化而改变；当前 exec guard 不是完整沙箱，必须继续向用户明示。
- 主动通知不泄露私有源码、路径元数据或远端连接信息到不受信信道。

## 13. 分阶段实施与验收

### P0-A：统一事件与可选异步

主要改造点：

- `operator_agent/app/mcp_server.py`：可选 `wait`、events 工具 schema/dispatch/instructions。
- `operator_agent/app/hitl_tools.py`：统一业务回包和实例引用。
- `operator_agent/app/tool_calls.py`：前台长调用事件发射与状态投影。
- `operator_agent/app/autonomous.py`：后台 run 事件发射与心跳。
- 新增独立事件模块，避免把事件逻辑写入判定器。

验收：

- verify/repair/bench 异步启动立即返回实例，不等待完整 GPU 工作。
- 后台执行期间可查询和取消，同步默认行为不变。
- 事件可去重、续读，迟到事件不覆盖终态。
- 契约或源码变化后，旧结果不更新新任务结论。
- 事件写入失败不改变既有验证结果和证据语义。
- MCP 重启后不重复启动 Worker。

### P0-B：确定性 Watchdog 与远端对账

主要改造点：

- 新增独立 watchdog 控制环与审计文件。
- 复用现有实例所有权、共享单调时钟、persistent SSH 清理回执和预算模块。
- 在 `operator_status` 中投影对账摘要，不创造新的通过结论。

验收：

- 覆盖 owner 消失、PID 复用、心跳陈旧、状态冲突和宿主重启。
- 覆盖本地取消成功但远端清理未知的保持与后续更新。
- 执行文件哈希变化不会复用旧测量授予资格。
- Watchdog 崩溃不影响 Worker 和 MCP 协议。
- 所有自动动作有上限、有审计，不执行任意命令。

### P1：Compact Status、证据召回与订阅直通

主要改造点：

- 收敛 status/events 默认字段，提供稳定引用和游标。
- 在 DSH 宿主能力明确后实现 Event Adapter；此前保留轮询降级。
- `/op` 保持短回执，增加必要的事件续读或异常摘要。
- 多任务时引入资源队列和逻辑 Router，不先拆分 Conductor。

验收：

- 长任务多轮运行时上下文只包含摘要和必要引用。
- 模型能够沿引用找回指定候选、失败验证和最终证据。
- 无关 Worker 事件不会进入当前任务上下文。
- 同 GPU 任务不越过资源锁并行测量。

### P2：受预算约束的投机执行

验收：

- 默认无投机 GPU/模型消耗。
- 去重、取消、预算和审计有效。
- 投机结果不会被写成正式裁决，不自动入库。
- 通过消融实验证明等待时间或人工介入改善足以抵消额外资源成本。

## 14. 评测方案

### 14.1 将编排与算子质量分开

借鉴参考文章的消融方法，使用 Mock Worker/Backend 先测控制面，不把模拟耗时当作真实 GPU 能力：

| 方案 | 目的 |
|---|---|
| A：当前同步调用 + 主动轮询 | 基线 |
| B：统一异步 + 完成事件 | 测全双工与通知收益 |
| C：B + Watchdog | 测异常恢复与未知率改善 |
| D：C + 订阅直通/多 Worker | 仅在多任务负载下测路由收益 |

真实 GPU 实验只用于验证后端对账、资源互斥和证据完整性，并单独报告正确性与性能。

### 14.2 指标

| 维度 | 指标 |
|---|---|
| 完成时间 | 从任务接受到可交付结果的 p50/p95，排队时间另列 |
| 人的负担 | 主动轮询次数、需要人工恢复次数、阻塞期间不可响应时长 |
| 模型成本 | Router/DSH 读缓存与输出 token、事件召回次数 |
| 资源成本 | GPU 占用小时、模型调用、投机消耗、重复执行次数 |
| 稳定性 | lost/unknown 比率、重复 Worker 数、事件缺口、恢复成功率 |
| 取消闭环 | 本地、远端、服务商各自清理状态，不能合并为一个“已停止” |
| 算子质量 | 完整 L2、独立终评、validity/eligibility、加速比，单独评价 |

需要预注册任务负载、重复次数、停止条件和异常口径。不得用编排实验的完成时间改善，宣称生成质量或插件整体优于原生 DSH。

## 15. 风险与开放问题

1. **DSH 推送能力未知。** 需要先验证真实宿主 API；`operator_events` 轮询降级必须独立可用。
2. **事件与状态双写一致性。** 采用单写入者、序号、原子状态投影和对账，不能用事件覆盖既有判定事实。
3. **远端可恢复能力有限。** 没有精确远端身份时，只能保留未知，不能承诺自动恢复。
4. **多 Worker 可能增加 token 和资源消耗。** 只有多任务收益明确时才扩展。
5. **长程记忆不在首期范围内。** 引用图解决按需召回，不等于跨月知识管理已经解决。
6. **主动化放大安全影响。** 外部 Trigger 与代码执行之间必须保留确定性准入和预算边界。
7. **默认异步的兼容性。** 在真实客户端验证前不修改现有同步默认。

## 16. 与既有质量工作的关系

本设计不替代以下独立工作线：

- 是否增加 `operator_generate_candidate`。
- 是否评估并启用完整 CoderPipeline。
- repair 是否使用 run-local failure DB。
- 新算子布局、正确性 profile 和性能基线覆盖。
- 插件相对原生 DSH 的完整 A/C 对照。

架构改造与上述工作可以共享任务身份和证据协议，但应分别变更、分别评测、分别形成结论。

## 17. 推荐决策

先批准 P0-A 与 P0-B：它们直接对应当前长同步调用、轮询负担、`lost/unknown` 和远端清理不确定等实际问题，同时可以复用现有实例、取消、预算和证据机制。

P1 的 Router/Worker、订阅直通和上下文召回按真实多任务需求实施；P2 投机执行最后考虑。整个过程中保持一条边界：**控制面可以变得更自主，判定事实必须仍然保守、可复核。**
