## 1. 问题、决策边界和作用范围

研究问题：在固定任务、模型、预算、执行资源和最终判定规则下，DSH 接入插件是否让任务更容易得到完整正确的候选，以及实现这一结果的模型调用和耗时是否改变？可测得合格且独立确认的性能时，再比较达到性能目标的覆盖。结果允许无变化、成本升高、效果变差或未知。

既有 [内外层分工决定 §7](hitl-generation-boundary.md#7-我无法确立的事)于 2026-10-25 暂停 Q1「外层裸写 vs 内层生成」单独对照。S5 的研究单位是**完整开发流程及插件增量**，三组各可有多轮、工具调用与修复；不执行 Q1 所定义的同模型单次生成实验，也不能用结果回答该问题或推断模型固有能力。用户要求继续 S5 不改变 Q1 的暂停决定。不为本对照改默认 Coder 为 CoderPipeline，也不推断 candidate_origin 即来源证明。

## 2. 三组与对照关系

| 组 | 配置 | 可回答的问题 |
|---|---|---|
| A：裸 DSH | 同版本 DSH 和同一外层模型；给相同任务声明及标准运行环境，不注入本仓 core、插件、其提示词或技能 | 基线流程能否完成、成本如何 |
| B：DSH + core CLI | 同 A；额外提供**与 C 完全相同**的 core 版本、CLI 和固定使用说明，不加载本仓插件 | B−A 是 core + 说明这一整包的增量，不是单独某模块的因果贡献 |
| C：DSH + 插件 | 同 B；加载实际 DSH 插件及 MCP/命令接入，保留与 B 相同的 core、CLI 和使用说明 | C−B 是该配置下插件接入/工具可发现性的增量，包含由插件入口引发的流程变化 |

三组使用相同外层模型、相同系统资源和公共任务材料；B/C 内层若调用模型，同样使用冻结的内层模型/端点，所有调用纳入各组总账。A 的开发环境允许相同的 Python/Torch/Triton 能力和受预算限制的执行；但不提供 core CLI/插件。B/C 不能靠额外外层对话、隐藏上下文、历史生成结果或更高内层预算取得不公平优势。禁止人工代改源码；任何人工干预、重跑和原因单独记账，不能混入自动化结果。

同一个模型不代表路径相同：三组必须留存**实际**模型请求身份、提示及工具调用的可审计绑定（敏感原文可 hash 和安全封存），记录 C 的插件/MCP 实际被调用，B 的 CLI 实际被调用，A 确无 core/插件挂载。审计层只读观察、在调用前拦截预算，不向模型额外反馈。三组各自任务独立工作区与运行内语料；无跨组候选、反馈或缓存继承。机器级缓存/预热的处理及状态需固定并记录，不因顺序更改预算或阈值。

**当前缺口：**生产 core 的 `model-journal` 覆盖其内层调用，但尚不能据此证明 DSH 外层调用全部被记账和事前限制；A 组的模型/验证成本也不能由 core 账本推算。没有完成可信外层调用捕获、统一预算门和工具路径证据前，不能认为三组成本公平、也不能启动正式样本。

**可研究的接线点（尚未实现）**：本机 DSH CLI `0.1.1-rc.2` 的 `@deepseek-ai/dsh-llm` 声明了包围流式模型调用的 `llm/stream` waterfall；实验专用 middleware 可以在调用 `next()` 前向外层与 Python 内层共享的持久账本申请预留，再捕获返回的 usage。本机 agent-loop 的重试循环重新调用 stream，但 middleware 顺序、直接调用、子 agent、provider 内部重试，以及与 Python 进程的原子竞争仍须用假 adapter 和故障注入验证；接口存在不等于覆盖已经闭合。Desktop 安装包中的 `dsh-llm 0.2.1-rc.2` JS 也能看到该 waterfall，但安装目录不证明 profile 正在使用这一副本；正式实验须核对实际进程和包版本。

DSH usage 的 `inputTokens` 是未命中缓存的输入，缓存读取和写入分别计数；Python core 的 provider `prompt_tokens` 是另一口径。汇总前须按实际 provider 语义归一化，缺失缓存字段保持未知，不简单把不同字段直接相加当作同一计费口径。会话中已结束消息的可选 usage 也不能证明失败、取消或中途断流的完整派发次数。

本机 `desktop` profile 的适配器配置是 `dsh-llm-pi-ai`，不能把另一 DeepSeek 适配器的处理直接当成它的证据。所检查的 Desktop 代码路径会把 usage 初始为零、对部分缺失字段使用零默认值，并在结束或错误事件中映射 usage；因此仅看到零值不能证明服务商确实返回零，需在原始响应层确认字段存在，否则记未知。该 profile 路径的 `maxRetries` 显式设为 0；agent-loop 的恢复重试和其他路径仍须在实际加载的宿主中验证，不能靠静态检查声称所有 HTTP 派发均被计数。会话压缩、标题等辅助模型调用可能没有 session ID；正式实验须明确禁用这些调用或把它们纳入共享账本，不能只凭 session ID 筛选后声称覆盖完整。

## 3. 任务草案：14 项，不将历史任务冒充未见样本

优先复用 [quality_suite.py](../../operator_agent/quality_suite.py) 的 10 个版本化任务及其明确语义：

| 原任务 | 算子 / 主形状 / 精度 | 特征 |
|---|---|---|
| `matmul-aligned-fp16` | MatMul 64×64×64 / fp16 | 整齐 |
| `matmul-tail-fp16` | MatMul 31×47×19 / fp16 | 尾部 |
| `matmul-strided-fp32` | MatMul 17×29×13 / fp32 | 非连续 |
| `layernorm-aligned` | LayerNorm 8×64 / fp32 | 整齐 |
| `layernorm-tail` | LayerNorm 7×33 / fp32 | 尾部 |
| `layernorm-large-mean` | LayerNorm 9×63 / fp32 | 大均值 |
| `layernorm-constant-strided` | LayerNorm 9×17 / fp32 | 非连续常数 |
| `softmax-tail` | Softmax 7×33 / fp32 | 尾部 |
| `softmax-extreme` | Softmax 5×63 / fp32 | 大幅值 |
| `softmax-constant-strided` | Softmax 9×17 / fp32 | 非连续常数 |

为提高大形状性能测量可能性，提议再加 4 个明确标为**待可行性和来源检查**的任务：fp16 MatMul `1024×1024×1024` 和 `1001×1003×997`，fp32 Softmax `4096×1024`（末轴），fp32 LayerNorm `4096×1024`（末轴、无 affine、eps=1e-5）。它们不是已测可用形状，也未证明足够抵抗启动地板；各组默认连续主输入，其他布局和数值边界由共同套件检查。不得将新形状本身称为对模型或开发者保密，也不能在查验来源之前称作独立未见任务。

10 个历史任务已用于开发和评估，按**已知样本层**报告；4 个候选新任务须检索历史 prompts、规则开发和报告，确认其精确语义及相近形状暴露情况，未能确立则标为 exposure unknown。通过固定逻辑和种子生成候选，无成功后改题；扩样到 12–20 项或替换不适用任务须在任何三组调用前重新冻结清单和理由。最终报告分别列已知/未确立暴露样本，不凭总平均值宣称泛化。

已生成 [14 项任务草案清单](../../output/plugin_completion/20261027-s5/task-manifest-draft.json)，可用 `python -m benchmarks.s5_task_manifest --output <新文件>` 重建；其内容哈希为 `8663285abafdd8fbbb3cfd9d0c6affa726c97cc0e1d27ab11555825eb0e12d26`。这只是评估输入草案，尚非正式试验封版。前 10 项与 `quality_suite.suite_manifest()` 的契约、主输入及两个 holdout 逐字段一致；四项新候选的 exposure 与性能可测性都维持 unknown。历史代码中曾出现 1024³ MatMul 和 4096×1024 LayerNorm 的相似形状，但精度或 affine 语义不同，不能由形状推断任务是否完全见过。此前量尺预检的 2048³、4096³ 结果不能转移为这些候选形状的资格。

现有 `quality_suite` 的主输入/holdout 含 pattern、layout 与种子；生产 `operator_run`/`prepare` 的声明不保证携带这些字段。故不能只复用任务名字或形状就声称复用了同一质量任务。正式执行前须让公共评估器按原定义重建并检查这 10 项主输入、两个 holdout 和完整可信 L2，冻结每组输入表示、dtype/strides、参考与容差哈希；三组均使用**同一个独立评估器**，开发过程中拿到的反馈和最终评估留存分开。公开任务声明对三组一致，保留的 holdout 是额外评测材料，并不声称从未被模型见过。

## 4. 预算草案与公平执行

以下是用于估算和实现预算门的**候选上限，不是已批准或已冻结的支出**；确认任务范围和实际账户前可调整，一旦正式采样开始不得按效果追加。模型拟沿用 S4 的 `deepseek-v4.1-flash-1017`，外层及内层实际 endpoint、模型标识、thinking、fallback、温度/输出上限均在正式计划记录，以真实生效值而不是配置意图为准。凭据不进入日志和证据包。

- 14 项 × 3 组 = **42 个任务运行**。每组每任务外层 + 内层合计最多 **6 次模型请求派发预留**、最多 **1800 秒工作进程墙钟**，失败、超时和取消不退款；绝不是每层各给 6 次。正式对照最多 **252 次模型请求预留**。
- 单次输出上限最多 40960 tokens 时，252 次的保守**请求输出上限总和**为 **10,321,920 tokens**；实际请求上限按账本逐次累加，输入 token、账单单价、服务商计费和 GPU 时间均不受此数硬限制。API 缺 usage 不计零，保留 unknown。不要把该上限称为预计消耗或金额预算。
- 每任务各组开发阶段的候选验证输入组上限拟 **12 单位**，含不可挪用的最终确认份额；内部 suite case、L3 配对样本和 kernel launch 不是该单位。额外的统一最终评估按每任务每组单独限定最多 1 次完整 L2、1 次首轮 L3、仅当首测有资格时 1 次独立确认，显式记作评估成本而非开发免费额度；没有额外机会根据最终评估反馈重新开发。
- 一次三组严格串行且每任务完整用尽 1800 秒，光开发任务上限可达 **21 小时**，不含冻结、预检、最终评估和清理；它不是预计时长，且无 GPU 秒或费用硬上限。需先确定总体 API 消费预算、独立评估墙钟上限与资源可用时间，否则仍不可执行。不得用估算充当服务商账单硬限额。
- 预备阶段只进行不调用真实模型/GPU 的检查及 mock 回放；真实小规模性能量尺预检另有自己的冻结计划和控制核预算，不计作三组结果。若未来要跑付费对照前的小样本，另冻任务和预算，显式决定能否复用于正式分母，不能因为结果好坏选择。

共同预检包括 CLI/MCP/DSH 安装与模型身份；所有臂调用链须可证明可控；冻结源码/依赖/任务/runner/评估器；外层与内层计费、禁止隐式 fallback、未知 usage；按身份验证 GPU 型号与 UUID、现有计算进程及空闲资源，**0% 利用率不证明独占**。资源、源码/任务/模型身份、调用账本或远端 owned 会话清理状态不能确立则停止；不停止或修改现有共享服务，除非另有明确指示。GPU 空闲只是一刻的快照，不是租约；结果报告资源竞争、未知和有效性，不补造独占。

## 5. 评估与统计

1. 统一可信评估器独立物化输入，对每组最终候选执行同一完整 L2，包括给定 primary、额外 holdout、边界、非连续布局、必要的一致性和参考身份检查；所有结果绑定候选源码、任务契约、suite 和环境。首个完整 L2 时刻与水位来自不可变事件；任务中途崩溃须保留已发生调用及部分证据。
2. 对完整 L2 通过的候选执行 L3，使用相同任务语义和可比基线、同卡同窗口的配对测量。固定 `min_speedup` 和有效性门；仅有效首测具资格时再以相同源码、契约、基线、独立窗口和原确认门复测。无合格读数、参考身份/输入保真未知、设备干扰或确认缺失均记性能未知；原始数值不能升级成达标。
3. 事先固定任务顺序与三臂交替顺序，建议每个任务按 A→B→C、B→C→A、C→A→B 循环；每臂使用独立输入副本和工作区，不并发占用同卡。相同初始资源条件不可确立时标注并停批，不只排除表现差的臂。失败、预算耗尽、取消、未执行、未知保留 42 的规划分母及原因；完整正确、性能确认达标、性能未知、失败、成本缺失分别列数，避免 `passed` 或退出码代替多级事实。
4. 主要成对比较 B−A、C−B 的最终完整正确率及首次完整正确耗时/调用/usage；正确且确认达标只对具资格测量展示，同时给全任务分母、未知和合格样本数。算出每个固定任务的三臂差异，报告共同成功/独有成功/共同失败/未知和结果边界；未执行不视作失败，费用未知不填零。可给成对差异与不确定性描述，但 14 项且其中历史已见任务偏多，只代表固定小样本，不把差值或名义显著性推成真实总体提升。
5. 自主 run 内已有模型账本与阶段事件可参考；它们不能代表 A 的外层成本。报表须从各臂保留的源码、实际路径证明、终态、分级事件、预算账本和 API usage 重算。`quality_evaluation.py --paired` 比的是共同初始候选下诊断增量，并非三组 S5 驱动，不能拿其历史成绩替代本实验。
