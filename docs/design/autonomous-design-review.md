## 一、问题详述

### P1-1 §14 验收门不覆盖正确性

**文档位置**：§14 "这是**标定『标定器』本身**的测试集。全绿才允许往上盖 Stage 3（搜索）与 Stage 4（LLM 提议）。"
**核对**：`tests/test_stage1_acceptance.py` 共 30 条用例，逐条属于：好核测量/心跳锚点/慢核判决/资格全 False/被污染降级/快照原子性/契约哈希/跨设备跨窗口拒绝/断窗失效。**没有一条喂一个数值错的候选并断言它被拒。**

这不是"正确性没测"—— 正确性测得相当好，且**不在这个文件里**：

- `tests/test_l2_tolerance.py::test_scaled_kernel_rejected` —— 把输出整体缩放 3% 的核被拒；
- `::test_one_bad_set_fails_whole_verification` —— 多输入套件里一组错则整体失败；
- `::test_nonfinite_always_fails` / `::test_matched_ratio_gate`；
- `operator_agent/tolerance.py` 是分精度的 abs+rel **AND** 容差表，且**任务只能收紧不能放宽**；
- `operator_agent/verifier.py:66,798` + `remote_scripts/run_kernel.py:620-640` 已经产出
  `first_bad_index` / `first_bad_actual` / `first_bad_expected`。

**所以问题是门禁的形状，不是覆盖的缺失。**§14 既是"造 Stage 3/4 的许可条件"，又是文档里唯一的验收清单；它系统性地只考尺子。后果具体：一个**完全不检查数值**的实现，只要通过那 30 条，就能按文档的规则合法盖起 Stage 3 与 Stage 4。

> **建议**（最小改动）：§14 加第 10 条 —— "喂一个数值错的候选（缩放 / 丢一个输入 / 尾块越界），断言它被 G2 拒且**理由指向**该处"。它不需要新模块，只是把已经在 `test_l2_tolerance.py` 里成立的事实接到文档自己的门禁上。
>
> 更进一步值得做的是把 §14 拆成**两节**：§14-A「尺子可信」（现有八条）与 §14-B「尺子量的是对的东西」（新增）。文档现在把两者合成一节，导致读者以为前者蕴含后者。

### P1-2 `require_double_confirm` 默认关，与脊柱自相矛盾

**已核**：`operator_agent/conductor.py:299` `require_double_confirm: bool = False`；`conductor.py:1966` 处才在打开时跑第二次 `verify_l3_only`；`conductor.py:2394` 把 `requires_remeasure` 接到该开关。`oracle.py:361-363` 与 `tests/test_spine_wiring.py:54`（`test_good_run_still_persists_without_double_confirm_flag`）都把"默认单次读数即可入库"钉成现状。
**文档要求**：§7「任何永久结论需**两次确认**」、§10.5-4「一次 `valid` 且 FAST **+** 一次独立重测仍然不劣」、§10.2 留 10% **不可挪用**预算给最终确认。

三处是**设计要求**，实现默认关掉它。现有理由（`conductor.py:362`、`budget.py:27-29`、`oracle.py:361-363`）是一致的：**"默认生效的机时承诺会改变每一次真机运行的行为，而『本轮要不要花这次钱』是任务级的决定"**。这个理由本身是成立的工程判断，我不认为它是疏忽。

**我的分歧在于算术**：§10.2 已经把那 10% 划走且**不可挪用**（`budget.py` 的"先切预留、四格之和恒等于总数"）。也就是说"多测这一次"的机时**已经被预先承诺、不占探索/精修那 90%**。"省机时"省下的是一笔设计上已经决定不花到别处的钱。而它的代价是：这套系统花了几百行（`confirm.py`、`oracle.admit_to_corpus` 的第 3 道门、预留预算、`report.py` 里的 `can_persist=False` 单列一行）来防"一次噪声读数变成永久真理"，然后在最常见的生产配置里把那扇门开着——**而 §16 点名的反模式「让一个噪声大的数永久拉黑配置」正是从这扇门进来的。**

补一条对当前论证有利的证据：`spine-review.md` P2-10 记录了这个开关早期"打开即入库率归零"的自锁状态，且已修（生产者 `_produce_remeasure` + 字段 `artifact.remeasure` + 消费者 `_save_to_db` 现在成对存在）。**也就是说"打开它"今天是一个可用状态，不是一个会打断链路的开关** —— 挡住翻转默认值的那个技术理由已经不存在了，剩下的只有机时。

> **建议**：翻转成 **opt-out**（默认开），关掉时必须留痕（报告里写明"本轮未要求两次确认"已在 `oracle.py:363` 存在，保留它）。若因机时坚持 opt-in，则至少把文档 §7 / §10.5-4 的措辞从"需"降级为"可选"，**不要让设计要求与默认行为长期互相矛盾** —— 那正是本条 P2-6（文档形态）会漏掉的那类腐烂。

### P1-3 交付物缺「该不该用这个 kernel」的裁决

**已核**：`grep -rn "use_library\|USE_LIBRARY\|recommend_library" operator_agent/` → **零命中**。
**文档位置**：§17 交付物四件，第 1 件是 best-known-good；§10.4 预算耗尽时"交付 best-known-good，**不装作成功**"。

诚实，但缺一个部署者真正要读的字段。若最终最好的正确 kernel 是 0.9×，交付它是一次回归；0.9× 与 1.8× 的产物在机器可读层面形状相同。§10.4 的"达标"条件只在 ≥ 目标时收工，预算耗尽于目标以下时没有对应结论。

> **建议**：在交付物里加一个显式裁决字段，并**让它本身受 `can_persist` 约束**：
>
> ```
> verdict: USE_CUSTOM | USE_LIBRARY | INCONCLUSIVE
> ```
>
> 理由不只是完整性：文档反复防范的失效模式是"噪声读数造成永久后果"。**"因为一次噪声读数就建议你别上自定义核"与"因为一次噪声读数就永久拉黑一个配方"是同一失效模式的两个方向** —— 而现在只有后一个方向有资格位闸门（§4.3 规则 6）。加裁决时必须把它接进同一套资格位，否则等于在下游开了个没有闸门的新口子。

### P2-4 形状分布是性能目标，不是正确性要求

§3 第 3 项把形状分布（**含边缘形状：非对齐尾块、batch=1、极大/极小 k**）列为**优化目标**（加权几何平均），这是对的。但同一批形状对正确性的意义没有被写成要求：它同时是**唯一能挡住"针对测试 shape 特化"的东西**。

已核：`grep -rn "no_op\|noop\|null_op\|sensitivity\|perturb" operator_agent/` → **零命中**。即没有扰动探针、没有空转探针、没有"换一个 shape 还对不对"的显式检查。（`test_l2_tolerance.py:141` 抓的是"整体缩放"，不是特化。）

需要说清这不是"零防线"：多形状套件（`test_one_bad_set_fails_whole_verification` 那类）与 `matched_ratio` 门实际上提供了部分防线。准确的批评是——**这个防线存在，但它是一条未被声明的副业**：文档把多形状挂在性能目标名下，正确性依赖它的效果没有成为契约的一部分。一个后来者删掉"多输入套件"时，没有一条设计条款会反对他。

> **建议**：§3 第 3 项拆成两条 —— 3a「性能用形状分布 + 权重」、3b「**正确性用形状集，必须包含每类边界各一，且候选须在全部形状上通过**」。同时在 `CONTRACT_LINT` 的检查清单里加一句"正确性形状集是否覆盖每类边界"（该清单现有条目：参考实现存在吗 / 容差能区分对错吗 / 形状分布覆盖边缘形状吗 / 数值语义钉死了吗 / 基线可复现吗 / 后端能力满足吗 —— **"覆盖边缘形状吗"这句现在只对性能负责**）。

### P2-5 代码型路径：既判不了收敛，也没有跨运行学习

**文档已诚实标注**（§10.4 `unknown`；§10.3 边界"证据不进快照"）。我建议把它从"边界"改记为**设计成本**，因为它的位置不对等：

- 按 §19.2，速度收益主要来自**优化循环**（优化反馈 1.509× vs 纠正循环 1.222×，且"两者不能互相替代"）—— 那正是**代码型**路径，不是模板型路径；
- 而代码型路径今天既**无法判"已穷尽"**（只能靠轮数与预算收口），又**每次运行从零信念开始**（`c` 未标定、bandit 证据不进快照、不跨运行）；
- 净效果：无人值守长跑时**分不清"收敛了"和"放弃了"**。这恰好是这份文档最想避免的那类不可区分（§17 第 3 条的整个"无法确立"章节就是为了消灭它）。

> **建议（便宜的缓解）**：代码型候选已经带着 `struct_sig`（α-等价结构签名，与去重同源），把它**也用于跨运行的覆盖度累积**。今天仍不能证明"穷尽"，但可以证明"这个结构族已试 12 个点、近 K 轮没有新结构出现" —— 一个真实且单调的信号，代价接近零，且让 `unknown` 至少能区分"从未见过新东西"与"一直在换结构"。

### P2-6 实现状态混进设计文档

**量化**：设计正文（§1–§18）约 800 行；"实现状态"引用块分布在 §10.2、§10.3、§10.4、§12、§13.5、§14，单块 30–50 行；顶部落地状态表第 21/27/30/32 行单格 500 字以上。

三个具体伤害，按严重性：

1. **设计变更无法 review。** 行为变更与状态更新共用一个文件 ⇒ `git diff` 这份文档不可读 ⇒ review 事实上已经转移到 `CHECKLOG`（文档里 I46–I75 那些编号在承担这件事）。**设计文档一旦开始承载实现考古，它就不再是一份稳定契约。**
2. **同一格里出现了自我更正。** 第 21 行单元格里写着"本条一次误判已撤回 —— 我当时是把两句历史注释当成了现状"，并附了一句"决定：保持 opt-in"。当更正需要写进历史状态而不是覆盖它，说明承载机制选错了地方 —— 这条证据正好落在 P1-2 上：一次关于"两次确认"的判断被推翻又写回，而读的人必须读完 500 字才能知道现在的口径是什么。
3. **信噪比。** 想读懂 §10.4 的停止条件（半页），必须先穿过 40 行关于 `phase_caps` 何时从"计划"变成"约束"的考古。

> **建议**：状态与设计分家，两步：
> 1. 设计文档只留设计 + 一列指向 `docs/design/status/` 的链接；
> 2. **让 ✅ 从验收测试派生，而不是从人写的段落派生** —— 单元格里写"`tests/test_stage1_acceptance.py::test_xxx` 存在且通过"，而不是一句段落。
>
> 第 2 步是关键：它让"落地状态"这个概念**不可能腐化**，勘误就不需要发生了（也就顺带修掉第 2 条伤害）。

### P2-7 `score` 的分母近似常数

§10.3：`score(c) = P(beats_best) × 预期增益 / 预期 GPU 秒`，文档明确说分母是**控制端测量墙钟**（`time.monotonic()` 包住 L3），与 §10.2 墙钟同一货币。

问题不是"用墙钟不对"，而是这个墙钟里含 SSH 往返、部署，以及**候选与基线共享的那条基线臂**。基线臂是常数 ⇒ 分母在候选之间近似常数 ⇒ `score` 退化为 `P(beats_best) × 预期增益`，**除法在做无事可做的事**。若候选之间真有成本差（编译缓存命中与否），这个墙钟又把"这个臂测起来贵"与"这次部署慢"混进了同一个数。

文档的 `mean_cost*`（本臂平均测量秒，没有则全局均值兜底）才是"该臂的边际成本"，却只当兜底。而**控制端墙钟的正面价值**（与 §10.2 同一货币、可离线复算、抽签可复算）被 §10.3 自己保留为优点的同时，恰好用在了唯一不成立的那个位置上。

> **建议**：`分母 = mean_cost*`，缺失时降级到全局均值并标注；把"控制端墙钟"从 `score` 分母里拿掉，**但保留在 ε 抽签与账本里**（那两处它确实是可复算的同一种货币）。或者：若坚持用墙钟，需要在文档里承认"这个除法当前近似无效，它是为将来候选成本真正可分时预留的接口"。

### P3-8 / P3-9 / P3-10 / P3-11

- **§18 #3 续跑语义**：§1.3 把"每个动作必须可恢复"列为硬约束，§10.6 伪代码 `checkpoint(belief, best)` 已经隐含选定"从信念状态续跑"（不是从 best）。这是承重项，不该留在待定表。**建议**：要么写进设计（checkpoint 三元组：belief + best + ledger，各轮幂等键是什么），要么说明它已由 §10.6 决定、待定的只是 checkpoint 粒度。
- **算法级层到不了**：§19.2 说速度收益主要来自优化循环，而"算法级（融合 / split-K / 算法替换）"是 §9.1 的第一层。可是到达它的门（§10.3 三条件）里，条件 2"可归因的硬限制证据"**今天只有 `smem-bound` 一条量具，且只在上界 ~×1.2 那条带里成立**（文档 §10.3 落地状态自陈）。**杠杆最大的一层，装备最少。** 建议单列为一条工作项（哪怕只是给 `spill` / `occupancy` / `bank conflict` 各补一条量具与阈值），而不是留在三条件里当一个隐含假设。
- **变异测试不可见**：落地状态表里"9/9 变异红""18/18 变异红""13/13 变异红"随处可见，§11 也承认 `cross_window_refused` "靠 fakes 用例与变异证明它是活的"。**这是这套代码实际的验证主力方法**，但设计文档没有一节讲它。考虑到这份文档两次被真机抓出"算了但没接上"（I46 资格位取错来源、I48 远端盾证据不落地），而那正是变异测试的典型目标，**方法论显式化的收益是直接的**：每条防御性规则配一条变异，证明它会响。建议加一节「规则的可活性证明」。
- **§16 只有反模式**：11 条全是"不要"。而 §4.3 的九条资格推导与 §10.5 的五件安全装置本身就是极好的**正模式**（"资格决定这个数被允许造成什么后果，而不只是过没过"这类句子是可执行的规则）。建议加一节「正模式」，从这两处提炼。
