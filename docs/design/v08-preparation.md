# v0.8 开发与收益验证准备

2026-11-07 · 准备方案

当前实现和验收进度见 [v0.8 进度入口](../status/v08/README.md)。

以已发布的 v0.7.2 为起点，先量化插件对算子开发流程的帮助，再用同一套评价方法验证 v0.8 新增优化能力。两轮实验分别回答插件工作流的价值和优化功能的增量价值。v0.8 的目标是在既定预算内，用可复核的测量定位瓶颈、选择候选，并交付经过独立终评的源码。 [产品演进路线](operator-development-product-roadmap.md#5-可用版本迭代路线)

## 1. v0.7.2 已有证据

| 证据 | 可支持的结论 | 来源 |

## 2. 两轮实验各比较什么

| 轮次 | 两侧入口 | 主要问题 | 首要指标 |
|---|---|---|---|
| v0.7.2 工作流对照 | A 使用普通 DSH 和常用编辑、执行、验证脚本。B 使用同一 DSH 与已发布的 v0.7.2 插件工作流 | 相同开发预算下，插件能否让更多任务交付可验证的正确源码？ | 独立终评完整 L2 通过数及配对差值 |
| v0.8 增量对照 | B 使用固定的 v0.7.2。C 使用启用待验能力的 v0.8 | 相同预算下，瓶颈诊断与候选比较能否带来更好的最终性能？ | 通过独立 L2 且满足预登记性能目标的任务数，以及可比候选的性能差值 |

B 的计划工件为 PyPI `dsh-operator-agent==0.7.2`、npm `dsh-operator-agent@0.2.5`、工具契约 `12`，采用 `host` 模式。冻结时记录下载工件 SHA256、安装回执、宿主与工具版本及实际模型入口。历史封版插件 `0.2.2`、候选包和公开 npm 包的验收记录分别按工件身份关联。 [发布记录](../status/v072-release-20261106.md) · [支持清单](../testing/v072-support.md)

两侧均由 Agent 开发、运行和记录。A 能按常规方式生成代码、调试并执行共同的验证脚本，B 通过插件获得领域材料、执行和预算约束。两侧交付的最终源码都由同一版本的独立评测器验收。旧一期脚手架可复用预登记、隔离、实例绑定及汇总能力。B 侧须接到当前发布包的 DSH 外层路径，并核对实际工具调用。 [一期实验脚手架](../testing/phase1-study.md)

## 3. v0.7.2 收益基线怎么测

1. **预登记任务和预算。** 首轮采用四任务八格。可从历史 Matmul、Softmax、较大 ReLU 和较小 ReLU 的任务骨架取材，覆盖归约、布局和长短任务。冻结每格的声明、输入分布、参考实现、起始代码、正确性套件、停止条件、各项预算以及独立终评预留。另留未参与规则开发的任务给 v0.8 正式评估。
2. **核对实际模型调用。** 两侧使用同一 provider、模型和有效采样参数，统一统计从用户任务起点起的主模型派发。插件账本覆盖绑定后的调用，因此共同采集还需记录绑定前准备、失败重试及结算，辅助请求单列。采样参数或 usage 缺失时保留对应未知项。输出预留、实际 token 和账单金额分列。
3. **先跑一对再启动八格。** 先用隔离 DSH 和本地 provider 验证记录链，再用一对真实任务核对入口、调用计量、候选哈希和独立终评。测性能前校准主机负载和本卡噪声。同一 GPU 串行配对，交替两侧执行顺序，并记录环境漂移和停机原因。
4. **统一终评和统计。** 每格在冻结预算内提交终稿，独立终评绑定同一契约及源码哈希。完整 L2 作为工作流比较的主要结果。性能另列有效性和对应输入、设备及基线，只有成对有效的 L3 读数才计算相对倍率。保留所有已派发任务的成功、失败、未知，以及计划内未执行格位。

| 指标 | 记录和解释 |
|---|---|
| 独立终评通过率 | 以全部已派发任务为分母，列各侧通过、失败及未知，并逐任务给出配对差值 |
| 首次完整 L2、终评总耗时 | 起点为提交任务，记录到首次完整 L2 及终评完成的时间。未达标任务保留停点，耗时与通过率并报 |
| 模型与执行资源 | 记录实际请求、有效 token、验证派发次数、墙钟和可观测 GPU 时间。费用依实际 usage 和账单核对 |
| 用户介入 | 从事件记录提取纠正、接管及其观测覆盖。人工活跃分钟单列，缺失为 `unknown` |
| 最终核性能 | 分别报告相对任务参考实现的读数和两臂终稿间的有效配对差值，附测量有效性与噪声带 |

四任务八格用于找方向。首轮结束后复跑预先选定的关键配对和留出的任务，报告效应是否复现。若两侧均通过完整 L2，耗时和用量可提供补充信号。若收益仍不清楚，优先处理实际缺失的对账或测量条件。 [收益评价口径](operator-development-product-roadmap.md#6-如何证明用户收益)

## 4. v0.8 开发顺序

| 优先级 | 交付 | 完成条件 |
|---|---|---|
| P0 可信测量 | 记录同卡基线、运行条件、候选/契约身份、性能读数与有效性 | 同一候选可复测，噪声或不可判状态有明确回执，后续决策能引用对应证据 |
| P1 单类瓶颈诊断 | 从基线暴露的常见问题中选择一类，输出观测依据、诊断假设与建议实验 | 在保留的任务上可核对诊断及后续实验结果。证据不足时返回明确状态 |
| P1 有限候选比较 | 在原任务预算内提交少量候选，比较已通过 L2 的候选和有效性能结果 | 候选、调用、验证消耗、停止原因及选中依据可追溯，终稿独立终评 |
| P2 搜索扩展 | 对经配对重复显示收益的方向，增加有预算上限的实验策略 | 新增调用及验证成本纳入对照，收益在留出任务上复现 |

新增功能沿用 v0.7.2 的分工。插件提供可核对的领域事实、测量和判定，DSH 结合用户目标选择候选并决定下一轮。验收保留生成、修复、恢复、取消、预算硬门及同源码独立终评。把需要比较的优化能力做成可独立启用的入口，便于复验与回退。 [v0.7.2 外层工作流](dsh-host-context-workflow.md)

## 5. 开工材料和验收出口

- [ ] **冻结 v0.7.2 参考包。** 交付工件身份清单、A/B 两套入口、共同计量口径和预登记任务表。
- [ ] **完成基线试跑。** 交付一对预跑回执、四任务八格结果及关键配对复测，按实际证据选 v0.8 的第一个诊断场景。
- [ ] **确定首个增量目标。** 在查看 B/C 结果前，登记任务级性能目标、可接受的最小改进、噪声带、重复次数、预算和停止规则。性能差值需要超过测量噪声，且最终候选满足完整 L2。
- [ ] **验证 v0.8 增量。** 用留出任务完成 v0.7.2 对 v0.8 的同预算配对与必要复测，交付诊断、实验、候选选择和独立终评证据。可复现收益进入发布说明。未达目标的方向按记录收缩范围或继续研究。

每轮在仓外保留计划、运行身份、逐格账本、日志、候选源码、独立终评和汇总。仓库文档记录版本、可复核引用和结论边界。v0.8 首项准备以 **v0.7.2 参考包身份和 A/B 预登记** 为交付物。
