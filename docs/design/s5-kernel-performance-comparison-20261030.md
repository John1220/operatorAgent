# DSH 算子性能优化 A/C 对照计划（2026-10-30）

状态：**已完成一个 GPU7 LayerNorm A/C 定向配对；原定 8 格实验仍未完成，现有证据不能证明插件整体优于原生 DSH。** 首轮及后续配对结果、偏差见[实测记录](../status/dsh-operator-s5-kernel-performance-results-20261030.md)及[预检记录](../status/dsh-operator-s5-kernel-performance-preflight-20261030.md)。本计划是新增的性能优化实验，不补齐已经结项的旧 S5 正确性对照分母。历史 valid 读数不能作为本次放行凭证。

## 1. 问题与比较对象

在同样的模型、初始实现、模型调用预算和墙钟上限下，比较原生 DSH 与 DSH＋发布插件最终交付的 kernel 正确性、GPU 延迟及开发成本。插件通过 `operator_bench` / `operator_verify` 提供的监督 GPU 反馈属于被测处理的一部分，因此两臂的实际 GPU 调用成本可能不同，须分别报告，不能声称 GPU 调用数完全匹配。目标是检查**安装插件后这套 DSH 工作流能否帮助性能优化**，不将相对 PyTorch 的 kernel 加速直接解释成插件优于原生 DSH，也不拆分 core、测量反馈与 MCP 接入各自的贡献。

| 组 | 开发可用能力 |
|---|---|
| A：原生 DSH | 普通 DSH 文件/bash 工具及两臂共有的公共 L2 测试文件；无插件、产品 CLI、core 导入或实现源码访问。若会话环境本身不提供远端 GPU 访问，不为 A 临时注入产品私有通道 |
| C：DSH＋插件 | 与 A 相同的 DSH 环境，额外发现发布插件的 `operator_verify` / `operator_bench`；插件后台可用 core，但参与者不直接阅读或执行 core |

两组相同任务提示、输入语义、起始源码与起点预检信息，不额外强制 C 调用插件。C 未使用插件仍是本实验的有效使用结果。A 不获得产品私有 SSH/验证入口；若 A 在正常 DSH 环境下不能连接 GPU，这应作为产品能力差异保留，并在结论中限定为本次“原生 DSH 环境 vs 安装插件”对照，而非声称模型在完全匹配 GPU 反馈条件下的纯界面因果效应。外层模型承担优化；内层 `operator_run` / `operator_repair` 及其他辅助模型调用不在本实验范围，执行入口须在派发前拒绝，不能事后把未记账的内层成本忽略掉。

## 2. 任务与共同起点

| 任务 | 主 workload | 起点来源 |

| LayerNorm | `16384×6144`，fp32，末轴、无 affine、`eps=1e-5` | [历史插件入口最终候选](../../output/plugin_completion/20261029-s5-plugin-entry-acceptance-v1/execution/runs/layernorm-tail/C/candidate.txt)，SHA256 `df189e4c0ab4bef63000147d5ad2f5844b805ea1797c099df21dd2edce69e0fd` |
| Matmul | `M=N=K=4096`，fp16 | [S4 matmul-aligned 最终候选](../../output/plugin_completion/20261027-s4/gpu6-8004/tasks/matmul-aligned/candidate/code.py)，SHA256 `1cc3de9144390a883b4e64e8df1dc54a7ed4e708fef231fd66511dd3329b89d2` |

起点是有明确来源的正常 Triton 实现，不改成故意慢核，也不提供 GPU7 冻结验收中的最快手写候选。LayerNorm 源码原先对应 `7×33`、Matmul 源码原先对应 `64³`；源码可按输入尺寸运行，但原任务通过不证明目标大形状正确或性能合格。本轮按表中目标形状重新构建契约并做完整 L2 与计时预检。先静态保存实现特点与来源，不根据预检快慢换候选，优化余量不足也是允许结果。若起点不正确或计时不合格，本任务停止，不悄悄换 seed、shape、套件或容差。

每任务 A/C 各两次重复，共 **8 格、4 个配对**。两次重复是同一任务的重复观测，不等于新增两个独立任务；结论只覆盖两类有限 workload，不能外推整体算子开发能力。

## 3. 冻结与执行前置

1. 保存本次完整只读实现快照：监督驱动、产品代码、`remote_scripts/`、插件、prompts/skills、构建元数据与依赖版本；模型会话和验证都从该版本运行。按全部文件清单核对前后身份，避免工作区并行编辑影响测试。
2. 初始计划将 `algorithm-h20` GPU2（UUID `GPU-13c6c4b4-45ce-8963-1122-df2b3d72fb76`，H20）冻结为共享卡，并固定 runner 环境与部署文件哈希。用户随后确认 GPU7 也可用于并行；因此 GPU2 LayerNorm 与 GPU7 Matmul 各自使用独立冻结计划。GPU7 UUID 为 `GPU-52ca6155-d8bc-a416-847a-6f0c71db1552`（H20），其派发前无 compute-app 进程；GPU2 保留允许驻留 PID `162589, 822889, 1641644, 1677855, 3885613, 3890552, 3916094`。两张卡均按共享卡记录，不声称独占。
3. 每次验证前后都用 `s5_shared_gpu.snapshot` 核对 GPU 身份、至少 8192 MiB 空闲、利用率不高于 5%，且计算进程只能是冻结的 PID 子集；进程集合若前后变化则该次记 unknown。性能读数仍须由生产量尺给出 `valid`、`measurement_can_gate=true`、`benchmark_contaminated=false` 与可比基线。已知驻留进程数大于零本身只作为共享状态记录，不单独拒绝读数；如果测量门判定受污染或无资格，结果不得作性能结论。空闲快照不等于租约，窗口内外干扰和环境漂移都保留。
4. 对两个共同起点各最多 **两次完整 L2→L3**，新增模型调用 0。核对候选、契约、完整 correctness suite、输入保真、回执、计时与性能资格；两次均合格才建立可用于相对优化目标的起点读数。起点数值失败、设施 unknown 或计时不合格即停止模型派发，不自动重跑。
5. 无模型探针已验证 A 公共 L2 客户端、C 真实 `operator_verify` MCP 与 `operator_bench` 工具发现；没有执行 benchmark 工具或派发 GPU。现有 A 探针没有 SSH 凭据，故不能把“ A 自行 SSH 测时”写成已验证能力。模型格冻结时要明确 A 仅可使用的 DSH 普通工具，以及 C 的 MCP 端点、单格配置计数和证据方式，再冻结最终任务/顺序/说明/端点/模型/资源/预算与停止规则。预检、无模型接线与正式八格分别记账，不混为模型优化成果。

既有 [GPU7 性能材料](../status/dsh-operator-gpu-freeze-20261030.md)仅支持任务与量尺选择，不能替代本轮预检。旧 [S5 结项](../status/dsh-operator-s5-closeout-20261030.md)及 [安装工件验收](../status/dsh-operator-s5-installed-gpu-acceptance-20261030.md)分母保持不变。

## 4. 每格预算与候选计数

| 项 | 固定限制 |
|---|---|
| 模型 | `deepseek-v4.1-flash-1017`，Responses，reasoning `medium` |
| 单次输出 | 最多 32768 token |
| 模型派发 | 最多 24 次；总输出预留 786432；失败不退款，不自动重试 |
| 开发会话 | 最多 2400 秒，包含模型等待、普通命令与开发验证；独立终评另记耗时 |
| 单模型请求 | 网关硬截止 900 秒，适配器 idle 930 秒 |
| 候选/配置 | 每格最多 3 个不同源码或显式配置；重复计时样本不当成新候选。C 的 `operator_bench` 每个候选臂各计 1 份；A 任何本地/远端实际尝试也逐项计数。A 若无可用 GPU 入口，实际 GPU 探索数就记 0，不为凑平衡伪造对照 |
| 独立终评 | 每格预留最多两次完整 L2→L3，均由监督器执行且不回传模型 |
| 单次生产验证 | 最多 600 秒监督限时，清理与远端状态另外记录 |

`operator_bench` 一次调用含三臂就消耗三份配置额度；A 的一个 shell 命令若执行多个配置，也逐个计。源码/显式配置、工具调用、实际 GPU 派发和回包要能对上；编译或数值失败、超时仍消耗已派发额度。起点若在开发中重新提交也占候选额度。`triton.autotune`、脚本循环等实际执行的配置不能藏在一次工具调用内。因插件提供的 GPU 探索机会不对称是处理本身，逐臂报告调用和费用，不以等 GPU 调用数作无效的强制配平。

本轮保留用户已允许的合作环境假设，不新建完整恶意代码/网络隔离。A 仅使用 DSH 会话原本提供的 shell/SSH 能力，不额外注入远端凭据或产品私有执行路径；若原环境可运行自有 GPU 命令，配置逐个计入并留痕，若不可用则按 0 次 GPU 探索记录。工具调用数不能证明自由 shell 下 GPU 额度绝对不可绕过；候选/配置计数若无法从留存记录核实，标为协议 unknown/无效，不能写成硬预算已经被证明。发现超限即结束该格，保留实际成本，不删除多余配置后补算为三份。两组均不获得监督器终评入口或其额度。

“原生 DSH 不获得 core”描述本实验提供与允许的工具面，不等于自由 SSH 下已经建立远端文件的强制隔离。不得主动向 A 提供生产验证脚本；观察到读取其他组候选或产品实现、使用产品 CLI 等范围外能力时保留污染证据，停止并记协议 unknown，不把受污染格纳入可归因的 A/C 性能结论。

全批最多 **192 次模型派发预留、6291456 输出 token 预留**；最多 **24 次开发配置评测＋16 次独立终评＋4 次起点预检＝44 次生产验证**。这些是上限，不是 GPU launch 数、GPU 秒数、预计耗时或服务商金额。完整 L2/大输入传输可能占据主要时间；不得按模型回答速度承诺整批短时间完成。真实 API usage 缺失与账单金额未知继续明确保存。

## 5. 顺序与共同终评

预先固定模型会话顺序：repeat-1 为 LayerNorm A→C、Matmul C→A；repeat-2 反转为 LayerNorm C→A、Matmul A→C。每格独立 HOME/workspace/账本，从相同起点开始，不携带前格源码或会话记忆。

模型最终答复按两组相同规则提取源码，保留原答复；监督器不事后挑选历史最快版本替代终稿。性能优劣由独立终评判断，不采信模型自行宣称、开发脚本或插件 `bench` 的探索读数作为最终成绩。

每个配对在两组终稿均确定后，以同一设备和测量配方执行 **A1→C1→C2→A2**（下一配对反向），避免先连续测两次 A 再测 C。每个终稿先完整 L2，之后才进入既有 L3；不改参考、容差、缓存/冲刷方式、warmup、采样或有效性门。两次确认必须是分别保留证据的独立调用，不能把一次窗口内的多次采样或先前开发测量当第二次确认。

实际 samples、median、离散度、基线及候选延迟、执行环境、窗口与有效性记录均保留。最终读数若与起点的设备、环境、基线语义或量尺不再可比，相对起点收益记 unknown；独立确认不一致也不挑选较快那次。正确性失败不做性能成绩，性能不达目标与设施/计时 unknown 分开统计。

## 6. 主要终点与报告

主要终点是每组固定四格中**完整正确且确认达到性能目标**的格数。性能目标预先固定为相对共同起点至少 **1.05×**，两次独立终评均须满足完整正确、有效计时和目标；5% 是本轮工作负载的交付目标，不是统计显著性阈值，也不替代现有测量资格门。

同时逐格报告：完整 L2、性能合格/未达目标/未知、最终延迟与两次确认差异、相对共同起点及记录基线的加速比、模型调用/usage/墙钟、探索配置数和真实插件使用。首次达到目标的开发步骤只能在真实有合格证据时报告；调用水位缺失不能反推精确调用成本。

双方都正确且性能合格的配对报告 `A 最终延迟 ÷ C 最终延迟`；取两次独立确认的预先固定汇总（中位数），同时保留两个原始读数。该配对表不替代四格固定分母：A 或 C 失败、性能无效、预算未完成、协议无效与设施 unknown 都保留。成本只在可比成功配对中作补充，同时报告所有已派发的实际支出。

不得把跨基线的 PyTorch 加速比直接当 A/C 的效果；不得将未用插件的 C 格剔除或强制重跑。两任务小样本只作有限描述，不宣称整体显著提升，不报告不受数据支持的泛化结论。允许结果为 C 更快、持平、更慢或证据不足。

## 8. 首轮执行状态

用户确认 GPU7 可用后，LayerNorm 配对在 GPU2、Matmul 配对在 GPU7 并行运行；每个 workload 的 A/C 仍固定在同一设备。GPU2 计划 hash 为 `8618f1b71ab26813b94dd591962ed8fe4faedd55cc9ed23a0d691f76c1c662d5`，GPU7 计划 hash 为 `df9f116fd471f3fea10b91e1f406afc8c035835d88586fe9b034fdc0b7a0cc20`，计划文件分别保存在 `trial-v2-gpu2/plan.json` 和 `trial-v2-gpu7/plan.json`。首轮只执行 repeat-1。GPU2 LayerNorm A 在旧 runner 版本下完成 18 次模型调用预留和完整 L2，但 runner 在写记录时崩溃；保留的候选与 L2 证据被单独恢复做了一次有效 L3。随后修复 runner 并冻结新计划运行 LayerNorm C，因此该 A/C 配对的计划哈希不同，不能作为严格同版复现实验。

LayerNorm A/C 均通过 L2，独立 L3 分别为 0.229248 ms 与 0.226208 ms，直接比值 `A/C=1.0134×`，低于预设的 1.05× 交付目标。Matmul C 通过 L2，但其独立 L3 为 PyTorch 基线的 0.9867×；Matmul A 用完 24 次调用预留额度后没有终稿，结果 unknown。Matmul C 的两次 `operator_verify` 尝试都被 relay 拒绝，实际成功验证数为 0。按未知结果停止后续派发的预注册规则，repeat-2 未执行。完整数字、来源及限制见[首轮实测记录](../status/dsh-operator-s5-kernel-performance-results-20261030.md)。

## 9. LayerNorm 定向配对

首轮后追加一个独立的 C→A 定向配对，固定在 GPU7、同一冻结源码快照、同一 LayerNorm repeat-1 契约。首个路由尝试因模型使用 `/work/task` 绝对路径而被宿主 relay 拒绝，18 次模型调用预留后记为 unknown，没有继续到 A。随后把接口说明改为相对任务路径 `task`，隐藏已不需要的 `operator_prepare`，并在 runner 中要求 C 同时留下真实 `operator_bench` 与 `operator_verify` 成功证据；新计划 hash 为 `98e1f4b5c52835e417201ef7286e465c3fca88f7835183ab6e60801f60548c15`。

修正后的 C 使用 3 次 `operator_bench`、1 次 `operator_verify`，最终完整 L2 通过。C 选择的终稿与共同 seed 完全相同；工具使用真实发生，但插件没有让模型交付一个不同的最终候选。A 与 C 也都通过完整 L2。两组各有一次独立 L3，有效性与 gating 均通过：C 为 0.227744 ms，A 为 0.228288 ms，`A/C=1.0024×`（C 快约 0.24%），低于 1.05× 的 A/C 目标。两次读数均来自同一 GPU7，分别 193 与 192 个配对样本，测量时无其他 compute-app 进程。该单次配对是有限补充观察，不是原定 8 格的替代，也不足以证明可重复的性能提升。

修正配对消耗 C 20 次、A 19 次模型调用预留；usage 均未从 provider 返回。加上首个错误路由尝试，本轮 follow-up 总预留 57 次，账单金额仍未知。首轮后续配对的完整证据见[实测记录](../status/dsh-operator-s5-kernel-performance-results-20261030.md#layernorm-定向配对)。
