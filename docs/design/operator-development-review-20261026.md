# 算子开发方案评审（2026-10-26）

本文记录对当前算子开发方案的评审意见。它不是新的设计规范，也不表示下列建议已经获准实施；现有契约、验证标准和已决边界继续生效。

评审基于 `design/autonomous-spine` 分支的当前工作区，包含未提交和未跟踪改动。评审时 HEAD 为 `2f2d281dc0ee7e828eeaec43dcc0b1c09e2ef736`；该提交号不能单独复现被评审的完整工作区。代码引用以文件及符号为主，行号可能随后续修改漂移。

## 1. 总体判断

**总体架构值得保留，可信评测的设计比较扎实；但“从零稳定开发出更快算子”的能力，证据仍明显弱于评测与审计能力。下一阶段应优先对齐生产入口，并验证端到端收益。**

系统已把契约冻结、正确性验证、测量资格、独立确认与长期记忆准入组织成较完整的链路。这些机制为自动开发提供了可靠基础。但机制存在、局部测试通过和最终交付收益是不同层面的证据，不能互相替代。

本次重点查看了主设计规范、内外层分工、近期生成与修复实验，以及 Conductor、生成器、验证器和插件入口代码。本文是有针对性的设计评审，不是全仓实现审计，也没有重新运行 GPU 实验。

## 2. 应保留的设计

### 2.1 提议权与裁决权分离

LLM 可以生成、修复和提出优化，但不能更改参考实现、容差、基线与目标。这样更换模型或生成策略时，判据仍然稳定，性能结论也不会依赖模型的解释。

依据：[设计规范 §1–§5](autonomous-operator-agent-design.md)。

### 2.2 正确性、性能与部署建议分离

“算得对”“测得快”“值得替换库实现”是三个不同结论。冻结 workload、逐 case 资格、回退上限和独立确认，能够防止主 case 的好成绩掩盖其他必判 case 的回退，也能避免把产物落盘或入库直接当成部署许可。

依据：[Workload 级性能决策与确认](workload-level-performance-decision.md)。

### 2.3 证据与允许的后果绑定

`can_verdict`、`can_tune`、`can_persist`、`can_report`、`can_count_progress` 分别约束证据的用途。一次受干扰的测量可以保留诊断价值，但不能自动成为长期知识或搜索收敛依据。这比单个 `passed` 更适合无人值守搜索。

依据：[设计规范 §4.3](autonomous-operator-agent-design.md#43-资格推导策略本层即产品)。

## 3. 主要问题与建议

以下优先级是本次评审对后续工作的排序，不是全部已确认的实现缺陷。各项分别列明事实与判断。

### R1 / P1：插件入口能力与最新分工文档不一致

**已核事实：**

- [内外层分工文档 §4.3](hitl-generation-boundary.md)将 `operator_run` 描述为 `Conductor → CoderPipeline`，包含规划、三温度采样与 smem 剪枝编译门。
- [autonomous.py](../../operator_agent/autonomous.py) 的 `main()` 构造 `Conductor` 时显式设置 `use_coder_pipeline=False`。
- [conductor.py](../../operator_agent/conductor.py) 的构造函数只在该开关开启且存在 LLM 时创建 `CoderPipeline`。

因此，不能把完整 CoderPipeline 的能力直接归到当前插件的 `operator_run` 入口上。这里并不意味着插件没有生成、修复或搜索能力；不一致集中在所声明的生成流水线。

代码注释表明，关闭 pipeline 是避免入口接线顺带改变候选选择口径的有意选择。本次评审不建议直接翻转开关。

**建议：**先对齐文档与实际入口，列清每个入口使用的生成器、知识注入、候选数、验证路径和预算；再通过入口级测试固定这些事实。是否切换 pipeline 应作为独立策略变更评估。

**验收方向：**测试直接检查入口实际构造的策略，而不是只证明 CoderPipeline 模块自身可运行；报告能够辨认本次实际使用的生成路径。

### R2 / P1：生产入口尚未统一任务总预算

**已核事实：**

- `autonomous.main()` 创建 `LLMClient` 时设置单次输出 token 上限和超时，但没有传入 `LLMCallBudget`。
- 同一入口创建 `Conductor` 时没有传入 `BudgetPlan`。
- [budget.py](../../operator_agent/budget.py) 中 `BudgetPlan` 的 `oracle_total`、`wall_clock_s`、`llm_tokens` 默认均为 `None`；[Conductor](../../operator_agent/conductor.py) 未收到预算时使用默认计划。

现有优化轮数限制、单次模型超时和后端超时确实提供了约束，但不等同于整个任务的墙钟、模型消耗或测量次数上限。不能将实验驱动中的有界性直接视为插件入口已有的能力。

**建议：**无人值守入口应要求显式预算，或提供有限默认值；生成、修复、搜索与最终确认使用统一账本。配置层的预算接线与硬超时执行是两个验收项：仅在新一轮开始前检查时间，不足以证明运行中的动作会在总截止时间内结束。

**验收方向：**明确每项预算的计量单位、预留与超限行为；缺失预算的入口行为可测试；失败调用和重试不能漏记。对暂时不能提供的 GPU 时间或账单金额硬上限，应保留明确边界。

**实现进展（2026-10-26）：**MCP/CLI 无人值守入口已接入有限默认任务预算：1800 秒本机执行时限、24 次模型调用预留、20 单位按输入组计的验证派发预留；失败不退款，最终确认份额不可挪用。独立监督进程处理在途本机工作，模型请求共享截止点，状态与产物保存实际预留、剩余及停止原因。校准只记账例外、远端取消未知及非账单/GPU秒数上限均明确保留。详见[生产入口任务预算](production-task-budget.md)。

### R3 / P2：需要重新校准生成质量在目标中的位置

**事实与背景：**主设计强调“写出来是容易的部分”“样本效率 > 生成质量”。这些判断适用于已有正确候选、进入性能优化的阶段；对于从零开发，获得首个正确候选本身可能就是主要瓶颈。

[十任务三候选实验](../research/operator-quality-portfolio-20261024.md)记录：

| 指标 | 首槽基线 | 三候选组合 |
|---|---:|---:|
| 完整 L2 通过任务 | 8/10 | 9/10 |
| 模型调用 | 10 | 30 |
| API 返回 tokens | 27,267 | 83,506 |

首槽费用已经包含在组合费用内。新增成功来自替代一个预检被拒的首候选；已确认的失败没有被救回。该实验没有运行 L3，且不是当前生产 CoderPipeline 的完整对照，不能用它直接证明该流水线的性能或成本收益。

**评审判断：**上述结果支持多候选有覆盖收益的可能，但不足以支持默认三候选更划算，也不足以证明生成质量已经不是瓶颈。

**建议：**将开发目标显式分成两个阶段：

1. 获得首个完整正确候选：关注成功率、首次成功时间与成本。
2. 在正确候选上优化：关注固定预算内的 workload 性能、回退约束和最终独立确认。

两个阶段应使用不同的采样、修复和停止策略。评价完整系统时，应同时保留失败与未知任务，避免只统计成功候选的加速比。

### R4 / P2：内外层分工应建立在可复用能力与实测上

**评审判断：**外层负责需求澄清、资源取舍与结果判读，内层负责有状态的生成、修复和搜索，这种分工合理。但“知识只注入内层，所以写核必须归内层”不是充分理由，因为知识上下文本身可以共享。

更有说服力的分工依据是：统一生成器是否提供更好的预算控制、候选质量、状态管理与复现能力。`candidate_origin` 有助于观察来源，但当前是声明式归因；它不能单独证明候选实际经过了某个生成器或技能注入。

当前工具面还有一个已被文档识别的缺口：`repair` 要求已有源码，`run` 启动整段流程，而“只生成一个候选并交回控制权”没有对应工具。依据：[内外层分工文档 §4–§5](hitl-generation-boundary.md)。

**建议：**把生成上下文和候选产出整理为可复用服务，使单步工具与整段控制器可以共用。保留不同采样策略，但显式记录其差异，避免不同入口悄悄获得不同能力。

**实现进展（2026-10-26）：**生产生成路径已接入共享 `build_generation_context()` 和统一候选记录：普通 Coder、可选 Pipeline、Fixer 与有界单候选生成器共用事实构建和记录协议，各自采样、修复及停止策略保留。Conductor / repair_loop 收集成功、拒绝、无候选与失败记录；产物绑定最终源码哈希，MCP 修复回包提供摘要和完整证据路径。人工/外层候选不补造内层血缘。详见[共享生成上下文与候选记录](shared-generation-context.md)。该实现尚不构成内层质量更好的实测证据，实验生成臂与 Q1 暂停状态保持原样。

这与“是否现在开放 `operator_generate_candidate`”是两个决定。本文不推翻既有暂停 Q1 对照实验的决定，不将未来实验或新工具列为已授权实施项，也不主张禁止外层或人工提供候选。

### R5 / P2：诊断复杂度的增长需要增量收益证据

[重复故障诊断实验](../research/operator-quality-diagnosed-repair-20261024.md)中，基线与诊断两组均修好 2/2 个案例，诊断覆盖 2/2，额外修复收益为 0。该结果证明诊断能绑定真实证据并进入模型请求，尚未证明它提高总体修复成功率；也不能据此断言诊断无效。

**建议：**下一批样本优先覆盖首次修复仍失败、误修和多个缺陷并存的情形，并使用未参与规则开发的独立任务。在相同预算下衡量额外修复率、误修率和成本，依据这些结果决定继续扩大诊断规则的范围。

验证规则必须正确和某条诊断是否值得开发，是不同问题。前者继续由正反例守卫，后者需要真实对照。

## 4. 建议推进顺序

| 顺序 | 工作 | 要回答的问题 |
|---|---|---|
| 1 | 对齐入口、文档与任务预算 | 用户启动的究竟是哪条流程，成本边界是什么？ |
| 2 | 统一生成上下文与候选接口 | 不同入口能否共享能力，同时明确保留策略差异？ |
| 3 | 经单独确认后开展同预算端到端评测 | 这些机制是否让可交付算子更多、更快或更便宜？ |
| 4 | 根据增量收益扩展诊断与搜索 | 新复杂度是否解决了当前流程仍无法解决的问题？ |

端到端评测应至少记录：首次完整 L2 成功率与成功成本、预算结束时完整正确候选覆盖率、最终独立确认的 workload 加速比、回退越限情况，以及全部尝试的模型调用、tokens 和墙钟。未知成本保持未知，不能将墙钟直接当成 GPU 时间。

对照应固定模型、任务、验证标准与预算，明确唯一变化因素；加入未参与提示词或诊断规则开发的任务。有限任务集上的结果只说明对应范围，不能直接外推到任意算子或架构。
