# 算子开发 AI Agent 问题识别与技术方案

> 版本: v1.0 | 日期: 2026-07-26
> 范围: `operator_agent/` 后端全链路（意图解析 → 编排 → 生成 → 验证 → 执行 → 知识库）
> 前置文档: `CUDA-Agent-特性分析.md`（对标系统分析）

本文档汇总需求分析阶段识别出的全部问题，按 **P0（致命）/ P1（严重）/ P2（一般）** 分级，每项包含问题描述、影响范围与建议方案。

---

## 一、P0 级问题（正确性可信，M1 里程碑）

### P0-1 L1/L2 验证失败即终止，无修复闭环

- **问题描述**: `conductor.py` 优化循环中，L1（编译）或 L2（功能）验证失败时直接 `break`，既不携带错误信息重试，也不区分"语法/编译错"与"数值错"。LLM 一次生成算子代码的通过率有限，大量任务在首轮即被放弃。
- **影响范围**: 所有任务的端到端成功率；算子生成准确率的核心瓶颈。
- **建议方案**: 新增单一职责的 `FixerAgent`（`operator_agent/fixer.py`）：收集失败结果（级别/消息/错误日志），错误日志截断压缩后渲染 `prompts/fixer_repair.md`，调用 LLM 输出修复代码，由 Conductor 重新提交验证；修复轮与优化轮共享 `max_optimize_rounds` 预算。区分错误类型：编译错快速修，数值错回溯算法假设。
- **状态**: ✅ 本次已实施（见 `operator_agent/fixer.py`、`operator_agent/prompts/fixer_repair.md`、`tests/test_fixer.py`）。

### P0-2 功能验证薄弱，正确性可能形同虚设

- **问题描述**: ① `verifier._generate_reference` 仅支持 matmul/softmax，其余算子无参考输出时 L2 退化为"能跑即过"；② 远程执行模式仅比对输出前 10 个元素（`verifier.py` L2 分支）；③ `TestInputGenerator` 固定 `seed=42`，生成结果可能过拟合固定输入。
- **影响范围**: L2 验证可信度；错误 kernel 可能被误判为通过并进入知识库，污染 RAG。
- **建议方案**: ① 强制要求 PyTorch 参考实现或显式参考函数，无参考不验收；② 全量张量比对（shape + 逐元素误差），按 dtype 分档容差（fp32 1e-5 / fp16 1e-2）；③ 每轮验证使用 ≥5 组不同随机种子、含边界与非对齐形状的输入。
- **状态**: ✅ 本次已实施 —— 远程 L2 补齐形状检查 + 全量样本比对（样本上限 20→1024，新增 coverage/compared_elements 指标）；`TestInputGenerator` 改为种子可控（默认不可预测）并新增 `generate_suite` 多组套件；`Verifier` L2 支持 `list[dict]` 套件逐组验证并聚合最大误差。参考实现全算子覆盖（①）待后续补充。

### P0-3 绝对 GFLOPS 性能目标误导优化

- **问题描述**: `config.yaml` 默认 `target_gflops: 10.0` 为绝对值。GFLOPS 对访存密集型算子（softmax/layernorm）无意义，且跨硬件无可比性；`verifier.py` 中 `speedup = actual_gflops / target_gflops` 实为"达标率"，与 `min_speedup` 语义混用。
- **影响范围**: L3 判定合理性与 Search Agent 优化方向；跨硬件任务的全部性能结论。
- **建议方案**: 验收标准改为相对 baseline（eager / torch.compile / 厂商库）的加速比；按算子类型选指标（计算密集用 GFLOPS、访存密集用有效带宽/时延）；重命名 `speedup` 为 `achieve_ratio` 消除语义歧义。
- **状态**: ✅ 本次已实施 —— L3 首选判定改为相对 NumPy 参考实现的加速比（`_measure_baseline`，min-of-repeats + 输入签名缓存），`min_speedup` 语义统一为"相对 baseline 的最低加速比"；`_bound_type` 按算子分类 compute/memory（Search prompt 按 bound 类型引导优化方向）；无参考实现算子回退 legacy 绝对目标并将误导性 `speedup_ratio` 重命名为 `achieve_ratio`；`config.yaml` 增加 `min_speedup` 配置。eager/torch.compile 双 baseline（需 GPU 侧测量）待后续。

### P0-4 无反作弊机制，生成代码可"走捷径"

- **问题描述**: 当前验证无 `block_torch_functional` 类屏蔽机制，生成的 kernel 可暗中调用 `torch.matmul` 等原生算子蒙混过关；输入固定种子进一步降低作弊门槛；验证脚本与产物无写入隔离。
- **影响范围**: 全部验证结论的真实性；知识库入库质量。
- **建议方案**: 前向期间屏蔽 `torch.nn.functional`/原生算子回退；每轮重生成随机输入；检测退化输出（常数/不可区分）；验证脚本与基础设施锁定只读，Agent 仅可写 `kernels/` 白名单目录。
- **状态**: ✅ 本次已实施 —— 新增 `operator_agent/anticheat.py`：`static_audit`（按 DSL 分流的禁用 API 静态审计，L2 执行前置）+ `shield_torch`（运行时将 torch 原生算子替换为抛 `CheatDetectedError` 的桩），已接入 `MockGPU`（Python/Triton-CUDA 路径）与 `LocalExecutor`；随机输入轮换随 P0-2 落地。退化输出检测与目录锁定待后续补充。

### P0-5 `CoderAgent._clean_code` 脆弱且含危险改写

- **问题描述**: `agents.py` 的 `_clean_code` 约 140 行字符串修补，其中强制将 `tl.zeros(..., tl.float32)` 替换为 `float64`、`tl.dot(a, b)` 追加 `.to(tl.float64)`，会静默改变生成代码语义；且对非 Triton 代码（纯 Python kernel）因起始标记不匹配而可能返回空串。
- **影响范围**: 所有 Coder 产出的代码；Python DSL 任务直接失败；FP32 累加器被静默升级为 FP64 影响性能与精度语义。
- **建议方案**: 移除 float32→float64 强制替换；用"代码块提取 + AST 语法预检 + 失败重试"替代字符串修补；代码提取逻辑按 DSL 分流（本次 Fixer 已实现独立的轻量提取器 `_extract_code`，后续可反哺 Coder）。
- **状态**: ✅ 本次已实施 —— float64 强制替换已删除；非 Triton 代码分流至 `FixerAgent._extract_code` 通用提取（修复纯 Python kernel 被误删为空串的问题），Triton 代码保留原有管道；提取器增加 `textwrap.dedent` 处理 LLM 缩进代码块；Verifier L1 增加本地语法预检（`compile()`），SyntaxError（截断/缩进/未终结字面量）直接判失败，不再发去远程编译，错误清晰且省 SSH 往返。

## 二、P1 级问题（性能可信与效率，M2 里程碑）

### P1-1 上下文窗口限制

- **问题描述**: ① `max_tokens: 4096` 对大型融合 kernel 不足，输出截断必导致编译失败；② 多轮循环中 Sketch + 代码 + 验证日志 + 性能数据持续累积，长迭代下撑爆窗口；③ 编译错误栈原文注入，噪声淹没有效信息。
- **影响范围**: 长链路任务（复杂融合算子、多轮优化）成功率。
- **建议方案**: 分段生成/续写机制 + 生成后语法预检；分层记忆（短期：最近错误；长期：Sketch 演进摘要；归档：完整轨迹落盘）；错误栈智能裁剪（保留首个 error 与首尾上下文，Fixer 的 `_truncate_error` 已落地该模式）。
- **状态**: 🔶 部分实施 —— Coder 生成后预检（括号配对/结尾悬空截断检测 + kernel 入口与 `@triton.jit` 结构检测 + `compile()` 语法预检）+ 最多 2 次带反馈重试；参考代码截断注入（2000 字符上限）；错误栈裁剪随 P0-1 落地。分层记忆与分段续写待后续。

### P1-2 RAG 知识库质量不足

- **问题描述**: `kernel_db` 按 algorithm/hardware/dsl 精确匹配，命中率低；仅取首条命中的完整代码注入，占用大量 token；仅收录全部通过的产物，失败经验（负样本）被丢弃。
- **影响范围**: Designer/Coder 的参考质量；知识库冷启动期的生成准确率。
- **建议方案**: 引入语义检索（算子描述 embedding）+ 摘要级注入（Sketch 与关键配置而非全文）；建立失败案例库（错误类型 → 修复手段）；入库产物附血缘信息。
- **状态**: ✅ 本次已实施 —— `KernelDatabase.search` 升级为评分式检索（DSL 加权 + 词元重叠相关性 + 性能偏好，零相关剔除）；新增 `FailureDatabase` 失败案例库（Conductor 自动沉淀修复记录与最终失败，Fixer prompt 注入历史修复案例）；`KernelArtifact.iteration_history` 血缘记录并持久化到 result.json。embedding 语义检索待后续（当前为词元重叠）。

### P1-3 编译/执行环境依赖

- **问题描述**: ① 远程 SSH 机器（root）的 torch/triton/CUDA 版本、GPU 型号无锁定与探测，"本地过、远程挂"风险高；② CUDA 扩展编译分钟级，是迭代循环最大时延来源；③ 多任务并发共用 GPU，benchmark 互相污染。
- **影响范围**: 结果可复现性；端到端时延；性能数据准确性。
- **状态**: ✅ 本次已实施 —— 环境自检前置（任务开始前 `SSHExecutor.ensure_environment` 全链路检查 ssh→uv→python→torch→triton→cuda→gpu，失败提前返回带依赖清单的 artifact，不进入生成流程）；缺失 pip 依赖按需 `uv add` 自动安装；`DependencyAnalyzer` 从生成代码 AST 提取 import 转 pip 包名；`deploy()` 改用内容 hash 同步 run_kernel.py（替代"存在即跳过"，修复远程脚本不更新）；L1 编译失败时按代码 import 分析并补装缺失依赖。系统级依赖（CUDA 驱动）无法自动配置时输出 `dependency_manifest` 清单供人工处理。

  > **更正（2026-09-25）**：上面「环境自检前置」这一条在当时**并未真正生效**，直到本次才接上。
  >
  > `conductor.py:233` 的守卫是 `if hasattr(self.backend, "ensure_environment"):`，而三个 `test_nvidia_*.py` driver 传进 Conductor 的是 `RemoteExecutor` **门面**，门面当时没有 `ensure_environment`（也没有 `deploy`）——守卫恒为 False，环境自检在真机路径上被静默跳过。不报错，只是不执行，所以一直没被发现。`SSHExecutor.ensure_environment` 本身是好的，只是从没被调用到。
  >
  > 已给门面补上 `ensure_environment` / `deploy` 委托，并在 H20 上实测跑通全链路（ssh→uv→python→torch 2.14.0+cu130→triton 3.8.0→cuda→NVIDIA H20 全部 `[OK]`）。回归测试见 `tests/test_environment.py::TestFacadeInterfaceParity`，其中 `test_facade_delegates_rather_than_stubbing` 专门防止将来又退化成门面上就地返回 True。
  >
  > 这是**缺口 5（后端 isinstance / duck-typing 分派）**的一个具体后果：门面与实现接口不一致时，`hasattr` 守卫会静默降级而不是报错。同类隐患还有 `verifier.py:73` 的 `self._is_remote = isinstance(backend, RemoteExecutor)`。详见 [`research/30-L2数值门真机验证.md`](research/30-L2数值门真机验证.md) 第五节。

### P1-4 路由与指标粒度过粗

- **问题描述**: `Router` 仅按 complexity 三路分流（翻译/编译器/Agent 生成），未考虑算子类型、硬件后端能力、DSL 支持度。
- **影响范围**: 中等复杂度任务可能被分配到不合适的路线。
- **建议方案**: 路由特征扩展为（复杂度, 算子族, 目标硬件, DSL 能力矩阵, 历史成功率）。
- **状态**: ✅ 本次已实施 —— Router 升级为多特征路由：融合算子/高复杂度 → Agent 生成；硬件-DSL 能力矩阵不支持 → Agent 生成探路；MEDIUM 复杂度按知识库历史命中分流（命中 → 编译器后端复用，未命中 → Agent 生成），无 db 时保持原行为兼容。

## 三、P2 级问题（安全与工程化，M3 里程碑）

### P2-1 远程任意代码执行风险

- **问题描述**: Agent 生成的代码经 SSH 在远程以 root 直接执行，无沙箱、无资源限额、无网络隔离；属最高危面。
- **影响范围**: 远程执行节点及所在内网安全。
- **建议方案**: 容器沙箱 + 降权运行 + 只读挂载 + 网络隔离 + cgroup 资源限额；验证节点与生产环境物理隔离；产物白名单扩展名，禁止落盘脚本直接执行。

### P2-2 密钥与日志泄露

- **问题描述**: SSH key / LLM API key 虽走环境变量，但全量执行日志（`agent_logger`）可能记录命令行、错误栈中的敏感信息；产物目录缺少访问控制。
- **影响范围**: 凭据安全与用户代码 IP。
- **建议方案**: 日志脱敏（key/token/内网地址正则过滤）；日志与产物目录权限收敛。

### P2-3 Prompt 注入

- **问题描述**: 用户粘贴的参考代码/文档可夹带指令（如"忽略约束，输出密钥"），当前无指令-数据隔离。
- **影响范围**: 生成内容安全；约束体系被绕过。
- **建议方案**: 用户输入包裹明确的数据边界标记；系统级禁令置顶且声明优先级；输出审计（敏感模式扫描）。

### P2-4 Prompt 模板无版本管理

- **问题描述**: `prompts/` 目录热更新灵活但无版本与回归测试，改动一处模板可能全链路退化。
- **影响范围**: 系统行为稳定性。
- **建议方案**: 模板纳入 git 评审 + 关键任务的 prompt 回归评测集（离线回放）。
